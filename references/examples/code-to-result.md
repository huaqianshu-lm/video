# 代码走读与结果：让语义、改动与反馈各有可见依据

代码镜头的主角不是高亮框，而是当前表达式、变量关系或一处真正的改动。先决定观众要读懂什么，再设计取景。代码行被照亮只表示“请看这里”，不证明程序执行到这里；代码换成新版本也不证明它已运行成功。

本文区分 **源码可见**、**抽帧可见**、**制作推导** 与 **旧版记录**。新增依据包括 Remotion 官方 Code Hike 的代码过渡，以及 Shotcraft 官方样片中的代码评审画面；二者职责不同，不将后者的静态评审页冒充前者的运行画面。未运行上游、未正常速度观看或试听。旧版走读参数的原始素材未重新定位，末部保留，不能归为这两个上游的实测值。

## ２．先设计结果怎样被理解，再排代码窗

| 教学问题 | 完成态应该保留什么 | 为什么不是普通代码卡 |
|---|---|---|
| 这段代码在做什么 | 关键表达式与可核对的输入／推导值 | 原文和语义对应，而非逐行读旁白 |
| 哪一处改了 | 稳定上下文、明确的新旧差异 | 同一位置帮助看清改动量，不让全窗重打 |
| 为什么报错 | 出错位置、相关输入或条件、实际错误信息或明确的预期 | 不让红色高亮替代错误原因 |
| 修改是否生效 | 修改后的代码与有来源的运行输入／结果 | 将写完、运行、输出核对分开 |

**制作推导**：短代码可占主画面，结果在邻区或下方；长代码先截取完整语义片段并保留函数／文件定位。结果需要大面积图形解释时，代码收为一处可读定位，图形成为主体。不要固定五五分屏，让两边都小得不能读。无需一开始把终端、文件树、浏览器和全部日志同时铺满。

改动前后长短不同时，先决定比较锚点：函数签名、未改行或当前表达式的起点。整个版心自动居中会让所有行一起漂，观众分不清移动是代码改了还是布局变了。除非要解释结构重排，优先保持共同上下文和阅读起点稳定。

## ３．代码本身怎样具有清楚的美术层级

### ３．１　字体、缩进与换行是内容结构

**源码可见**：Code Hike 示例使用 Roboto Mono、常规与粗体、示例字号４０、行高１．５及固定 tabSize；所加载子集是 Latin。**制作推导**：这些数值只说明原实现条件。实际教程中中文注释要核对中文字形与回退，不能因等宽英文字体已加载，就认定中英文基线和宽度都已固定。保持缩进、运算符与字符串边界，必要时按代码合法断点换行；不能把长表达式截掉末尾后还让观众猜执行含义。

行号是定位层，不需要和代码同样亮；只有确有阅读作用时保留。语法色要帮助分辨关键字、字符串和数字，不为每个 token 分配一种高饱和颜色。讲一个变量时，用额外的局部强调标出它；全屏语法色与当前强调不能竞争到看不出重点。

### ３．２　编辑器外壳要服务当前任务

**抽帧可见／源码可见**：Shotcraft 末段是浅色评审页，左侧文件树、右侧代码，行号与增删标记分栏，顶部有评审标题和状态，底部有评论。它用具体结构建立“代码评审”的身份，而非玻璃窗加几行代码。但其中路径、通过徽章、评语均为作者演示构造，不能搬来证明本项目结果。

**制作推导**：讲表达式时可以去掉外壳，仅保留代码和输入；讲真实文件编辑时保留实际文件定位；讲 diff 时保留 `+／-` 与稳定上下文。没有在教编辑器操作，就不添加假菜单和小图标占面积。深色与浅色代码都可成立：正文对比清楚、背景低竞争、重点色有职责，比统一玻璃渐变更重要。

### ３．３　空间感不能破坏代码阅读

代码精读优先正视。需要从全景转近景时，先确保完整目标行、相关上下文和输出位置都在取景范围内。薄边、软影可以把窗口与环境分开，但不要让文字跟随玻璃反光忽明忽暗；不以景深把必须读的后半行虚掉。原例的评审画面通过页面、列与明暗分层建立质感，不需要代码每行都带立体厚度。

## ４．走读、改动和运行分别怎样组织

### ４．１　走读应按语义组，不按每行平均点名

**制作推导**：先把当前片段分为输入、关键处理、输出或分支。一个表达式跨多行时共同解释；空行不单独分配一拍；重复赋值没有独立教学价值时可一起处理。高亮从当前内容的行／token 边界求得，而非写死“第 n 行×固定行高”，因为中文换行、注记与空行都可能改变高度。

焦点切换可以让高亮先建立、观察再跟上，或让两者共同移动，但需要在阅读前稳定。相机不必每行都推拉；目标仍在可读范围时，只改变重点即可。多行依赖需要同时看见，就扩大阅读范围，不让镜头在两行之间来回跳。

### ４．２　从全景推近时，保持目标位置有解释

```text
q = 代码局部中当前语义组的定位点
T = 希望它在画面中落到的阅读位置
scale = 当前取景倍率
translation = T - scale × q
screenPoint(x) = translation + scale × x
```

这是**制作推导**的二维锚点模型，不是 Code Hike 源码。局部点、外层窗口偏移和输出坐标必须统一；若有父级变换，继续组合或求逆。只插值 scale、不同时维护目标定位，当前行就会被推向画边。检查的是整条代码外框，不能仅保证行中心还在。

若推近会截断长行，先改片段或使用合法分行；确需横向阅读时给出明确的连续取景和充足停留，不让相机持续横扫同时要求听懂推导。注记展开改变布局时，优先提前预留区域，避免代码全体下跳。

### ４．３　代码修改保留未改部分的身份

**源码可见**：Code Hike 先取得旧代码的布局快照，再对新布局计算 token transitions；主流程按当前帧求进度，平移／颜色与透明度使用的进度方式也有区分。它不是逐行把旧代码删净再打印新代码，也不是执行调试器。

**制作推导**：未改部分稳定，新增、删除和移动分别可辨。修改很小就只强调该表达式；重构范围很大时可明确切换，再给关键差异近景，不强迫每个字符飞到新地址。重复变量名、相似括号和大段重排时，要观察匹配是否制造错误的连续身份，不能凭算法存在就默认转换成立。

过渡开始前字体和布局须就绪，否则旧快照与最终字宽不同，会出现跳位。Remotion 需要跳帧可重建，不能依赖“前一帧已经播放过”才有正确高亮。这里学习状态与几何关系，不复制上游副作用代码，不新增 Code Hike 依赖作为制作前提。

### ４．４　时间安排不继承上游均分

**源码可见**：示例 Main 将总段长按代码步骤数量均分，另固定每次过渡为３０帧。Callout 与错误信息的可读文本中也有固定帧窗，网页未完整保留全部 JSX 样式。**制作推导**：这是演示编排，不是教程的时间依据。解释一处难点可以比三处简单修改用更久，错误注记须在当前内容可读且讲到原因时出现。

时间由真实 Timeline 与内容决定。高亮只表示阅读焦点时按语义安排；表示执行行时须有执行顺序依据，尤其注意循环、函数调用和条件分支，不能从代码顶部一路照到尾部就冒充真实执行。

### ４．５　结果必须有自己的证据与观看阶段

有实测输出就展示当前输入、运行触发和该次结果；只有数学推导就明确作推导，不伪造终端成功。新代码稳定后再运行或推导，输出出现后留给核对。报错时错误位置与必要上下文保持，不立刻被一个大红弹窗全部盖住。

绿色勾、通过徽章与执行日志不能由“动画走完”产生。代码正确与业务任务完成也不相同：打印一个值不等于文件已保存、测试已通过或系统已部署。教程结论严格匹配这次显示的证据范围。

### ４．６　表达式、推导和输出的映射要具体到内容

**制作推导**：代码原文、当前教学输入、重点范围、推导值与输出不能各自维护一份互不关联的文案。简单例子可以直接由同一输入计算展示值；复杂程序使用真实运行记录或经资料核实的教学推导。不在渲染时执行任意项目代码，也不把渲染帧数当作业务执行进度。

对走读来说，重点可以是连续几个 token、一条完整表达式或相邻多行。对修改来说，新旧代码中的身份由语义决定：变量重命名意味着同一角色换名，新增另一个同名局部变量则未必是同一个对象。没有可靠映射时，清楚显示旧／新版本比错误连续变形更好。

对输出来说，保持与输入一致的有效位、数据类型和单位。示意推导显示４，实际 Python 输出显示４．０时，应按读者理解交代数值与显示格式，不把字面不同画成错误。图解中的总和、数量与返回值分别附在对应对象旁，避免同色大数字同时出现而不知道分别指什么。

### ４．７　差异很多时，用层级而不是用更多运动解决

**制作推导**：先选出本段真正改变行为的一处，把其他变化保留为上下文或稍后另讲。新增行可以在最终行盒内揭示，删除行可以保留短暂删除参照再收起；移动代码需要可追踪起终点，但不必让所有标点分别穿越画面。`+／-`、位置和短说明共同区分差异，不能只靠红绿颜色。

若新增注记或错误提示占据了行高，代码与高亮范围都应重新计算；可以提前预留注记带，避免整段代码被顶走。输出面板应有稳定的边界和来源名称，内容更新在其内部完成，不用每次结果出现都让整个编辑器弹跳。关键信息多到无法同屏时，先建立输入与修改，再让输出接管，保留一小段代码作为定位。

中段暂停时应能判断“哪些字仍是旧代码、哪些字正在换入、当前输出属于哪一版”。如果两版代码都半透明叠着、结果又提前变成新值，先重排状态窗口。漂亮的 token 轨迹不能补救版本关系混乱。

## ５．已有样片能核对到什么

本轮核对了 Shotcraft `word-relay-filmstrip` 的第１０／３５／７０／９８／１２５／１７９帧；代码页在后段进入。它帮助判断代码评审页的完整构图与焦点交接，不提供 Code Hike 过渡的视觉认证。

| 画面位置 | 静态可见 | 不应扩大到的结论 |
|---|---|---|
| 第９８帧 | 当前还是构建界面，下一张浅代码页在邻区 | 不能把构建日志认作代码页的运行结果 |
| 第１２５帧 | 代码评审页正进入，页面有纵向拖影，右侧词尚未完整 | 不能由这一帧判断精读清晰度或认定代码内部在编辑 |
| 第１７９帧 | 文件树、增删行、评审标题与评论形成完整页面 | 能看版式层次，不能据缩略小字认证逐字阅读，更不能继承通过状态 |

Code Hike 的连续预览、中文注释与重复 token 的动态效果仍未实际观察；需要这些效果时，应先核对该预览或当前原创实现。未观察的画面不以文字想象补成原片事实。参见 [GitHub 解释动画案例](github-explanatory-animation.md) 的 Code Hike 条目。

## ６．原创演绎：从“总和”改为“平均值”

以下是未实现的原创教学设计。给定非空数列，例如 `[2,4,6]`，需要说明“求和”和“平均”不同；先展示求和表达式，再增加除以元素数量，最后核对结果。具体输入与代码应换成当前视频资料支持的例子。以下数值是可计算的教学推导，不宣称已经跑过某个软件或修改文件。

### ６．１　先明确认识变化与完成态

观众从“看到一个输出数字”走到“知道哪部分得到总量、哪部分得到数量、两者怎样形成平均”。完成态保留同一输入、改后的关键表达式，以及 `12 ÷ 3 = 4` 的对应推导；若展示 Python 浮点输出，可读值为 `4.0`。输出取代代码下方的临时解释，不另加三张“输入／处理／输出”卡。

主体是可读代码区。输入数列靠近使用它的表达式，结果区留在邻侧或下方；代码上方保留必要语言／片段身份，不需要假编辑器菜单。数列各元素在同一轨道排列，数量标记附着在整组边界，总和标记靠近求和子表达式。两种关系可以由同一输入派生，不让观众以为有两组不同数列。

采用克制的制图语言：清楚代码、低竞争背景、当前操作的一处强调，推导用与代码对应的文字颜色。运算符和括号是语义，不把它们做成装饰粒子；如果使用连接线，起点落在真实子表达式边界，终点落在对应推导值，而非穿过整行。

### ６．２　完整动作与阅读顺序

| 状态 | 对象与构图怎么变 | 观众获得什么 | 焦点如何交给下一步 |
|---|---|---|---|
| 建立 | 输入与短代码正视同屏，代码尚未高亮 | 知道这次处理哪组数据 | 先读完整语义，不急着逐字打出 |
| 看总量 | 求和子表达式获得重点，邻区出现对应的１２ | 理解当前代码得到总和 | 输入留在原位，其他代码不漂移 |
| 提出区别 | 总量与所需平均明确区分，代码旁留出修改空间 | 知道需要按数量分摊 | 不用一个“错误”大叉代替解释 |
| 改表达式 | 未改部分保留，仅新增除号与数量表达式；有必要时保持旧值短参照 | 看清改在哪里 | 过渡结束后再解释，不边换字边推导 |
| 看数量 | 数列整组边界与数量表达式对应，显示３ | 知道分母来自何处 | 不让多条强调线同时围住每个数字 |
| 核对结果 | 清楚显示１２除以３得到４；若有实际运行再展示该次输出 | 从新代码推到新结果 | 当前代码与结果同时停稳，临时引导退出 |
| 接下一镜 | 沿分母或输入条件继续，只有本片需要时再讨论空数列 | 认识适用边界 | 不无依据补上“空输入返回０”等业务规则 |

首次解释求和可完整展开，数量只需一个组边界与短值，避免每个输入元素再做一轮飞行。若这一镜只教现有代码，不需要“修改前总和”这个问题，就直接从完整平均表达式开始；不能为了保留 code transition 强造错误版本。

### ６．３　长代码与中段应怎样修

先用实际代码和中文注释排完整态，再检查修改中段：新增分母是否挤出右边、括号是否被词槽裁切、注记是否把未改部分推走。相机推近时，输入、关键表达式与结果的对应标记至少保留当前需要的两端；不能只剩一个大运算符，丢失语义。

阅读期间相机、高亮边界和结果值稳定。只有当前焦点真正移出可读区才重取景。运行输出需要等待真实内容支持的时刻，不把参考演示的固定过渡长度或旧版０．３２秒停留用于实际教程。声音若使用，修改反馈轻短、运行与输出分别有对应，不能每个字符敲一次声音盖住讲解。

## ７．失败修正与可观察判据

| 失败画面 | 可能的结构问题 | 优先修正 |
|---|---|---|
| 高亮扫遍每行，但不知道程序做什么 | 按行数排动作，没有语义分组 | 先划出输入、关键处理与结果 |
| 相机推近，行尾和括号消失 | 仅看中心点，没看整行范围 | 重排片段、合法换行或改变取景 |
| 中文注释突然换宽，代码抖一下 | 字体回退或加载时机改变布局 | 实际字体就绪后测量，核对中英文行盒 |
| 改一个词，所有代码都漂 | 新布局重居中或未改部分失去锚点 | 固定共同上下文与阅读起点 |
| 两个同名变量飞到错误位置 | 连续身份未经画面核对 | 减小改动范围，必要时明确切换，不硬做字符变形 |
| 代码写完就出现成功 | 将过渡完成当作运行证据 | 分开写完、运行与实际输出核对 |
| 推导数字与输入对不上 | 图形示意与代码各维护一套数据 | 同一教学输入派生数量、总量与显示值 |
| 看起来像一个代码截图 PPT | 只有入场，没有解释内部关系 | 让当前表达式与推导／结果发生可见对应 |

静态通过应能找到当前表达式、相关输入与结果，字体、缩进、标点与重点色都清楚。动态通过应能跟到真正的改动或语义步骤，稳定阅读后理解结果；声效与口播不相互遮盖，下一镜沿实际问题继续。没有运行的内容保留推导身份。当前原创实现、Code Hike 连续画面、中文长行及正常速度观看尚未验证，不能宣称本项目已具备已验代码动画模板或达到商用成片水平。
