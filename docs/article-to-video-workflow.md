# 文章内容视频化工作流设计

## 目标

这套流程的目标，不是把文章简单改成“口播 + PPT”，而是：

> **让文档和视频成为两个相互独立、信息密度接近、表达形式不同的内容作品。**

也就是说：

- 看过文档，不需要再看视频
- 看过视频，也不需要再看文档
- 两者表达的是同一套核心知识
- 但视频要充分发挥“声音 + 时间 + 动画 + 演示 + 对比”的优势

所以，文档和视频共享的应该是“知识源”，而不是表达形式。

```text
                 原始知识
                    │
             ┌──────┴──────┐
             ↓             ↓
          文档表达        视频表达
          文字逻辑        时间+声音+视觉
```

而不应该是：

```text
文档
 ↓
改成口语
 ↓
配图
 ↓
视频
```

后一种方式很容易最终变成“有配音的 PPT”。

---

## 现有流程的问题

当前流程大致是：

```text
原文
 ↓
生成口播
 ↓
生成音频 / 字幕
 ↓
根据口播生成场景
 ↓
视频
```

这个方向本身没有问题，但有一个核心风险：

> **口播成为了整个视频的唯一中间产物。**

这样一来，视觉内容就只能“服务口播”。

例如口播说：

> ChatGPT 更像顾问，而 Claude Code 更像真正坐在你旁边工作的搭档。

如果直接根据口播生成场景，很容易变成：

- 左边 ChatGPT
- 下面写“顾问”
- 右边 Claude Code
- 下面写“搭档”

这本质上还是动态 PPT。

真正适合视频的方式应该是直接把这个差异“演出来”。

例如：

### ChatGPT 工作流

```text
复制报错
  ↓
打开浏览器
  ↓
粘贴
  ↓
AI 回答
  ↓
回编辑器
  ↓
找代码
  ↓
手动修改
```

然后画面不断切换，突出流程割裂。

### Claude Code 工作流

```text
“帮我定位这个错误并修复”
              ↓
           搜索文件
              ↓
           阅读代码
              ↓
           修改文件
              ↓
           运行测试
              ↓
           ✅ Passed
```

这时观众不是“听你解释区别”，而是直接“看到区别”。

---

# 推荐的新流程

建议把整个视频生成流程改成：

```text
原始文章
   ↓
① Content Analysis
内容分析 / 信息提取
   ↓
② Video Narrative
重新设计视频叙事
   ↓
③ Scene Script
逐场景设计
   ↓
        ┌───────────────┐
        ↓               ↓
④ Narration       ⑤ Visual Production
口播稿              Remotion 场景
   ↓               ↓
TTS                动画 / Demo / 图示
   ↓
时间轴
   ↓
字幕
        ↓
⑥ Composition
音频 + 字幕 + 场景
        ↓
⑦ Quality Check
信息完整度 / 视觉有效性 / 节奏
        ↓
最终视频
```

---

# ① Content Analysis：先分析内容，而不是先写口播

第一步不要急着把文章改成口语。

应该先分析：

- 这篇内容真正想让观众理解什么
- 核心命题是什么
- 哪些知识点必须保留
- 哪些内容只是文章里的辅助信息
- 哪些知识点之间存在因果关系
- 哪些存在前后关系
- 哪些适合做对比
- 哪些必须通过案例才能理解
- 哪些内容适合视觉化

例如 Claude Code 这篇文章，核心命题可以提炼成：

> **Claude Code 不只是生成代码，而是进入项目执行任务。**

支撑这个核心命题的内容包括：

```text
顾问 → 搭档

Copilot → Agent

单段代码 → 整个项目

给建议 → 直接执行

人工逐步操作 → AI 接收任务

AI 能做什么 → AI 不能做什么

人负责判断 → AI 负责执行
```

这些才是后续视频真正应该保留的信息骨架。

---

# ② Video Narrative：重新设计视频叙事

视频不一定要按照文章章节顺序来做。

文章可能是：

```text
01 Claude Code 是什么
02 在哪里运行
03 能做什么
04 和其他工具的区别
05 安装
06 总结
```

但视频可以重新组织成：

```text
开发者遇到一个 Bug
        ↓
ChatGPT 怎么解决
        ↓
Claude Code 怎么解决
        ↓
为什么体验完全不同
        ↓
Agent 到底意味着什么
        ↓
Claude Code 还能继续做什么
        ↓
为什么不能完全托管项目
        ↓
ChatGPT / Cursor / Claude Code 怎么分工
        ↓
新的 AI 编程工作方式
```

这里的重点是：

> **信息可以保持不变，但叙事顺序可以完全按照视频重新设计。**

这样视频才会成为一个独立作品，而不是文章朗读版。

---

# ③ Scene Script：建立真正的视频中间层

这是整个流程里最值得增加的一层。

不要直接生成纯口播。

应该先生成一份 Scene Script。

例如：

```text
Scene 01

目的：
制造问题，让观众先感受到传统 AI 编程流程的割裂。

口播：
你可能已经用 ChatGPT 写了很久代码……

画面：
IDE 和 ChatGPT 浏览器窗口并排。

开发者不断：
复制代码
→ 切浏览器
→ 粘贴
→ 查看回答
→ 回编辑器

视觉信息：
报错 → 复制 → ChatGPT → 返回编辑器

重点：
让观众先“感受到问题”，而不是先解释概念。
```

然后：

```text
Scene 02

目的：
解释 Claude Code 的核心变化。

口播：
Claude Code 最大的区别，是它可以真正进入项目工作。

画面：
终端输入：

“Find the cause of this error and fix it.”

随后依次展示：

读取文件
↓
搜索引用
↓
修改代码
↓
运行测试
↓
Passed

屏幕文字：

Advice → Action
```

Scene Script 应该同时回答几个问题：

- 这一幕讲什么
- 为什么现在讲
- 口播是什么
- 画面是什么
- 观众应该看到什么
- 需要突出什么信息
- 使用哪种视觉表达方式

因此它不是单纯的 Storyboard，也不是单纯的口播稿。

更准确地说，它是：

> **视频内容与视觉设计之间的中间层。**

---

# ④ Scene Script 再拆成两条生产线

Scene Script 完成之后，再拆成两条生产线。

```text
                    ┌→ 口播稿 → TTS → 音频
Scene Script ───────┤
                    └→ Visual Script → Remotion Scenes
```

字幕建议主要根据最终音频时间轴生成：

```text
TTS 音频
   ↓
时间轴
   ↓
字幕
```

而不是让字幕、场景、口播全部从同一段纯文本里直接生成。

---

# ⑤ 建立固定的场景类型

为了避免 Claude Code 每一次都重新设计一套视觉方案，可以建立一套固定 Scene Type。

## 1. Demo 演示

适合：

- Terminal
- IDE
- 网页
- 工具实际运行
- 代码执行结果

例如：

```text
输入命令
↓
Claude 读取文件
↓
修改代码
↓
运行测试
```

---

## 2. Process 流程

适合展示：

- 一个任务如何完成
- 一个操作如何一步步发生
- 一套工作流

例如：

```text
需求
 ↓
理解项目
 ↓
修改文件
 ↓
运行测试
 ↓
验收
```

---

## 3. Comparison 对比

适合：

- ChatGPT vs Claude Code
- Copilot vs Agent
- 传统开发 vs AI Agent
- 旧流程 vs 新流程

---

## 4. Concept Visualization 概念动画

适合抽象概念。

例如：

```text
Copilot
   ↓
Agent
```

或者：

```text
Suggest
   ↓
Execute
```

---

## 5. Diagram 图解

适合：

- 架构
- 系统关系
- 数据流
- 模块关系
- 工作流

---

## 6. UI Simulation 界面模拟

不一定需要真实录屏。

可以使用 Remotion 模拟：

- Terminal
- VS Code
- Claude Code
- 浏览器
- Git
- 测试运行

这样可以保证整体视频风格统一。

---

## 7. Code Focus 代码特写

适合突出：

- 某段代码变化
- Diff
- 函数拆分
- Bug 修复
- API 调用变化

---

## 8. Text Emphasis 文字强调

只用于真正重要的核心结论。

例如：

```text
AI 负责执行
人负责判断
```

不要大量使用，否则视频会再次 PPT 化。

---

# 视频画面的基本原则

视频不能只是把口播重新显示一遍。

应该遵循：

> **声音告诉观众“为什么”，画面告诉观众“发生了什么”。**

或者：

> **声音讲概念，画面给例子。**

例如：

### 不好的方式

口播：

> Claude Code 可以读取整个项目。

画面：

```text
Claude Code 可以读取整个项目
```

这只是字幕放大版。

---

### 更好的方式

口播：

> Claude Code 可以读取整个项目。

画面：

```text
src/
├── components/
├── hooks/
├── api/
├── utils/
└── tests/
```

文件树快速展开。

随后多个文件被依次扫描。

最后形成：

```text
Project Context
      ↓
Claude Code
```

这才是在利用视频表达。

---

# 一个非常重要的质量检查标准

可以把下面这条直接加入 Claude Code 的视频规则：

> **如果一个 Scene 删除画面后，仅听口播仍然几乎没有信息损失，那么这个 Scene 的视觉设计可能不够好。**

这并不意味着每一秒都必须增加新的知识。

而是应该尽可能让：

```text
音频信息
   +
视觉信息
   =
完整理解
```

而不是：

```text
音频信息
   =
视觉信息
```

# 最终推荐工作流

最终建议固定成：

```text
原始文章
   ↓
Content Analysis
   ↓
提取知识模型
   ↓
Video Narrative
   ↓
重新设计视频叙事
   ↓
Scene Script
   ↓
┌─────────────────────┐
│                     │
↓                     ↓
Narration          Visual Script
↓                     ↓
TTS                Remotion
↓                     ↓
音频                场景
↓
字幕时间轴
│
└──────────┬──────────┘
           ↓
      Composition
           ↓
      Quality Check
           ↓
         成片
```

---

# 核心原则

整个系统最重要的原则可以总结成一句话：

> **不是“把文章变成视频”，而是“用视频重新表达同一套知识”。**

文档和视频之间应该是：

```text
同一知识源
   ↓
不同媒介重新创作
```

而不是：

```text
文章
 ↓
口语化
 ↓
配画面
 ↓
视频
```

最终目标应该是：

> **一份知识，两种独立媒介作品。**
