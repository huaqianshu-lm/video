# VIDEO-PRODUCTION-RULES.md

> 版本边界：`storyboard-v1` 按 [Storyboard 生产契约](STORYBOARD-PRODUCTION-CONTRACT.md) 整合 Scene／Visual Script，Gate 2 审核口播与分镜，无 HTML 原型或旧动态自检要求；本文原型制作及观看要求只适用于旧契约。新契约保留视觉质量规则，实际动态检查在 Gate 3 完成。


> 适用于所有基于文章 / 文档进行再创作的视频项目。  
> 本文件只定义视频项目内部长期稳定的公共规则，不包含 TTS、字幕生成等外部项目的具体实现方法。

---

# 1. 核心目标

视频不是文章的 PPT 版，也不是文章的朗读版。

正确目标是：

> **文档和视频共享同一套知识，但拥有独立的表达结构。**

要求：

- 看完文档，不需要再看视频
- 看完视频，也不需要再看文档
- 两者信息密度接近
- 视频必须发挥时间、动画、演示、对比、流程和状态变化的优势

禁止：

```text
文章
↓
改成口语
↓
配几张图
↓
视频
```

应该采用：

```text
Source
↓
Content Analysis
↓
Video Narrative
↓
Scene Script
↓
Narration Script + Visual Script
↓
Visual Prototype
↓
Remotion
↓
Review
```

# 2. 内容设计原则

## 2.1 先提取知识，再设计视频

不要按文章章节直接生成 Scene。

必须先完成：

```text
原始文章
↓
核心命题
↓
知识骨架
↓
认知关系
```

需要识别：

- 核心命题
- 必须保留的信息
- 因果关系
- 对比关系
- 流程关系
- 案例
- 可视觉化内容
- 可删除的辅助内容

---

## 2.2 Video Narrative 独立于文章结构

视频叙事应该按照观众的认知过程重新组织。

优先：

```text
问题
↓
对比
↓
发现差异
↓
解释原因
↓
建立概念
↓
制造转折
↓
形成结论
```

避免机械使用：

```text
定义
↓
功能列表
↓
特点
↓
总结
```

除非内容本身确实最适合这种结构。

# 3. Scene 规则

Scene 是视频的基本叙事单位。

每个 Scene 必须只承担一个主要认知任务。

每个 Scene 至少需要明确：

```text
sceneId
title
purpose
narrativeRole
narrationIntent
visualIntent
visualType
keyOnScreenText
videoValue
```

其中：

- `purpose`：这一幕为什么存在
- `narrativeRole`：它在整条视频里的作用
- `narrationIntent`：声音需要解释什么
- `visualIntent`：画面需要证明 / 演示什么
- `visualType`：使用哪种视觉表达
- `keyOnScreenText`：真正需要强调的屏幕文字
- `videoValue`：为什么这一幕必须用视频表达

如果一个 Scene 没有明确的 `videoValue`，应该重新设计。

# 4. 声音与视觉分工

核心原则：

> **声音负责解释，视觉负责演示、证明和建立直觉。**

理想状态：

```text
声音：解释意义
+
画面：展示过程
=
完整理解
```

错误方式：

```text
旁白：
Claude Code 可以修改文件。

画面：
Claude Code 可以修改文件。
```

正确方式：

```text
旁白：
Claude Code 可以直接参与项目修改。

画面：
auth.ts      Modified
user.ts      Modified
tests.ts     Created
```

# 5. Narration Script 规则

Narration Script 不直接从原文生成。

必须基于：

```text
Scene Script
```

生成。

口播主要承担：

- 解释
- 推进
- 因果
- 转折
- 结论
- 建立认知

口播不需要重复视觉已经明确表达的信息。

Narration Script 是视频内容设计的一部分，但音频生成方式不属于本文件管理范围。

---

# 6. Visual Script 规则

Visual Script 不是“配图说明”。

它必须描述：

- 画面结构
- 视觉动作
- 状态变化
- 动画顺序
- 信息重点
- 场景类型
- 视觉与口播的互补关系

# 8. 避免 PPT 化与视觉收敛

这是一条适用于所有 Workflow 的公共质量基线，但不是简单禁止标题、卡片、代码界面或静态画面。判断标准是：画面是否通过动作、证据、关系或状态变化提供了视频特有的价值。

## 8.1 所有 Workflow 的公共基线

尽量避免：

- 大段文字承担主要信息
- 多层列表或多张卡片承担整幕叙事
- 大量静态页面连续出现
- 口播全文上屏
- 每个 Scene 都是同一套“标题 + 卡片 + 转场”模板
- 画布左上固定显示醒目的 Scene 大标题，让主体画面成为标题的配图
- 只替换文案，不改变视觉机制
- 场景之间仅靠翻页、淡入淡出或版式切换连接

优先使用：

```text
变化
移动
连接
扫描
执行
比较
展开
替换
状态变化
持续对象
视觉证据
```

一个短暂的静态停留可以用于阅读或强调，但不能成为整条视频默认的组织方式。如果任意代表帧都可以脱离上下文被当作 PPT 页面，必须判定视觉收敛失败。

新制作的 Prototype 和 Remotion 画面左上只保留有资料依据的简短内容文字，不显示 `SCENE 01`／`场景 01` 一类编号标识或固定大标题。例如原型中的「SCENE 05 · 上下文」只显示「上下文」。需要强调概念时，让文字跟随正在变化的对象、操作或证据出现；不能先摆一个标题，再逐项填充内容。历史已冻结原型不因本条自动失效，正在修改的视频须重新走对应人工 Gate。

### 轻量动态原型与正式视频的分工

Visual Prototype 是覆盖全片视觉逻辑的可播放设计稿，使用估算节奏验证布局、事件顺序、前态／动作／后态、阅读停留和跨幕承接。必须支持播放、暂停、重播和切幕；不要求制作真实音频、正式字幕或精确时间轴，不得依赖 Gate 2 后才产生的 TTS 资源。原型字幕区显示口播语义提示或设计提示，并明确为预估预览。

每个关键事件使用稳定的事件标识；原型按口播语义 组织事件。Gate 2 冻结视觉设计后，Remotion 复用布局与动作含义，将事件绑定实际 Cue／Segment。精确时机与阅读停留在 Gate 3 复核；明显改变主体布局、事件逻辑或跨幕承接必须重新确认 Gate 2。HTML 与 React 可以分别实现，不复制整套真实音频播放和字幕时间逻辑。

自检由实际观看画面的执行者记录；没有实际画面证据时保留失败／待检查结果，不得由模板或结构校验自动生成 passed。已完成视频永久只读；未完成历史项目在继续执行 Gate 2 及下游时检查当前自检，不批量重写状态。自检阻断不能被 legacy 校验策略降为警告。Gate 2 因自检阻断处于 ready／failed 时，也允许用户带明确原因驳回到 Visual Script，以便重新设计；不得通过修改状态绕过自检。

### 新视频的动态视觉设计

每个 Scene 先选一个当前最值得看的主体：可以是产品、界面中的操作、代码差异、流程节点、人物或有资料依据的视觉比喻。画面需要让观众看见它的**前态、触发动作和后态**；配角提供必要语境，不与主体争抢注意力。一个 Scene 若包含多个主体，须说明焦点何时从谁转到谁。

Visual Script 的每个关键视觉事件至少写明：触发它的口播语义、变化前的可见状态、主体如何变化、变化后的可读状态，以及旧主体的去向。相邻 Scene 要交代承接对象或转场理由；不能把三张彼此独立的页面当作连续过程。原型必须能预览这些关键变化，正式 Remotion 再按已确认的原型和实际时间基准实现。

主体动作完成后可以静置，让观众阅读、比较或听清口播。只在聚焦、空间关系或状态传递确有需要时使用缓慢运镜；不要为了避免静止检测结果而添加循环漂浮、扫光、无意义光效或强行切镜。检查的重点是“说到这里，画面是否提供了新的理解”，不是每秒是否有像素在动。

## 8.3 `narrated-tutorial-v1` 的适用方式

- `TUTORIAL-1 [MUST]`：可以使用标题、代码、终端、UI、流程图、对比卡或解释面板，但它们必须推进口播中的认知过程或提供可核验的视觉证据。
- `TUTORIAL-2 [MUST]`：允许短暂的教学标题或总结卡，但不能让每个 Scene 都退化为同一套标题页模板。
- `TUTORIAL-3 [MUST]`：代码、界面和流程图应通过执行、修改、扫描、连线、高亮、状态改变或结果出现来表达信息；静态界面不能只是口播的背景图。
- `TUTORIAL-4 [MUST]`：视觉可以解释口播没有直接说出的过程、状态和关系，不得只是把口播重新排版上屏。

## 8.4 标题作为视觉事件

缩小标题或把标题移到左上角，不足以解决逐页演示的问题。Visual Script 必须说明标题为什么出现、解释哪个对象／状态、如何交出焦点和何时退出。允许的处理包括：

- 开场概念文字短暂承担主视觉，随后缩小、移动或变形，交给实际主体；不能每幕重复一遍。
- 对象标签跟随对象，状态文字在状态改变后出现，结论文字在证据成立后突出；不能提前透露尚未发生的结果。
- 到达目标后，在落点附近揭示结果文字；下一动作开始前让旧文字退出或有意降权。

片段名称和导航留在预览控件区，最终视频不输出这些控件。标题、主体和字幕不能争夺同一阅读区域；依据 9.2 和 10.3 检查完整进入、移动、让位及退出过程。具体文案来自当前视频资料，不复制样片的任务名称或结论。

## 8.5 同一空间持续演进与跨幕承接

对连续过程，优先把 Scene 作为同一对象／空间的不同阶段：主体移动、展开、拆分、合并、处理、变形或交付，镜头按需要接近、拉远和跟随。不能默认每幕创建一套独立版式，再用转场连接。确需切换到另一个证据、地点或视角时，Visual Script 写明切换理由与接续关系。

Visual Script 必须记录持续主体的标识、空间中来源／处理端／目标的位置关系、各阶段状态、镜头焦点和视野变化、上一阶段留下的语境及其退出时机。背景、已建立的关系和主体可以跨 Scene 延续，但未来节点与路径必须按 9.2 隐藏；空间连续不能成为全片元素常驻的理由。

Prototype 和 Remotion 在跨幕时保持对象身份、位置、比例、状态和运动方向的可理解连续性；需要变化时呈现变化过程。持久空间与主体在共同容器维护，Scene 负责事件区间，不能因切幕卸载并重建主体而重播入场。连续状态按统一时间求值，显式处理全片帧与局部 Sequence 帧的换算；不能每幕把镜头和动画进度归零。

可采用以下承接机制，并按视觉任务选择：

| 机制 | 使用方式 |
|---|---|
| 对象延续 | 同一个主体接住上一动作的结果，继续改变状态或进入下一操作。 |
| 展开／合并／变形 | 从主体中展示组成关系，再收回主体或形成结果，保留身份线索。 |
| 运镜承接 | 在既有空间内推近检查、拉远建立关系、平移跟随对象；给观看者留足定位时间。 |
| 遮挡／遮罩揭示 | 借当前主体、视野或遮罩引出下一证据，交代前后关系，避免只加一个全屏擦除效果。 |
| 有理由的切换 | 更换证据或地点时说明叙事原因，保留必要的对象、方向或结果线索。 |

Gate 2／Gate 3 连续观看每个交界，并检查交界前、交界时和交界后的主体、镜头、文字与可见元素；出现位置跳变、背景重置、重复入场或独立页面替换时返回视觉设计。允许为理解静置，不强制整片一镜到底。

# 9. 动画规则

动画必须传递信息。

动画分三层：

## 一级：信息动画

必须优先。

例如：

- 节点出现
- 文件被扫描
- 代码被修改
- 测试运行
- 流程连接
- 状态改变

## 二级：注意力动画

少量使用。

例如：

- 高亮
- 放大
- 聚焦
- 淡化其他元素

## 三级：装饰动画

尽量少用。

例如：

- 粒子
- 无意义漂浮
- 无意义旋转
- 过多弹跳
- 炫技式转场

如果删除动画后信息完全不受影响，说明它可能只是装饰。

## 9.1 动作语义与通用组件复用

口播教程应根据当前视觉任务选择动作。同一种语义在同一视频中使用一致的动作表达；跨视频优先延续已验证的表达，颜色、对象和布局按当前资料与 Style 调整，不照搬其他视频的业务文案。不能为了套用组件而虚构传递、状态改变或焦点切换。

代码执行与路径表达必须遵守以下三条：

1. **代码执行优先通过逐行高亮、条件成立／不成立、变量与返回值变化表达。** 高亮须对应实际执行步骤，并配合判断或结果变化；已执行行让位，不能只移动焦点框而省略执行含义。
2. **路径用于确有意义的数据传递、调用关系或空间移动。** Visual Script 须说明传递的对象、来源、目标及路径所解释的关系；组件可用不能成为添加路径的理由。
3. **路径的分叉、绕行、回环必须有内容依据。** 不得让观众误读为不存在的分支、循环或执行步骤。仅为避让文字而产生的大幅绕行，应改布局或换表达方式，不能用满足遮挡检查代替动作语义检查。

| 动作 | 表达的含义与适用条件 | Remotion 通用组件 |
|---|---|---|
| 路径传递 | 表达对象、任务或信号从来源到达目标；来源、目标和方向必须清楚。路径揭示可说明连接关系；若口播强调对象到达，还需对象沿路径移动或目标接收后的状态，单纯画出连线不等于完成传递。 | `PathTransfer`：揭示 SVG 路径，不自动实现对象移动或目标接收。 |
| 状态替换 | 表达同一对象从旧状态变为新状态，例如待处理变为完成、草稿变为已发布。旧状态退出，新状态接替；对比任务可以有意保留旧状态，但须说明对比关系。 | `StateReplacement`：在同一区域让旧内容退出、新内容出现。 |
| 焦点转移 | 表达关注点从一个对象转到另一个对象。焦点框、高亮或配角降权用于引导阅读，不能用焦点变化代替实际操作或状态改变。 | `FocusTransfer`：移动焦点框；配角降权由场景按需要实现。 |

Visual Script 应说明关键事件采用的动作语义、它解释什么变化，以及完成后需要的阅读停留；没有传递或变化的内容可以静置，不要求每幕使用上述三种动作。Prototype 使用轻量 HTML／CSS／JS 表达相同含义；正式 Remotion 优先复用 `src/components/SemanticMotion.tsx`，不得在单条视频目录重复实现已经适用的公共动作。组件不能表达当前任务时，先确认差异；有复用价值的能力进入通用目录，一次性业务内容仍保留在本地视频目录。

动作起点必须来自当前 Workflow 已校验的事件时间绑定，持续时间按可读性和实际节奏安排，不另设一套固定间隔时间轴。Gate 2 检查动作是否解释了变化，Gate 3 检查它是否对应真实时间、是否完整发生及是否留足阅读时间；组件调用或类型校验通过不能替代实际画面检查。

## 9.2 元素的显示与退出时机

口播教程必须为视觉元素明确进入触发、可见区间、退出触发，以及跨 Scene 保留的理由。同一空间持续演进不等于所有元素全程常驻；尚未发生的路径、箭头、节点、结果和提示不得提前显示，已完成视觉任务的元素须按设计退出或有意降权保留。路径底线、描边、箭头、标签、光效和相关子元素必须一起受显示时机控制，不能只隐藏动画主体而留下底层轨迹。

跨幕保留必须指出该元素在后续哪个具体事件中仍有何用途，以及用途结束时的退出边界；只写“保持空间连续”“保留来路”或“降低透明度”不能作为保留依据。已完成的传递轨迹在后续展开、处理、检查等事件中没有具体用途时，应在交接后退出；降低透明度仍属于显示，必须接受同样的可见区间检查。

Visual Script 记录元素的可见性安排；Prototype 与 Remotion 按同一事件实现进入／退出。narrated 视频的正式时间绑定来自 Cue／Segment／Timeline，不能靠当前页面、播放历史或固定估算补时间。初始帧、暂停、回放、跳帧和反向拖动必须还原目标时刻的可见状态。

Gate 2 与 Gate 3 必须检查元素出现前、出现时、任务结束后及相邻 Scene 交界，特别检查未来路径提前泄露、旧标签残留和隐藏主体的子元素仍可见。发现错时元素时修正生命周期并重新观看，不能以空间连续、类型检查或时间轴结构校验通过代替此项验收。当前规则不代表 Harness 已具备自动识别画面中错时元素的能力。

## 9.3 React／Remotion 动画能力的选型与复用

先明确动作要解释的变化，再选择适用能力。不能把通用场景的淡入、平移、打字作为默认的全部动作，也不能只添加入场动画就宣称消除了 PPT 感。React 负责组织可复用组件；正式视频中的动画进度由 Remotion 帧驱动，不能假定普通网页动画库可以直接用于逐帧渲染。

| 能力 | 适用视觉任务 | 使用边界 |
|---|---|---|
| `useCurrentFrame`、`interpolate`、`Easing` | 位移、缩放、透明度、进度和镜头参数随事件变化 | 明确起止帧和外推边界，控制图层及阅读区域；单纯淡入不是状态演示。 |
| `spring` | 主体落位、展开、收拢和带重量感的响应 | 按任务设置阻尼、刚度、持续时间与是否允许回弹；延迟前隐藏元素，传入的局部帧不得为负，不让文字无意义弹跳。 |
| `Sequence`／`Series` | 安排局部事件区间与顺序 | 明确局部帧偏移；持久主体放在共同空间中，不按 Scene 重置。区间安排本身不构成转场设计。 |
| `@remotion/paths` | SVG 描边、路径变形、沿路径运动 | 按需要选择 `evolvePath`、`interpolatePath`、`getLength`、`getPointAtLength`、`getTangentAtLength`；描边、对象运动和到达反馈分别设计，共享同一路径／进度。 |
| `@remotion/transitions` 的 `TransitionSeries`、`linearTiming`／`springTiming` | 确需切换视角／证据时的淡化、擦除等过渡 | 不能把页面切换包装为连续空间；转场重叠会改变总时长，必须核对当前 Workflow 的区间、音画映射与总帧数，不得挤压既有时间基准。 |
| `SemanticMotion.tsx` 的三个公共动作 | 路径关系、同区状态替换、焦点转移 | 按 9.1 的实际能力复用；`PathTransfer` 不自带沿路径运动，`FocusTransfer` 不自带配角降权，`StateReplacement` 不自带形状变形。 |
| SVG／CSS 属性的帧驱动组合 | 进度环、接收波纹、错峰展开、合并、遮罩与空间运镜 | 已有能力不覆盖时组合实现；有复用价值的部分提取到通用目录，不把一次性业务写进公共组件。 |

实施顺序：核对现有通用组件与实际依赖 → 查官方 API 和版本兼容 → 用轻量 Prototype 验证视觉任务 → Gate 2 确认后实现公共 React／Remotion 能力 → 当前视频绑定真实事件 → Gate 3 对照实际画面。需要新增包时说明必要性，Remotion 配套包与实际核心版本兼容，不能只因组件多而引入依赖。

`@remotion/paths` 和 `@remotion/transitions` 已接入公共组件，使用方法、实际版本和通用 Studio 样片见 `docs/MOTION-COMPONENTS.md`。公共 HTML 样片的弹簧仍是原型近似；Remotion 能力样片使用官方实现，实际观感仍须人工复核。选择其他 React 动画库前，必须确认支持按目标帧确定性求值；正式渲染不依赖 CSS 自行播放的 animation／transition、墙钟计时或播放历史。

官方依据（本轮核对，后续实施仍按实际版本确认）：[动画属性与帧驱动](https://www.remotion.dev/docs/animating-properties)、[spring](https://www.remotion.dev/docs/spring)、[路径工具](https://www.remotion.dev/docs/paths/)、[TransitionSeries](https://www.remotion.dev/docs/transitions/transitionseries)。

## 9.4 动作链、节奏与音画映射

全片围绕可观察的变化链安排节奏：开场给出问题／动作／证据钩子，中段交替推进与阅读，结尾明确结果并及时收束。信息先后由内容决定，不要求同屏所有元素一开始全亮，不按每个要点平均时间依次淡入。通过动作速度、错峰、停顿、信息密度和焦点让位组织节奏，不用持续运动替代内容。

关键动作可以包含准备、执行、到达反馈和完成态停留：例如任务离开来源、路径揭示、对象沿路径移动、目标接收、状态更新；展开后看清关系，再合并到下一主体；处理进度完成后才出现完成标记。各环节是否需要以及持续多久由当前资料和理解负担决定，不能虚构步骤或反馈。

原型可按字数或语义估算节奏，必须标明预估；正式 narrated 视频使用已校验 Cue／Segment／Timeline 绑定「说到哪句，哪个元素在何帧变化」，不能继续按字数占比分配正式子时长。口播教程在 Gate 3 复核起点、过程、完成态、阅读时间与跨幕交界。

若当前视频使用 BGM／音效，应在资料中说明氛围、音效对应事件、音量关系及淡入淡出；口播清晰度优先，音效不能替代视觉到达反馈。无声样片不代表配乐、混音或旁白听感已验证。

# 10. Visual Prototype 规则

正式进入 Remotion 前，推荐先制作 Visual Prototype。

当前推荐方式：

```text
HTML + CSS + 少量 JS
```

Prototype 用于验证：

- 视觉方向
- 信息密度
- 场景结构
- 视觉语言
- 是否 PPT 化
- Scene 之间是否统一

Prototype 不是最终实现。

Gate 2 通过时必须冻结 Visual Script 与 Visual Prototype 的内容指纹和 Scene 清单。冻结结果是 Remotion 的实现基线；原型或视觉脚本随后发生变化时，旧的 Remotion 对齐记录必须失效并重新制作。

## 10.1 Gate 2 前视觉收敛自检

所有 Workflow 在请求 Gate 2 前都必须完成以下自检。自检必须基于实际 Prototype／预览画面或代表帧，不能只看 Markdown、源代码、文件是否存在或 Harness 结构校验结果；自检不替代用户的人工 Gate 2。

| ID | 级别 | 验收标准 | 失败处理 |
|---|---|---|---|
| VC-1 | [MUST] | 每个 Scene 有明确视觉焦点，关键事件能看见前态、动作和后态；不是只有文字入场和装饰。 | 回到 Visual Script，补齐主体、视觉任务和状态变化。 |
| VC-2 | [MUST] | 整条序列不依赖重复的“标题 + 卡片 + 转场”页面结构；同屏信息有主次，旧主体在新主体出现时有明确去向；按 8.3 执行教程视觉约束。 | 判定为 PPT 化，重做视觉机制与信息让位。 |
| VC-3 | [MUST] | Scene 之间存在可理解的连续关系、对象延续或有理由的切换；不能只靠换页连接。 | 重做跨 Scene 的承接对象和视觉叙事。 |
| VC-4 | [MUST] | 文字层级不压过视觉证据；画布左上没有 Scene／场景编号或固定大标题，保留的简短文字能追溯到当前视频资料；按 10.3 检查动画过程，当前需要阅读的文字不得重叠、被遮挡或裁切。 | 修正文字区域、运动路径、图层和旧内容退出方式，重新检查完整动作。 |
| VC-5 | [MUST] | 已按正常速度查看开头、中段、结尾及各类关键 Scene 的实际动态预览，按 10.3 补查关键事件的开始、途中、到达／完成和状态替换交叠时刻，并逐项记录通过／失败证据；有意静置的阅读区不因静止本身判失败。 | 未完成实际画面检查时，不得声称视觉已验证。 |
| VC-6 | [MUST] | 任一 MUST 失败时，不能进入 Remotion 或下一生产阶段，必须回到 Visual Script。 | 保持当前阶段为阻塞或重新生成后续视觉资料。 |

最少的自检记录应包含：使用的 Visual Script／Prototype 版本、代表帧或预览范围、VC-1～VC-6 的结果、发现的问题和对应修正。没有实际画面证据时，只能报告“结构已校验，视觉未验证”。

## 10.2 Gate 2 机器校验契约

视觉自检必须落为当前视频资料目录下的 `visual-self-review.json`。口播教程使用 `videos/<slug>/visual-self-review.json`；该文件属于本地视频资料，不进入通用能力代码。

最小结构如下：

```json
{
  "schemaVersion": 1,
  "videoSlug": "example",
  "workflow": "narrated-tutorial-v1",
  "visualScriptFingerprint": "...",
  "prototypeFingerprint": "...",
  "reviewedAt": "2026-09-19T12:00:00+08:00",
  "evidence": [
    {
      "id": "opening",
      "kind": "frame-sheet",
      "path": "visual-review/opening.png"
    }
  ],
  "checks": [
    {
      "id": "VC-1",
      "status": "passed",
      "evidenceIds": ["opening"],
      "note": "存在可观察的作品生成动作。"
    }
  ],
  "workflowChecks": [
    {
      "id": "TUTORIAL-1",
      "status": "passed",
      "evidenceIds": ["opening"],
      "note": "界面变化推进口播中的认知过程。"
    }
  ]
}
```

Gate 2 的自动前置校验必须检查：

- JSON 存在、格式正确、`schemaVersion` 受支持，`videoSlug` 和 `workflow` 与 Harness Registry／项目配置一致。
- `visualScriptFingerprint` 和 `prototypeFingerprint` 与当前资料一致；Visual Script 或 Prototype 改动后，旧自检自动失效。
- `VC-1`～`VC-6` 全部出现且为 `passed`；教程的 `TUTORIAL-1`～`TUTORIAL-4` 也必须全部出现且通过。
- 每个 `evidenceIds` 都能找到记录，证据路径是安全的项目内相对路径且文件真实存在；不能用空文件、占位字符串或旧版本证据绕过。
- 任一必检项缺失、失败、指纹过期或证据无效时，Gate 2 不能进入可人工审批的就绪状态，也不能推进 TTS 或 Remotion。

该机器校验只负责验证“自检记录完整、针对当前版本且没有失败项”，不能自动判断视频是否好看，也不能替代用户人工通过 Gate 2。Harness 尚未接入这份契约前，只能标记为“规则已定义、机器校验待实现”，不得报告为已完成的自动阻断能力。

## 10.3 动画过程中的文字与遮挡检查

本检查适用于口播教程的新视频与未完成视频。Gate 2 检查实际动态 Prototype，Gate 3 根据真实时间检查 Remotion 预览；只看完成态截图不足以通过。已完成视频保持永久只读。

- 每个包含文字的移动、路径传递、主体让位或状态替换事件，先按正常速度查看完整动作，再暂停检查开始、途中、到达／完成，以及旧新内容同时可见的时刻。路径转折、跨越其他对象和终点标签出现处须额外检查；几个代表帧不能代替完整播放。
- 当前需要阅读的标题、标签、状态、代码和字幕必须保持可读；不得与其他文字重叠，被卡片、移动对象或焦点框遮挡，或被容器／画布边缘裁切。连线和移动对象应绕开文字区域，终点须为对象和标签预留空间；给文字提高图层不能替代合理布局。
- 同一位置的状态文案替换，应让旧文案退出或分时显示，避免两段文字交叠到无法辨认。确需淡入淡出时，应在替换前后提供完整可读的停留，交叠期间不承担新的阅读任务；比较旧新状态时使用分开的可读区域。
- 修正时优先调整文字区域、路径、对象位置、旧内容退出时机或替换方式，不通过把文字缩得难读、隐藏必要信息或加快动作掩盖问题。修改后重新播放完整事件，并检查其前后承接。

Gate 2 将结果记入现有 `VC-4`／`VC-5` 的 `note` 与 `evidenceIds`，不新增检查 ID 或改变 JSON schema。证据应标明 Scene、稳定事件 ID、检查范围和关键时刻，以及发现的问题与修正；可以采用附有这些信息的人工观看记录、录屏或关键帧。没有实际观看证据时保持待检查／失败，不得由源代码、类型检查或结构校验生成通过结论。

Gate 3 使用同样的检查方法，记录实际帧号或时间及复查结果；Prototype 通过不能代替真实音频时序下的 Remotion 检查。遮挡未解决时不得请求 Gate 3 通过或完整渲染；若修正明显改变冻结的主体布局、事件逻辑或跨幕承接，按既有规则重新确认 Gate 2。本规则要求人工画面复核，不代表 Harness 已具备自动碰撞或遮挡识别能力。

# 11. Remotion 的职责

Remotion 是：

> **实现层**

不是：

> 内容设计层。

Remotion 不应该重新决定：

- 视频讲什么
- Scene 怎么拆
- 视觉应该怎么表达
- 哪个知识点重要

这些必须在前面确定。

Remotion 主要依据：

```text
Scene Script
+
Visual Script
+
Visual Prototype
+
外部提供的音频 / 字幕数据
```

对于有明确口播的视频，Remotion 制作必须先读取已校验的 Audio Manifest、Subtitle Manifest 和 Timeline Manifest，并以 `timeline-manifest.json` 作为唯一时间基准。Scene 时长、音频起点、字幕位置和视觉事件时间必须从同一套 Scene／Segment／Cue 映射产生；TypeScript 配置统一复用 `src/lib/timing.ts` 的 `createNarratedTiming`，`remotion-alignment.json` 的每个 Scene 必须记录这些来源、起止秒／帧和动画事件绑定；不得在单条视频目录内重新实现时间映射，也不得先按估算时长或任意硬编码时间完成画面，再事后适配音频。缺少映射时必须停止制作并报告原因。

每条新视频进入 Remotion 后必须生成 `videos/<video-slug>/remotion-alignment.json`，逐 Scene 记录：

- 对应的原型指纹
- 关键布局关系
- 视觉事件
- 屏幕文字
- Remotion 实现文件

Harness 负责检查指纹是否仍然有效、Scene 是否完整覆盖、实现文件是否存在；Gate 3 负责人工判断画面是否真正兑现原型，不使用像素相似度代替视觉判断。

- 字幕文本是什么

# 16. Quality Review

每个 Scene 完成后至少做以下检查。

## Visual Convergence Test

在进入 Gate 2 前，先执行 10.1 的 VC-1～VC-6；在 Gate 3 前，再对照冻结的 Visual Prototype 和 Remotion 输出复查。结构校验、类型检查、文件存在和指纹一致只能证明生产资料可消费，不能证明视频好看或已经摆脱 PPT 化。

如果开头、中段或结尾的代表帧仍然像独立幻灯片，或者连续播放时只是不断替换标题和卡片，即使所有自动校验通过，也必须判定失败并回到 Visual Script。

## Silent Test

关闭声音。

问：

> 只看画面，能不能大概理解这一幕发生了什么？

如果完全不能，画面可能只是装饰。

## Duplication Test

问：

> 画面是不是只把口播重新显示了一遍？

如果是，需要重新设计视觉。

## Motion Value Test

问：

> 动画是否真正表达了信息？

如果删除动画没有任何影响，可能只是装饰。

## Video Value Test

问：

> 这一幕为什么必须用视频来表达？

如果没有答案，需要重新设计。

# 17. 公共规则与单条视频必须分离

本文件只能保存：

> 所有视频都长期适用的规则。

本章的视觉收敛基线适用于所有新建或尚未完成的视频；已标记为 `completed` 的视频仍按项目永久只读规则保护，不因本规则回写旧资料。教程的解释性画面仍不能绕过实际画面自检。

禁止写入：

- 某个具体 Scene 的设计
- 某条视频的配色临时决定
- 某个案例的画面方案
- 某个主题的口播内容

单条视频自己的内容应该放在独立目录中，例如：

```text
content-analysis.md
video-narrative.md
scene-script.md
narration-script.md
visual-script.md
visual-prototype.html
```

# 18. 最终原则

整个系统必须始终遵守以下几条：

1. **文档和视频共享知识，不共享表达结构。**
2. **先设计视频，再写口播。**
3. **Scene 是基本叙事单位。**
4. **声音负责解释，视觉负责演示和证明。**
5. **动画必须表达信息。**
6. **Visual Prototype 用于在 Remotion 前验证视觉方向。**
7. **Remotion 负责实现，不负责重新设计内容。**
8. **逐 Scene 实现，不一次生成整条视频。**
9. **公共规则和单条视频设计必须分离。**
10. **TTS / 字幕属于外部生产模块，Video 项目只消费标准化结果。**
