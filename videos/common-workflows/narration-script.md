# Claude Code 常见工作流 · Narration Script

## Scene 01｜日常活儿，其实就四类

你回想一下，自己天天对着代码到底在干什么？说白了，翻来覆去就四件事：接手一个看不懂的项目、修一个莫名其妙的 bug、把一坨代码重构干净，再给某个函数补上测试。

这四类活儿各有各的标准打法。今天我们不讲抽象的说话技巧，直接把四套能调出来就用的模板拆开。

## Scene 02｜先按动不动代码选工具

先认准一个判断维度：这活儿动不动你的代码？

探索代码库基本是只读，重点是它讲得对不对。修 bug 要改已有代码，重点是根因和回归测试。重构也会改代码，但行为必须保持不变。写测试主要是增加验证文件，最该盯的是边界情况有没有覆盖。

所以关键不是会不会用 Claude，而是这件活儿该掏哪把工具。

## Scene 03｜探索代码库，从大到小三层问

接手陌生项目时，别一上来就钻进某个文件。最稳的节奏是从大到小问三层。

第一层，先要整体架构和主要模块职责。第二层，找到你关心的功能在哪些文件里，以及这些文件怎么协同。第三层，再追踪一条核心流程的完整执行路径。前两层可以在 Plan Mode 里问，先读和讲，不让它改源码。

## Scene 04｜修 bug，先找根因再动手

修 bug 最容易翻车，因为“报错消失”不等于“问题解决”。正确流程是四步：贴完整报错和复现步骤，让 Claude 先定位根因并解释为什么会错；根因确认后再改；最后补一个能复现这个问题的回归测试，并跑一遍确认通过。

少了最后这把锁，同一个 bug 以后还会原地复活。

## Scene 05｜重构，整理代码但不能改行为

重构的风险更高，因为它动的是本来没坏的代码。重构不是把代码改得看起来更漂亮，而是结构可以变，对外行为不能变。

先让 Claude 解释当前行为和边界，再说清重构目标；如果没有测试，先把现有行为测下来。然后小步修改，改前和改后都跑测试，结果一致才算完成。

## Scene 06｜写测试，重点不是正常路径

写测试时，Claude 会沿用项目已有的测试框架和断言风格，但如果你不特别交代，它很可能只测正常情况。

所以要明确要求它覆盖空输入、零、负数、超大值和类型不对这些边界，也让它帮你补充没想到的组合。真正容易出 bug 的，通常不是正常路径。

## Scene 07｜实战，先让 bug 可复现

光看模板还不算会，我们拿一个真 bug 跑一遍。

先创建一个叫 `bug-demo` 的玩具项目，在 `calc.py` 里写一个计算平均值的 `average` 函数。它看起来没毛病，但传入空列表时，长度是零，函数就会因为除以零崩溃。

## Scene 08｜把报错和复现步骤一次交代清楚

接着把错误说清楚：调用 `average([])` 时出现 `ZeroDivisionError`，给 `average` 传空列表就必现。

这时不要只说“帮我修一下”。要让 Claude 先解释根因：空列表让 `len(numbers)` 变成零，所以除法失败；先别改代码，等它把原因讲明白。

## Scene 09｜修复后，测试必须跑绿

根因确认后，再批准修复，并补上回归测试。至少验证空列表这个问题已经处理，同时确认正常输入仍然通过。

当 `test_average_empty_list` 和 `test_average_normal` 都显示 `PASSED`，这次修 bug 才算真正闭环。你留下的不只是一个暂时不报错的改动，还有一把防止问题复活的锁。

## Scene 10｜把四类模板存成速查卡

最后把四套打法记成一张卡：探索是从大架构到文件再到执行链路；修 bug 是贴报错、找根因、修改、补回归；重构是讲现状、定目标、小步改，并保证行为不变；写测试是显式覆盖边界，再让 Claude 帮你补漏。

以后遇到复杂任务，也可以把这四类工作组合起来。下一篇我们继续处理那些文字不容易说清的输入：图片与多模态。
