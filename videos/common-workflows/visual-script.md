# Claude Code 常见工作流 · Visual Script

> 目标：让声音解释四类工作的判断逻辑，让画面演示风险差异、验证闭环和一次完整的修 bug 过程。

## 全局视觉原则

### 1．声音负责解释，画面负责证明

口播负责说清任务差异、步骤原因和验收标准；画面不重复整段旁白，而是展示任务分流表、调用链、错误状态、测试结果和前后对照。

### 2．每幕只保留一个视觉中心

10 个 Scene 依次处理四类任务地图、分流表、探索路径、修 bug 闭环、重构对照、边界测试、实战复现、根因诊断、回归通过和总结预告。每幕不同时塞入多个主结论。

### 3．保持 16:9 深色教程感

- 1920 × 1080 横屏构图。
- 深色背景，蓝紫色作为结构强调，绿色只表示测试通过，红色只表示错误或风险。
- 标题控制在 1～2 行，终端、文件名、函数名和测试结果使用等宽字体。
- 卡片、终端和表格留出安全边距，避免底部字幕区域被主内容占满。

### 4．画面文字必须有当前资料依据

所有任务名称、命令、文件名、函数名、错误、测试结果、Plan Mode 和下一集预告均来自 `source.md`、Content Analysis、Video Narrative、Scene Script 或本 Visual Script。不复用其他视频的业务语义或固定状态文字。

## 逐 Scene 视觉设计

### Scene 01｜日常活儿，其实就四类

- **画面结构**：深色工作台中央放置四张任务卡，背景以模糊的代码窗口作为统一环境。
- **视觉动作**：卡片按“探索 → 修 bug → 重构 → 写测试”依次亮起，最后汇聚成一个“四类高频任务”标签。
- **信息重点**：四类名称及其不同的任务性格。
- **与口播互补**：口播解释日常工作的重复性，画面建立四类对象，不把整段文章做成字幕。
- **场景类型**：`Concept Diagram + Cards`。

### Scene 02｜先按动不动代码选工具

- **画面结构**：四行对比表，列为“任务／代码影响／Claude 主要做什么／最该盯的”。
- **视觉动作**：先高亮“动不动代码”，再逐行显示只读、修改、行为不变和新增测试四种状态。
- **信息重点**：`只读`、`修改`、`行为不变`、`新增测试`。
- **与口播互补**：口播说明分流规则，表格让四类差异同时可比较。
- **场景类型**：`Comparison Table`。

### Scene 03｜探索代码库，从大到小三层问

- **画面结构**：左侧项目架构树，中部功能文件，右侧执行链路；三者用箭头相连。
- **视觉动作**：镜头从整体项目缩放到相关文件，再沿一条流程连线向下追踪；角落保持 `只读` 标签。
- **信息重点**：`整体架构`、`相关文件`、`执行链路`、`Plan Mode`。
- **与口播互补**：口播解释三层问题，画面直接演示从面到线的探索节奏。
- **场景类型**：`Code Exploration + Process`。

### Scene 04｜修 bug，先找根因再动手

- **画面结构**：一条横向流程：报错和复现 → 根因解释 → 修复 → 回归测试。
- **视觉动作**：红色错误卡先停在“先别改”节点，根因节点出现后才开放修改，最后测试状态变绿。
- **信息重点**：`先找根因`、`不要盖住症状`、`回归测试`。
- **与口播互补**：口播讲“错误消失不等于问题解决”，画面用权限顺序和颜色变化证明这条原则。
- **场景类型**：`Process + Test Loop`。

### Scene 05｜重构，整理代码但不能改行为

- **画面结构**：左右两个代码窗口，左为“改前”，右为“重构后”，中间是一把写着 `行为不变` 的锁。
- **视觉动作**：右侧函数结构拆开或整理，底部同一组输入输出和测试结果保持一致。
- **信息重点**：`改前测试`、`小步改`、`改后测试`、`行为不变`。
- **与口播互补**：口播解释重构的风险，画面将结构变化和行为不变并列呈现。
- **场景类型**：`Before/After Comparison + Test`。

### Scene 06｜写测试，重点不是正常路径

- **画面结构**：一个测试矩阵，顶部是正常输入，四周是空输入、零、负数、超大值和类型不对。
- **视觉动作**：正常输入先通过，边界输入逐个进入矩阵并被标记为“需要覆盖”；最后出现“帮我补漏”的提示。
- **信息重点**：`正常路径`、`边界情况`、`空输入`、`零`、`负数`、`类型不对`。
- **与口播互补**：口播说明测试不能只测正常情况，画面把测试范围扩大过程变成可视化动作。
- **场景类型**：`Test Matrix`。

### Scene 07｜实战，先让 bug 可复现

- **画面结构**：终端窗口占主区域，依次显示项目目录、`calc.py` 和 `average` 函数。
- **视觉动作**：输入 `mkdir bug-demo`，随后显示函数代码，执行 `average([])` 后出现红色 `ZeroDivisionError`。
- **信息重点**：`bug-demo`、`calc.py`、`average([])`、`ZeroDivisionError`。
- **与口播互补**：口播交代玩具项目，终端提供共同的复现现场。
- **场景类型**：`Terminal Demo`。

### Scene 08｜把报错和复现步骤一次交代清楚

- **画面结构**：左侧是包含报错和复现步骤的提示卡，右侧是因果链：空列表 → `len(numbers) = 0` → 除以零。
- **视觉动作**：提示卡中的“先别改代码”形成暂停线，因果链节点依次亮起。
- **信息重点**：`先定位根因`、`len(numbers) = 0`、`先别改代码`。
- **与口播互补**：口播解释模板的写法，画面将根因坐标和动作顺序同时展示。
- **场景类型**：`Prompt + Causal Diagram`。

### Scene 09｜修复后，测试必须跑绿

- **画面结构**：终端分成修复 diff 和测试结果两段，底部放一条“回归锁”。
- **视觉动作**：修复完成后，两个测试行依次显示 `PASSED`，锁从打开变为闭合。
- **信息重点**：`test_average_empty_list PASSED`、`test_average_normal PASSED`、`回归测试`。
- **与口播互补**：口播说明测试全绿才算闭环，画面用结果和锁证明“以后不容易复活”。
- **场景类型**：`Terminal Demo + Test Result`。

### Scene 10｜把四类模板存成速查卡

- **画面结构**：四格速查卡排列四种任务及模板核心，右下方留出独立预告卡区域。
- **视觉动作**：四格依次亮起，随后主卡收缩，`17 图片与多模态` 预告卡升起并停留约 2～3 秒。
- **信息重点**：四条模板核心、`17 图片与多模态`。
- **与口播互补**：口播负责记忆口诀和系列承接，画面提供可保存的速查结构。
- **场景类型**：`Summary Card + Preview`。

## 全片视觉类型、组件与动画标准

### 视觉类型

- `Concept Diagram`：用于四类任务地图和行为锁。
- `Comparison`：用于四类分流表、重构前后和正常／边界输入。
- `Process`：用于探索三层路径和修 bug 四步闭环。
- `Terminal Demo`：用于 `bug-demo`、`calc.py`、错误和测试结果。
- `Summary Card`：用于四条模板核心与下一篇预告。

### 组件标准

- 所有窗口使用统一深色标题栏、细边框和圆角。
- 任务卡、流程节点和测试结果使用相同的间距与标签尺寸。
- 终端文本统一等宽字体，错误用红色，通过用绿色，普通说明用低对比度灰蓝色。
- 预告卡与字幕区域分离，底部保留足够安全空间。

### 动画标准

- 卡片和流程节点按口播顺序依次淡入或轻微上移。
- 错误、根因、修复、通过使用明确的状态变化，不使用无意义的快速闪烁。
- 探索路径使用缩放和连线表现层级，重构使用左右对照表现不变的行为。
- Scene 09 的测试结果按行出现，Scene 10 的预告卡在总结后停留约 2～3 秒。
