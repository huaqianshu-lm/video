# Claude Code 常见工作流 · Content Analysis

> 目标：从原文提取四类高频编码任务的区别、标准打法和验证闭环，再据此设计一条以“选对工具、控制风险、留下证据”为主线的视频。

## 1．核心命题

这篇文章真正要解决的不是让观众背下四段提示词，而是建立一个任务分流判断：

> **探索代码库、修 bug、重构和写测试虽然都能让 Claude Code 参与，但它们对代码的影响和主要风险不同，因此必须使用不同的工作流模板。**

四类任务的共同方法是把目标、上下文、动作和验证说清楚；差异在于：探索强调只读和从大到小，修 bug 强调先找根因并补回归测试，重构强调行为不变并比较改前改后，写测试强调边界情况覆盖。

## 3．必须保留的信息

### A．四类任务的分流维度

| 任务 | 对代码的影响 | Claude 主要做什么 | 用户最该检查什么 |
|---|---|---|---|
| 探索代码库 | 不动，偏只读 | 读文件、解释架构和调用链 | 讲得是否准确 |
| 修 bug | 修改已有代码 | 定位根因、修复、补回归测试 | 根因是否找对，回归测试是否通过 |
| 重构 | 修改已有代码，但行为必须不变 | 等价改写、整理结构 | 改前改后行为是否一致 |
| 写测试 | 新增测试文件或用例 | 遵循现有测试风格，覆盖场景 | 边界情况是否覆盖 |

这一张分流表是全片的认知骨架，不能只做成装饰性总结。

### B．探索代码库：从大到小三层问

- 第一层是整体架构和主要模块职责。
- 第二层是某个功能涉及哪些文件，以及这些文件如何协同。
- 第三层是追踪一条核心流程的完整执行路径。
- 前两层适合在 Plan Mode 中进行，目标是只读和理解，不让 Claude 误改源码。
- 探索的核心验收不是“改出了什么”，而是解释是否准确。

### C．修 bug：诊断到回归的四步闭环

1. 提供完整报错、堆栈和复现步骤。
2. 先定位根本原因并解释为什么会错，不要立即改代码。
3. 根据根因实施修复，不要只压住错误症状。
4. 补一个能复现问题的回归测试，并运行确认通过。

文章用 `average([])` 的 `ZeroDivisionError` 说明：错误消失不等于根因解决，回归测试才是防止同一问题复活的“锁”。

### D．重构：行为不变的安全路径

- 先解释当前代码的行为和容易忽略的边界。
- 明确重构目标，例如拆分函数、换现代写法或消除重复。
- 采用小步、可测试的增量，不一次性推翻重写。
- 改前先跑测试，改后再跑测试，结果应保持一致。
- 没有测试覆盖时，先补测试记录现有行为，再开始重构。

重构的核心不是“代码看起来更干净”，而是“对外行为完全不变”。

### E．写测试：不要只测正常路径

- 先指定文件和函数，并沿用项目已有测试框架和断言风格。
- 明确要求覆盖空输入、零、负数、超大值、类型不对等边界。
- 主动让 Claude 补充用户没有想到的边界组合。
- 写完运行测试，把失败修到通过。
- 用 `@` 精确引用目标文件，减少上下文定位误差。

### F．完整实战的可视化链路

原文给出一个 `bug-demo` 玩具项目：创建 `calc.py`，其中 `average(numbers)` 在空列表上除以零；启动 Claude Code；提供报错和复现步骤；先让 Claude 解释根因，再批准修复；新增测试并看到正常输入和空列表用例通过。这个实战必须保留，因为它把“模板”变成可观察的流程。

## 4．认知关系

### 任务分类关系

```text
四类高频任务
├─ 只读理解：探索代码库
├─ 修复已有行为：修 bug
├─ 保持行为的整理：重构
└─ 新增验证资产：写测试
```

### 风险与验证关系

```text
探索 → 防止误改 → Plan Mode／三层提问
修 bug → 防止治标 → 根因解释／回归测试
重构 → 防止行为漂移 → 改前改后测试
写测试 → 防止覆盖虚高 → 边界情况／运行通过
```

### 实战因果链

```text
average([])
↓
len(numbers) = 0
↓
ZeroDivisionError
↓
先解释根因
↓
修复并补回归测试
↓
正常输入与空列表都通过
```
