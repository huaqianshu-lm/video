## 1. 核心命题

Claude Code 用得好不好，关键不只在模型能力，而在使用者是否建立了一套能让 AI 稳定工作、自己验收、及时纠偏的协作方式。

这套方法可以压缩成一个总约束和六条法则：上下文窗口是最稀缺的工作记忆；因此要给出可执行的验收方式，先探索和规划再编程，把需求说具体，把 `CLAUDE.md` 写精，发现跑偏立即纠偏；单个会话稳定后，才考虑并行和审查扩展。

## 2. 文章必须保留的知识

### A. 总约束：上下文窗口

- Claude 的 context window 会快速被对话、读取的文件和命令输出填满。
- 上下文逐渐填满后，模型更容易忘记早期约束、降低判断质量。
- 后面的实践都在服务同一个目标：减少无效来回，保持上下文干净，让有限的工作记忆留给真正的问题。
- 文章用“固定大小的白板”比喻上下文：白板不是越多越好，而是要把重要信息留在上面。

### B. 法则一：给它一个能自己验收的方式

- 没有检查时，“看起来完成”就是 Claude 唯一的完成信号，用户被迫成为验证循环。
- 测试、构建退出码、linter、固定基准比对、截图比对，都可以提供“过／不过”的反馈。
- Prompt 应明确写出规则、示例和“完成后运行验证”。
- 应要求展示测试输出、命令返回内容或截图等证据。
- 验证要解决根因，不应通过注释错误、加绕过标记或把类型断成 `any` 来压住症状。

### C. 法则二：先探索，再规划，最后编程

- 陌生项目或多文件任务，不应一上来就修改。
- 推荐顺序：在 Plan Mode 探索代码和现状 → 形成计划 → 退出 Plan Mode 实现 → 运行验证。
- 计划可以被用户检查和修订；满意后再实施。
- 一句话能描述清楚的 diff，例如改拼写、加日志、重命名变量，可以跳过计划。

### D. 法则三：把话说具体，并把上下文喂足

- Claude 能推断意图，但不会读心；文件、场景、边界、参考模式和验收标准越明确，返工越少。
- 具体 prompt 应说明：改哪个文件、发生了什么症状、覆盖哪些边界、什么结果才算修好。
- 可引用现有文件和历史、贴图、给 URL、用管道输入数据，或让 Claude 自己用命令／工具取上下文。
- 模糊提问仍有价值，但只适合探索阶段，用来发现原本没想到的问题；确定要实现时应收紧。

### E. 法则四：`CLAUDE.md` 要写精，不是写多

- `CLAUDE.md` 是每次新会话都会读的常驻便签，应放 Claude 无法从代码推断的命令、项目特有约束、测试方式、分支规矩和常见坑。
- 每一行都要问：删掉它会不会导致 Claude 犯错？不会就删。
- 不应塞入代码本身能说明的背景、标准常识、长篇教程、易过时信息、详细 API 文档或偶尔才用的规范。
- 偶尔使用的细则应放到 Skill；详细文档应链接出去；重要规则可用 `IMPORTANT` 或 `YOU MUST` 强调。

### F. 法则五：一跑偏就立刻纠偏

- 发现方向错时，立即按 `Esc` 停止，或用 `/rewind` 回退、明确要求撤销错误修改。
- 同一问题纠正三次仍未解决时，应 `/clear`，带着已经学到的教训在干净会话重开。
- `/compact` 用于压缩仍有价值的上下文；`/clear` 用于上下文已经被错误方向污染。
- 可把调查工作交给 subagent，只把结论带回主会话；给会话起描述性名字，并用 `claude --continue` 或 `claude --resume` 续接。

### G. 法则六：一个 Claude 用顺了，再横向铺开

- 并行不是第一步；一个 Claude 还没指挥顺时，多个会话只会放大混乱。
- 互不依赖的任务可以用多个会话并行，最好用 worktree 隔离修改。
- Writer／Reviewer 模式让一个会话实现、另一个全新会话审查，利用干净上下文减少自我偏袒。
- `claude -p` 可用于非交互脚本，`--output-format json` 适合结构化输出，`--allowedTools` 用于限制无人值守权限。
- 对抗性审查应只追踪影响正确性的发现，不能为了回应每个审查意见而过度工程。

### H. 沟通习惯和实践实验

- 在陌生代码库中，直接问 Claude 资深工程师会问的问题：日志如何工作、如何新建 API、某段代码为何这样调用。
- 大功能先让 Claude 用 `AskUserQuestion` 采访技术实现、UI／UX、边界、顾虑和权衡，再沉淀成 `SPEC.md`，用新会话实现。
- Claude 说“应该可以了”时，要求它运行验证并贴出证据。
- 对比实验用密码强度函数展示：模糊 prompt 让模型自行猜规则且通常没有测试；具体 prompt 明确文件、规则、示例和验证，用户可以直接验收结果。

## 3. 认知关系

### 因果关系

上下文窗口会被快速填满 → 无效读取、反复纠正和冗长常驻规则会挤占工作记忆 → 需要压缩沟通、验证、纠偏和分工 → Claude 更容易在正确方向上完成任务。

### 流程关系

探索 → 规划 → 实现 → 验证；如果方向错误，则停止／回退／重开，再进入更干净的流程。

### 对比关系

- 没有验收 vs 有验收：用户质检 vs Claude 自验。
- 模糊 prompt vs 具体 prompt：模型猜规则 vs 按明确规则执行。
- 直接编程 vs Plan Mode：先改后发现方向错 vs 先理解再动手。
- 肥大的 `CLAUDE.md` vs 精简便签：重要规则被噪音淹没 vs 每条都能被看见。
- 长会话硬熬 vs 干净会话重开：错误上下文累积 vs 带着教训重新开始。
- 单会话自审 vs Writer／Reviewer：同一上下文偏袒自己 vs 新鲜上下文发现问题。

### 角色关系

- 人：定义目标、提供边界、做取舍、判断业务是否正确、审查证据。
- Claude：探索代码、形成方案、执行修改、运行检查、反馈证据。
- Subagent／Reviewer：承担调查或独立审查，避免污染主会话或陷入自我确认。

## 4. 可视觉化内容

- 固定大小的白板被对话、文件和命令输出逐渐填满。
- “任务完成”与“验证通过”之间的闭环：执行 → 检查 → 读结果 → 修正。
- Plan Mode 的四段流程：Explore → Plan → Implement → Verify。
- 模糊与具体 prompt 的左右对照，以及具体 prompt 的文件、规则、示例、验证四个支点。
- `CLAUDE.md` 便签的精简／膨胀对照。
- 跑偏后的 Esc／Rewind／Clear 路径。
- 单 Claude 稳定后，扩展到并行会话、Writer／Reviewer、脚本和独立审查。
- 密码强度实验的两次输出对比。
