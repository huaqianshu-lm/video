# Claude Code 最佳实践视频化 · Narration Script

## Scene 01｜一句模糊指令，为什么会修错

你对 Claude 说一句“修一下登录的 bug”，它真的可能开始改代码。但哪个登录？什么 bug？在哪个文件？怎么算修好了？这些信息它都只能自己猜。

换成“用户报告 session 超时后再登录会失败，先看 `src/auth/` 的 token 刷新，写个能复现的测试，再让它通过”，任务就从猜谜变成了可以执行、也可以验收的工作。

## Scene 02｜所有问题都指向一块有限的白板

这背后有一个总约束：Claude 的上下文窗口会很快被对话、它读过的文件和命令输出填满。

你可以把它想成一块固定大小的白板。白板写满以后，早先的提醒会被后面的内容挤掉，Claude 就更容易忘记约束、重复犯错。

所以后面的每条最佳实践，本质上都在帮它省这块白板。

## Scene 03｜给它一个能自己验收的方式

第一条，也是最重要的一条：给 Claude 一个它能自己运行的检查。

没有测试、构建或截图比对时，Claude 做完只能觉得“看起来完成了”，你就被迫成为质检员。

如果 prompt 里写清规则和示例，并要求完成后运行验证，它就能执行、读取结果、发现问题、继续修改，最后把测试输出或命令结果作为证据交给你。

## Scene 04｜先探索，再规划，最后编程

面对陌生项目或多文件任务，不要让 Claude 一上来就改。先在 Plan Mode 里读代码、了解现状，再给出计划；你确认方向以后，退出计划模式实施，最后运行验证。

当然，改个拼写、加一行日志这种一句话就能说清的 diff，不需要套完整流程。能用一句话描述清楚，就直接做；方向不明或范围较大，就先探索和规划。

## Scene 05｜把话说具体，并把料喂足

具体的指令，至少要说清四件事：改哪个文件和范围，出现了什么症状和边界，项目里有什么现成模式可以参考，以及什么结果才算完成。

需要的上下文也一次给足。用 `@` 引用文件，贴上截图，提供 URL，或者把日志通过管道交给它。探索时可以开放地问“你会怎么改进”，真正要实施时，就把要求收紧到另一个工程师也能照做的程度。

## Scene 06｜`CLAUDE.md` 是便签，不是百科全书

`CLAUDE.md` 是 Claude 每次新会话都会读的常驻便签。它应该只放 Claude 从代码里猜不到、但漏掉就会犯错的命令、项目约束、测试方式和常见坑。

代码本身能说明的背景、标准常识、长篇教程和偶尔才用的规范，都不该把这块便签写满。每一行都问自己：删掉它，Claude 会不会因此犯错？不会，就删掉，或者把细则放到 Skill 和文档里。

## Scene 07｜一跑偏，就停、退、重开

发现方向不对时，别让一串错误修改继续污染上下文。按 `Esc` 停下，用 `/rewind` 回退，或者直接说明要撤销哪个动作。

如果同一个问题纠正三次还没有解决，就用 `/clear` 带着已经学到的教训重开一块干净白板。调查工作可以交给 subagent，只把结论带回来；重要会话则用描述性名字保存，之后再继续。

## Scene 08｜一个用顺了，再横向铺开

并行是扩展层，不是起点。一个 Claude 还没用顺，开五个只会把混乱放大五倍。

等单个会话稳定以后，再用 worktree 隔离多个互不依赖的任务；让一个会话写，另一个拥有全新上下文的会话审查；需要时用 `claude -p` 接入脚本。

但审查者报出的每个问题都不一定是真缺陷。只追踪影响正确性的发现，别为了回应每一条意见而过度工程。

## Scene 09｜把 Claude 当资深同事问，并索要证据

接手陌生代码库时，直接问 Claude 你会问资深工程师的问题：日志怎么工作，怎么新建 API，某一行代码为什么这样调用。

大功能动手前，可以让它用 `AskUserQuestion` 采访技术实现、界面、边界和权衡，聊透以后把结果写成 `SPEC.md`，再用新的会话实现。

还有一个简单动作：它说“应该可以了”时，让它跑一下验证，把输出贴出来。把声称变成证据，才是真正的验收。

## Scene 10｜对比实验：具体到底值多少

现在做一个五分钟的对比。第一条 prompt 只有一句：“写个判断密码强不强的函数。”规则由 Claude 自己猜，结果可能没有测试，你也不知道它到底对不对。

清空会话后，改成具体版本：写一个放在 `password.js` 的 `isStrongPassword` 函数；长度至少八位，包含一个大写字母和一个数字；再给出三个示例，并要求跑完把输出贴出来。

这一次，规则、文件和验收结果都在眼前。你不用猜它理解得对不对，也不用亲自当质检员。

## Scene 11｜六条法则，回到一个总原则

遇到它做完却不放心，就补一个验收；方向不明，就先探索和规划；它总是理解错，就把文件、边界、参考和完成标准说具体。

常驻规则太多，就把 `CLAUDE.md` 写精；同一个问题纠正几轮仍在跑偏，就停下、回退或重开；一个会话用顺以后，再用并行和独立审查扩展。

这六条不是僵硬的咒语，而是围绕“省着用上下文”的一组起点。下一篇 **50「反模式：常见的错误用法」**，我们再看哪些做法千万别这么用。
