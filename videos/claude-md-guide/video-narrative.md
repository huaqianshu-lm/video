# Claude.md 使用指南视频化 · 第二步：Video Narrative

> 目标：让观众从“为什么规则不生效”出发，建立一套能写、能维护、能验证 CLAUDE.md 的判断方法。

## 1. 视频的叙事目标

这条视频不把 CLAUDE.md 做成规则清单朗读，而是让观众先看到一个具体失败：一条“只用 pnpm”的规则被埋在长文档里，Claude 仍然使用 `npm install`。由此引出真正的问题不是“Claude 不听话”，而是记忆文件把重要规则稀释了。

观众最终应建立四个判断：

1. CLAUDE.md 是每次会话加载的项目入职手册，但不是铁律。
2. 不同层级有不同作用范围，加载是从广到窄的拼接。
3. 只保留长期事实和具体、可验证的规则，控制在约 200 行以内。
4. `@` 适合组织已有文档，不会减少上下文；维护要靠增量写入、验证和定期精简。

## 2. 整体叙事结构与路径

```text
规则被埋没
    ↓
CLAUDE.md 的正确定位
    ↓
三层加载关系
    ↓
该写什么、删什么
    ↓
@ 引用的真实代价
    ↓
会话中补记忆、定期精简
    ↓
用可验证规则和最小项目验收
    ↓
把文件从百科全书变成项目护栏
```

## 3. 第一段：先展示“写得多却没生效”

### 叙事目的

用开发者熟悉的包管理器错误制造问题，先让观众感受到“内容越多不一定越有效”。

### 内容设计

- 屏幕是一份冗长的 CLAUDE.md，背景介绍、愿景、历史说明占据大部分空间。
- 深处闪过一条“依赖管理只用 pnpm”的规则。
- 任务执行时却出现 `npm install`，规则被标为未生效。
- 旁白给出反转：问题不在它不听话，而在重要规则被埋没、上下文被稀释。

### 视觉事件

```text
长文档滚动 → 规则短暂出现 → npm install → 重要规则被埋没
```

## 4. 第二段：先把 CLAUDE.md 定位准确

### 叙事目的

在观众接受问题后，给出定义和边界，避免把它误解为安全锁或自动记忆系统。

### 内容设计

- 每次新会话从白纸开始。
- CLAUDE.md 像每天重读的项目入职手册。
- 它作为用户消息在系统提示后传递，Claude 会尝试遵循，但没有严格遵守保证。
- 需要硬性阻止危险操作时，不应只依赖它。

### 视觉事件

```text
Blank session → Read CLAUDE.md → Start task
```

画面同时显示“强烈建议”和“非铁律”两种边界标签，帮助观众建立准确预期。

## 5. 第三段：三层不是覆盖，而是从广到窄拼接

### 叙事目的

解决最容易记反的加载关系，并让观众知道不同信息应该放在哪一层。

### 内容设计

- 用户级管理个人习惯。
- 项目级管理团队共享规则。
- 子目录级管理某个模块的细则。
- `CLAUDE.local.md` 作为只给当前用户的项目本地变体。
- 加载从最广泛到最具体，越靠近工作目录越晚读取；多个文件拼接，不是覆盖。

### 视觉事件

```text
User → Project → Subdirectory
广范围 → 窄范围
先读 → 后读
```

## 6. 第四段：用“该写／不该写”做一次减法

### 叙事目的

把抽象的“精简”落到可执行取舍，建立篇幅感和内容边界。

### 内容设计

- 应写五类：项目概述、技术栈、常用命令、代码约定、明确的不要做。
- 不写长篇背景、过时信息和 Claude 看代码就能知道的内容。
- `尽量整洁`、`注意安全` 是不可验证的散文；`函数不超过 50 行`、`禁止修改 legacy/` 才是规则。
- 以约 200 行作为目标，展示从 300 行压缩到精简版本。

### 视觉事件

```text
五类规则逐条落位 → 背景段落被裁掉 → 300 lines → < 200 lines
```

## 7. 第五段：`@` 是组织工具，不是上下文减肥术

### 叙事目的

处理一个看似高级、实际容易误判的功能，并强调它的真实代价。

### 内容设计

- 用 `@README`、`@docs/git-instructions.md` 表示引用。
- 相对路径从包含引用的文件解析，也可以用绝对路径。
- 引用可递归最多四跳，项目外第一次引用会要求批准。
- 被引用内容启动时展开进上下文，所以 `@` 改善组织，不减少 token 或上下文占用。

### 视觉事件

```text
CLAUDE.md → @docs/rules.md → 展开内容
文件结构更清楚，但 Context usage 不下降
```

## 8. 第六段：维护不是一次写完，而是持续收敛

### 叙事目的

让观众知道什么时候加规则、什么时候删规则，以及发现失效时如何排查。

### 内容设计

- 临时形成的长期约定，直接让 Claude 加进 CLAUDE.md，或用 `/memory` 打开并编辑。
- 换包管理器、调整依赖、改变约定或超过 200 行时，主动精简。
- 规则失效时按顺序排查：文件是否加载、规则是否模糊、规则是否冲突。

### 视觉事件

```text
纠正一次 → 加入 CLAUDE.md → /memory 确认
项目变化 → 删除旧规则 → 保留当前规则
```

## 9. 第七段：把“好规则”变成可验收的结果

### 叙事目的

用对照和玩具项目把方法落地，避免结尾停在抽象建议。

### 内容设计

- 左侧是“代码应该整洁”“尽量写测试”等模糊规则。
- 右侧是“一眼能判定”的具体规则。
- 最小项目只保留一个 `add` 函数，CLAUDE.md 不到 15 行。
- 用 `/memory` 确认文件加载，再让 Claude 做一件会触碰约定的任务。

### 视觉事件

```text
模糊散文 → 具体规则 → /memory → 执行任务 → 看 diff 验证
```

## 10. 第八段：总结“护栏”，并预告下一篇

### 叙事目的

把前面的判断压缩成可记忆的工作原则，再自然承接文章已经给出的下一篇主题。

### 内容设计

- CLAUDE.md 不是百科全书，而是项目护栏。
- 用户级、项目级、子目录级解决范围问题。
- 具体规则、精简内容和持续维护解决遵守问题。
- `@` 解决组织问题，不解决上下文容量问题。
- 结尾预告下一篇“上下文管理”，只提出问题，不提前讲解。

### 视觉事件

```text
Scope → Rules → References → Maintenance → Verification
```

## 11. 叙事节奏

| 段落 | Scene | 节奏 | 认知变化 |
| --- | --- | --- | --- |
| 问题 | 01 | 快 | “写得多”不等于“听得进” |
| 定义 | 02 | 稳 | 建立文件的能力边界 |
| 层级 | 03 | 清晰 | 知道规则放在哪里 |
| 取舍 | 04 | 收紧 | 知道什么值得占上下文 |
| 引用 | 05 | 转折 | 发现拆文件不等于省上下文 |

| 验证 | 07 | 加速 | 规则从散文变成验收条件 |
| 收束 | 08–09 | 放慢 | 形成护栏概念并进入下一篇 |

## 12. Video Narrative 最终版

1. **规则为什么失效**：用 `pnpm` 与 `npm install` 的冲突制造问题。
2. **它到底是什么**：CLAUDE.md 是持久指令和入职手册，不是铁律。
3. **规则放在哪里**：三层范围从广到窄加载，并且拼接。
4. **什么值得写**：五类长期事实与 200 行边界。
5. **为什么 `@` 不省上下文**：引用展开改善组织，但不减少加载量。
6. **如何维护**：直接补入、用 `/memory` 检查、定期删除旧规则。
7. **如何判断写得好**：从模糊散文到一眼可验证的规则，并跑最小验证。
8. **最后留下什么**：把 CLAUDE.md 变成项目护栏，下一篇进入上下文管理。

## 13. Gate 1 内部结论

- 叙事顺序遵循问题、定义、层级、取舍、代价、维护、验证、收束的认知路径，没有机械沿用 01–08 章节顺序。
- 每个 Scene 的主要认知任务单一，内容覆盖了 source 的核心知识而没有把下一篇文章提前展开。
- 视觉事件优先使用滚动、堆叠、裁剪、展开、连接和验证状态，避免把文章变成静态目录。
- 结尾预告的主题和顺序来自 source，预告停留时间在原型中单独保留。
