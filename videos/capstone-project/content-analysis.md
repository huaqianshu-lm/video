# Claude Code 综合实战视频化 · 第一步：Content Analysis

## 1. Source 识别

- 主题：综合实战：从零到上线，把前 47 篇学到的 Claude Code 能力串成一条真实工程流。
- 核心案例：一个带本地 JSON 存储、测试和 README 的命令行任务清单工具 todo-cli。
- 内容范围：立项、规划、MCP、subagent、检查点、验证、git 交付，以及玩具练习与真实项目的差异。
- 本视频只基于 source.md 的当前文章，不展开下一篇文章的内容；结尾预告只使用原文已经给出的下一篇标题「最佳实践」。

## 2. 核心命题

这篇文章不是功能百科，而是一张中等项目从开工到交付的工程地图：

> 单独会用 CLAUDE.md、权限、MCP、subagent、检查点和 git，不等于能把它们合成一套稳定的真实项目流程；真正的毕业设计，是知道它们在什么时候接力、如何跨会话交接、如何验证和退回，并把交付边界守住。

视频需要让观众完成这次认知变化：

~~~text
我学过一组零件
↓
中等项目会跨会话、需要外部上下文，也会失败
↓
流程要把立项、规划、执行、验证、容错和交付串起来
↓
可靠的 AI 协作依赖清晰规矩、可检查状态和可恢复退路
~~~

## 3. 知识骨架

### 3.1 总体流程

1. 立项：确定项目、写简洁的 CLAUDE.md、配置权限基线。
2. 规划：通过采访沉淀 SPEC.md，再按功能切分会话。
3. 接外部：在需要频繁复制外部资料时接入 MCP，并先验证信任。
4. 分活：用 subagent 隔离探索，用新鲜上下文做代码审查。
5. 容错：小范围用检查点倒带，大范围回到稳定 git 提交。
6. 交付：亲手验证、审查改动范围、commit，并由人把守 push。

流程不是单向直线。一个会话完成一轮验证后，可能回到规划阶段，继续下一块工作。

### 3.2 关键概念

- 中等项目：比单文件练习复杂，包含多个文件、持久化、测试、文档，并需要多个会话。
- CLAUDE.md：项目规矩的持久化载体，内容应足够少但覆盖 Claude 无法自行猜出的约束。
- 权限基线：把反复执行且已确认安全的命令纳入允许范围，同时保留对陌生改动的审查。
- SPEC.md：跨会话交接的稳定备忘录，记录接口、边界、范围和验收方式。
- MCP：把项目外部的文档、数据库或项目管理系统连接进来；连接前要验证服务器信任，数据库优先只读。
- subagent：在独立上下文中完成探索，只返回摘要，避免主对话被文件全文塞满。
- 检查点与 git：检查点适合撤销当前会话的 Claude 编辑；git 负责跨会话的稳定提交和更大范围的恢复。
- 交付边界：本地 commit 可以纳入流程，但 push 到远程必须由人亲自把关。

### 3.3 案例事实链

~~~text
todo-cli
├─ Python 标准库
├─ 本地 todos.json
├─ add / list / done
├─ unittest
└─ README

会话 1：骨架、读写、add、测试
会话 2：list / done、测试
会话 3：边界处理、补测试
会话 4：README、整体检查、交付
~~~

文章中的示例命令包括 git init、编写 CLAUDE.md、生成 SPEC、接入官方文档 MCP、派 subagent 探索、/code-review、/rewind、运行 python3 -m unittest、检查 git diff 和 git status、创建 commit。视频把这些作为流程中的状态证据，不把它们误述为本次视频项目实际执行过的命令。

## 4. 观众认知路径

1. 观众容易把前面学过的能力理解成彼此孤立的技巧。
2. 先用「毕业设计／乐队合奏」建立总问题：会零件不等于会组织项目。
3. 再展示中等项目的回路：立项、规划、接外部、分活、容错、交付。
4. 通过 todo-cli 让抽象流程落地到文件、测试、会话和提交。
5. 用失败恢复和 push 红线补上可靠性与责任边界。
6. 用玩具项目和真实项目对照收束，留下可重复的工作方法。

## 5. 可视觉化内容

- 六棒流程图，带从验证返回规划的回路。
- todo-cli 文件树、CLAUDE.md、todos.json、测试和 README 的项目骨架。
- SPEC.md 作为跨会话交接卡，会话 1 到会话 4 的接力。
- MCP 从本地项目连接到文档、数据库和 GitHub 的关系图。
- subagent 在独立上下文探索，主对话只接收摘要。
- 检查点与 git 的轻档／重档恢复对比。
- 测试输出、真实功能输出、code review、git diff、commit 和 push 红线。
- 玩具练习与真实项目的七项对照。

## 6. 内容取舍与事实边界

保留：

- 「中等项目不是把小任务拉长，而是多了跨会话、外部连接、并行分工和恢复机制」这一核心差异。
- todo-cli 的具体工程流，因为它把每个能力放进真实上下文。
- 先验证再相信、干净退回、勤 commit、push 由人把关等风险控制。
- 文章明确给出的 MCP 信任提醒与数据库只读建议。

压缩：

- 不逐一解释前 47 篇的编号和全部背景，只保留当前流程需要的能力名称。
- 不把每条命令和预期输出都做成独立 Scene，选择能证明状态变化的关键节点。
- 不展开 Agent Teams 的实验性细节，只在分活场景说明 subagent 与新鲜审查上下文。

禁止引入：

- 下一篇「最佳实践」文章的内容。
- 当前项目之外的真实 todo-cli 运行结果。
- 未在当前文章或本视频生产资料中出现的产品承诺。
- 把文章中的示例命令当作本次任务要执行的指令。

## 7. Video Value 基线

本视频必须通过过程、状态和回路让观众理解「如何把零件组织成工程流」。如果只把六个名词和一张表铺在页面上，观众只能得到功能清单，无法看到跨会话、验证、退回和交付之间的关系。因此每个 Scene 至少有一个可观察的状态变化：项目从空白到有规矩、任务从模糊到有 SPEC、上下文从本地到外部、工作从主会话分出、错误从混乱退回稳定、改动从完成走向验证和交付。
