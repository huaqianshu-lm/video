# Claude Code 综合实战视频化 · 第三步：Scene Script

## Scene 01｜毕业设计不是新功能

### 目的
把观众从「继续学功能」切换到「组织已有能力」的问题。

### 叙事角色
开场命题，建立整条视频的观看目标。

### 口播方向
说明前 47 篇像零件，真正困难的是让它们在一个正经项目里合奏。

### 画面方向
散落的 CLAUDE.md、权限、MCP、subagent、检查点、git 标签被吸入一条项目时间线，最后形成乐队指挥台。

### 屏幕重点
~~~text
学会零件
≠
完成项目
~~~

### Scene Type
Concept Visualization

### 信息分工
- 声音：解释「学会」与「合奏」的差异。
- 画面：让零散能力发生聚合。

### Video Value
只有通过零件聚合、顺序和状态变化，观众才能直觉理解「综合实战」不是新功能列表。

## Scene 02｜中等项目是一条带回路的工程流

### 目的
建立全片地图，告诉观众接下来会看到哪些环节。

### 叙事角色
总览和路线确认。

### 口播方向
中等项目的骨架是立项、规划、接外部、分活、容错、交付；验证完一轮，还会回到规划继续下一块。

### 画面方向
六个节点依次亮起，最后从交付回到规划形成回路；跨会话标签沿回路移动。

### 屏幕重点
~~~text
立项 → 规划 → 接外部 → 分活 → 容错 → 交付
~~~

### Scene Type
Process Diagram

### 信息分工
- 声音：解释直线变回路的原因。
- 画面：展示六棒顺序和回路。

### Video Value
回路动画把「跨会话接力」和「验证后回到规划」变成可见关系。

## Scene 03｜立项：先把规矩和退路立起来

### 目的
说明中等项目的第一步不是马上写代码，而是建立规则和恢复原点。

### 叙事角色
为后续所有会话搭地基。

### 口播方向
todo-cli 需要多个文件、持久化、测试和 README；因此先用 CLAUDE.md 写约束，用权限基线减少重复批准，再用 git 留下干净原点。

### 画面方向
空项目依次出现 CLAUDE.md、todos.json、test_todo.py、README，下方生成 git init 原点；权限允许列表亮起。

### 屏幕重点
~~~text
先定规矩
先留退路
~~~

### Scene Type
Project Setup Simulation

### 信息分工
- 声音：说明规矩、权限和 git 各自解决什么问题。
- 画面：展示项目从空白到有地基。

### Video Value
文件和状态的逐步出现，证明「立项」是后续协作的前置条件，不是形式文档。

## Scene 04｜规划：SPEC 让大活儿可以跨会话

### 目的
展示如何把模糊需求变成可交接的多会话计划。

### 叙事角色
从地基进入可执行的项目拆分。

### 口播方向
先让 Claude 采访边界和取舍，再把结果写进 SPEC.md；之后按功能切分会话，每个新会话先读 SPEC 和 git log。

### 画面方向
模糊需求卡片经过采访问题，收敛为 SPEC.md；四个会话卡片依次接力，SPEC.md 始终位于中间。

### 屏幕重点
~~~text
SPEC.md
会话 1 → 会话 2 → 会话 3 → 会话 4
~~~

### Scene Type
Cross-Session Workflow

### 信息分工
- 声音：解释文件化交接为何比口头记忆可靠。
- 画面：展示一份 SPEC 跨会话传递。

### Video Value
接力和共享 SPEC 的运动关系，是静态列表无法表达的核心价值。

## Scene 05｜接外部：MCP 把够不着的资料接进来

### 目的
解释 MCP 的使用信号以及连接能力的信任边界。

### 叙事角色
把项目上下文从本地延伸到外部。

### 口播方向
当你不断从文档、数据库或 GitHub 复制资料时，就到了该连接 server 的时机；但连接前要验证信任，生产数据库优先只读。

### 画面方向
项目窗口左侧反复出现复制粘贴断点，随后一条 MCP 连接接通文档、数据库和 GitHub，连接旁出现信任检查与只读标记。

### 屏幕重点
~~~text
先验信任
数据库只读
~~~

### Scene Type
Connection Diagram

### 信息分工
- 声音：解释什么时候需要 MCP，以及为什么不能盲接。
- 画面：展示外部上下文接入和安全条件。

### Video Value
连接从断开到接通，同时保留警示标签，能把「能力扩大」和「风险扩大」的关系同时呈现。

## Scene 06｜分活：隔离探索，保留主上下文

### 目的
让观众理解 subagent 和新鲜审查上下文的分工。

### 叙事角色
解决项目变大后的上下文与质量问题。

### 口播方向
让 subagent 去摸清 todos.json 的读写位置，只回传文件和函数摘要；功能完成后，再用新鲜上下文审查 diff，不让作者自己给自己打分。

### 画面方向
主会话把「探索 todos.json 读写」任务派出，subagent 在独立档案室扫描，回传一张摘要卡；另一条审查通道接收 diff 并标记问题。

### 屏幕重点
~~~text
只回传摘要
新鲜上下文挑刺
~~~

### Scene Type
Delegation + Review

### 信息分工
- 声音：解释隔离探索和独立审查各自解决什么。
- 画面：展示任务外派、摘要回传和 diff 审查。

### Video Value
上下文边界和信息压缩是分工的关键，必须通过两条独立路径才能看清。

## Scene 07｜容错：改崩时先干净退回

### 目的
提供中等项目的失败恢复心智模型。

### 叙事角色
在流程中加入止损和恢复。

### 口播方向
改崩以后不要在烂摊子上继续补丁；小范围用 /rewind 撤当前会话编辑，大范围回到稳定 git 提交，再补清楚约束重新开始。

### 画面方向
左侧代码越补越乱，右侧从稳定提交分出两档恢复：检查点轻档和 git 重档；最终回到干净状态。

### 屏幕重点
~~~text
干净退回
不是硬补
~~~

### Scene Type
Recovery Comparison

### 信息分工
- 声音：说明检查点和 git 的边界。
- 画面：展示从混乱状态回到稳定点的路径。

### Video Value
回退动作本身是流程可靠性的关键证据，无法用一句「可以恢复」替代。

## Scene 08｜真实项目：先规划，再开始动手

### 目的
把前面的地基和规划落进 todo-cli 的真实操作顺序。

### 叙事角色
从概念回到端到端演示。

### 口播方向
进入项目后，先在 plan mode 明确 todo-cli 的 add、list、todos.json 和 unittest，再等待确认后开始修改；每改一处都检查 diff 是否符合方案。

### 画面方向
Terminal 中出现项目任务，plan mode 输出文件结构和命令；批准按钮亮起后，todo.py、test_todo.py 和 todos.json 依次出现。

### 屏幕重点
~~~text
先出方案
再开始
~~~

### Scene Type
Terminal + Plan Simulation

### 信息分工
- 声音：说明先计划、再修改的顺序。
- 画面：展示计划、批准、文件生成和 diff 检查。

### Video Value
这个 Scene 把抽象原则转为可观察的操作门槛，避免视频停留在方法论口号。

## Scene 09｜真实项目：验证和挑刺

### 目的
建立「结果必须由证据确认」的验收标准。

### 叙事角色
把执行推进到质量检查。

### 口播方向
先跑 unittest，再跑真实 add 和 list；最后用 /code-review 找新鲜上下文挑出正确性问题。Claude 说改好了，不等于项目已经验收。

### 画面方向
Terminal 先显示测试 OK，再显示两条任务和未完成标记；/code-review 生成审查卡，指出待检查项。

### 屏幕重点
~~~text
跑出来才是事实
~~~

### Scene Type
Verification Demo

### 信息分工
- 声音：解释测试、真实功能和 review 的证据链。
- 画面：展示从命令到输出再到审查的连续状态。

### Video Value
输出状态的连续变化能证明「验证」不是一句承诺，而是交付前的实际动作。

## Scene 10｜交付：看范围、写 commit、守住 push

### 目的
收束本地交付流程，并明确人的最终责任边界。

### 叙事角色
从「完成实现」转向「可控交付」。

### 口播方向
交付前先看 git status 和 git diff，确认范围，再拟清楚的中文提交信息并 commit；本地 commit 可以交给流程，push 到远程必须自己把关。

### 画面方向
工作区文件进入 diff，diff 被压缩成一条明确 commit；远程 push 按钮停在人工检查线之前。

### 屏幕重点
~~~text
commit
↓
人把关 push
~~~

### Scene Type
Delivery Boundary

### 信息分工
- 声音：解释范围审查和 push 红线。
- 画面：展示改动从工作区到本地提交，随后在远程发布前停住。

### Video Value
「停在 push 前」是责任边界的视觉事件，能避免把自动化交付误解成无人监督。

## Scene 11｜玩具打法与真实打法

### 目的
把全片方法压缩成可复用的判断标准。

### 叙事角色
对照和总结。

### 口播方向
玩具练习可以省步骤，真实项目不能。规矩、规划、会话接力、外部信任、新鲜挑刺、容错和交付把关，省掉任何一个，往往只是把成本推到后面。

### 画面方向
左侧玩具流程短而断裂，右侧真实流程完整并带回路；七个差异标签逐个从左侧迁移到右侧。

### 屏幕重点
~~~text
流程不是镣铐
是把项目做大的骨架
~~~

### Scene Type
Comparison Diagram

### 信息分工
- 声音：给出玩具与真实项目的判断。
- 画面：展示省略步骤如何造成断点，以及完整流程如何支撑规模。

### Video Value
对照不是把表格念一遍，而是通过断点和回路让因果关系可见。

## Scene 12｜合奏完成，下一集预告

### 目的
回收核心命题，并完成系列视频的下一集预告。

### 叙事角色
结论、停留和系列承接。

### 口播方向
这篇没有新功能，而是让前面学过的零件在一个中等项目里真正活起来；当流程稳住，才敢把任务交得更大。下一篇进入「最佳实践」，继续讨论怎样把这套流程做得更好。

### 画面方向
六个能力节点回到同一条项目曲线，合奏指挥台变成清晰的交付路线；最后只留下下一集预告卡片。

### 屏幕重点
~~~text
下一集
49「最佳实践」
~~~

### Scene Type
Summary + Preview

### 信息分工
- 声音：总结方法和系列承接。
- 画面：让全片零件汇聚并把预告单独留在最后 2～3 秒。

### Video Value
结尾回路和预告卡片共同完成记忆收束与系列导航，不能只靠口播顺带提及。
