# MCP：给 Claude 接上外部世界 · Video Narrative

> 目标：不机械复述文章章节，让观众从“Claude 够不着外部服务”走到“能正确、安全地接上并验证一个 server”。

## 1. 视频叙事目标

观众的认知变化：

```text
一个参数位置错误，让 server 连不上
↓
问题不在 MCP 神秘，而在“谁解析哪一段命令”
↓
MCP 是把 Claude 接向外部服务的统一接口
↓
先按运行位置分清 stdio、HTTP 和已弃用 SSE
↓
再把选项、分隔线和 scope 放到正确位置
↓
工具注册后仍有状态检查和两道批准闸
↓
连接第三方服务前必须验证来源、限制权限
↓
用 add → list → approve → remove 跑通完整闭环
```

## 2. 叙事起点和结论

### 起点

从“装第一个 database server 时折腾一小时”的真实坑开始。观众先看到一条看起来合理却失败的命令，再看到参数位置修正后的瞬间连接成功，由此产生“命令到底是谁来解析”的问题。

### 中段问题

先回答 MCP 补上的是什么，再用“本地还是远程”的判断轴区分三种 transport；之后把命令语法和 scope 具体拆开，避免抽象定义停留在概念层。

### 结论

MCP 不是绕过权限的万能插口。正确的连接流程是：选对 transport 和 scope，确认 server 状态，批准项目来源与首次工具调用，验证第三方信任并使用最小权限，最后及时清理不用的 server。

## 3. 整体叙事结构

```text
01 参数放错，server 连不上
↓
02 MCP：给 Claude 接上外部世界
↓
03 三种 transport：本地、远程、已弃用
↓
04 `add` 命令：选项、名称与 `--` 分界
↓
05 三种 scope：谁能在什么项目里用
↓
06 工具出现以后：状态与两道批准闸
↓
07 第三方 server：先验证信任，再给权限
↓
08 实战前两步：add 与 list
↓
09 实战后两步：批准、调用与 remove
↓
10 收束选择，下一篇看 Subagent
```

## 4. 逐段叙事设计

### 第一段：用坑建立注意力

先展示错误命令和反复下载，再用正确命令解释 `--` 的责任边界。第一幕不先讲协议定义，让“位置”成为全片记忆钩子。

### 第二段：把 MCP 从黑盒变成扩展坞

用 Claude 的本地能力和外部 Jira、数据库、Figma 的断开关系，解释 MCP 为什么存在；扩展坞类比只做直觉入口，随后落到开放标准。

### 第三段：按运行位置分类

让观众先问“server 跑在哪里”，再看 stdio、HTTP、SSE 的连接方式。SSE 只承担“认识旧配置、不要新用”的信息，不抢主线。

### 第四、五段：把命令变成可检查的结构

第四段放大命令的四个区段，解决开关与 `--` 的位置；第五段把 local、project、user 画成不同范围，回答“这个 server 给谁用”。

### 第六、七段：能力出现不等于无条件执行

先展示 server 工具注册和连接状态，再用两道批准闸与第三方信任梯度把安全边界落地；声音讲原因，画面展示状态从待批准到可用的变化。

### 第八、九段：用真实 server 走一遍闭环

前两步展示 add 与 list，后两步展示会话内点名、首次工具批准、调用旁边的 server 名称和 remove 清理；全程只模拟，不执行命令。

### 第十段：从命令记忆收束为选择原则

用“本地／云端／共享范围／安全闸门”的四个结论回收内容，再给出 source 中已有的下一篇 23“子代理（Subagent）”预告，保留独立停留空间。

## 5. 叙事节奏

- Scene 01—03：快速建立坑点、核心定义和 transport 判断轴。
- Scene 04—07：集中讲命令、scope、状态和安全，是信息密度最高的解释段。
- Scene 08—09：用四步实战把概念变成连续状态，屏幕文字以命令和结果为主。
- Scene 10：降低密度，给总结和下一集预告各留出可读停留。

## 6. 声音与视觉分工

| 叙事信息 | 声音负责 | 画面负责 |
|---|---|---|
| 开头坑点 | 解释错误来自参数责任边界 | 错误命令、`--` 分界和正确命令 |
| MCP 定义 | 解释本地短板和开放标准 | 本地工具、MCP 层、外部服务连接 |
| transport | 说明本地／远程／弃用关系 | 三路连接与运行位置 |
| add 与 scope | 解释选项位置和共享范围 | 命令拆分、配置文件和范围覆盖 |
| 工具与批准 | 说明状态和批准为什么存在 | 工具注册、状态牌、两道闸门 |
| 信任边界 | 解释提示注入和最小权限 | 信任梯度、只读标签和警告 |
| 实战闭环 | 串联四步操作和预期结果 | add、list、approve、remove 状态变化 |
| 结尾 | 给选择原则和下一集主题 | 总结映射、独立预告卡 |

## 7. Gate 1 叙事审查结论

- 叙事按照“先看到失败，再理解原因，再建立模型，最后实战验证”的认知过程重组，没有直接把 source 章节当 Scene。
- “位置决定责任”贯穿命令语法、transport、scope 和批准流程。
- transport、scope、批准和信任分别使用不同视觉机制，不会被压成一张功能列表。
- 实战命令仅用于屏幕展示和叙事验证，不在本任务中执行。
- 结尾只使用 source 已给出的下一篇标题和 Subagent 主题，不提前读取或补写下一篇内容。

**Gate 1 结论：通过，可进入 10 个 Scene Script。**
