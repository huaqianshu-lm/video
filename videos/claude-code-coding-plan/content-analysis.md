# Claude Code 订阅套餐与计费视频化 · 第一步：Content Analysis

> 目标：从原文中提取“怎么选、钱花在哪、怎么查、怎么省”的知识关系，不直接把文章章节改写成口播或镜头。

## 1. 内容定位

### 1.1 原文解决的问题

原文表面上在介绍套餐和三个命令，真正要解决的是一个成本决策问题：

> **使用 Claude Code 时，费用来自哪里，应该选择哪种付费路径，以及如何确认钱没有从错误的接口流走。**

它同时覆盖四层内容：

- 认知：Claude Code 工具本身免费，真正计费的是模型处理请求的算力。
- 决策：按量计费、官方订阅和国产 Coding Plan 各自适合什么人。
- 排错：Coding Plan 的 Base URL 和专属 Key 配错，可能绕过套餐额度产生按量费用。
- 习惯：用 `/usage`、`/usage-credits`、`/status` 观察和约束开销，再通过减少上下文和返工来省 token。

### 1.2 内容边界

- 套餐价格、促销、额度和厂商接口规则会变化，视频不把当期金额当成永久事实。
- 火山方舟的 `/api/coding`、`/api/v3` 和阿里百炼的 Key 前缀只能作为源文档中的示例，画面必须明确“以厂商当前官方文档和控制台为准”。
- 视频讲的是选择逻辑和检查方法，不重新展开上一篇的完整接入教程。
- `/usage-credits` 的适用范围必须说清是官方 Pro／Max 场景，不能暗示所有 Coding Plan 都共享同一套额度规则。

## 2. 核心命题

### 2.1 主命题

> **Claude Code 不按“问了几次”简单收费，而是按模型处理的 token 和上下文产生成本；选对付费路径只是第一步，配置正确、及时检查和控制上下文，才是真正的成本控制。**

### 2.2 观众必须带走的三句话

1. Claude Code 工具本身免费，输入、输出和扩展思考消耗的是模型算力；上下文越大，单次请求越容易变贵。
2. 按量计费、官方订阅和国产 Coding Plan 没有绝对最优解，应该根据模型偏好、使用强度、支付和网络条件做选择。
3. 买了 Coding Plan 不等于请求一定走套餐；Base URL、API Key 和 `/status` 必须一起核对，平时再用 `/clear`、Sonnet 和具体提示减少浪费。

### 2.3 视频成功标准

观众看完后能够：

- 说出 Claude Code 的主要计费单位是 token，并理解输入、输出和上下文会影响成本。
- 区分官方按量计费、官方订阅和国产 Coding Plan 的选择条件。
- 识别 Coding Plan 的两个高风险配置点：套餐专属 Base URL 和套餐专属 Key。
- 用 `/usage` 看当前会话，用 `/usage-credits` 理解官方计划的支出上限，用 `/status` 检查配置是否生效。
- 通过 `/clear`、默认 Sonnet、复杂任务先 plan mode 和具体提示控制 token。
- 完成一次 `/status → 小任务 → /usage → /usage-credits` 的最小检查流程。

## 3. 必须保留的知识骨架

### A. 先回答：钱到底花在哪

必须保留的关系：

```text
Claude Code 工具
        ↓ 发起请求
模型处理输入、输出和思考
        ↓ 按 token 计量
成本产生
```

出租车类比可以保留，但画面同时要出现 `input tokens`、`output tokens` 和 `context`，避免观众只记住“里程”而忘记计费机制。

需要强调：

- 读取大文件会增加输入 token。
- 长对话会把旧上下文带入后续请求。
- 扩展思考会增加输出侧处理量。
- 费用和“提了几个问题”不是简单正相关，和每次带入的上下文量关系更大。

### B. 三条付费路径是选择题，不是排名题

| 路径 | 核心机制 | 更适合 | 主要代价或风险 |
|------|----------|--------|----------------|
| 官方按量计费 | 按 token 使用量扣费 | 想用官方原生模型、用量波动可接受 | 账单浮动，可能超预算 |
| 官方订阅 | 固定月费和计划额度 | 高频使用、希望支出更可预期 | 支付、网络和额度规则有限制 |
| 国产 Coding Plan | 固定月费、多工具共享额度 | 国内用户、成本敏感、接受模型差异 | 厂商规则变化，模型和兼容性不同 |

画面要表达“谁适合哪条路”，不能只做价格从高到低的排行榜。

### C. Coding Plan 的核心陷阱是“买了套餐却没走套餐”

必须保留这条因果链：

```text
买了 Coding Plan
        ↓
填错 Base URL 或 Key
        ↓
请求没有消耗套餐额度
        ↓
转而按量计费
        ↓
月底出现额外账单
```

火山方舟示例需要并列展示：

- `.../api/coding`：源文档说明的 Coding Plan 路径。
- `.../api/v3`：源文档说明的普通 API 路径。

同时强调：这是源文档中的厂商示例，具体路径和 Key 前缀可能调整，动手时以厂商官方资料为准。

### D. 三个命令承担三种不同职责

```text
/usage          看当前会话和估算用量
/usage-credits  设官方计划的使用上限
/status         查版本、模型、账户和连通性
```

不能把三个命令混成一个“用量面板”：

- `/usage` 的美元数是本地估算，权威账单仍看 Console。
- `/usage-credits` 是官方 Pro／Max 计划的控制能力，不等于厂商 Coding Plan 的统一额度开关。
- `/status` 是配置验收入口，尤其用来确认模型和连通性是否符合预期。

### E. 省钱核心是减少无效上下文和返工

保留四个动作：

1. 不相关任务之间使用 `/clear`。
2. 日常编程默认 Sonnet，复杂架构和多步推理再考虑 Opus。
3. 复杂任务先进入 plan mode，减少方向错误的返工。
4. 提示具体到文件、函数和目标，减少无关扫描。

这四项要被组织成“减少上下文、降低模型档位、减少返工、缩小搜索范围”四个可解释的省钱杠杆。

### F. 最小实践闭环

原文的三步动作适合收束成可执行流程：

```text
启动 Claude Code
    ↓
/status：确认模型、账户、连通性
    ↓
做一个小任务
    ↓
/usage：建立成本基准
    ↓
/usage-credits：官方 Pro／Max 设置上限
```

这里的“基准”是观察方法，不在视频里承诺固定金额，因为模型、任务和版本都会影响结果。

## 4. 关系与转折

### 4.1 因果关系

- 上下文变大 → 输入 token 增加 → 单次成本可能变高。
- Base URL 或 Key 配错 → 请求走错计费路径 → 套餐额度和额外账单出现偏差。
- `/status` 不核对 → 配置错误可能直到账单出现才被发现。
- 不清理旧上下文或提示含糊 → 模型读取更多内容、返工更多 → token 浪费。

### 4.2 对比关系

- 按量计费 vs 固定订阅：弹性和可控性的取舍。
- 官方原生模型 vs 国产 Coding Plan：模型偏好、网络、成本和规则的取舍。
- 坏习惯 vs 好习惯：同样的任务，不同上下文管理带来不同成本。

### 4.3 认知转折

```text
“选个便宜套餐就行”
        ↓
“先弄懂 token 和计费路径”
        ↓
“再确认配置真的走了套餐”
        ↓
“最后靠上下文管理控制成本”
```

## 5. 可视觉化内容

- 账单从“看不懂的总额”拆成输入、输出和上下文三类计量。
- 三条付费路径用三列卡片和用户条件标签对比。
- Base URL 的 `/coding` 与 `/v3` 用红绿分流展示，表现“同厂商、不同计费路径”。
- `/usage`、`/usage-credits`、`/status` 用终端命令和状态面板演示职责差异。
- `/clear`、Sonnet、plan mode、具体提示用坏习惯到好习惯的替换动作展示。
- 最后把三步检查流程压缩成一条可以照着执行的路径。

## 6. 可以弱化或删除的信息

- 企业平均每天 13 美元、每月 150–250 美元可以作为开场冲突，但不应成为价格承诺或整条视频的主线。
- 具体厂商名单、促销金额和 Key 前缀不宜铺开太多，保留一个典型示例并加时效性提示即可。
- `/usage` 面板中的完整英文输出不需要逐行朗读，画面展示、口播解释其含义。
- 空闲会话通常不到 0.04 美元属于辅助冷知识，若时长紧张可以删掉，不影响主命题。
