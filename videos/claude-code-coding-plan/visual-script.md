# Claude Code 订阅套餐与计费视频化 · 第五步：Visual Script

> 目标：基于 Scene Script 和 Narration Script，明确每个 Scene 的画面结构、状态变化和声音／画面分工。正式 Remotion 只复用本脚本已确认的视觉事件。

## 全局视觉原则

### 1. 画面负责展示成本如何产生

口播解释 token、套餐和省钱逻辑，画面不重复整段解释，而是用账单拆分、请求流向、命令结果和状态变化来证明。

### 2. 所有价格和厂商配置都带时效边界

价格、促销、额度和厂商接口规则不写死为永久结论。厂商 URL 只展示源文档中的示例，并在相关 Scene 显示：

```text
以当前官方文档和控制台为准
```

### 3. 一个 Scene 只有一个视觉中心

每幕只保留一个主动作：账单拆分、token 计量、方案选择、请求分流、命令验收、习惯替换、行动清单或总结预告。

### 4. 视觉表达过程，不做文章 PPT

优先使用：

```text
增长、拆分、分流、亮起、替换、打勾、切换
```

避免同时堆叠长段文字、表格、终端和多组解释卡片。

### 5. 屏幕文字全部可追溯

标题、标签、命令、URL、状态和预告文案必须能追溯到当前 Source、Content Analysis、Video Narrative、Scene Script 或本 Visual Script；不复用其他视频的业务语义、固定文案和状态文字。

## Scene 01｜账单为什么会失控

### 视觉目标

快速建立“账单看不懂、成本可能增长”的问题，不在开场直接给套餐结论。

### 画面结构

深色背景中间是一张简化 Console 账单卡片，初始只显示：

```text
Total cost: $0.00
```

右侧出现 Claude Code 请求轨迹。每次请求后，账单总额增长，卡片内部逐步露出 `model processing` 和 `context` 标签。

### 动画顺序

1. 账单卡片淡入。
2. 请求点沿轨迹进入模型处理节点。
3. 总额从模糊的数字跳动到较高金额，避免写死具体价格。
4. 金额区域被放大并出现屏幕重点“我到底在为什么付钱？”。
5. 账单卡片收缩，为下一幕的计量解释让位。

### 画面文字

```text
我到底在为什么付钱？
model processing
context
```

### 视觉与口播分工

- 口播：说明高额平均值和个人账单只是问题入口。
- 画面：表现总额如何随着请求增长，并留下疑问。

### Visual Type

`Billing Simulation`

## Scene 02｜Token 到底怎么计费

### 视觉目标

把 token 从抽象名词变成可视化的计价过程。

### 画面结构

左侧是 Claude Code 请求框，右侧是三段横向计量带：

```text
Input → Context → Output
```

下方用三个小例子驱动计量带变长：读取大文件、长对话、扩展思考。

### 动画顺序

1. 输入文本被拆成小 token 方块，流入 `Input`。
2. 文件树和旧对话片段进入 `Context`，带长度增加。
3. 模型返回文本进入 `Output`，输出带变长。
4. 三条带汇入一个简化的费用计量器。
5. 最后只保留“不是问了几次，而是每次带了多少上下文”。

### 画面文字

```text
Input
Context
Output
不是问了几次
而是每次带了多少上下文
```

### 视觉与口播分工

- 口播：解释输入、输出、旧上下文和扩展思考。
- 画面：演示不同内容如何进入计量器。

### Visual Type

`Token Flow`

## Scene 03｜三条付费路径怎么选

### 视觉目标

把三个方案表现为不同条件下的选择，不形成价格排行榜。

### 画面结构

三列等宽卡片，分别为：

```text
按量计费
官方订阅
国产 Coding Plan
```

每列仅保留两层标签：收费机制和适用条件。卡片下方显示一个简短风险标签。

### 动画顺序

1. 三张卡片依次落位。
2. 左侧“官方原生模型”标签连接到按量计费。
3. 中间“固定支出”标签连接到官方订阅。
4. 右侧“国内成本／网络”标签连接到 Coding Plan。
5. 三张卡片同时出现“没有唯一最优解”的结论。

### 画面文字

```text
按量计费
官方订阅
国产 Coding Plan
官方原生模型
固定支出
国内成本／网络
没有唯一最优解
以当前官方定价和厂商活动页为准
```

### 视觉与口播分工

- 口播：解释适合人群、支付和网络等取舍。
- 画面：用标签连线表达选择条件，不显示未经验证的固定价格。

### Visual Type

`Plan Comparison`

## Scene 04｜买了套餐，为什么还会多一笔账单

### 视觉目标

用请求分流证明 Base URL 错误会改变计费路径。

### 画面结构

左侧是配置终端，中央是路由节点，右侧分成两条结果：

```text
套餐额度
按量账单
```

先展示正确示例，再展示错误示例。两条 URL 只突出末段：

```text
.../api/coding
.../api/v3
```

下方独立显示：

```text
套餐专属 API Key
```

### 动画顺序

1. 正确 URL 进入绿色路由，结果写入“套餐额度”。
2. 路由回到中央，替换为 `/api/v3`。
3. 请求进入红色“按量账单”，额外账单数字出现。
4. API Key 标签出现黄色核对提示。
5. 画面收束为“买了套餐 ≠ 一定走套餐”。

### 画面文字

```text
.../api/coding
.../api/v3
套餐额度
按量账单
套餐专属 API Key
买了套餐 ≠ 一定走套餐
以当前官方文档和控制台为准
```

### 视觉与口播分工

- 口播：解释厂商示例的因果和时效边界。
- 画面：展示同一请求因路径不同而进入不同账单。

### Visual Type

`Routing Terminal`

## Scene 05｜三个命令分别看什么

### 视觉目标

把三个命令与三种控制目的绑定。

### 画面结构

左侧终端依次输入命令，右侧面板只显示对应结果：

```text
/usage          Session
/usage-credits  Limit
/status         Status
```

### 动画顺序

1. `/usage` 输入后，Session 卡片出现 token 和本地估算金额。
2. 面板切换，`/usage-credits` 输入后出现月度上限滑杆或数字框。
3. 面板切换，`/status` 输入后出现 `version`、`model`、`account`、`connectivity`。
4. 三张小卡片横向排列，形成“看明细／设上限／核配置”。

### 画面文字

```text
/usage
/usage-credits
/status
看明细
设上限
核配置
本地估算，不等于最终账单
```

### 视觉与口播分工

- 口播：解释适用范围和本地估算边界。
- 画面：展示命令输入与结果类型的对应关系。

### Visual Type

`Terminal Commands`

## Scene 06｜省钱不是只换便宜套餐

### 视觉目标

让观众看到四种节省动作如何减少上下文、模型成本和返工。

### 画面结构

四行替换列表，左侧是坏习惯，右侧是好习惯，中间有替换箭头：

```text
长会话 → /clear
全程 Opus → 默认 Sonnet
直接开干 → plan mode
含糊提示 → 具体文件和函数
```

背景中有一条上下文堆叠条，随着每行替换逐渐缩短。

### 动画顺序

1. 第一行长会话堆叠被清空。
2. 第二行模型标签从 Opus 切换到 Sonnet。
3. 第三行错误分支在执行前被 plan mode 截断。
4. 第四行搜索范围从整个项目收缩到目标文件。
5. 四行最终只留下四个好习惯。

### 画面文字

```text
/clear
Sonnet
plan mode
具体提示
```

### 视觉与口播分工

- 口播：解释每个习惯省在哪里。
- 画面：用清空、切换、截断和收缩表达省钱机制。

### Visual Type

`Habit Swap`

## Scene 07｜现在就建立用量感知

### 视觉目标

将全片知识收束为可以复现的五分钟动作链。

### 画面结构

横向终端流程清单：

```text
启动 Claude Code
↓
/status
↓
小任务
↓
/usage
↓
设置上限
```

每完成一步，右侧出现绿色勾选；最后将“官方计划上限”和“厂商控制台额度”分成两个边界标签。

### 动画顺序

1. 清单第一步亮起。
2. 每个命令和动作按顺序执行，状态逐项打勾。
3. `/usage` 后出现“建立个人基准”。
4. 末尾分成官方 Pro／Max 与国产 Coding Plan 两条边界说明。

### 画面文字

```text
/status → 小任务 → /usage → 设置上限
建立个人基准
官方 Pro／Max
厂商控制台
```

### 视觉与口播分工

- 口播：解释动作目的和不同方案的边界。
- 画面：表现按顺序完成、产生基准和设置边界。

### Visual Type

`Checklist Flow`

## Scene 08｜总结与下一集预告

### 视觉目标

先完成本集结论，再把下一集预告作为全片最后一个视觉事件，保证两者不争夺同一字幕区域。

### 画面结构

第一阶段是三张总结卡片，纵向排列：

```text
看懂计费
核对路径
控制上下文
```

总结卡片淡出后，整个画面切换为居中的预告卡片：

```text
下一集
07 第一次使用：跑通第一个例子
正式启动 Claude Code，跑通第一个真实项目
```

预告卡片下方保留独立安全区，底部字幕若存在则上移或暂时不显示，不能与预告标题叠放。

### 动画顺序

1. 三张总结卡片依次出现并稳定停留。
2. 总结卡片收缩到背景并淡出。
3. 预告卡片从中心进入，标题和副标题分两拍出现。
4. 预告完整停留约 2～3 秒。
5. 结束，不再出现额外按钮、导航、调试说明或其他画面文字。

### 画面文字

```text
看懂计费
核对路径
控制上下文
下一集
07 第一次使用：跑通第一个例子
正式启动 Claude Code，跑通第一个真实项目
```

### 视觉与口播分工

- 口播：先总结三条结论，再说出下一集预告。
- 画面：用场景切换明确区分本集总结与下集预告，并确保预告是最后一个视觉事件。

### Visual Type

`SummaryScene`

## 全片视觉类型、组件与动画标准

### 视觉类型

- `OpeningScene`：Scene 01 的账单问题和开场疑问。
- `ConceptScene`：Scene 02 的 token 计量带。
- `ComparisonScene`：Scene 03 的三条付费路径。
- `TerminalScene`：Scene 04、05 的配置分流和命令结果。
- `StepListScene`：Scene 06、07 的习惯替换和行动清单。
- `SummaryScene`：Scene 08 的总结与预告。

### 通用组件

- 深色横屏 Scene 容器。
- 顶部标题和简短阶段标签。
- 终端、账单、计划卡片、状态面板、流程箭头和字幕 overlay。
- 所有卡片使用一致的圆角、边框、轻发光和进入动画。

### 动画标准

- 主要状态变化使用淡入、位移、宽度变化和轻微缩放，不使用复杂 3D 或粒子。
- 重要数字和命令先出现，解释性标签延后半拍，形成阅读顺序。
- 不让列表或终端输出在字幕还未读完时切走。
- 预告卡片至少保留 2～3 秒完整阅读时间，且预告阶段不叠加总结字幕。

### 屏幕文字标准

- 主标题控制在 1～2 行。
- 每个卡片只放关键词，不把 Narration Script 整段搬进画面。
- 命令和 URL 使用等宽字体，保持完整可辨识。
- 价格和厂商规则必须使用“参考”或“以当前官方资料为准”的边界提示。
- 最终 Composition 不包含预览导航、自动播放、进度提示、调试标记和制作说明。
