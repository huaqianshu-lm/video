# Claude Code Git 工作流 · Narration Script

## Scene 01｜一串 `fix`，从痛点开始

翻一翻很多人的 git 提交记录，经常会看到 `fix`、`update`、`wip`，甚至一句“改了下”。

这不一定是因为人懒，而是代码刚改完，脑子还在逻辑里，这时候再准确概括到底改了什么、为什么改，收益实在太低。

可等几个月以后，你对着一长串重复的提交，想找当时那次判空到底是哪一笔加的，就会发现自己几乎没法检索。

## Scene 02｜先划线：本地和远端不是一回事

所以动手之前，先把 git 操作分成两类。

第一类只动本地，改错了还能回头：看状态、看 diff、写 commit、建分支、解冲突。这些活交给 Claude，通常比较放心。

第二类会影响远端和其他人，而且很难收回：git push、删除远程分支、发布 tag，尤其是 force push。

这就像报销单可以让助理帮你填，最后把钱打出去的按钮，还是应该由你自己来按。

## Scene 03｜看 diff：把满屏红绿讲成人话

最适合先交出去的，是看懂一坨改动。

你可以让 Claude 看一下暂存区的改动，用中文总结主要改了哪几件事，并指出有没有不对劲的地方。

它会读取 `git diff --staged`，把满屏的红绿整理成几条人话摘要，也可能顺手揪出调试日志、写死的测试数据，或者误删的代码。

## Scene 04｜写 commit：diff、历史、规范汇成一句话

让 Claude 写 commit message，关键不在于让它凭空想一句漂亮话，而是让它同时看三样东西：暂存区的 diff、项目以前的提交，以及 `CLAUDE.md` 里的规范。

这样它就能沿用项目原来的 `feat:`、`fix:` 这类前缀，把今天实际改了什么写清楚。

而且 commit 还只在本地，没推出去之前，写错了可以 reset，也可以 amend。

你的工作变成过目和签字，而不是每次从“fix”开始硬憋。

## Scene 05｜开 PR：`gh` 让副手接上 GitHub

提交完成以后，下一步常常是开 PR。

如果你使用 GitHub，最好先安装并登录 `gh` CLI。这样 Claude 可以用认证状态创建 PR、读取评论；否则它退而使用未认证 API，更容易碰到限流。

用 `gh pr create` 创建 PR 后，会话还会和这个 PR 关联起来。之后可以用 `claude --from-pr <number>` 回到原来的上下文继续处理。

## Scene 06｜读评论和解冲突：能看懂，不等于盲目照做

不过，能读 PR 评论，不代表要盲目执行评论里的每句话。

PR 描述、issue 和 reviewer 评论都是外部内容，里面可能藏着提示注入。尤其是要求执行陌生命令、访问地址或者发送敏感信息的内容，必须先由人判断。

解 merge 或 rebase 冲突时也一样。先让 Claude 解释两边改动分别想做什么，给出合并方案；你确认理解正确以后，再让它修改，最后跑测试确认没有合坏。

## Scene 07｜权限规则：把 push 红线焊进机制

这里要特别记住，写在 `CLAUDE.md` 里的“不要 push”，只是请求，不是保证。

真正的硬约束要写进权限规则：只读的 `git status`、`git diff` 和 `git log` 可以放进 `allow`；本地的 `git commit` 放进 `ask`，每次留一个确认；`git push *` 写进 `deny`，直接拦住。

而且 `deny` 的优先级高于 `allow` 和 `ask`。force push 更应该永远由你自己手动执行，并在按下之前确认推的是哪个分支。

## Scene 08｜完整心智模型：Claude 是副手，你是签字人

把前面串起来，Claude 在 git 流程里就是副手。

看 diff、写 commit、开 PR、分析冲突，这些本地或者可控的活，它可以帮你跑；到了要推向远端的地方，就把最后的签字关交回你手里。

这样你既不用因为害怕出事而什么都自己做，也不会为了省事把 push 也甩给它。

## Scene 09｜玩具仓库：先建立本地历史

下面在一个全新的玩具仓库里，走一遍最核心的本地链路，而且全程不碰远端。

先创建 `git-demo`，初始化 git，写入一个只有 `add` 函数的 `calc.py`，然后暂存并提交，提交信息是 `feat: 初始 add 函数`。

这一步的目的，是先给仓库留下一笔历史，供 Claude 后面参照风格。

## Scene 10｜玩具仓库：制造改动，让 Claude 读 staged diff

接着修改 `calc.py`，新增一个 `sub` 减法函数，再把文件加入暂存区。

进入 Claude 会话，让它用中文总结暂存区的改动。

如果它准确说出“新增了一个 `sub` 减法函数”，就说明它真的读到了 diff，而不是在猜。

## Scene 11｜玩具仓库：照风格 commit，再用 log 验证

然后让 Claude 参照上一笔提交的风格，把这次改动提交掉，message 用中文。

它可以先给出类似 `feat: 新增 sub 减法函数` 的 message，得到确认后执行本地 commit。

最后回到终端运行 `git log --oneline`。看到两条前缀一致、又说清楚改了什么的提交，就说明这条本地链路跑通了。

注意，全程没有执行 `git push`。

## Scene 12｜小结与下一集预告

这一篇的核心分工可以浓缩成一句话：本地可逆的 diff、commit、PR 和冲突分析，放心交给 Claude；远端不可逆的 push 和 force，把钥匙留在自己手里。

而真正守住这条线的，是权限规则，不是 `CLAUDE.md` 里的一句提醒。
