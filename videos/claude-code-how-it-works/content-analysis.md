# Claude Code 如何工作视频化 · 第一步：Content Analysis

> Source：`03-how-it-works.md`。本文档只提取知识结构，不直接决定视频剪辑顺序。

## 1. 核心命题

Claude Code 与普通聊天框的根本区别，不是“回答更长”，而是它由模型和工具共同驱动一个可重复的代理循环：收集上下文、采取行动、验证结果；循环是否继续，由任务结果决定。用户既不是旁观者，也不是一次性写完提示词的人，而是可以随时打断、补充和决定边界的控制者。

## 2. 必须保留的核心信息

### A. 代理循环

- `agentic loop` 的三步是：想（收集上下文）、做（采取行动）、看（验证结果）。
- 一步的结果决定下一步；未完成时从验证回到收集。
- 简单问题可能只需要收集上下文，复杂任务会循环多轮。
- 模型负责“想”，工具负责“做”和“看”。

### B. 人的控制权

- `Esc` 立即取消当前工具调用。
- 打字并按 `Enter` 不打断当前操作，只补充下一条指令。
- 不需要憋出完美提示，先给方向、观察执行、再纠正。

### C. 工具层

- 五类工具：文件操作、搜索、执行、网络、代码智能。
- 前四类开箱即用；代码智能需要额外插件，以官方文档为准。
- 模型根据当前任务和返回结果选择工具，而不是每次由用户指定。
- Skill、MCP、Hook、Subagent 是架在内置工具之上的扩展层，不是本节的主知识点。

### D. 视野与安全

- Claude Code 的视野大致等于当前目录下终端能触达的范围。
- 可访问项目文件、终端命令、git 状态、`CLAUDE.md` 和已配置扩展。
- 检查点能恢复 Claude 通过编辑工具改动的文件，但不回滚 bash 命令或外部副作用。
- 权限模式控制会话级自主权；权限确认、Plan Mode、自动接受编辑和 Auto Mode 的边界不同。
- `Plan Mode` 适合复杂任务先读、先搜、先出方案；`.claude/settings.json` 可配置受信命令。

### E. 最小实验

- 在空目录启动 Claude Code。
- 进入 Plan Mode，要求创建 `add.py` 和测试，但先只给计划。
- 批准后建文件、运行测试、读取结果。
- 故意把加法改成减法并再次测试，观察失败如何推动下一轮。

## 3. 关键关系与认知边界

### 代理循环不是固定脚本

“想→做→看”是机制，不是写死的步骤清单。任务越复杂，循环可能越多；验证通过后才结束。

### 模型与工具分工

模型提供判断和下一步选择，工具提供读、写、执行、搜索和验证的实际能力。只有模型没有工具时，它只能输出文字。

### 自主执行与用户控制并存

Claude 可以连续工作，但用户可通过 `Esc` 或补充指令改变方向。自主不等于无监督。

### 视野与权限不是“整个硬盘”

当前目录是主要工作边界；可访问范围还受终端权限、项目配置和操作确认约束。检查点解决部分本地文件恢复问题，不等于完整事务回滚。

## 4. 最容易混淆的关系

| 容易混淆 | 应保留的区分维度 |
|---|---|
| 普通聊天框 vs Claude Code | 是否能调用工具并验证结果 |
| 想 vs 做 vs 看 | 收集信息、改变状态、检查结果 |
| `Esc` vs 打字 + `Enter` | 取消当前动作、还是排队补充指令 |
| 模型 vs 工具 | 判断下一步、还是实际触达项目 |
| 检查点 vs git | Claude 编辑快照、还是版本历史与更完整恢复 |
| Plan Mode vs 自动模式 | 先只读出方案、还是由安全检查辅助连续执行 |

## 5. 可视觉化内容

- 聊天框只返回文字，Claude Code 在 IDE／终端中连续读、改、跑、验。
- 代理循环节点按时间顺序出现，并从“验证”回到“收集”。
- `Esc` 让正在运行的工具调用即时停止，补充指令则在当前动作后进入。
- 五类工具以工具箱分组，并映射到一次修复失败测试的真实顺序。
- 项目文件、终端、git、规则和扩展围绕工作目录出现，表现“项目视野”。
- 检查点、权限模式和 Plan Mode 作为操作前后的安全闸门出现。
- 空目录实验从计划、建文件、测试到失败后再循环形成完整时间线。

## 6. 可弱化或不直接展开的信息

- Sonnet、Opus、`/model` 和 `--model sonnet` 只保留为模型可切换的例子，不展开模型选型。
- 修车师傅和智能手环的类比只服务理解，不需要分别做成独立知识点。
- `settings.json` 白名单只作为后续配置篇的连接点，不在本视频深讲。
- 代码智能插件的官方链接和安装细节不进入画面主叙事。

## 7. 内容边界与事实审查

- 所有屏幕文字必须来自 Source 或本资料明确提炼的关系：`想`、`做`、`看`、工具类别、`Esc`、`Plan Mode`、`Checkpoint` 等均有原文依据。
- 不把后续 `04 · API 配置` 的身份、计费或第三方模型语义提前带入。
- 不把 `03` 原文中的示例项目扩展成真实执行；原型中的终端只模拟文章里的空目录实验。
- 不把“检查点”表现为能回滚数据库、API、部署等外部状态。
- 不把“能访问当前项目”扩大成无条件读取整个硬盘。

## 8. Gate 1 内部审查结论

- 核心命题、五类工具、用户控制权、项目视野、安全边界和最小实验均保留。
- 叙事可从“它为什么会自己干活”开始，再建立循环、工具、边界和实验闭环。
- 12 个 Scene 足以覆盖 6 个原文章节，同时为循环、工具选择、权限和实验保留视觉事件。
- Scene 脚本可复用基线字段和 16:9 横屏表达，不需要新增场景组件类型。
