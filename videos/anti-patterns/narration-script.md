# Narration Script｜Claude Code 反模式

## Scene 01｜好工具也能被用废

Claude Code 用得不顺，十有八九不一定是工具不行，而是用法掉进了反模式。今天不讲更多高级功能，专门把那些看着合理、实际特别容易让你返工的用法，一张张挑出来。

## Scene 02｜七个坑会互相喂养

这七个坑也不是各自独立的。需求一口气塞太宽，再让它无范围地调查，上下文很快就满；上下文一满，错误变多；错误一多，你又开始不信它、不验证，甚至为了省确认直接裸奔。真正的破局点，是拆需求、清上下文、给验证、把范围收窄。

## Scene 03｜一句话塞一大堆需求

第一种，一句话塞一大堆需求。登录改 OAuth、修报错、调按钮、补测试，全混在一起，哪个都做不透。小任务、方向明确，可以直接做；大任务或者边界没想清楚，就先探索、进 Plan Mode 出方案。核心只有一句：一次只推进一条主线。

## Scene 04｜不写或全塞进 CLAUDE.md

第二种，CLAUDE.md 不是不写，就是写成百科全书。不写，每次开会话都要重新交代项目规矩；写太长，真正重要的约束又会被噪音淹没。判断每一行只问一句：删掉它，会不会导致 Claude 犯错？不会，就别放在常驻规则里，大块知识按需加载。

## Scene 05｜一个会话从早开到晚

第三种，一个会话从早开到晚。上午修 bug，顺手聊 Python，下午又回来写功能，无关话题和失败版本全堆进上下文。任务换了就用 /clear，同一个任务太长就用 /compact；同一个问题纠正两次以上，也该清屏重说。

## Scene 06｜把它当搜索引擎，而且说啥信啥

第四种，把 Claude 当搜索引擎，而且说啥信啥。版本信息可能过期，冷门 API 可能是模型猜的，没真正读过的文章也不能只凭标题总结。要查最新信息，就让它查真实来源；要用产出，就运行、查文档，或者要它亮出证据。看着对，不等于真的对。

## Scene 07｜不给它能自己验证的办法

第五种，不给它一个能自己验证的办法。你让它写完一个函数，它说完成，代码也看着像那么回事，可空字符串、多个 @、中文域名这些边界情况可能全漏掉。给它测试、构建或截图对比，让它自己看到通过和失败。修报错时还要盯住根因，别把异常吞掉就算结束。

## Scene 08｜无脑开启 bypassPermissions

第六种，为了省掉确认，直接在工作机上开启 bypassPermissions。它会跳过检查，也没有提示注入和意外操作的保护。日常迭代可以用 acceptEdits，更省心可以用 auto；真要完全无人值守，就把它放进隔离容器或虚拟机，别拿工作机裸奔。

## Scene 09｜调查一下，却不给范围

第七种，让它调查一下，却不给目录和问题范围。它会很尽职地读几十上百个文件，把主上下文灌满。知道大概位置，就指定目录和关注点；不知道位置、只需要结论，就派 Subagent 在独立窗口里读完，只把摘要带回来。

## Scene 10｜反面操作体检

现在做个体检。有人一天之内同时改 OAuth、修报错、调样式、补测试；项目没 CLAUDE.md；一个会话里混聊 Python；让它调查整个项目；第三方 API 不验证就复制；工作机全程跳过权限；最后只说一句「把构建报错弄掉」。这七条，正好对应七个反模式。正确做法就是拆开主线、补精规则、清理会话、收窄调查、查证 API、保留安全边界，并验证根因已经解决。

## Scene 11｜七条速查与下一篇预告

把它压成七个动作：拆需求、写精规则、清上下文、查证据、给验证、保安全、限范围。以后觉得 Claude 越用越笨，先别急着怪工具，拿这七张症状卡逐条自查。下一篇是第 51 篇 FAQ／Troubleshooting，专门处理装不上、登不进、命令卡死和其他报错型问题。
