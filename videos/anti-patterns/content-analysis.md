## 核心命题

Claude Code 用得不顺，很多时候不是工具能力不足，而是用户反复落入一组「看起来合理、实际会放大风险和返工」的反模式。最有效的改进不是盲目追求更多高级功能，而是识别症状、缩小范围、保持干净上下文、给出可执行的验证方式，并为高风险操作保留安全边界。

## 文章要解决的问题

文章面向已经接触过 Claude Code、但在真实使用中遇到「越用越笨」「改不对」「不敢信」「确认太烦」等问题的读者。它不再讲功能入门，而是把常见错误用法集中列成七张症状识别卡，并为每张卡提供 Before／After 和回读入口。

## 知识骨架

### 1. 反模式不是单点错误，而是连锁系统

七个反模式会互相喂养：

1. 一次塞太多需求，方向和边界变模糊。
2. 不写或过度膨胀 `CLAUDE.md`，常驻规则失去重点。
3. 一个会话持续过久，无关信息和失败尝试堆满上下文。
4. 把模型当搜索引擎并全盘相信，未经核验就使用答案。
5. 不给产出验证方式，把「看着完成」当成真正完成。
6. 为了省确认而无脑开启 `bypassPermissions`，移除安全闸门。
7. 让它无范围调查，读取大量文件并烧空主上下文。

文章给出的恶性循环是：需求宽泛或调查无范围 → 方向跑偏、上下文膨胀 → 结果出错 → 归咎工具、拒绝验证 → 为了省事进一步裸奔 → 问题继续扩大。破局点是拆需求、清上下文、给验证、收窄范围。

### 2. 七个反模式与正确替换

| 编号 | 反模式 | 主要症状 | 核心替换 |
|---|---|---|---|
| 1 | 一句话塞一大堆需求 | 多条任务混在一起，哪个都没做透 | 一次只推进一条主线；大任务先 Plan Mode |
| 2 | 不写或全塞进 `CLAUDE.md` | 每次复读，或规则被长文淹没 | 只保留会导致错误的常驻规则，大块知识按需加载 |
| 3 | 一个会话从早开到晚 | 无关话题和失败版本污染当前任务 | 任务切换用 `/clear`，任务过长用 `/compact` |
| 4 | 当搜索引擎并说啥信啥 | 版本、冷门 API 或未读文档被模型脑补 | 实时信息用联网工具，产出必须查文档、运行或索要证据 |
| 5 | 不给验证办法 | 代码看似合理，边界情况和根因问题漏掉 | 给测试、构建、截图对比等可产生通过／失败信号的检查 |
| 6 | 无脑开启 `bypassPermissions` | 工作机上的文件、命令和外部内容失去确认保护 | 日常使用 `acceptEdits` 或 `auto`；裸奔只在隔离环境 |
| 7 | 无范围地「调查一下」 | 读取大量文件，主上下文被原始资料灌满 | 指定目录和问题，或用 Subagent 隔离读取后只返回摘要 |

### 3. 文章中的操作原则

- 小任务、方向明确时直接执行，避免为简单改动增加额外流程。
- 大任务、跨文件任务或方向未定时，先探索和规划，再实现。
- `CLAUDE.md` 的每一行都要能回答「删掉它会不会导致 Claude 犯错」。
- 同一问题连续纠正两次以上，应该清理上下文并重写初始提示。
- 外部 API、最新版本和文章内容不能凭记忆或标题猜测。
- 修复报错要解决根因并验证成功，不要用吞异常或绕过标记隐藏问题。
- `bypassPermissions` 不提供提示注入或意外操作保护，不能把工作机当隔离环境。
- 调查任务必须明确位置、问题，或把大量阅读隔离到 Subagent。
