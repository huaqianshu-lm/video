# 03 · 安装与登录 · Video Narrative

> 叙事目标：让观众从“我该复制哪条安装命令”的焦虑，转向按自己的使用方式、系统环境和登录条件，走完一条可验证、可恢复的 Codex 启动路径；本阶段只定义认知顺序，不写口播、不拆 Scene、不设计具体镜头。

---

## 1. 叙事目标

这条视频不把安装讲成平台命令的汇总，而要帮助观众解决一个更实际的问题：

> **我怎样在自己的环境中，选择正确入口、确认工具可用，并完成安全的登录？**

观看完成后，观众应能形成以下行动顺序：

```text
先判断我怎么使用 Codex
↓
再让安装路径匹配系统和运行环境
↓
用版本号确认 CLI 真的可执行
↓
选择适合当前环境的登录方式
↓
遇到问题先定位根因，而不是盲目重装
```

最终结论是：安装成功不是某条命令结束，而是在自己的环境中建立一个可验证、可登录、可安全工作的起点。

---

## 2. 叙事原则

### 从常见误解开场，而不是从产品定义或命令清单开场

观众最常见的起点是“找一条命令直接安装”。叙事先指出这条路径为什么不完整：使用入口、账号方式、网络与系统环境都会改变后续选择。这样平台差异和登录步骤才有明确的存在理由。

### 把“选择”作为主线，把“命令”作为选择结果

桌面 App、CLI、macOS、Windows、Linux、原生 Windows 与 WSL2 不是需要逐章背下的对象。它们依次回答两个判断：我准备怎样工作？我的系统和运行环境允许怎样安装、怎样运行？

### 用两次状态确认建立完整闭环

安装后先确认“命令是否可执行”，登录后再确认“工具是否能在当前环境中开始工作”。这两次确认分别阻止“装完就算完成”和“能运行就等于已可用”的误解。

### 把排错设计成方法收束，而不是末尾报错列表

PATH、网络、登录回调环境和 Windows 权限策略分别对应不同的环境边界。结尾应回扣整条路径：现象出现在哪一步，就先检查那一步的条件。

---

## 3. 整体叙事结构

### 第一段｜问题：为什么一条安装命令不够

**观众起点**：我只想尽快装好 Codex，应该直接运行哪条命令？

**叙事推进**：先打破“一条命令适合所有人”的预期。安装能否顺利完成，取决于使用入口、账号路径和网络条件；忽略这些条件，后续的下载、登录或运行失败会显得毫无头绪。

**认知变化**：从“寻找唯一命令”转为“先确认自己的条件”。

**必须带走的信息**：安装前要判断使用方式、账号路径与网络连通性。

---

### 第二段｜选择入口：桌面 App 还是 CLI

**观众问题**：我应该从图形界面开始，还是从终端开始？

**叙事推进**：将桌面 App 和 CLI 表达为两种工作入口，而不是优劣对比。桌面 App 服务于 macOS／Windows 的图形项目工作流；CLI 服务于终端、自动化和三平台一致的工作流。Linux 用户需要直接走 CLI。

**认知变化**：入口由工作方式和系统决定，而不是由某条流行命令决定。

**必须带走的信息**：桌面 App 与 CLI 可以通向同一个工作目标，但适用条件不同；CLI 的官方独立安装器也不要求先安装 Node.js。

---

### 第三段｜匹配环境：系统决定脚本，运行环境决定边界

**观众问题**：选定入口后，为什么不同电脑的安装和运行建议仍然不同？

**叙事推进**：把复杂的平台差异压缩成一条判断链：系统平台决定安装路径，运行环境决定权限、性能和项目位置。macOS 要区分芯片架构；macOS／Linux 可走 shell 路径；Windows 要区分 PowerShell 原生安装、原生沙箱和 WSL2。Windows 原生与 WSL2 不是互相替代的开关，而是面向不同权限策略与 Linux 工具链需求的环境选择。

**认知变化**：从“照抄别人的安装步骤”转为“让路径适配自己的系统和项目环境”。

**必须带走的信息**：Windows 默认优先考虑原生 `elevated` 沙箱，受策略限制时使用 `unelevated`；只有需要 Linux 原生工具链或项目已在 WSL2 时才选 WSL2，并把仓库放在 Linux 文件系统而非 `/mnt/c/...`。WSL1 不在支持范围内。

---

### 第四段｜验证安装：从“装过”到“命令真的可用”

**观众问题**：安装命令执行完后，怎样知道自己真的可以继续？

**叙事推进**：把 `codex --version` 建立为安装后的最小可观察验证：在新终端中看到版本号，才说明系统可以找到并执行 CLI。若出现 `command not found` 或同类提示，优先检查 PATH 或多重安装冲突，而不是立即重装。

**认知变化**：从“安装过程没有报错”转为“我已经得到可验证的可用状态”。

**必须带走的信息**：版本号是验证类型，不是固定版本承诺；当前可用子命令和升级方式应查看 `codex --help` 与当前官方说明。

---

### 第五段｜完成登录：从可执行工具到可工作环境

**观众问题**：命令已经能运行，为什么还不能立刻开始工作？

**叙事推进**：把登录放在验证之后，明确它完成的是身份与使用边界的连接。ChatGPT 账号和 API key 都可用于本地 CLI，但对应的能力与用量边界不同；CLI 与 IDE 扩展共享登录缓存，凭据必须按密码保护。

**认知变化**：从“安装已结束”转为“验证与授权共同构成启动完成”。

**必须带走的信息**：正常图形环境可走浏览器登录；远程、headless 或 localhost 回调受阻时，设备码登录是标准替代路径。认证缓存迁移和 SSH 端口转发只在明确需要时使用，且不能暴露凭据。

---

### 第六段｜排错收束：按现象回到对应环境条件

**观众问题**：如果其中一步失败，应该从哪里开始？

**叙事推进**：将高频问题映射回前面的闭环，而不是追加一张报错表：找不到 `codex` 回到 PATH 与多重安装；下载超时回到网络连通性；浏览器登录失败回到回调环境并改用设备码；Windows 沙箱失败回到系统权限策略和运行环境选择。

**认知变化**：从“遇到错误就重装”转为“先判断失败发生在哪个环境边界”。

**必须带走的信息**：不要为 npm 权限错误直接使用 `sudo`；优先修正用户目录中的 Node 环境，或选择不依赖 npm 的官方安装器。

---

### 第七段｜结论与下一集预告：建立自己的稳定起点

**观众终点**：我不需要背下所有平台命令，但知道如何为自己的条件选择一条完整路径。

**叙事收束**：重申闭环：选择入口、匹配环境、验证命令、完成登录、按根因排错。它让安装不再是一次不可控的尝试，而是一套可以检查和恢复的启动方法。

**下一集预告**：继续解释 ChatGPT 套餐登录与 API key 登录的用量边界和计费选择，帮助观众在已能使用 Codex 的基础上理解不同账号路径的实际差异。

---

## 4. 叙事节奏与信息取舍

```text
误解与前置判断
→ 入口选择
→ 系统／环境匹配
→ 版本验证
→ 登录授权
→ 根因排错
→ 可复用结论与下一集预告
```

- 开头先给出观众能立刻代入的选择困难，避免用产品定义消耗注意力。
- 中段以“入口选择”和“环境匹配”承载差异信息，不按操作系统或安装器逐项念清单。
- `codex --version` 放在安装路径之后，作为从选择到可用的明确转折点。
- 登录紧接验证，避免被误解为可有可无的附加步骤。
- 排错只保留四类根因与对应的环境条件；认证缓存迁移、SSH 转发、所有安装参数和具体版本号不进入主叙事。
- 结尾回到“可验证、可登录、可安全工作”的目标，并为下一集的账号路径与计费边界留下连续问题。
