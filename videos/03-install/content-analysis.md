# 03 · 安装与登录 · Content Analysis

> 目标：先确定“这条视频必须讲清楚什么”，提取安装、验证与登录的知识骨架、关键关系和可视觉化内容；暂时不写口播，不拆 Scene，不设计具体镜头。

## 1. 核心命题

这份内容表面上在罗列 Codex 的安装命令和登录方法，但真正需要建立的认知不是：

> 记住每个平台各有哪一条命令。

而是：

> **Codex 的安装是一条从“选择合适入口”到“验证可用”再到“完成身份授权”的连续路径；平台、网络、权限和运行环境不同，选择也不同。**

观众最后应该记住：

> **先按使用方式和平台选入口，再验证 CLI 与登录状态；出问题时优先定位环境边界，而不是盲目重装。**

---

## 2. 必须保留的核心信息

### A. 安装前先做三项判断

视频开头必须先消除“拿到一条命令就能安装”的误解：

- 先确定使用入口：桌面 App 适合图形界面工作流，CLI 适合终端和跨平台工作流。
- 确认账号路径：ChatGPT 套餐登录与 API key 登录对应不同的用量和功能边界。
- 确认网络可稳定访问 OpenAI；国内网络不通会直接表现为下载或登录失败。

这三项不是铺垫信息，而是后续安装、验证和排错都成立的前提。

### B. 桌面 App 与 CLI 是两条不同的起点

必须讲清：

- 桌面 App 目前覆盖 macOS 和 Windows，Linux 没有桌面 App，首次使用需要登录、选择项目目录并确认本地执行。
- CLI 覆盖 macOS、Windows 和 Linux，是跨平台的通用路径。
- CLI 的官方独立安装器不依赖 Node.js；Homebrew 与 npm 是已有对应工具链时的备选路径。

核心不是把两条线做成优劣对抗，而是让观众知道：

> **入口取决于自己的工作方式和系统，不是所有人都该走同一条安装命令。**

### C. 平台差异会改变安装与运行环境

必须保留的差异：

- macOS 需要区分 Apple Silicon 和 Intel 安装包；macOS 与 Linux 可使用官方 shell 安装脚本。
- Windows 原生使用 PowerShell 安装脚本；Windows 的原生沙箱与 WSL2 是不同运行环境。
- Windows 默认优先考虑原生 `elevated` 沙箱，受公司策略限制时才使用 `unelevated`；需要 Linux 原生工具链或仓库本就在 WSL2 时才选 WSL2。
- WSL1 不在支持范围内；使用 WSL2 时，仓库应放在 Linux 文件系统而非 `/mnt/c/...`，避免性能和权限问题。

这里的关键关系是：

> **系统平台决定安装脚本，运行环境决定权限、性能和项目文件位置。**

### D. 安装完成必须通过可观察的验证

必须保留 `codex --version` 这一最小验证：

- 在新终端中看到版本号，才说明 CLI 已能被系统找到并执行。
- `command not found` 或 Windows 的同类提示，优先指向 PATH，而不是立刻判定安装失败。
- 当前版本支持哪些升级或子命令，应以当前 `codex --help` 和官方说明为准，不把视频中的示例版本号当成固定结论。

这一步把“安装动作”变成“可确认的可用状态”。

### E. 登录是把可执行工具变成可用工作环境

必须讲清：

- 默认可使用 ChatGPT 账号登录；API key 也可用于本地 CLI，但部分依赖 ChatGPT 工作区的能力受限。
- CLI 与 IDE 扩展共享登录缓存；凭据文件或系统凭据应当按密码处理，不能提交、公开或随意复制。
- 远程、无图形界面或 localhost 回调受阻时，设备码登录是标准替代路径；无法使用时才考虑认证缓存迁移或 SSH 端口转发。

重点不是解释 OAuth 细节，而是让观众理解：

> **安装成功只证明工具在；完成适合环境的登录，才真正进入可工作的状态。**

### F. 常见故障应按根因归类，而不是按报错死记

需要保留四类高频根因：

- 找不到 `codex`：PATH 未包含安装目录，或多个安装版本发生冲突。
- 安装超时或下载卡住：网络无法稳定访问下载地址。
- 登录回调失败：远程、headless 或本机 localhost 环境不适合浏览器回调。
- Windows 沙箱失败：系统或企业策略不允许所需的权限配置。

观众应得到的排错方法是：

> **先用现象对应环境条件，再选择修法；不要把所有故障都归结为“重新安装”。**

## 3. 安装、验证与登录是一条连续闭环

这条视频最需要建立的不是命令清单，而是一条可复用的操作闭环：

```text
我要在哪种环境使用 Codex？
↓
选择入口：桌面 App 或 CLI
↓
按系统与运行环境选择安装路径
↓
安装完成
↓
用 codex --version 验证命令可用
↓
选择 ChatGPT 账号或 API key 登录
↓
进入项目并开始工作
```

一旦某一步失败，回到对应环节定位：

```text
命令找不到
→ PATH 或多重安装

下载失败
→ 网络连通性

浏览器登录失败
→ 回调环境，改用设备码路径

Windows 沙箱失败
→ 系统权限与运行环境选择
```

这让“安装教程”从彼此独立的命令，变成可检查、可恢复的路径。

## 4. 安装决策应分成 3 层

源材料中的信息很多，视频不应平铺成平台、命令和报错的长列表。更适合按三个连续层级组织。

### 第一层：入口选择

先回答“我准备怎么用”：

- 需要图形界面、本地项目选择和审查界面：桌面 App。
- 需要终端、自动化或跨平台一致性：CLI。

也就是：

> **先选使用方式。**

### 第二层：环境匹配

再回答“我的系统与工作环境允许怎么装、怎么跑”：

- macOS 芯片架构。
- macOS／Linux 的 shell 路径。
- Windows PowerShell、原生沙箱与 WSL2 的分支。
- 网络、PATH、文件系统位置等前置条件。

也就是：

> **再让安装方式匹配系统与环境。**

### 第三层：可用性确认

最后回答“现在能不能真的开始工作”：

- 命令是否能输出版本。
- 账号是否完成登录。
- 在远程或受限环境中，是否选用了可行的授权方式。
- 凭据和权限边界是否被妥善保留。

也就是：

> **最后验证工具可执行、身份可用、边界清楚。**

## 5. 安全与边界信息必须保留

这部分不能删，否则视频会把安装讲成无条件的一键过程。

- 不应为了 npm 权限错误直接使用 `sudo`；优先使用用户目录中的 Node 环境，或改走不依赖 npm 的官方安装器。
- API key 与本地认证缓存属于敏感凭据，不能进入 Git、工单或公开环境。
- 远程／无图形界面环境不应强行等待浏览器回调；设备码登录的价值是绕开这一环境限制。
- Windows 的 `elevated`、`unelevated` 和 WSL2 不是同一个开关，分别对应权限策略与 Linux 工具链需求。
- 任何命令、版本号和安装目录都可能随版本调整；固定的是“先按当前官方说明确认，再执行”的原则。

最终应收束为：

> **安装的目标不是让某条命令跑完，而是在自己的环境里建立一个可验证、可登录、可安全工作的 Codex。**

---

## 6. 桌面 App、CLI 与 Windows 运行方式怎么讲

这些项目容易被误讲成相互替代关系，视频应明确它们解决的问题不同：

```text
桌面 App
图形项目界面 → 登录 → 选择本地项目 → 发起任务

CLI
终端 → 安装 → 验证命令 → 登录 → 在项目中执行

Windows 原生 elevated / unelevated
同一原生系统内的不同沙箱权限路径

WSL2
需要 Linux 工具链或 Linux 项目环境时的另一套运行环境
```

因此不应把叙事写成“App 对 CLI”或“原生对 WSL”的简单胜负关系，而应保留：

> **先看目标和约束，再选择对应路径；不同路径最后都要回到可验证、可登录、可工作的状态。**

## 7. 哪些信息不适合作为视频主体

### 全部安装方式与每个参数的逐字罗列

官方 shell 脚本、Homebrew、npm、PowerShell、无人值守变量都需要出现为可选择的依据，但不应在主体中逐行念完所有命令和参数。

视频主体应优先讲清选择逻辑；具体命令适合在对应路径中短暂展示，或作为屏幕上的可复制信息。

### 具体版本号和可能变动的实现细节

示例中的 `codex-cli 0.139.0`、特定版本开始支持或停止支持的细节，不能被表达成长期不变的承诺。

它们的作用只是说明“应看到什么类型的验证结果”或“为何要看当前帮助与官方说明”。

### 认证缓存复制与 SSH 转发的命令细节

这两种方式是远程登录的后备路径，需要保留其适用场景与安全边界，但不应抢占主叙事。

优先顺序应是：正常浏览器登录 → 设备码登录 → 在明确环境需要时再使用后备方案。

### 下一篇的计费细节

本篇只需要解释套餐登录与 API key 登录的工作边界，具体额度、价格与成本比较留给下一集。

## 8. 这份内容隐藏的认知路径

后续视频叙事应让观众依次完成以下认知变化：

```text
① 我是不是直接复制一条命令就能装？

↓

② 先要选：我是从桌面 App 还是 CLI 开始？

↓

③ 系统与运行环境会改变我的安装和运行路径。

↓

④ 安装完成不等于可用，先用版本号确认命令真的能运行。

↓

⑤ 工具能运行也不等于能工作，还要完成适合环境的登录。

↓

⑥ 报错不必盲目重装：PATH、网络、回调环境与系统策略分别对应不同问题。

↓

⑦ 我已经具备一套从选择、安装、验证到登录的完整启动方法。
```

这条路径比按“桌面 App → CLI → Windows → 验证 → 登录 → 报错”的章节顺序依次讲解，更容易让观众在每一步知道自己为什么要继续。
