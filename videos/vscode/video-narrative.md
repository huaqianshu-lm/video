# VS Code 集成视频化 · 第二步：Video Narrative

## 1. 视频叙事目标

让第一次把 Claude Code 搬进 VS Code 的观众，在一条视频里完成三次认知转换：

1. 从“扩展没装好”转换为“入口出现有条件，先打开具体文件”。
2. 从“扩展只是聊天面板”转换为“它把上下文、改动审阅和计划审阅嵌入编辑器”。
3. 从“扩展和 CLI 二选一”转换为“同一套能力按任务在两个入口之间切换”。

视频不逐段朗读文章，而是让观众看见问题如何发生、界面如何响应、用户在哪里保留判断权。

## 2. 叙事起点和结论

### 起点

一个空工作区里，用户装好了扩展，却在编辑器右上角找不到 Spark 图标。

### 中段问题

- 入口为什么会消失？
- 扩展和 CLI 到底是什么关系？
- 图形界面真正带来了什么？
- 如何避免 AI 改完代码后才发现方向错了？

### 结论

VS Code 扩展适合在文件、代码和改动旁边工作；CLI 适合完整命令、skills、MCP 配置和终端操作。两者共享配置与可恢复历史，用户可以按任务切换。

## 3. 整体叙事结构

| 段落 | Scene | 认知任务 | 视觉事件 |
| --- | --- | --- | --- |
| 问题钩子 | 01 | 让观众先感受到安装后的误判 | 空工作区找不到 Spark |
| 关系解释 | 02 | 建立扩展与 CLI 的共同核心和能力差异 | 两个入口连接同一核心 |
| 安装排查 | 03 | 给出可执行的安装和找图标路径 | 发布者确认、入口出现、清单排查 |
| 图形优势一 | 04 | 让观众理解 diff 是审阅而非盲目接受 | 左右 diff、手动修改、接受 |
| 图形优势二 | 05 | 让上下文输入变得具体 | @ 和选中代码进入提示框 |
| 图形优势三 | 06 | 建立“先计划、再执行”的安全习惯 | Markdown 计划和内联批注 |
| 完整练习 | 07 | 把前三个能力串成一次最小实践 | demo.py 状态链 |
| 日常切换 | 08 | 留下快捷键和回 CLI 的路径 | 快捷键与任务分流 |
| 收束预告 | 09 | 固化选择标准并引出系列下一集 | 扩展／CLI 分工和 JetBrains 预告 |

## 4. 逐段叙事设计

### 第一段：先让观众遇到“图标去哪了”

Scene 01 不从定义开始，而从空工作区、扩展已安装和右上角没有 Spark 开始。画面先显示用户反复刷新和重启的无效动作，再切到“打开具体文件”后入口出现。

这一幕要让观众记住一个操作条件：光打开文件夹不够。

### 第二段：别把扩展理解成另一个产品

Scene 02 把 CLI 和 VS Code 扩展放在同一张工作台上，展示共享配置、共享历史和不同能力标签。旁白解释同一个引擎的两个点单窗口，画面用连接线表达共同后厨，而不是把两者画成竞争产品。

### 第三段：把安装和排查变成一条路径

Scene 03 先显示 Anthropic 官方发布者，再通过 Cmd+Shift+X、直装链接和其他编辑器分支快速带过安装入口。随后把“打开文件、确认版本、重载、禁用冲突扩展、信任工作区”做成逐项排查灯，形成可执行清单。

### 第四至六段：连续展示扩展的三个核心价值

Scene 04 通过一个具体改动展示并排 diff：原稿、建议改动、手动修正、接受。它回答“为什么扩展更适合跟文件打交道”。

Scene 05 不解释“上下文很重要”这句抽象话，而把 @auth、文件夹提及和选中代码直接送进提示框。它回答“如何让 Claude 知道你说的是哪段”。

Scene 06 把大改动前的权限选择具象化：正常模式逐步询问、自动接受直接执行，而 Plan Mode 先打开 Markdown 计划，用户在第二步旁边加批注，之后才进入执行。

### 第七段：用最小项目验证完整路径

Scene 07 将前面三个价值点落到 vscode-claude-demo/demo.py：打开工作区、登录、选中 greet、生成 f-string 和类型注解 diff、接受改动，再切 Plan Mode 规划命令行参数。每个状态只停留到观众能识别为止。

### 第八至九段：形成日常选择

Scene 08 用快捷键和集成终端完成收尾工具箱：焦点切换、打开新对话、插入提及、恢复会话和回到 CLI。

Scene 09 不再重复功能列表，而是用一个任务分流画面收束：文件改动和审阅留在扩展，完整命令、skills、MCP 配置和终端操作切到 CLI。最后保留“09 JetBrains 集成”预告卡片，停留约 2～3 秒。

## 5. 叙事节奏

- Scene 01：快，先制造“我也会踩”的错觉。
- Scene 02—03：中速，建立关系和排查路径。
- Scene 04—06：每幕一个动作，给 diff、上下文、计划各自足够辨识时间。
- Scene 07：稍快但必须保留状态因果，不能剪成无意义的步骤闪现。
- Scene 08—09：收束，减少新概念，强化选择标准和预告。

## 6. 叙事中的声音与视觉分工

| 内容 | 旁白负责 | 画面负责 |
| --- | --- | --- |
| 图标排查 | 解释为什么空文件夹找不到入口 | 显示入口消失和出现 |
| 扩展／CLI 关系 | 解释共同引擎和能力边界 | 显示两个窗口连接同一核心 |
| diff | 解释审阅与许可 | 显示红绿改动、手动修正、接受 |
| @ 和选中 | 解释减少猜测成本 | 显示上下文标签进入提示框 |
| Plan Mode | 解释先审方案再执行 | 显示计划、批注和执行状态 |
| 快捷键 | 说明用途和平台差异 | 显示键位与动作的对应关系 |

## 7. Gate 1 叙事审查结论

- 叙事没有机械沿用文章章节，而是从真实阻塞开始，按认知难度递进。
- 9 个 Scene 均有明确的单一认知任务。
- 文章的关键事实、三个图形界面优势、练习闭环和系列预告均被覆盖。
- 与下一篇 JetBrains 的关系只作为最后预告，不扩展为本篇内容。
- 视觉原型中的所有功能性屏幕文字将从 Source 和本文件可追溯。
