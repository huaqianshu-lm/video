# 认识 Codex 与四种入口 · 第二步：Video Narrative

> 基于 `content-analysis.md` 重组视频叙事。视频不沿用文章章节顺序，而是按新手从“认错对象”到“会选入口、会划边界”的认知过程推进。

## 1. 叙事目标

让第一次接触 Codex 的观众在一条视频内建立三层地图：

1. Codex 是能进入项目执行任务的 AI 编程代理，不只是代码问答框。
2. 桌面 App、CLI、IDE 扩展和云端 Web 是同一能力的四种入口，差别主要在工作位置与执行环境。
3. AI 可以承担执行，人仍要负责目标、边界、审查和验收。

结束时，观众应能根据自己的工作习惯选择起点，并知道下一集需要补齐哪些核心概念。

## 2. 叙事策略

- 用“四个 Codex 到底哪个是真的”制造开场困惑，而不是先念产品定义。
- 先用“回答代码”和“进入项目执行”做动态对比，让“代理”变成可见动作。
- 把四入口放进同一张路由图，再按任务场景选择，不逐个念功能表。
- 先展示能力带来的效率，再立即补上人工责任边界，避免全自动幻想。
- 工具比较只帮助分类，不做价格、模型和绝对强弱排名。
- 用 `codex --version` 给出本集唯一的行动闭环。
- 最后以〈02 核心概念速览〉作为明确的下一集预告视觉事件。

## 3. 整体叙事结构

| 段落 | Scene | 认知任务 | 叙事推进 |
| --- | --- | --- | --- |
| 开场困惑 | 01 | 四个入口为什么都叫 Codex | 从“选哪个”转向“先认清它是什么” |
| 代理差异 | 02–03 | 看见回答与执行的区别，建立 Agent 动作链 | 从定义进入可观察的工作过程 |
| 四入口地图 | 04–05 | 认识入口与执行位置，学会按场景选 | 从“有哪些”进入“什么时候用哪个” |
| 能力与边界 | 06–07 | 理解可委托任务和人的责任 | 从效率转向协作边界 |
| 工具关系 | 08 | 区分 ChatGPT、Codex、Claude Code | 建立类别，不做强弱排行 |
| 行动与预告 | 09–10 | 确认本机状态，进入下一集概念地图 | 用小动作完成闭环并承接系列 |

## 4. 逐段叙事设计

### 第一段：先把“四个 Codex”合成一个

#### Scene 01｜到底哪个才是 Codex

桌面窗口、终端、IDE 侧栏和浏览器任务同时出现，四个入口都标着 Codex。观众的第一个问题不是“它有什么能力”，而是“为什么看起来像四个产品”。画面最后把四块收拢成一个核心节点。

### 第二段：代理不是更会聊天，而是会动手

#### Scene 02｜回答代码，和执行任务

同一个“项目跑不起来”问题走两条路径：一边只返回建议和代码片段，另一边进入文件树、终端、测试和 diff。通过动作数量的差异建立“代理”的直觉。

#### Scene 03｜一个目标如何变成结果

把 Codex 的工作压缩成“读取项目 → 定位问题 → 修改文件 → 运行测试 → 交付 diff”五个状态。重点不是宣称一次必然成功，而是展示它围绕目标执行一串动作。

### 第三段：四种入口是一张执行地图

#### Scene 04｜三扇门在本机，一扇门去云端

桌面 App、CLI、IDE 扩展三条线汇入本机项目；云端 Web 连接远程仓库和隔离环境。用空间关系直接解释执行位置。

#### Scene 05｜按工作场景选入口

四个任务卡片依次出现：看 diff 和并行任务、终端与 SSH、编辑器内持续开发、后台长任务。每张卡自动吸附到最匹配的入口，让观众学会用场景选择，而不是寻找“唯一正确入口”。

### 第四段：能力越强，边界越要清楚

#### Scene 06｜可以委托的五类工作

让“写代码、读项目、代码审查、调试修复、自动化杂活”依次进入任务队列，右侧的项目状态同步变化。它们共享同一条动作链，不展开成五段功能朗读。

#### Scene 07｜人负责什么，AI 负责什么

画面中间划出责任边界：人负责目标、需求、技术方向和验收；AI 负责分析、执行和重复劳动。随后让未经审查的 diff 被 Gate 拦住，强调“完成执行”不等于“自动正确”。

### 第五段：把相似工具放回正确类别

#### Scene 08｜问答工具与编程代理

先按“给建议／执行项目任务”分成两类，再展示 Codex 与 Claude Code 都属于编程代理，但产品来源、模型体系、说明文件和入口侧重不同。结论是按任务分工，不是判断谁永远更强。

### 第六段：完成一个零成本动作

#### Scene 09｜电脑认不认识 Codex

终端输入 `codex --version`，结果分成“显示版本号”和“command not found”两条。两条都标记为“状态已确认”，把错误信息从失败变成下一步依据。

#### Scene 10｜地图有了，下一步理解规则

四入口地图、代理动作链和人机边界收束为三张卡片。随后下一集预告卡进入：〈02 核心概念速览〉，展示代理循环、上下文、`AGENTS.md`、审批模式、沙箱、Skills、MCP，并保留约 2～3 秒停留。

## 6. Video Value 审查

- Scene 01：四块界面合并成一个核心节点，能立刻消除“多个产品”的误会。
- Scene 02：两条工作流并行推进，能看见“回答”和“执行”的动作差异。
- Scene 03：文件、终端、测试和 diff 的连续状态比口头定义更能解释 Agent。
- Scene 04：本机与云端的空间分流是四入口最重要的结构关系。
- Scene 05：任务卡自动匹配入口，把选择标准变成可迁移的方法。
- Scene 06：任务队列和项目状态变化能压缩能力清单，避免 PPT 式罗列。
- Scene 07：Gate 拦截未经审查的 diff，能把人工责任边界变成动作。
- Scene 08：先分类再并列，能减少工具名称造成的混淆。
- Scene 09：真实终端的两种结果分叉能形成可执行闭环。
- Scene 10：三张认知卡与下一集术语预告完成收束和系列承接。

## 7. 事实与范围审查

- 所有核心结论、四入口名称、执行位置、能力与限制均来自 Source 或 Content Analysis。
- 没有写入订阅额度、价格、模型跑分和当前版本号等易变化信息。
- 没有把安装命令放进本集主流程，也没有把 Source 中的个人案例夸大为稳定效率承诺。
- `codex --version` 只承担状态确认，不承诺安装或登录成功。
- 下一集主题与术语均有 Source 的系列预告依据。
