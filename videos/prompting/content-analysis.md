# Claude Code 提问与指令 · Content Analysis

> 目标：从原文提取“怎样让 Claude 少猜、少返工”的知识骨架，再决定视频表达。

## 1. 核心命题

这篇文章真正要解决的不是“记住几句提示词模板”，而是让观众理解：

> **Claude Code 能不能准确完成任务，很大程度取决于用户有没有把范围、上下文、成功标准和任务复杂度说清楚。**

模糊指令把关键决定留给 Claude 猜；具体指令则把它需要知道的信息提前交代。提问质量直接影响执行方向、返工次数和验证闭环。

## 2. 观众需要完成的认知变化

~~~text
信息缺口
↓ Claude 需要脑补
↓ 方向可能跑偏
↓ 多轮返工
~~~

## 3. 必须保留的信息

### A. 模糊指令为什么会失败

- “修一下这个 bug”没有说明具体问题。
- 没有指出文件、函数或代码范围。
- 没有定义期望行为，Claude 只能按一般情况猜。
- 猜错后可能修改多个文件，却没有解决真正的问题。

文章用“带新人”类比说明：说“把那个东西弄一下”不如说清位置、目标和约束。

### B. 具体指令的三个维度

1. **范围**：明确文件、函数、场景或目录。
2. **约束**：说明不要引入新库、保持兼容或不要改动哪些内容。
3. **参照**：给出一个已经满意的文件或实现模式，让 Claude 有可对齐的例子。

具体不是绝对规则：探索阶段可以故意开放提问，用来发现改进方向；要得到确定结果时，才需要尽可能具体。

### C. 上下文要直接提供

- 用 `@` 引用文件，让 Claude 直接读取完整内容。
- 报错不要概括，直接粘贴包含文件名、行号和调用链的完整 traceback。
- UI 问题可以直接提供截图。
- 能贴原始材料，就不要只用二手描述。

### D. 成功标准要可验证

指令应告诉 Claude 什么结果算完成，并尽量给出能运行或观察的检查：

- 示例输入和输出。
- 测试用例。
- 构建、lint 或截图比对。
- “解决根本原因，不要用 `try/except` 或 `@ts-ignore` 压住错误”之类的质量边界。

文章还介绍 `/goal`：把可展示、可检查的完成条件变成会话目标。评估模型只能判断 Claude 在对话中展示出来的证据，因此“测试全过”比“代码质量很高”更可验证。

### E. 复杂任务先规划

- 跨多个文件、方法不确定或不熟悉代码时，先让 Claude 说明文件范围和改动思路。
- 可以在普通提示里明确“先别改任何代码”。
- 也可以进入 Plan Mode，先读文件和出方案，批准后再落盘。
- 拼写错误、加日志、重命名变量等一句话能描述 diff 的小改动，可以直接执行。

### F. 对照实验

文章用 `average(nums)` 的空列表除零问题演示两种说法：

- 模糊：`@stats.py 帮我改改这个函数`。
- 具体：点名 `average`，说明空列表返回 `0`，给出 `average([])` 和 `average([2, 4])` 的预期结果，并要求跑测试。

实验的价值在于让观众看到：好指令把“改哪、改成什么、怎样算成功”都说清，Claude 不必替用户做决定。

## 4. 因果、对比与流程关系

### 因果关系

~~~text
信息缺口
→ Claude 需要脑补
→ 方向可能跑偏
→ 多轮返工
~~~

~~~text
范围 + 上下文 + 验收标准
→ Claude 能定位并执行
→ 检查结果可见
→ 形成验证闭环
~~~

### 对比关系

| 维度 | 模糊指令 | 具体指令 |
| --- | --- | --- |
| 改哪里 | 未说明，靠 Claude 猜 | 点名文件和函数 |
| 改成什么 | 只有“改好” | 给出期望行为和约束 |
| 怎么算完成 | “看起来差不多” | 测试、构建或示例结果 |
| 任务方式 | 直接让它自由发挥 | 复杂任务先规划 |

### 流程关系

~~~text
识别任务规模
→ 小任务直接执行 / 复杂任务先规划
→ 提供范围和上下文
→ 提供验收标准
→ 执行并展示验证结果
~~~

## 5. 可视觉化内容

- 同一条模糊需求导致错误猜测和无关 diff。
- “范围／约束／参照”三件套逐层补齐。
- `@文件`、完整 traceback、截图作为上下文入口。
- 失败测试到通过测试的验收闭环。
- Plan Mode 的“先读、先列计划、批准后修改”流程。
- `average([])` 对照实验的两条提示和两条执行路径。
- 四条心法收束为一张可复用的提问检查表。
