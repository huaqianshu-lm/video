# Claude Code 提问与指令 · Visual Script

> 目标：让声音解释“为什么”，让画面演示“信息如何改变执行结果”。

## 全局视觉原则

### 1. 画面优先展示因果，不把口播做成字幕卡

画面不重复整段旁白，而是展示模糊输入如何产生猜测、具体输入如何产生验证结果。

### 2. 每幕只引入一类信息

九个 Scene 依次处理：问题、具体、上下文、验收、规划、模糊实验、具体实验、检查表、收束。每幕保留一个主视觉中心。

### 3. 保持 16:9 深色教程感

- 1920 × 1080 横屏构图。
- 深色背景、蓝紫色强调、绿色只表示通过。
- 主标题控制在 1～2 行。
- 文件路径、命令、traceback 使用等宽字体。
- 卡片、终端和流程框留出安全边距。

### 4. 画面文字必须有当前来源

所有文件名、提示词、测试结果、标签和预告均来自 `source.md`、本文件或对应 Scene Script；不使用参考视频的业务语义、固定文案或状态文字。

## 逐 Scene 视觉设计

### Scene 01｜一句“修一下”为什么会跑偏

- **画面结构**：左侧是模糊输入气泡，右侧是项目文件树和错误 diff。
- **视觉动作**：输入“修一下这个 bug”后，三个无关文件依次闪出 `Modified`，真正问题仍标红。
- **信息重点**：`信息量约等于零`。
- **与口播互补**：口播解释缺少哪些信息，画面演示“只能猜”的结果。
- **场景类型**：`Demo + Diff`。

### Scene 02｜具体，不等于写得更长

- **画面结构**：中心是需求卡，三张卡依次接入：`范围`、`约束`、`参照`。
- **视觉动作**：从“修一下登录的错误”扩展为 `src/auth/`、token 刷新、`HotDogWidget.php` 参照。
- **信息重点**：每补一项，未知区域缩小一格。
- **与口播互补**：口播解释原则，画面让信息补齐过程可见。
- **场景类型**：`Process + Cards`。

### Scene 03｜把原始材料直接喂到 Claude 面前

- **画面结构**：三列输入入口：`@src/types/user.ts`、完整 traceback、截图。
- **视觉动作**：文件内容、行号调用链和界面截图依次进入 Claude 的上下文面板。
- **信息重点**：`@文件`、`完整 traceback`、`截图`。
- **与口播互补**：口播解释二手描述会丢失坐标，画面演示原始材料直接到位。
- **场景类型**：`Input Montage`。

### Scene 04｜什么结果算成功，要提前说

- **画面结构**：左侧是 `average(nums)`，右侧是验证面板。
- **视觉动作**：`average([])` 先显示 `ZeroDivisionError`，加入“返回 0”后出现两个测试用例并转为绿色通过。
- **信息重点**：`通过 / 失败` 和示例输入输出。
- **与口播互补**：口播解释验收标准的作用，画面展示验证闭环。
- **场景类型**：`Test Loop`。

### Scene 05｜复杂任务，先让它列计划

- **画面结构**：左右分岔：复杂任务和小改动。
- **视觉动作**：复杂侧依次出现“读取文件 → 列改动 → 批准 → 修改”；简单侧直接从“重命名变量 → 完成”。
- **信息重点**：`复杂：先规划` 与 `简单：直接做`。
- **与口播互补**：口播给判断边界，画面给出两条不同路径。
- **场景类型**：`Decision Split`。

### Scene 06｜同一个文件，模糊提示会发生什么

- **画面结构**：代码编辑器展示 `stats.py` 和 `average` 函数，下面是输入区。
- **视觉动作**：输入模糊提示后弹出两个猜测分支：类型注解、文档字符串；空列表问题仍未处理。
- **信息重点**：`方向全凭运气`。
- **与口播互补**：口播说出真正 bug，画面保持多个可能分支而不提前替观众下结论。
- **场景类型**：`Code Demo`。

### Scene 07｜把三件事一次说清

- **画面结构**：上方是完整具体提示，下方是终端执行日志。
- **视觉动作**：依次显示空列表分支、`average([]) → 0`、`average([2, 4]) → 3` 和 `✓ tests passed`。
- **信息重点**：改哪、改成什么、怎么验收。
- **与口播互补**：口播解释提示的组成，画面负责展示执行链和通过证据。
- **场景类型**：`Terminal Demo + Test Result`。

### Scene 08｜四条心法变成一张检查表

- **画面结构**：四张等宽检查卡：具体、给上下文、给验收标准、先列计划。
- **视觉动作**：卡片按口播顺序点亮，底部出现最小动作示例。
- **信息重点**：四条原则的名称和动作关键词。
- **与口播互补**：口播完成记忆收束，画面提供可暂停查看的检查表。
- **场景类型**：`Checklist`。

### Scene 09｜把话说清，Claude 才接得住

- **画面结构**：上半部是一条从“模糊需求”到“脑补返工”的灰色路径，下半部是一条从“清楚需求”到“执行验证”的强调路径。
- **视觉动作**：上半部箭头停在返工，下半部箭头完成闭环；最后切入独立预告卡。
- **信息重点**：`少猜，少返工`、`下一集：常见工作流`。
- **与口播互补**：口播总结提问本质，画面完成状态转化并承载下一集预告。
- **场景类型**：`Summary + Preview Card`。

## 全片视觉类型、组件和动画标准

### 视觉类型

- `Demo`：Scene 01、06、07。
- `Process`：Scene 02、03、05。
- `Comparison`：Scene 01、05、09。
- `Concept / Checklist`：Scene 04、08。

### 基础组件

- 深色 `stage` 场景容器。
- `window`、`terminal`、`editor` 模拟软件界面。
- `prompt-card`、`info-card`、`check-card` 信息卡。
- `flow-arrow` 和状态点，表示信息流与验证结果。
- 幕内字幕、上一幕／下一幕、自动播放和进度提示，仅属于 Visual Prototype 交互。

### 动画标准

- 输入、文件和日志按顺序淡入或向上进入。
- 通过状态使用绿色，错误状态使用低饱和红色，避免强闪烁。
- 卡片点亮传递“信息已补齐”，不能只做装饰性发光。
- Scene 07 的测试结果必须晚于修改和测试命令出现。
- Scene 09 预告卡独立停留约 2～3 秒，不能与字幕区域重叠。
