# Claude Code 提问与指令 · Narration Script

## Scene 01｜一句“修一下”为什么会跑偏

项目里一个函数报错了，你只对 Claude 说一句：“修一下这个 bug。”

它没有文件、没有报错位置，也不知道你想要的正确行为。于是它只能猜。等你再看 diff，可能改了三个文件，却没有一个真正解决你遇到的问题。

这时候很容易说“AI 不行”。但很多时候，问题其实出在这句话的信息量约等于零。

## Scene 02｜具体，不等于写得更长

好提问的第一条原则，是具体。

具体到三个地方：先说清楚范围，比如哪个文件、哪个函数或哪个场景；再说清楚约束，比如别引新库、保持向后兼容，或者别动测试文件；最后给一个你已经满意的参照，让它照着现成模式来。

你不是在堆字，而是在把 Claude 原本要猜的选择提前做掉。

不过，模糊也不是绝对错误。如果你还在探索方向，开放地问一句“这个文件有什么可以改进的”，可能会带来意外启发。要结果时具体，找灵感时留白。

## Scene 03｜把原始材料直接喂到 Claude 面前

第二条原则，是给上下文。

能直接贴的，就不要只用嘴描述。用 `@` 引用文件，把完整内容交给 Claude；遇到报错，就把包含文件名、行号和调用链的完整 traceback 原样贴进去；界面问题可以直接贴截图。

“项目里有个文件”和 `@src/types/user.ts`，对 Claude 来说不是一回事。

前者还要它自己找，后者已经把坐标交到它手里。你少做一次二手转述，它就少丢一层关键信息。

## Scene 04｜什么结果算成功，要提前说

第三条原则，是给一个可验证的成功标准。

不要只说“实现一个邮箱校验函数”，还要告诉它哪些输入应该通过，哪些输入应该失败，并要求写完跑测试。

修构建也一样：把报错贴出来，要求解决根因并验证构建通过，不要用 `try/except` 或 `@ts-ignore` 把问题压下去。

这样，任务就有了通过和失败的信号。Claude 做完以后能检查，检查没过就继续修，而不是凭“看起来差不多”收工。

## Scene 05｜复杂任务，先让它列计划

第四条原则，是复杂任务先规划。

如果一次改动会跨多个文件，或者你和 Claude 都还不确定应该怎么改，可以先说：“告诉我需要动哪些文件和改动思路，这一步先别改代码。”

也可以进入 Plan Mode，先读文件、列方案，等你批准以后再落盘。

但别把所有小事都规划一遍。拼写错误、加一行日志、重命名变量，这种一句话就能说清改动的任务，直接执行更合适。

判断标准很简单：一句话能说清改完长什么样，就不用把它变成一场规划会议。

## Scene 06｜同一个文件，模糊提示会发生什么

现在做一个小实验。

有个 `stats.py`，里面的 `average` 函数在传入空列表时会因为除以零而崩溃。

先用模糊说法：`@stats.py 帮我改改这个函数`。

这句话没有点出空列表，也没有定义结果。Claude 可能去加类型注解，也可能补文档字符串，但它不知道你真正关心的是哪个 bug。

这就是模糊提问的代价：你把决定交给了它。

## Scene 07｜把三件事一次说清

再换一种说法。

“`@stats.py` 里的 `average` 函数有个 bug：传入空列表时会因为除以零而崩溃。期望行为是空列表返回零。帮我修复，并补一个测试：`average([])` 应该返回零，`average([2, 4])` 应该返回三。写完把测试跑一遍，确认通过。”

这一次，改哪、改成什么、怎么算成功，全都说清楚了。

于是动作链也变得清楚：定位空列表分支，补上返回值，写出两个测试用例，再把测试结果展示出来。

同一个文件、同一个函数，差距不在 Claude 突然变聪明了，而在你不再让它替你做决定。

## Scene 08｜提问前，快速检查四件事

把这套方法收成四句话。

第一，具体：说清范围、约束和参照。

第二，给上下文：能用 `@`、报错和截图直接提供，就别只做口头概括。

第三，给验收标准：让它知道什么结果算完成，并且能自己检查。

第四，复杂任务先列计划；一句话能描述的小改动，直接执行。

## Scene 09｜把话说清，Claude 才接得住

提问的本质，不是背一套看起来专业的模板。

而是每次发出需求前，先想明白三件事：到底改哪里，期望变成什么样，以及怎样证明它真的完成了。

你把这些信息提前说清，Claude 就少一次猜测，你也少几轮返工。
