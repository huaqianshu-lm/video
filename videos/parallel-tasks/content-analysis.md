> 目标：先确定这条视频必须讲清楚什么，不直接把原文章节改成口播。

## 1. 核心命题

这篇文章表面上在介绍 Claude Code 的并行工具，真正要建立的认知是：

> **并行不是多开几个窗口，而是让互相独立的任务同时进行，并用隔离机制避免它们踩到同一份文件。**

如果观众最后只记住一句话，应该是：

> **先判断任务是否独立、是否会抢文件，再决定要不要并行。**

工具只是这条判断线之后的实现手段：worktree 负责隔离，后台会话负责调度，headless 负责批量执行。

---

## 2. 必须保留的核心信息

### A. 并行解决什么问题

并行适合两类工作：

- 任务天然互相独立，不需要等待彼此的结果。
- 任务规模较大，一个会话处理会让上下文和等待时间成为瓶颈。

但成立必须同时满足两个条件：

```text
任务互相独立
+
不抢同一份文件，或使用 worktree 隔离
```

开头的失败案例必须保留：两个终端进入同一个项目目录，同时修改 `package.json`，导致改动覆盖、状态混乱、合并困难。它不是一个偶然的操作失误，而是没有处理并行边界。

### B. 四种并行方式的区别

文章用“谁来协调”区分四种方式：

| 方式 | 协调者 | 关键用途 |
|------|--------|----------|
| 子代理 | 当前 Claude 会话 | 把辅助工作放到独立上下文，返回摘要 |
| 代理视图 | 人 | 后台派任务并集中查看状态 |
| 代理团队 | Claude | 多个会话共享任务列表并互相协作，实验性 |
| 动态工作流 | 脚本 | 批量运行并交叉验证，研究预览 |

还要说明：worktree 和 `/batch` 是配合工具，不是第五、第六种并行方式。

### C. 三套可执行手段

#### 1. Worktree 隔离

`--worktree` 或 `git worktree` 为每个会话提供独立副本和分支，核心价值是一个会话的编辑不会触及另一个会话的文件。需要保留三个实践坑点：

- `.claude/worktrees/` 应加入 `.gitignore`。
- 未跟踪的 `.env` 等文件默认不会进入新 worktree，可用 `.worktreeinclude` 指定复制内容。
- 非交互 `-p` 产生的 worktree 不会自动清理，需要手动 `git worktree remove`。

#### 2. 后台会话与代理视图

`--bg` 把任务甩到后台，`claude agents` 提供统一状态面板。用户只在需要时窥视、回复或附加进入会话。文章强调后台会话也消耗用量，并且较新的代理视图会自动为后台任务创建隔离 worktree。

#### 3. Headless 批量

`claude -p` 让任务非交互运行一次即退出；`--allowedTools` 预先批准工具，`--bare` 减少启动时的自动发现，`--output-format json` 输出可被脚本解析的结构化结果。再用 shell 循环套住它，就得到批量执行的雏形；规模更大且需要交叉验证时，再考虑 `/batch` 或动态工作流。

## 3. 判断线：什么时候别并行

这是视频的转折和结论，不应被工具演示淹没。

### 值得并行

- 三个互不相干的模块各修各的 bug。
- 同一套改动批量跑多个互不依赖的文件。

### 应该串行或谨慎处理

- B 必须依赖 A 的新结果：先完成 A，再做 B。
- 两个会话都要改同一份 `package.json`：串行，或先用 worktree 隔离。
- 五分钟就能完成的小改动：协调和合并成本可能更高。
- 任务需要频繁交换中间结果：先评估沟通成本，不要为了并行而并行。

并行越多，额度和管理成本越高。文章给出的经验是手动并行控制在三五个以内，大批量任务交给更工程化的批处理方式。
