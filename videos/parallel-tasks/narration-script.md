# 并行任务视频化 · 第四步：Narration Script

## Scene 01｜两个终端，撞在同一块地上

有一次我想同时推进两件事，开了两个终端，而且都进入了同一个项目目录。

一个会话改前端登录页，另一个会话顺手修后端的 bug。刚开始看起来像是效率翻倍，结果两边同时改到了 `package.json`。

一边刚写进去的依赖，被另一边的改动覆盖回去。等我再看 `git status`，工作区已经乱成一团，哪一行是谁改的，也很难分清。

这件事让我意识到，并行不是多开几个窗口这么简单。多个会话如果踩在同一块地上，越快开工，越快把问题搅在一起。

## Scene 02｜并行的两个前提

并行真正解决的是：几件互不相干的活，不用排队一件件等。

比如三个模块各自修自己的 bug，或者同一种改动要批量跑过很多个互不依赖的文件。这些任务天然可以同时开始。

但并行要成立，必须同时满足两个前提。

第一，任务之间互相独立，A 不需要等 B 的结果。第二，它们不能抢同一份文件；如果确实会碰到同一份代码，就要先用 worktree 把工作区隔开。

所以并行的铁律可以先记成一句话：独立，而且不抢文件。

## Scene 03｜四种方式，先看谁协调

Claude Code 里的并行不止一种方式。最容易记的区分方法，不是背名字，而是先看谁来协调。

子代理是在一个会话里由 Claude 派活、收回摘要。代理视图更像一块总控台，由你把几个独立任务甩到后台，再回来查看状态。

代理团队是多个会话一起工作，由 Claude 当工头统筹任务；动态工作流则把批量运行和交叉验证写进脚本里。

这里还要留意状态限定：代理视图和动态工作流在文章中标为研究预览，代理团队是实验性、默认关闭。Worktree 和 `/batch` 是给并行打配合的工具，不是另外两种并行方式。

## Scene 04｜Worktree：给每个会话一份副本

解决共享目录冲突，最直接的办法是给每个会话一份自己的副本。

启动时使用 `claude --worktree feature-auth`，Claude 会建立一个隔离的 worktree 和对应分支。另一个会话可以使用不同的名字，它们共享仓库历史，但不会直接改到彼此的文件。

不过，隔离副本也有几个容易漏掉的地方。`.claude/worktrees/` 应该加入 `.gitignore`。像 `.env` 这样的未跟踪文件默认不会进入新 worktree，可以用 `.worktreeinclude` 指定要复制的内容。

如果是非交互的 `-p` 会话，结束后也不会替你弹出清理提示。任务完成以后，记得检查并用 `git worktree remove` 清掉不再需要的副本。

## Scene 05｜后台会话：甩出去，一屏盯

文件隔离之后，还有一个问题：开了几个会话，难道要开几个终端来回切吗？

这时可以用 `--bg` 把任务甩到后台。命令返回一个短 ID，以及查看日志、附加会话和停止任务的管理入口。

再用 `claude agents` 打开代理视图，所有后台会话会集中显示。工作中的、需要输入的、已经完成的和失败的任务，按状态分组排列。

多数时候你只需要窥视一下；真正需要拍板时再回复或附加进去。要记住的是，后台会话和交互会话一样消耗用量，并行不是越多越好。

## Scene 06｜Headless：把任务写进脚本

如果任务规则很清楚，而且要重复跑很多次，就不必一直坐在终端前盯着。

`claude -p` 可以让 Claude 非交互地执行一次任务，然后直接退出。你可以用 `--allowedTools` 预先批准它能用的工具，用 `--bare` 减少启动时加载的上下文，再用 `--output-format json` 得到脚本更容易处理的结构化结果。

把同一条 `-p` 命令放进 shell 的 `for` 循环，就形成了批量执行的雏形。几十上百个文件，或者还需要互相验证结果时，再考虑 `/batch` 或动态工作流。

这里的重点不是多记几个参数，而是看清楚分工：人先定义规则，脚本负责重复，结果再交回检查。

## Scene 07｜最重要的判断：什么时候别并行

讲到这里，最重要的问题其实不是“怎么并行”，而是“什么时候不要并行”。

三个互不相干的模块各修各的 bug，适合并行。同一套改动批量跑多个文件，也适合交给 headless 或 `/batch`。

但如果是先重构 A，再基于新的 A 去修改 B，就应该串行。B 如果提前开始，只能拿旧版本做判断。

两个会话都要修改 `package.json`，要么串行，要么先做 worktree 隔离。一个五分钟就能完成的小改动，也不值得花时间拆任务。任务需要频繁交换中间结果时，更要先算清沟通成本。

并行越多，额度和管理成本也越高。手动并行控制在三五个以内，通常比一上来开一整屏更稳妥。

## Scene 08｜六步走通并行主链

如果想亲手练一遍，可以把它压缩成六步。

第一步，进入一个 Git 项目，先运行 `claude`，接受工作区信任。第二步，用 `claude --worktree test-parallel` 建一个隔离会话。

第三步，在主项目里运行 `git worktree list`，确认副本真的存在。第四步，用 `claude --bg` 把一个任务甩到后台。

第五步，打开 `claude agents`，观察状态，需要时再窥视或附加。第六步，停止后台任务，并用 `git worktree remove` 清理练习用的 worktree。

走通这六步，你就把“开隔离副本、甩后台、看状态、做清理”这条主链真正跑了一遍。

## Scene 09｜并行的正确姿势

回头看，worktree 解决的是文件隔离，后台会话解决的是集中调度，headless 解决的是重复任务的批量执行。

但它们都建立在同一个判断上：任务要互相独立，而且不能抢同一份文件。

所以拿到一个新任务，先判断，再拆分；先隔离，再启动会话。并行的价值不是让所有事情同时发生，而是让真正独立的事情不用排队。
