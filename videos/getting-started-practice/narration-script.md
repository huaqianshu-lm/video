# 实战入门：Narration Script

## Scene 01｜一句话交给 AI，为什么会失控

大多数人以为，AI 写代码就是把需求说清楚，然后等它把结果交回来。

但真实情况常常是：方向跑偏了，顺手多改了几个文件，说好的 Bug 修完还是会崩。最后花在收拾残局上的时间，反而比自己动手还多。

问题不一定是工具不够聪明，而是这趟流程里少了几个关键的交接棒。

## Scene 02｜一趟实战，就这六步

一个真实任务从接到手到交付，骨架其实只有六步：开工、探索、规划、动手、验证、交付。

这六步可以压缩，但不能跳。熟手可能把探索和规划合成一句，把验证和交付连起来；新手最容易做的，却是把中间几步直接删掉，只剩下说需求和拿结果。

接下来，我们用一个小任务，把每一棒都交到位。

## Scene 03｜先造一个有原点的练手项目

我们先造一个叫 `wordcount-demo` 的最小练手场。它只有一个 Python 脚本和一个输入文件，不依赖任何第三方库，有 `python3` 就能运行。

原始脚本能统计单词频率，但有两个正好适合练习的问题：它还没有 `--top N` 功能，而且不传文件名时会因为访问 `sys.argv[1]` 直接触发 `IndexError`。

先手动跑一次，确认原始输出正常；然后在开工前做一次 git commit。这个提交就是干净原点，后面无论改成什么样，都有地方可以退回。

## Scene 04｜开工先定最小规则

现在进入正确的 `wordcount-demo` 目录，启动 Claude Code。

开工时先给项目一份很短的 `CLAUDE.md`：这是纯标准库的 Python 命令行工具，不要引入第三方依赖；每次改完，用 `python3 wordcount.py sample.txt` 验证不报错。

小项目不需要堆一大篇规则。三五行把真正重要的约束钉住，后面整场都能复用。

## Scene 05｜探索：先看懂，别急着改

拿到任务的第一句话，不是“给我改”，而是“先别改，先看懂”。

比如先让它阅读 `@wordcount.py`，讲清楚入口在哪里、代码怎么工作、有没有明显的问题或容易崩的地方。

这一步只许看，不许动。它很可能自己发现：`main()` 直接读取 `sys.argv[1]`，如果没有文件名，程序就会越界崩溃。

小任务一句探索就够；到了真实项目，可以先问整体结构，再追问局部文件如何配合。

## Scene 06｜规划：先出方案，再砸代码

探索完还不能马上改。先让它把打算怎么改摆出来，你认可了再动手。

这个任务的方案可以是：用 `argparse` 替掉手写的 `sys.argv`，增加 `--top` 选项，用 `Counter.most_common(N)` 取前 N 个词，让缺少文件名时自动显示友好的用法提示。

小改动可以直接要求它先说方案；任务更大或心里没底，就用 plan mode，让它在批准前不能编辑源代码。

## Scene 07｜动手，但每处 diff 都过一眼

方案通过后，再让它开始改。

这时不要无脑接受每一次变更。看红行删了什么，绿行加了什么，再看范围有没有超出方案。

在这个任务里，应该看到 `main()` 使用 `argparse`，加入 `--top`，但不应该顺手改掉本来正常的 `count_words`，也不应该引入第三方依赖。

批准 diff 是一次事中拦截。趁改动还在眼前把边界看清，比事后回滚便宜得多。

## Scene 08｜验证：新、旧、边界三连验

代码改完，先别相信“已经改好了”。亲手跑三遍。

第一遍运行 `python3 wordcount.py sample.txt --top 3`，确认只显示最高频的前三个词。

第二遍不带 `--top`，确认原来的完整统计没有被改坏。

第三遍不带文件名，确认不再甩出 `IndexError`，而是显示 `usage` 和缺少 `path` 的提示。

这三遍分别覆盖新功能、旧功能和边界行为。跑出来的通过，才是事实。还可以把缺参行为写成测试，让这条关卡以后能重复运行。

## Scene 09｜交付：概览、commit、log

验证通过后，先问清楚这次到底改了哪些文件。理想结果是只改了 `wordcount.py`，新增 `--top`，并把缺参崩溃改成友好提示。

接着让它拟一条清楚的提交信息，确认后执行本地 `git commit`，最后查看 `git log -1`。

这样才算从开工走到了入库。记住，本地 commit 和远程 push 是两条边界；推到远程之前，仍然要自己把关。

## Scene 10｜改岔了：干净退回再重开

真实任务不一定每次都走得顺。验证变红时，别在已经改乱的代码上继续硬补。

改岔一两处，可以用检查点或 `/rewind` 撤销这一批编辑；整个方向都偏了，就回到开工前的 git 提交。

退回不是失败，而是止损。回到干净原点后，先想清楚是哪条约束没说清，再带着更具体的指令重新开始。

## Scene 11｜老手不是跳步，而是交接完整

同样六步，老手和新手的差距，不在于谁能把流程删得更多，而在于谁把交接棒交得更完整。

老手站对目录、先定规则；第一句话先探索；没把握就先 plan；每处 diff 扫一眼；亲手验证新功能、旧功能和 Bug；最后看范围、提交、确认入库。

任务越小，每一步越快。流程是骨架，不是镣铐。最该练成本能的，是开头先探索，结尾亲手验证。
