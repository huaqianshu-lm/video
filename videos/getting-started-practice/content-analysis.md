# 实战入门：Content Analysis

> 本文只分析 `39-getting-started-practice.md`。视频目标不是复述前 38 篇，而是把文章中已经出现的动作组织成一条可执行、可检查、可交付的实战路径。

## 1. 核心命题

AI 写代码最容易被误解成“说清需求，等待结果”。真正稳定的协作需要一条完整的交接链：先在正确项目中开工并定规则，再让 AI 探索现状、提出计划、执行改动、接受 diff 审查、跑验证，最后确认范围并交付。

这篇文章的新增价值不是某个新功能，而是把前面学过的动作按正确顺序连接起来。核心原则是：

> 先探索，再规划；批准后动手；动手后审 diff；完成后亲手验证；确认范围后再交付。

## 2. 文章要解决的用户问题

文章先指出“一句话然后等结果”的工作方式会导致：

- 方向跑偏。
- 顺手多改文件。
- Bug 看似修好但仍然崩溃。
- 最后收拾残局，比自己动手更费时间。

根因不是工具不够聪明，而是任务中间缺少关键交接棒。文章用“学会单个动作”和“把动作连成一趟”的鸿沟解释这一点。

## 3. 核心知识骨架

### A. 六步实战骨架

1. **开工**：进入正确的项目目录，写最小可用的 `CLAUDE.md`。
2. **探索**：先读代码、问入口、问明显问题，明确“先别改”。
3. **规划**：先让 AI 说打算如何改；复杂任务使用 plan mode。
4. **动手**：批准方案后执行，逐处查看 diff，确认没有越界或引入依赖。
5. **验证**：验证新功能、回归旧功能、复现并确认 Bug 修复。
6. **交付**：先看改动概览，再生成并确认 commit，最后检查 `git log`。

六步可以压缩节奏，但不能删掉中间环节。最常掉的是“没探索就动手”和“没验证就交付”。

### B. 练手项目是最小但完整的任务

练手项目是一个纯标准库 Python 小工具：

- `wordcount.py`：用 `Counter` 统计文本中的单词频率。
- `sample.txt`：`the quick brown fox the lazy dog the fox`。
- 原始实现直接读取 `sys.argv[1]`，不传文件名会触发 `IndexError`。

真实任务包含两个目标：

- 新增 `--top N`，只显示最高频的前 N 个词。
- 修复缺少文件名时的崩溃，让程序输出用法提示。

开工前使用 `git init && git add . && git commit -m "init: 一个简陋的数词脚本"` 建立干净原点，保证后续可以回退。

### C. 开工规则要短而有效

项目根目录的最小 `CLAUDE.md` 只需固定两条：

- 这是纯标准库 Python 命令行工具，不引入第三方依赖。
- 每次改完用 `python3 wordcount.py sample.txt` 验证不报错。

文章对比了手写最小规则和 `/init`：小项目手动写两条更准更短；`/init` 适合有一定规模、需要自动扫描的真实项目。

### D. 探索先于修改

第一句应是：

```text
先别改任何代码。给我讲讲 @wordcount.py 现在是怎么工作的，入口在哪、有没有什么明显的问题或者容易崩的地方？
```

探索要点：

- “先别改任何代码”划定这一棒只读不写。
- `@wordcount.py` 把目标文件直接带入对话。
- 对小项目，一句探索即可；真实项目可先问整体结构，再追问局部文件如何配合。
- 探索阶段可能主动发现 `sys.argv[1]` 的缺参隐患。

### E. 规划是低成本的方向闸门

有两种方式：

- 小改动：要求先说方案、等“开始”再动手。
- 大改动或没把握：用 `claude --permission-mode plan`，或在会话中用 `Shift+Tab` 切换 plan mode。

方案应覆盖：用 `argparse` 替换手写 `sys.argv`、加入 `--top`、使用 `Counter.most_common(N)`、缺少路径时由 `argparse` 给出友好提示，以及将要修改的文件范围。

### F. 动手必须伴随 diff 审查

批准后关注三类信号：

- 删除了什么：不应误删原本正常的 `count_words`。
- 增加了什么：应看到 `argparse`、`--top`，不应出现第三方依赖或未要求功能。
- 改动范围：应集中在 `wordcount.py`，符合已批准方案。

“全部接受”模式会失去事中拦截窗口；文章建议练手阶段逐处看 diff。

### G. 验证必须覆盖新、旧和边界

三条确定性验证：

```bash
python3 wordcount.py sample.txt --top 3
python3 wordcount.py sample.txt
python3 wordcount.py
```

分别验证：

- 新功能只输出前三个高频词，并按频率排序。
- 不带 `--top` 的旧用法仍输出完整计数。
- 不带文件名不再出现 `IndexError`，而是给出 `usage` 和缺少 `path` 的提示。

还可以把缺参行为写成可重复跑的测试：退出码非 0，并打印用法提示。它把一次人工确认升级为以后可重复的关卡。

### H. 交付和止损是闭环的一部分

交付顺序是：

1. 让 AI 给出改动概览。
2. 让 AI 拟定一句清楚的提交信息并请求批准。
3. 查看最后一次提交，确认成果入库。

本地 `commit` 和远程 `push` 是不同边界：文章只把本地提交纳入本次闭环，远程推送仍需使用者自己把关。

如果方向跑偏：

- 轻档用检查点或 `/rewind` 撤销这一批编辑。
- 重档用开工前的 git 提交作为干净原点。
- 回退后补清指令中的关键约束，再重新开始，不要在烂摊子上继续打补丁。

## 4. 认知关系

### 因果关系

跳过探索 → AI 只能猜 → 方向可能跑偏。

跳过规划 → 方案没有被确认 → 多文件或错误方向改动更难拦截。

跳过 diff 审查 → 越界修改可能直接落地。

跳过验证 → “我改好了”仍只是声明，不是事实。

没有干净 git 原点 → 改错后止损成本更高。

### 对比关系

| 新手路径 | 老手路径 |
| --- | --- |
| 随便找目录启动，不写规则 | 站对项目目录，先定最小规则 |
| 直接说“给我改” | 第一句先探索，明确不修改 |
| 直接动手 | 先出方案，必要时 plan mode |
| diff 不看一路批准 | 每处确认范围、依赖和目标 |
| 相信“已完成” | 亲手验证新功能、回归和 Bug |
| 改完晾着或直接提交 | 概览 → commit → `git log` |

### 流程关系

`开工` 交出规则与干净原点；`探索` 交出现状理解；`规划` 交出可审方案；`动手` 交出 diff；`验证` 交出通过证据；`交付` 将成果存入 git。

## 5. 可视觉化内容

- 六步接力棒：用逐步点亮与交接表现不能跳步。
- 练手项目：目录、两个文件、初始输出和 git 原点。
- `CLAUDE.md`：两条规则卡进入项目根目录。
- 探索：文件被读取，入口和 `sys.argv[1]` 被标注，代码保持未修改。
- 规划：需求进入 plan 卡，方案停在“等待批准”。
- diff：红删绿加，`argparse` 和 `--top` 出现，第三方依赖被排除。
- 验证：三条命令分别亮绿，旧功能与边界行为被区分。
- 交付：`git status` 概览、commit、`git log -1` 形成闭环。
- 止损：`/rewind` 与 git 原点两条退回路线。
- 老手／新手：交接棒是否完整的并列对照。
