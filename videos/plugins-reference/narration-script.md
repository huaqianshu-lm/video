# 插件参考手册：Narration Script

## Scene 01｜插件不是黑盒

给一个插件跑一下 `claude plugin details`，你经常会看到一组很容易被忽略的数字：每个会话常驻大约一百八十个 token，里面的两个 skill 触发时，还会分别增加大约两千四百和一千八百个 token。

这说明插件并不是一个挂在那里就什么都不占的黑盒。它由不同组件拼成，每一类组件占多少、放在哪里、什么时候触发，都有明确规则。

上一篇我们讲的是怎么用别人的插件。这一次，我们把视角换过来：看清它的内部结构，再自己造一个、测一个，最后发出去。

## Scene 02｜先把目录骨架摆正

先把插件想成一盒乐高。

`.claude-plugin/plugin.json` 像说明书，`skills`、`agents`、`hooks` 这些目录则是分格放好的零件盒。

这里有一条必须记住的规则：`.claude-plugin/` 里面只放 `plugin.json`。其他目录都要和它平级，放在插件根目录下。

如果把 skill 或 hook 塞进 `.claude-plugin/`，插件可能看起来已经加载了，但组件就是不会出现。

还有一点容易混淆：插件根目录里的 `CLAUDE.md` 不会自动变成项目上下文。插件要给 Claude 提供能力，应该使用 skill、agent 或 hook 这些组件。

## Scene 03｜plugin.json 定身份和扫描规则

插件的清单文件叫 `plugin.json`。如果写这份清单，唯一必填的字段是 `name`，而且要使用小写加连字符的格式。

这个名字不只是展示名称，它还会变成组件的命名空间。比如插件叫 `my-plugin`，里面的 skill 就会以 `/my-plugin:...` 这样的形式调用。

其他字段可以补充显示名、版本、描述、作者、仓库和关键词。路径字段则决定 Claude 去哪里找组件。

这里最容易搞反的是两种行为：`commands`、`agents` 和 `outputStyles` 会替换默认目录；`skills` 字段则是在默认 `skills/` 之外追加目录。

所以想“再加一个 agent”，不能只填新增目录，还要把原来需要保留的路径一起列出来。

## Scene 04｜插件能装哪些组件

一个插件可以把七类能力装在同一个包里。

`skills` 是专项能力，`commands` 是扁平的旧写法，`agents` 是专项 subagent；`hooks` 监听生命周期事件，MCP servers 连接外部服务，LSP servers 提供代码智能，monitors 则在后台观察日志或状态。

它们各有固定位置，也有各自的触发方式。除此之外，`bin` 里的可执行文件可以进入 Bash 工具的 PATH，`settings.json` 还可以提供插件默认设置。

你不需要一次记住所有细节，但要先建立一个总感觉：插件不是一个文件，而是一组按类型组织起来的零件。

## Scene 05｜组件不是没有边界

能力越多，边界越重要。

出于安全原因，插件提供的 agent 不支持 `hooks`、`mcpServers` 和 `permissionMode` 这三个 frontmatter 字段。也就是说，它不能通过这些字段偷偷挂上 hook、启动 MCP，或者改变权限模式。

`monitor` 也不是一个已经完全稳定的普通组件。它目前是实验性的，只在交互式会话里运行，并且需要 Claude Code 二点一百零五或更高版本。

所以看组件清单时，不只要问“它能做什么”，还要问“它在哪些条件下能做”。

## Scene 06｜不要把插件路径写死

插件里最容易出现的一类问题，是把脚本路径写成某台机器上的绝对路径。

插件安装和更新时，缓存目录可能发生变化。写死的路径在自己的电脑上也许能跑，换一台机器，或者更新一次插件，就可能失效。

标准做法是使用路径变量：`${CLAUDE_PLUGIN_ROOT}` 指向当前插件目录，用来找插件自带的脚本、二进制和配置；`${CLAUDE_PLUGIN_DATA}` 指向更新后仍保留的数据目录，适合放依赖、缓存和跨版本状态；`${CLAUDE_PROJECT_DIR}` 指向项目根目录。

记住这三个分工：自带文件找 ROOT，持久状态放 DATA，项目文件找 PROJECT_DIR。也不要用相对路径跳到插件目录之外。

## Scene 07｜从零造一个能跑的插件

现在真的造一个最小插件，名字叫 `my-greeter`。

先用 `claude plugin init my-greeter --with skills` 建出骨架，再写一个带 `$ARGUMENTS` 的 hello skill。

开发阶段不需要先建市场，直接用 `claude --plugin-dir` 加载本地目录就可以。这样做的好处是改动快，也不会把测试插件永久写进配置。

到这里，插件已经从一组规则变成了一个可以启动的本地包。

## Scene 08｜调用 skill，再用 reload 验证

插件里的 skill 会带上命名空间。启动后，可以用 `/my-greeter:hello Walter` 调用它。

如果修改了 skill 的内容，重新调用就能看到新的回应。hooks、`.mcp.json` 和 agents 这类组件有时需要 `/reload-plugins`，或者重启会话，才能加载最新变化。

初始化、加载、调用、重载，这四步就是插件开发时最小的内循环。

先在本地把这条内循环跑通，再考虑把插件交给更多人。

## Scene 09｜市场源不等于插件源

如果插件只给自己用，放在 skills 目录或者用 `--plugin-dir` 就够了。要发给团队或社区，才需要市场。

市场的核心文件是仓库根目录下的 `.claude-plugin/marketplace.json`。

这里要分清两个很像的概念：市场源，是去哪里拿商品目录；插件源，是目录里每个插件本体从哪里来。目录可以来自一个仓库，某个插件也可以从另一个 GitHub 仓库或 npm 包获取。

建好市场后，用 `claude plugin validate` 先检查目录和插件，再考虑共享给别人。

## Scene 10｜自用、开发、发布，路要选对

三种处境，对应三条路。

纯自用、想随手改随手用，可以放进 `~/.claude/skills/`；开发中反复测试一个本地包，用 `--plugin-dir`；准备发给团队或社区，再使用 marketplace。

发布前还要留意两个坑。

第一，`plugin.json` 里一旦写了 `version`，以后每次发布都要递增。只推新的代码、不改版本号，用户可能继续使用旧缓存。

第二，如果插件依赖其他插件，用 `dependencies` 写清依赖和版本范围。这样安装或启用时，Claude Code 才能按这张配料表准备依赖。

## Scene 11｜把插件当成可交付的配置包

现在回头看，插件就是一套可以被拆开检查的配置包：`plugin.json` 定身份，根目录组件装能力，路径变量保证它能迁移，本地内循环负责验证，marketplace 负责分发，version 和 dependencies 负责让更新可控。

所以这篇参考手册真正想让你获得的，不是背完每个字段，而是拥有一条从骨架到交付的路径。
