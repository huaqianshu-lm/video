# 上下文管理：别让它「失忆」也别烧爆 token

## Scene 01｜读得越多，怎么反而失忆？

刚接手一个不熟的项目时，很多人会先让 Claude 把整个仓库读一遍，觉得这样它才懂全局。

但文章里的真实结果是，读了二十几个文件之后，它明显变慢、变迟钝。等你让它修一个登录问题，它甚至会反问，auth 模块到底在哪个文件。

问题不是读得太少，而是工作台已经被太多内容占住了。

## Scene 02｜上下文窗口是一张有限工作台

这张工作台，就是上下文窗口。

它代表 Claude 在这一次会话里能同时看到的全部内容，按 token 计算。

工作台上不只有你说的话，还包括系统提示、全局和项目里的 CLAUDE.md、自动记忆、它读过的每个文件，以及命令输出和工具结果。

真正容易把工作台堆满的，往往不是你发的那几句话，而是它不断读进来的文件和不断产生的输出。

所以，上下文窗口不是越满越好。

它是一张有限的工作台，必须给真正的任务留出空间。

## Scene 03｜工作台塞满后，会出现上下文衰退

当工作台里的内容太多，模型的注意力就会被摊薄。

无关的调试内容开始干扰当前任务，这种现象可以叫作上下文衰退。

你会看到几个很明显的症状：它前后矛盾，忘了已经确认的方案；回答越来越笼统，细节越来越少；反复问你已经回答过的问题；同一个问题被纠正两遍，还是在原地打转。

这时候，与其继续在污染的上下文里反复纠正，不如主动清理工作台。

## Scene 04｜两把扫帚：`/compact` 与 `/clear`

Claude Code 给了你两把扫帚，但它们的用途完全不同。

`/compact` 是把当前对话历史打包压扁。它会把一堆逐字记录总结成精简摘要，保留结论，继续在同一个任务上工作。你还可以告诉它，压缩时重点保留哪些内容。

`/clear` 则是直接清空本次对话历史，等于换一张工作台重新开始。项目里的 CLAUDE.md 和自动记忆不会因此消失。

一个是压缩留用，一个是清空重开，别把它们混在一起。

## Scene 05｜什么时候压缩，什么时候清空？

判断其实很简单。

任务还没有完成，而且前面的架构决定、接口格式或整体结论后面还要用，就用 `/compact`，把重要内容留下来。

如果已经切换到完全无关的工作，或者旧上下文污染得太重，就用 `/clear`。

如果你连这次会话留下的痕迹都不想保留，那就退出后直接重新启动 Claude，获得一张更干净的工作台。

记住：同一个问题纠正两遍还不对，就别一直耗在原来的上下文里。

## Scene 06｜用 `/context` 和 `/usage` 盯住用量

别只凭感觉判断工作台是不是快满了。

`/context` 看的是，工作台究竟被什么占了。你可以看到系统提示、CLAUDE.md、MCP、对话历史等分类的实时占用，以及优化建议。

`/usage` 看的是，这次会话已经用了多少 token、持续了多久，以及本地估算的成本。

所以，一个回答“占了什么”，另一个回答“烧了多少”。

开始大任务前先运行一次 `/context`，比等到模型开始失忆再猜原因更可靠。

## Scene 07｜auto-compact 会保命，但别依赖它

当上下文快要顶到窗口上限时，Claude Code 会自动压缩对话历史，腾出空间继续工作。

这就是 auto-compact，它像流水线快堆满时的自动卸料，确实能避免直接撞上上限。

但它更像一个被动的保命机制。触发时机不由你决定，可能正好打断关键步骤；而且它没有听到你的保留指令，未必知道哪些内容对你最重要。

更稳妥的做法，是在占用偏高时主动运行 `/compact`，明确告诉它保留什么。也可以把压缩偏好写进 CLAUDE.md，让压缩优先留下测试结果、代码变更或已经确认的方案。

## Scene 08｜五个从源头省 token 的习惯

清理工作台是补救，少让它堆满才是预防。

第一，学习和试验时用只有三五个文件的玩具项目。

第二，提需求时用 `@` 精准指向文件，不要让一个模糊请求触发整个仓库的扫描。

第三，不要一次塞进五个不相关的需求，把它们拆成几次小提问。

第四，长任务分成相对独立的阶段，做完一段就 `/compact`，切换无关部分就 `/clear`。

第五，把测试、翻长日志和查文档这类冗长工作交给子代理，让它在自己的工作台里处理，只把结论摘要带回来。

## Scene 09｜三步亲眼验证压缩效果

你可以做一个最小实验，亲眼看到上下文怎么涨、又怎么被压回去。

第一步，启动 Claude 后先运行 `/context`，记下还没聊天时的初始占用。

第二步，让它读几个文件、聊几轮，再运行一次 `/context`，观察对话历史和文件占用变大。

第三步运行：`/compact 保留这个项目的整体结构结论，丢掉逐个文件的原始内容`，然后再跑一次 `/context`。

如果对话历史的占用下降，而整体结构结论还在，就说明压缩起作用了。

## Scene 10｜把注意力留给真正重要的任务

现在把整篇内容收成几句话。

上下文窗口是一张有限工作台，塞满之后可能出现变慢、变笼统、前后矛盾和反复询问。

任务没完成且前文有用，用 `/compact`；切换无关工作或污染太重，用 `/clear`；用 `/context` 看占用构成，用 `/usage` 看会话消耗。

更重要的是，从一开始就少读文件、拆小任务、分阶段清理，把冗长输出交给子代理。

管理上下文的本质只有一句话：把 Claude 有限的注意力，省着用在真正要紧的事情上。
