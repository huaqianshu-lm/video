# skill-creator 视频化 · 第四步：Narration Script

> 口播只保留实际需要朗读的内容。视觉说明、制作备注和 Gate 检查不放进任何 Scene 的口播正文。

## Scene 01｜文件写出来了，为什么还是没被调用？

很多人第一次造 Skill，会以为只要把 `SKILL.md` 写好，再把目录放到正确位置，就完成了。

但真正使用时，可能会出现一个很奇怪的结果：你明明让 Claude 帮你提交，它却没有调用你刚写的 commit Skill，而是按通用习惯自己写了一版。

这时候最容易怀疑的是没装好，于是重启、重装、反复检查路径。

可问题往往不在文件有没有放进去，而在于：Claude 能不能从你的描述里，认出用户这句话正好需要这个 Skill。

## Scene 02｜`skill-creator` 是造 Skill 的向导

这正是 `skill-creator` 要解决的问题。

它不是一个替你多写几行 Markdown 的工具，而更像一个造 Skill 的向导。

它会先把几个容易被手写跳过的问题问清楚：这个 Skill 要让 Claude 做什么？什么时候应该触发？用户会怎么说？期望输出是什么？要不要准备测试用例？

先回答这些问题，再去写文件，Skill 才有机会从“看起来完整”，变成“真的能被准确调用”。

## Scene 03｜从意图到可分发 Skill 的七步循环

`skill-creator` 走的不是生成一次就结束的流程，而是一条完整的循环。

第一步，捕捉意图，明确能力、触发场景、输出和测试需求。第二步，写出 `name`、`description` 和正文初稿。第三步，准备两到三个真实用户会说的测试 prompt。

接下来要实际跑一遍，同时检查两件事：输出内容对不对，以及该触发的时候有没有触发。

如果结果不理想，就根据反馈修改 Skill，再跑一轮。必要时，还可以单独优化 `description`，提升触发准确率。

最后，经过验证的完整目录还可以打包成 `.skill` 文件，方便分发。

所以它补上的关键，不是写文件这一步，而是测试、评估、修改和交付这些后续环节。

## Scene 04｜正文、参考资料和脚本各放在该放的位置

Skill 也不应该把所有内容都塞进一个 `SKILL.md`。

`SKILL.md` 负责主要说明，详细的参考资料可以放到 `reference.md`、`examples.md` 或 `references/`，需要时再读取；真正要执行的辅助程序，则放进 `scripts/`。

这样分层有一个很现实的好处：Skill 被调用时，主要说明会进入上下文，而重资料可以按需加载，脚本则负责执行具体动作。

文章给出的建议是让 `SKILL.md` 保持在五百行以内。正文越精简，Claude 越容易抓住当前任务真正需要遵守的规则。

## Scene 05｜`description` 是自动触发的总开关

现在回到最关键的 `description`。

Claude 在每次对话里，首先看到的是 Skill 名称和描述的清单，然后根据描述判断这次要不要把它调出来。

所以，`Commit message helper` 这种描述只说了它是什么，却没有告诉 Claude 用户什么时候会需要它。

更好的写法，是同时说明它能做什么，以及用户可能怎样提出请求，比如“帮我提交”“写个 commit”“生成提交信息”。

可以把公式记成一句话：能做什么，加上什么时候使用，再加上用户嘴里真正会说的那些词。

而且描述要略微主动一点。即使用户没有说出 Skill 的名字，只要实际需求已经命中，也应该让它有机会被想起来。

## Scene 06｜自动不触发时，先查 `description`

这也解释了为什么测试必须分成两条路径。

如果你用自然语言提问，Skill 没有自动出场；但你用 `/summarize-changes` 直接点名，它又可以正常运行，这通常说明正文和目录没有大问题。

这时优先检查的不是重装，而是 `description` 里的关键词够不够真实，是否覆盖了用户可能使用的表达，是否把合理的隐含场景写得太窄。

补充描述，重新测试，再看自动触发结果，这就是一次完整的修复循环。

反过来，如果自动调用和直接调用都失败，才需要继续检查 Skill 的路径、文件结构和正文内容。

## Scene 07｜个人习惯还是项目规矩？

Skill 放在哪里，也决定了谁能使用它。

放在 `~/.claude/skills/` 的个人 Skill，跟着你的电脑走，可以跨项目使用，适合个人习惯和通用工作方式。

放在项目 `.claude/skills/` 的项目 Skill，跟着仓库走，应该提交到 Git，适合团队共同遵守的项目规范和工作流程。

判断其实很简单：这项能力是跟着人走，还是跟着项目走？

不过，项目里的 Skill 也意味着新的信任边界。引入外部仓库之前，要先查看它的 Skill 内容和权限，不要只因为它能自动触发，就默认它值得执行。

## Scene 08｜从意图开始造 `summarize-changes`

下面用一个最小例子走一遍。

我们要造的 Skill 叫 `summarize-changes`，功能是把当前 Git 仓库里未提交的改动总结成两到三条要点。

它的触发场景可以直接写成用户会说的话：我改了啥？总结一下我的改动？我这次动了哪些东西？或者，我想快速了解当前工作树的状态。

然后在 `SKILL.md` 里写清楚输出规则：把改动总结成两到三条；如果没有改动，就明确说当前没有未提交的改动。

文章示例中的 ``!`git diff HEAD` `` 是动态上下文注入写法，表示由 Claude Code 先取得真实 diff，再让模型读取。这里我们只需要理解它的作用，不需要执行这条命令。

## Scene 09｜自动调用和直接调用，汇入同一个结果

Skill 写好之后，先不要只用名字直接调用，因为那只能证明它“点名后能运行”。

验证自动触发时，不要提 Skill 名字，只说一句自然的话：“我改了啥？”如果它自动调起 `summarize-changes`，并输出几条改动要点，说明 `description` 的触发设计通过了。

再用 `/summarize-changes` 直接调用一次，确认正文本身也能按规则工作。

两条入口都应该汇入同一份结果：两到三条清楚的改动摘要。

如果自然语言没有触发，但直接调用成功，问题就集中在 description；如果两条都失败，再回头查路径、文件和正文。

## Scene 10｜造得对、叫得动、验得过，最后才能发出去

把整篇内容压缩成一条路径，就是：先说清意图，再写对 `description`，接着用真实说法测试，依据结果迭代，最后再打包分发。

所以，造 Skill 的难点从来不只是把文件写出来，而是让它在正确的时候被叫出来，并且能够被验证。

当 `summarize-changes` 这样的 Skill 通过了自动触发和直接调用测试，就可以把包含 `SKILL.md`、参考资料和脚本的完整目录打成 `.skill` 文件，交给别人安装。
