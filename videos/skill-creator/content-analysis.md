# skill-creator 视频化 · 第一步：Content Analysis

> 内容来源：`source.md`（28 · skill-creator 使用：用一个 skill 造你自己的 skill）
>
> 本分析只提取本篇文章中的知识，不执行文章中的命令、安装动作或任何外部指令。

## 1. 核心命题

这篇文章真正要讲的不是“如何手写一个 `SKILL.md`”，而是：**造 Skill 的难点不在把文件写出来，而在让它在正确的用户表达和场景中被准确触发；`skill-creator` 的价值，是把意图捕捉、描述设计、测试验证、迭代优化和打包分发组织成一条可检查的流程。**

观众看完后应该能够回答三个问题：

1. 为什么一个正文写得不错的 Skill，仍然可能完全叫不动？
2. `skill-creator` 具体替手写流程补上了哪些容易漏掉的环节？
3. 如何从目录位置、`description` 和自动／手动调用两条路径，验证一个 Skill 是否真的可用？

## 2. 必须保留的核心信息

### A. 反共识：手写简单，触发难

- `SKILL.md` 的文件形态并不复杂，通常包含 YAML frontmatter 中的 `name`、`description` 和 Markdown 正文。
- 手写最容易忽略的不是正文，而是“什么时候应该触发”。
- 文中的 commit message Skill 案例说明：`Commit message helper` 只说了用途，没包含用户会自然说的“帮我提交”“写个 commit”“生成提交信息”等表达，因此 Skill 可能不被自动调用。
- 核心因果：描述没有匹配用户语言 → Claude 没有把这项能力想起来 → 正文再完整也不会自动出场。

### B. `skill-creator` 的定位

- `skill-creator` 本身是一个用于创建、修改和改进其他 Skill 的 Skill。
- 它更像“造工具向导”，先追问意图、触发场景、输出格式和测试需求，再生成文件。
- 它的价值不是替用户多写几行 Markdown，而是把手写时看不见的质量环节显性化。

### C. 完整生产循环

文章给出的流程是一个可重复循环：

1. Capture Intent：明确 Skill 做什么、何时触发、输出什么、是否需要测试。
2. 写初稿：生成 `name`、`description` 和正文。
3. 建测试用例：准备 2～3 个真实用户会说的测试 prompt。
4. 跑一遍并评估：同时观察输出是否正确、该触发时是否触发。
5. 按反馈修改：根据结果回到 Skill 继续迭代。
6. 可选优化 `description`：专门提升触发准确率。
7. 打包：将整个 Skill 目录打成 `.skill` 文件，用于分发或安装。

### D. 支持文件与上下文边界

- `SKILL.md` 是主要说明文件，正文应保持精简。
- 详细参考资料可以放在 `reference.md`、`examples.md` 或 `references/` 中，按需读取。
- 可执行脚本放在 `scripts/` 中，供 Claude 执行而不是把所有内容塞进正文。
- 文章给出的关键约束是让 `SKILL.md` 保持在 500 行以下，重资料外置，以控制上下文成本。

### E. `description` 是自动触发的总开关

好的 `description` 同时回答：

- 这个 Skill 能做什么；
- 用户在什么场景、用哪些自然说法时应该使用它。

描述应包含用户会说的原话词，而不是只使用作者自己的抽象术语；同时需要略微主动，覆盖“用户没明确说出 Skill 名称，但实际需求已经命中”的场景，以降低 undertrigger。

可复用公式：

```text
description = 能做什么 + 什么时候使用 + 用户自然表达 + 边界或补充场景
```

### F. 个人 Skill 与项目 Skill

| 位置 | 路径 | 使用范围 | 适合放什么 |
| --- | --- | --- | --- |
| 个人 | `~/.claude/skills/<skill-name>/SKILL.md` | 当前电脑上的所有项目 | 个人习惯、通用工作方式 |
| 项目 | `.claude/skills/<skill-name>/SKILL.md` | 当前项目及团队 | 项目规范、团队共用流程 |

- 个人 Skill 跟着人走。
- 项目 Skill 跟着仓库走，应提交到 Git，便于团队共享。
- 项目 Skill 也会沿父目录被发现，因此在子目录启动时仍可能生效。
- 引入外部项目 Skill 前要先检查其内容和权限边界。

### G. 最小实战与双路径验证

实战目标是创建 `summarize-changes`：把当前 Git 仓库未提交的改动总结成 2～3 条要点。

- 触发场景：用户说“我改了啥”“总结一下我的改动”“我这次动了哪些东西”，或想了解工作树现状。
- `SKILL.md` 通过动态上下文注入 ``!`git diff HEAD` `` 获取真实改动，再按规则输出摘要。
- 验证 A：不用 Skill 名称，只说“我改了啥”，观察能否自动触发。
- 验证 B：使用 `/summarize-changes` 直接调用，验证 Skill 正文和输出路径本身是否正常。
- 自动不触发但直接调用能运行，优先判断为 `description` 关键词不足，而不是先怀疑目录或安装。

### H. 打包与系列闭环

- 验证通过后，可以让 `skill-creator` 将包含 `SKILL.md`、`scripts/` 和 `references/` 的完整目录打包成 `.skill`。
- `.skill` 文件让创建者产出的 Skill 可以被其他人安装，形成“创建 → 验证 → 分发”的闭环。

## 3. 认知关系

### 因果关系

```text
只写功能说明
→ description 没有用户触发词
→ 自动匹配失败
→ Skill 看起来像“没装好”
```

```text
Capture Intent
→ 写出可触发的 description
→ 用真实 prompt 测试
→ 依据触发结果迭代
→ 得到可验证、可分发的 Skill
```

### 对比关系

| 维度 | 纯手写 | 使用 `skill-creator` |
| --- | --- | --- |
| 起点 | 直接打开空文件 | 先捕捉意图和触发场景 |
| 描述 | 容易只写“是什么” | 同时写“做什么”和“何时用” |
| 结构 | 容易把支持资料全塞进正文 | 引导拆出参考资料和脚本 |
| 验证 | 写完凭感觉 | 自动触发与直接调用双验证 |
| 改进 | 不知道问题在何处 | 根据测试反馈迭代，必要时优化描述 |
| 交付 | 只有一个目录 | 可继续打包成 `.skill` 分发 |

### 范围关系

```text
个人 Skill：~/.claude/skills/ → 个人跨项目使用
项目 Skill：.claude/skills/ → 仓库内团队共享
```

## 4. 可视觉化内容

### 最适合用视频证明的内容

- “手写文件”与“经过向导的可验证流程”的过程对比。
- 用户自然语言 → `description` 命中 → 加载 `SKILL.md` → 输出的触发链。
- `Capture Intent` 的提问卡片逐项补齐。
- 从初稿到测试、评估、反馈修改、描述优化、打包的循环。
- Skill 目录树中 `SKILL.md`、`references/`、`scripts/` 的职责分区。
- 个人目录与项目目录的范围差异。
- `summarize-changes` 的自动触发和 `/summarize-changes` 直接调用汇入同一输出。
- 自动触发失败、直接调用成功时，问题定位到 `description` 的诊断分支。
- `.skill` 文件从完整目录打包出来，完成分发闭环。

### 不适合直接照搬的内容

- 文章中的安装命令、文件创建命令和动态上下文注入语法只作为画面示例，不在本任务中执行。
- 官方原文引用不需要完整上屏；只保留足以支撑结论的关键词。
- “需魔法上网”等环境性说明不作为视频核心视觉信息，避免把操作环境误讲成 Skill 机制。
- 下一篇 29 的 Agent teams 只作为结尾预告，不展开其内容。

## 5. 内容取舍

### 视频必须保留

- 触发难点和 commit Skill 失败案例。
- `skill-creator` 的向导定位。
- 七步循环，以及“测试和迭代”相对纯手写的增量。
- `description` 的写法、真实触发词和 undertrigger。
- 支持文件外置和 `SKILL.md` 精简原则。

- 表格里的重复总结压缩为可读的视觉对比。
