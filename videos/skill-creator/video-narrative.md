# skill-creator 视频化 · 第二步：Video Narrative

> 叙事目标：让观众先感受到“Skill 为什么叫不动”，再理解 `skill-creator` 如何把触发设计、结构组织和验证迭代变成一条完整流程，最后用一个最小 Skill 实战证明这套方法。

## 1. 视频的叙事目标

观众一开始不需要先知道 `skill-creator` 是什么，而要先遇到一个看似合理却失败的结果：文件写好了，用户一说“帮我提交”，Skill 却没有出场。这个失败把问题从“会不会写 Markdown”转成“能不能被准确触发”。

随后视频给出 `skill-creator` 的真正价值：它像一个向导，先问清楚能力、触发场景、输出和测试，再让 Skill 经过测试、反馈和迭代。观众在理解机制后，才进入两个落地问题：资料放在哪里，以及怎样验证自动触发确实成功。

最终通过 `summarize-changes` 的最小实战完成闭环：写入真实用户说法，分别用自然语言和 `/` 直接调用验证，自动触发失败时定位到 `description`，最后把通过验证的目录打包成 `.skill` 分发。

## 2. 叙事原则

- 先展示“叫不动”的结果，再解释 `description` 的机制。
- 先建立“向导会追问和检查”的直觉，再展示完整七步流程。
- 声音解释为什么会失败，画面展示匹配、目录、分支和状态变化。
- 个人／项目目录放在结构已经建立之后，作为“谁能用”的范围决策。
- 实战不从空文件堆代码，而从意图和触发句开始，突出方法的改变。
- 结尾同时收束“造得对、叫得动、验得过、发得出”四个结果，并保留当前文章给出的 29 篇系列预告。

## 3. 整体叙事结构

| 段落 | Scene | 认知任务 | 叙事推进 |
| --- | --- | --- | --- |
| 问题钩子 | 01 | 让观众看到手写 Skill 可能完全不触发 | 从“文件存在”转向“能力没被叫出来” |
| 机制发现 | 02～03 | 解释 `skill-creator` 的向导定位与 Capture Intent | 从失败转向可控的起点 |
| 方法展开 | 04～06 | 展示七步循环、结构分层和 description 写法 | 从会写文件转向会设计触发和验证 |
| 范围与落地 | 07 | 判断个人 Skill 与项目 Skill 的位置 | 从“怎么造”进入“谁能用” |
| 实战验证 | 08～09 | 创建并验证 `summarize-changes` | 用两条入口证明规则真的工作 |
| 交付收束 | 10 | 打包、分发、总结和系列预告 | 从一次 Skill 走向可复用工具链 |

## 4. 第一段：先看见“写好了却叫不动”

### Scene 01｜文件写出来了，为什么还是没被调用？

开场用一个极简的失败演示：左侧是已经存在的 `SKILL.md`，右侧是用户说“帮我提交”，系统却走了通用路径，没有调用这个 Skill。把“装没装好”的直觉疑问停住，留下核心问题：真正的故障可能在 `description`。

这一幕不先讲完整定义，只让观众理解“文件存在”和“能力被匹配”是两回事。

### Scene 02｜`skill-creator` 是造 Skill 的向导

把 `skill-creator` 放到失败问题的答案位置：它不是替用户多打一份 Markdown，而是像向导一样先追问需求。画面出现四个问题：能干什么、何时触发、输出什么、要不要测试。

认知变化是：造 Skill 不是从空白文件开始，而是从可检查的意图开始。

## 5. 第二段：把隐形工作变成流程

### Scene 03｜从意图到可分发 Skill 的七步循环

用一条有回环的生产轨道展示：Capture Intent → 写初稿 → 建测试 → 跑一遍评估 → 按反馈修改 → 优化 description → 打包。关键转折是“跑测试”和“按反馈再改”会回到 Skill，而不是生成文件后就结束。

这一幕回答 `skill-creator` 比纯手写多做了什么，但不在此处逐条解释字段细节。

### Scene 04｜正文、参考资料和脚本各放在该放的位置

将一个 Skill 目录展开为 `SKILL.md`、`reference.md`、`examples.md` 和 `scripts/helper.py`。声音解释“正文保持精简、重资料按需读取、脚本负责执行”，画面通过上下文层级和文件职责分区建立直觉。

这一幕把“可维护性”和“上下文成本”联系起来，避免观众把所有材料都堆进 `SKILL.md`。

### Scene 05｜`description` 是自动触发的总开关

先把 `Commit message helper` 标成“只说是什么”，再替换成包含“帮我提交”“写个 commit”“生成提交信息”等用户原话的描述。随后用自然语言输入扫描多个 Skill，连线命中目标 Skill。

声音给出可复用公式：能做什么 + 什么时候使用 + 用户自然表达；画面突出“触发词来自用户嘴里，而不是作者脑中的术语”。

### Scene 06｜自动不触发时，先查 description

制造一个诊断分支：自动问法没有命中，但 `/summarize-changes` 直接调用成功。画面将结果归因到“关键词不足”，再显示“补充触发词、加入没明说名称但实际命中的场景、重新测试”的回路。

这一幕把 undertrigger 变成可观察、可修复的问题，不把失败笼统归因于安装或系统故障。

## 6. 第三段：确定 Skill 的作用范围

### Scene 07｜个人习惯还是项目规矩？

左右对比 `~/.claude/skills/<skill-name>/` 与 `.claude/skills/<skill-name>/`：前者跨项目跟着个人走，后者跟着仓库走并通过 Git 与团队共享。最后加上外部项目 Skill 的信任检查提醒。

这一幕的结论不是“哪个目录更好”，而是让观众用“跟着人走还是跟着项目走”做选择。

## 7. 第四段：用最小实战验证方法

### Scene 08｜从意图开始造 `summarize-changes`

把实战目标明确为“总结当前 Git 仓库未提交改动”，先展示三类触发说法，再出现 `summarize-changes` 的目录和 `SKILL.md`。动态上下文注入 ``!`git diff HEAD` `` 只作为文章中的机制示例显示，不执行命令。

声音解释：好的 Skill 不是只写“总结改动”，而是把真实用户表达和期望输出一起写进设计。

### Scene 09｜自动调用和直接调用，汇入同一个结果

左路使用“我改了啥？”测试自动触发，右路使用 `/summarize-changes` 直接调用，两路都汇入“2～3 条改动要点”。再用一个小分支说明：A 失败、B 成功时，优先回到 `description` 优化；A、B 都失败才继续检查路径和正文。

这一幕是整条视频的验证证据，证明“触发设计”与“Skill 正文可运行”是两个需要分别检查的层次。

## 8. 第五段：交付和认知收束

### Scene 10｜造得对、叫得动、验得过，最后才能发出去

先把完整目录压缩成一个 `.skill` 文件，再用四个节点回顾：意图 → description → 测试 → 分发。最后停留在文章给出的下一篇预告“29「Agent teams 智能体团队」”，只说明系列从单个 Skill 继续走向更复杂的协作主题，不展开下一篇内容。

## 9. 叙事节奏

| 节点 | 情绪／认知状态 | 画面节奏 |
| --- | --- | --- |
| 01 | 困惑：文件存在却没触发 | 快速展示输入与错误路径 |
| 02～03 | 释然：原来可以先问清楚再造 | 问题卡片逐项出现，流程轨道展开 |
| 04～06 | 掌握：结构、描述和诊断都有方法 | 目录展开、关键词命中、失败分支回溯 |
| 07 | 判断：选择个人还是项目范围 | 稳定左右对比，降低动画速度 |
| 08～09 | 验证：真实 prompt 走通两条入口 | 输入、命中、输出连续推进 |
| 10 | 收束：从一次创建到可分发工具 | 流程压缩、打包完成、预告停留 |

## 10. 画面文字边界

所有画面文字都来自本篇 `source.md` 或由其直接压缩而来，包括：`SKILL.md`、`description`、`Capture Intent`、`references/`、`scripts/`、`~/.claude/skills/`、`.claude/skills/`、`summarize-changes`、`/summarize-changes`、`!\`git diff HEAD\``、`.skill` 和下一篇 29 预告。原文中的命令只作为画面示例，不在本任务中执行。
