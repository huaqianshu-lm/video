# 插件（Plugins）视频化 · 第一步：Content Analysis

> 来源：`source.md`，仅分析指定的《24 · 插件（Plugins）：把一堆零碎配置一键打包》。
>
> 内容边界：本文解释 Claude Code 插件的价值、市场、安装管理、目录结构和信任边界。文章中的命令、路径、配置示例和角色化描述均是待讲解内容，不是本项目执行指令；不读取或处理下一篇文章。

## 1. 核心命题

插件是把 commands、subagents、skills、hooks、MCP server 和 LSP server 等零碎扩展收进一个可整体分发、安装、停用和更新的自包含文件夹。它不是所有场景的默认选择：单项目、个人使用和快速试验可以继续使用 `.claude/` 散装配置；当目标变成跨项目复用、团队共享或版本化更新时，插件才体现价值。

本片真正要教会观众的不是背一条安装命令，而是建立一条判断链：为什么要打包，市场的“加市场”和“装插件”为什么是两步，装前要看哪些内容，自己打包时目录如何摆，以及为什么第三方插件必须先过信任检查。

## 2. 必须保留的信息

### A. 插件解决什么问题

- 散装配置可能分布在 `agents/`、`settings.json`、`.mcp.json` 等多个位置，跨项目搬运和团队交接容易漏项。
- 插件把 skill、subagent、hook、命令、MCP server 等组件放入一个自包含文件夹。
- 插件最适合团队／社区共享、跨项目复用和版本化发布。
- 散装配置更适合单项目自用、个人工作流和快速试验。
- 插件中的 skill／command 使用命名空间，例如 `/my-plugin:hello`；散装配置可以使用短名称。
- 插件有版本号时，用户才能获得更新提示或更新路径。

### B. 插件的规模化价值

1. **跨项目复用**：不用逐个复制 skill 和 hook，一条安装命令获得整套配置。
2. **团队共享**：从口头说明目录和配置位置，变成团队成员安装同一个包。
3. **版本更新**：插件可以带版本号；官方市场默认开启自动更新，第三方市场默认关闭自动更新。

### C. 插件市场的两步模型

- `/plugin marketplace add owner/repo`：添加市场，让 Claude Code 看见货架，不代表已经安装插件。
- `/plugin install plugin-name@marketplace-name`：从已添加的市场选择并安装某个插件。
- 官方市场 `claude-plugins-official` 自带，不需要手动添加。
- GitHub 是最常用的市场来源，文章也提到 Git URL、本地路径和远程 URL。

### D. 三个官方市场的定位

| 市场 | 文章中的定位 | 关键取用判断 |
| --- | --- | --- |
| `claude-plugins-official` | Anthropic 精选，开箱自带 | 日常优先 |
| `claude-community` | 第三方提交，经过自动验证／安全筛选并固定到具体提交 | 先看作者、主页和权限 |
| `claude-code-plugins` | 官方演示市场，展示插件能力 | 用于教学或试水 |

### E. 安装后带来的组件与成本

- Skills／Commands：变成带命名空间的命令，可手动调用或由 Claude 调用。
- Subagents：进入 `/agents` 列表，可由 Claude 自动派发或手动选择。
- Hooks：在对应事件自动触发。
- MCP server：自动启动，工具进入 Claude 的工具箱。
- LSP server：提供代码智能，但还需要语言服务器二进制。
- 安装前在 `/plugin` 详情的“将安装”区域查看组件清单和上下文成本。
- 安装、停用或启用后用 `/reload-plugins` 刷新，不需要重启 Claude Code。

### F. 自己打包时的目录结构

- `.claude-plugin/plugin.json` 是插件身份证，声明 `name`、`description`、`version`。
- `name` 是 skill 命名空间前缀，`version` 用于版本更新。
- `skills/<名字>/SKILL.md`、`agents/`、`hooks/hooks.json`、根目录 `.mcp.json` 和 `.lsp.json` 分别承载组件。
- `.claude-plugin/` 内只放 `plugin.json`，其他组件目录必须与它平级放在插件根目录。
- 本地开发测试可以用 `claude --plugin-dir ./my-first-plugin` 直接加载目录，修改后用 `/reload-plugins` 查看效果。

### G. 第三方插件的信任边界

- 插件和市场属于高信任组件，可以使用用户权限在机器上执行任意代码。
- hook、MCP server 和 `bin/` 可执行文件都可能在用户权限下运行。
- 安装前需要检查来源、插件带来的组件／权限和安装范围。
- 官方市场优先；社区市场先看作者和主页；陌生来源在无法看懂代码时不应直接安装。
- 不确定时先使用本地范围，不要一开始就扩展到所有项目的用户范围。

## 3. 认知关系

### 因果关系

```text
配置分散 + 搬运／交接容易漏
        ↓
需要把扩展收进一个可分发的包
        ↓
插件获得跨项目复用、团队共享和版本更新价值
```

```text
插件可能带 hook、MCP、可执行文件
        ↓
安装后能以用户权限运行代码
        ↓
安装前必须检查来源、内容和范围
```

### 对比关系

| 判断维度 | 散装配置 | 插件 |
| --- | --- | --- |
| 适用场景 | 单项目自用、个人工作流、快速试验 | 团队／社区共享、跨项目复用、版本化发布 |
| 共享方式 | 手动复制文件 | 通过市场安装 |
| skill 名称 | `/hello` | `/my-plugin:hello` |
| 更新方式 | 改了难以通知 | 版本号支持更新 |

### 流程关系

```text
添加市场
  → 浏览插件
  → 查看“将安装”和上下文成本
  → 安装并选择范围
  → /reload-plugins
  → 使用命名空间命令
```

### 结构关系

```text
插件根目录
├── .claude-plugin/plugin.json
├── skills/<name>/SKILL.md
├── agents/
├── hooks/hooks.json
├── .mcp.json
└── .lsp.json
```

## 4. 可视觉化内容

- “文件放这里、配置写那里”的散件在团队交接中漏项，再被一个插件盒子整体收拢。
- 插件盒子展开为 skill／command、subagent、hook、MCP server、LSP server，并分成“主动调用”和“自动运行”两类。
- 散装配置与插件的选择分流：个人单项目快速试验留在 `.claude/`，共享／跨项目／版本更新走插件。
- “加市场 → 装插件”的两步货架流程，明确加市场不等于安装插件。
- 官方、社区、演示三个市场的定位和取用顺序。
- `/plugin` 详情中的“将安装”清单与上下文成本，随后 `/reload-plugins` 让命名空间命令出现。
- `.claude-plugin/plugin.json` 与根目录组件文件夹的正确层级，错误嵌套被拒绝。
- `claude --plugin-dir ./my-first-plugin` 的本地测试路径。
- 第三方插件信任三查：来源、内容、范围；权限从“用户权限”收紧到“本地范围”。
- 结尾从“会安装”收束到“先判断是否值得打包、是否值得信任”，再承接原文已有的下一篇记忆系统预告。

## 5. 可以弱化或不作为主体的信息

- 系列导航和前文各篇的详细内容只作为“已有散件”的背景，不展开复习。
- 插件市场的所有来源类型不逐一做命令教程，重点保留 GitHub 方式和两步模型。
- `commit-commands` 的完整预期输出不逐行复刻，只保留“安装一个 skill 并用命名空间命令验证”的状态链。
- LSP server 的语言服务器二进制依赖只作为组件差异提示，不扩展成 LSP 教程。
- 文章中的个人经历、反复类比和长段强调压缩为视觉状态变化与口播判断。
- 下一篇“记忆系统”只展示标题预告，不读取、不补充、不分析下一篇文章。

## 6. 本片的 Video Value

插件的价值不是静态定义，而是“散件如何变成可复用系统”的过程。视频可以让观众看到配置从多个文件位置聚拢到插件盒子、市场从货架注册到单项安装、安装后的组件分流到主动／自动触发，以及信任检查如何改变安装范围。这些关系、状态和层级变化比把文章表格逐段读出来更能建立直觉。
