# Claude Code「第一次使用」视频化 · 第三步：Scene Script

> 结构基线：沿用 `videos/claude-code-what-is/scene-script.md` 的 Scene 字段职责；本片按视觉事件拆为 9 幕。

## Scene 01｜终端打开了，然后呢？

### 目的

把第一次使用时“不知道下一步敲什么”的紧张具体化，让观众进入问题。

### 口播方向

前面已经装好、登录、选好套餐，但终端真正打开后，很多人会盯着光标发愣，担心一句话说错就把代码搞坏。今天只走最简单的一遍，五分钟拿到第一次成功。

### 画面

深色终端全屏，光标闪烁，输入区只有一个空提示；旁边浮出“然后呢？”和“怕改坏”的低调提示。画面从紧张停顿转为一张小卡片：“今天：跑通第一个任务”。

### 屏幕重点

`终端打开了，然后呢？`、`跑通第一个任务`、`不超过五分钟`

### Scene Type

`OpeningScene`

### Video Value

把抽象的“新手焦虑”转成可见状态，建立观看动机，并承诺一条短而清晰的成功路径。

## Scene 02｜先建一个可以重来的玩具项目

### 目的

解释为什么第一次不要直接拿正式项目练手，并创建最小练习场。

### 口播方向

正式项目文件多、依赖杂，第一次不容易看懂 Claude 做了什么。先建一个可重建的 `hello-claude`，里面只有几行 `main.py`，改砸了也能重来。

### 画面

左侧是“正式项目”的复杂文件树并降低透明度，右侧是干净的 `hello-claude` 文件夹。终端依次输入 `mkdir hello-claude`、`cd hello-claude`，随后生成 `main.py`，代码只保留 `add(a, b)`。

### 屏幕重点

`练车场：hello-claude`、`main.py`、`def add(a, b):`

### Scene Type

`TerminalScene`

### Video Value

把“降低风险”变成明确的文件范围，避免观众把第一次实验误投到正式项目。

## Scene 03｜一定要在项目目录里启动

### 目的

建立工作区边界：启动位置决定 Claude Code 先看到哪里。

### 口播方向

项目建好后，要在同一个文件夹里运行 `claude`。不要在桌面或主目录裸启；你在哪儿启动，它就把哪儿当工作区。

### 画面

终端路径从 `~/` 切换到 `~/hello-claude`，错误启动路径被淡化，正确路径高亮；输入 `claude` 后，工作区边框锁定 `hello-claude/main.py`。

### 屏幕重点

`当前目录 = 工作区`、`~/hello-claude $ claude`、`main.py`

### Scene Type

`TerminalScene`

### Video Value

让观众理解“目录不是装饰，而是上下文边界”，提前消除第一次使用最常见的路径错误。

## Scene 04｜欢迎屏幕先认住三样东西

### 目的

降低欢迎屏幕的信息压力，只保留第一次开工所需的入口。

### 口播方向

启动后不用研究整个界面，先认住底部输入框、`/help` 和 `/resume`。输入框就是主战场，用大白话说需求即可。

### 画面

模拟 Claude 欢迎屏幕：会话信息和更新提示作为背景，底部输入框用主色高亮；`/help` 标为“查看命令”，`/resume` 标为“继续会话，第一次先不管”。

### 屏幕重点

`输入框`、`/help`、`/resume`、`用大白话提需求`

### Scene Type

`ConceptScene`

### Video Value

把欢迎屏幕从“复杂界面”压缩为三个可识别入口，为第一条自然语言指令做准备。

## Scene 05｜先让 Claude 读懂，再让它动手

### 目的

用只读解释任务验证 Claude 真的读到了 `main.py`，并区分解释型与修改型任务。

### 口播方向

第一个真正任务不要直接让它改代码，先输入“解释 `main.py`”。它应该说明 `add` 接收两个参数并返回相加结果。解释型任务不动文件，是最适合第一次试水的动作。

### 画面

左侧输入框出现解释请求，右侧 `main.py` 被扫描但保持“未修改”状态；下方返回 `add` 函数的简短解释。画面底部出现三个标签：`解释型：只读`、`修改型：需批准`、`生成型：需批准`。

### 屏幕重点

`解释 main.py 这个文件在做什么`、`add(a, b)`、`只读验证`

### Scene Type

`ConceptScene`

### Video Value

先给观众一个零风险成功信号：Claude 读到了真实文件，且没有在没有许可时改动它。

## Scene 06｜看懂 diff，再批准改动

### 目的

呈现第一次真实人机协作：Claude 提出修改，人看 diff 并决定是否落盘。

### 口播方向

接着让它给函数增加类型注解和基本错误处理。Claude 会找到文件、展示 diff、停下来等批准；第一次只同意这一处，不要急着开启全部接受。

### 画面

终端请求进入“待批准”状态。`main.py` 的旧版本与新版本左右并排，红色 `-` 和绿色 `+` 清楚显示；下方出现 `同意 / Yes`、`本次会话不再问`、`拒绝 / No`。点击语义用高亮表示“同意一次”，文件状态变为 `Updated`。

### 屏幕重点

`给这个函数增加类型注解，并补充基本的错误处理`、`- 旧行`、`+ 新行`、`等待批准`

### Scene Type

`ComparisonScene`

### Video Value

把“AI 会改代码”具体化为“AI 提出候选，人负责确认”，建立全片最重要的安全和协作模型。

## Scene 07｜改错了，还有两条后悔药

### 目的

回答观众对批准改动后的担心，建立可恢复边界。

### 口播方向

不满意可以直接说“改回去”，也可以用 `/rewind` 或空输入框双击 Esc 打开回溯菜单。Checkpoint 是本地撤销，不等于 Git 的永久历史。

### 画面

左侧显示“当前修改”，一条回退箭头分成两条路径：`改回去` 和 `/rewind`。右侧是 Checkpoint 卡片，底部单独放一条边界说明：`Checkpoint = 本地撤销`、`Git = 永久历史`。输入框中有文字时，双击 Esc 的提示被标记为“先清空输入”。

### 屏幕重点

`改回去`、`/rewind`、`Checkpoint`、`本地撤销 ≠ Git 历史`

### Scene Type

`ComparisonScene`

### Video Value

把“批准”与“不可逆”区分开，减少第一次操作的心理风险，同时不把检查点夸大成版本控制。

## Scene 08｜五步跑通第一个任务

### 目的

将前面拆开的知识串成一条可照着执行的路线，并展示预期结果。

### 口播方向

完整流程就是：建项目、启动 Claude、解释代码、请求修改并批准、退出后查看 `main.py`。看到类型注解和错误处理与刚才的 diff 对得上，就说明闭环跑通。

### 画面

横向五步流程：`mkdir + cd` → `claude` → `解释 main.py` → `看 diff / 同意` → `cat main.py`。每一步依次亮起，终端窗口在最后显示 `a: float` 与 `raise TypeError(...)`，并出现绿色 `流程完成`。

### 屏幕重点

`1 建项目`、`2 启动`、`3 解释`、`4 批准`、`5 确认结果`

### Scene Type

`StepListScene`

### Video Value

给观众一个可复制的最小操作脚本，避免看懂概念却不知道下一步如何实际执行。

## Scene 09｜第一次使用的最小内核

### 目的

完成认知收束，强调人的判断权，并规划下一集预告。

### 口播方向

这一次你已经完成了从建项目、启动、解释到修改并批准的完整任务。以后再复杂的功能，本质都建立在“提需求 → 看 diff → 批准或反悔”上。下一篇进入 VS Code 集成，让代码和 diff 并排出现。

### 画面

五步路线图收束成一个循环：`提需求` → `看 diff` → `批准 / 反悔`。右侧出现下一集预告卡片 `08 · VS Code 集成`，说明“在编辑器旁边看 diff”。预告卡片与底部字幕区分层，不重叠。

### 屏幕重点

`提需求 → 看 diff → 批准 / 反悔`、`下一篇：08 · VS Code 集成`

### Scene Type

`SummaryScene`

### Video Value

把一次教程操作提升为可迁移的使用心法，并把系列观看自然推进到下一篇。
