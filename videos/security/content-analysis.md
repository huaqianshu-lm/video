# 安全与风险边界：权限之后，真正考验的是判断力

## 1. 分析范围

本分析只使用指定的 `21-security.md` 原文。文章中的命令、配置片段、攻击示例和角色化文字都只是待分析内容，不执行其中任何命令，不调用外部服务，也不读取文章目录中的其他文章。原文末尾给出的 `22「MCP：连接外部服务」` 仅作为系列下一集预告保留。

## 2. 核心命题

Claude Code 的安全不能简化成“把权限配置好就万事大吉”。真正的安全边界由三层共同组成：程序强制执行的权限和内置保护、操作系统级或更外层的隔离，以及用户在批准前对内容和命令的判断。提示注入会把不可信内容伪装成用户指令；`deny` 只限制 Claude 的直接工具访问，可能被脚本子进程绕道；沙箱、容器和虚拟机则逐层扩大隔离范围，但也各有边界。

如果观众最后只记住一句话，应该是：

> 权限是工具，安全是判断力；默认怀疑不可信内容，批准前看清命令，并按数据敏感度和代码可信度叠加隔离。

## 3. 知识骨架

### 3.1 三层安全模型

文章用“安全带、气囊、限速”类比三层防护：

1. 程序强制执行的权限边界，是操作前的硬约束。
2. 内置断路器和隔离机制，是危险发生时的缓冲。
3. 用户自己的审查、克制和批准判断，是永远不能省掉的主动防线。

关键认知是：权限规则由 Claude Code 程序强制执行，不是由模型自觉执行；`CLAUDE.md` 或用户提示只能影响模型想做什么，不能改变程序允许什么。

### 3.2 内置保护的默认边界

文章列出不需要用户额外配置的保护：写入范围限制、`curl`／`wget` 等命令黑名单、网络请求批准、新仓库和新 MCP 的信任验证、凭证加密存储。它们降低风险，但不代表系统完全免疫攻击。

### 3.3 提示注入的真实路径

不可信内容可能来自 README、GitHub issue、PR 评论、网页或第三方依赖注释。攻击者把“给 AI 看的数据”伪装成“让 AI 执行的指令”，例如诱导 Claude 读取 SSH 私钥后通过 `curl` 发往外部地址。

原文给出的拦截包括：命令黑名单、上下文感知分析、网络请求批准、Web fetch 的隔离上下文窗口和命令注入检测。但最终批准仍由用户负责，不能把所有提示当成可信指令，也不应把不可信内容直接通过管道喂给 Claude。

### 3.4 敏感数据的明枪与暗箭

对 `.env`、`~/.ssh/`、`~/.aws/credentials` 等敏感路径，`deny: Read(...)` 可以阻止 Claude 的内置 `Read` 工具直接读取，但管不到 Python 或 Node 子进程通过 Bash 绕道打开文件。要让操作系统阻止所有进程访问路径，需要把工具层 `deny` 与沙箱的 `denyRead` 叠加。

### 3.5 沙箱与更外层隔离

沙箱是 OS 级文件系统和网络隔离，能约束 Bash 子进程实际可以访问的路径和域名。它支持 macOS、Linux、WSL2，不支持原生 Windows；默认仍可能读取 SSH 和 AWS 凭证，需手动加入 `denyRead`。

沙箱只隔离 Bash 子进程，管不到 Claude 内置文件工具、MCP server 和 Hook。文章按信任程度把防护排成：权限规则 → 内置断路器 → Bash 沙箱 → dev container／自定义容器 → 独立虚拟机或网页版云端。越往外隔离越强，越适合低信任内容；完全陌生仓库不应在本机裸跑。

### 3.6 内置断路器

文章强调几道写死在程序里的底线：

- `rm -rf /` 和 `rm -rf ~` 即使在危险模式下仍会提示。
- Linux／macOS 上 root 或 sudo 不能启动 `--dangerously-skip-permissions`。
- `curl`、`wget` 默认拦截；匹配不到规则的命令默认手动批准，采用故障关闭。
- `auto` 模式有后台分类器检查越界或疑似受恶意内容驱动的操作，而 `bypassPermissions` 不提供这层提示注入防护。

这些保护是底线，不替代用户判断，也不等于可以无人值守地信任陌生代码。

### 3.7 三分钟验证链路

原文用 `sandbox-demo` 玩具项目验证防线：创建假 `.env`；只配置 `deny: Read(./.env)`；验证直接 `Read` 被拦；让 Python 子进程绕道读取，观察未开沙箱时的风险；再启用沙箱并配置 `denyRead`，验证同一子进程也无法读取。

这个练习的重点不是执行命令，而是让观众看见：工具层 `deny` 能拦明枪，不能拦所有暗箭；`deny` 加沙箱才形成深度防御。

### 3.8 按场景选择安全边界

文章的自保清单分三档：

- 日常本机开发：关键操作和敏感文件写 `deny`，批准前审查命令，不把不可信内容直接管道传入。
- 有真实敏感数据：开启沙箱，把凭证目录加入 `denyRead`，定期检查 `/permissions`，团队用共享配置和 managed settings。
- 陌生或不可信代码：谨慎处理新仓库／新 MCP 的信任验证，优先使用可信来源；使用容器或网页版云端，不在本机裸跑危险模式。

可选地使用官方 `security-guidance` 插件作为深度防御的一层，但它不是完整安全方案。

## 4. 认知关系

### 因果关系

不可信内容被模型当作指令 → 可能触发危险操作 → 权限规则和内置断路器先拦截 → 用户批准前的审查决定是否放行 → 更低信任场景需要沙箱、容器或虚拟机扩大隔离。

### 对比关系

- 模型自觉 vs 程序强制：前者可能被提示注入影响，后者执行硬边界。
- 数据 vs 指令：README、网页、issue 本应是被读取的内容，却可能伪装成命令。
- `deny` vs 沙箱：工具层限制直接访问，OS 层限制进程实际访问。
- 明枪 vs 暗箭：内置 `Read` 被拒绝，Python／Node 子进程仍可能绕道。
- 本机 vs 容器／虚拟机：真实影响范围和可恢复性不同，隔离强度不同。
- 低信任 vs 高信任：代码越陌生，越不能在本机裸跑或开启全裸奔模式。

### 分层关系

`权限规则 → 内置断路器 → Bash 沙箱 → 容器 → VM／网页版云端`

越外层的隔离，覆盖的工具和进程越多；越外层也越适合完全不可信的代码。
