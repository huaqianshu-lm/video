# Narration Script｜开发配置：把 Claude 干活的工作环境调顺

## Scene 01｜别再靠一只手按着 Ctrl+C

接手一个没看过的私有仓库，你是不是也会下意识盯住 Claude 跑出的每一条命令？担心它碰到 SSH 密钥、npm 凭据，或者工作台里其他私密文件。这样盯一下午，手还得一直放在 Ctrl+C 上，最后可能什么都没做成。

更好的问题不是“我要不要永远批准命令”，而是“能不能先给 Claude 安排一个合适的工作环境”。

## Scene 02｜开发配置其实只管五件事

开发配置不是一堆零散开关，它其实在安排 Claude 干活的五个侧面。

第一是隔离，决定它隔到哪里干；第二是网络，决定这间房间的门窗通到哪里；第三是终端，决定桌椅和灯光顺不顺手；第四是模型，决定派谁来干；最后是验证，确认你改的配置真的生效。

所以，连不上时先查网络，老问权限时先看隔离，别把所有问题都归到同一个开关上。

## Scene 03｜沙箱给 Bash 圈一块试车场

沙箱解决的是一个矛盾：你想让 Claude 跑得顺，又不想让它跑得太野。

在 Claude Code 会话里输入 `/sandbox`，打开面板后选择自动允许。操作系统会给 Bash 命令划出边界：在当前工作目录内，命令可以少一些权限提示；第一次要访问新的网络域时，再停下来让你批准。

这和写一句“请不要乱跑命令”不一样。这里是底层边界在限制它，而不是只靠 Claude 自己答应。

## Scene 04｜沙箱不是整台 Claude 的防护罩

但要记住，自带沙箱只管 Bash。Claude 的 Read、Edit、WebFetch，以及你安装的 MCP server 和 Hook，仍然直接在主机上运行。

所以，日常在自己的机器上工作，沙箱适合用来减少 Bash 权限提示；如果你想让整个 Claude Code 进程都离开主机，就要考虑 devcontainer、自定义容器、虚拟机，或者云端隔离环境。

## Scene 05｜devcontainer 是一间团队共用的工作间

devcontainer 解决的是另一组问题：团队环境不一致，以及你想让任务无人值守地跑。

把 Claude Code 装进由 `.devcontainer/devcontainer.json` 定义的 Docker 环境里，命令就在容器中执行，项目文件的修改仍然可以显示在本地仓库。团队成员拿到同一份配置，Node 版本和工具环境就不必各自猜一套。

不过容器不是金钟罩。只使用受信任的仓库，仍然要监控 Claude 的活动，也不要把主机的 SSH 密钥或云凭据挂进容器。

## Scene 06｜代码越不熟，隔离就越往右

把几种方式放在一起看，就更容易选择。

不开隔离，是 Claude 直接在主机上工作；自带沙箱只圈 Bash；devcontainer 圈住整个开发环境；自定义容器或虚拟机可以提供更强的隔离；Claude Code on the web 则由云端托管整个操作系统环境。

个人机器日常想少一些提示，可以先用沙箱；团队要一致环境或无人值守，可以用 devcontainer；代码完全不信任，就往虚拟机或网页版移动。代码越不熟，隔离就越应该往右。

## Scene 07｜连不上，先查网络三段链路

如果 Claude Code 卡在登录或第一次请求，先别去翻沙箱设置。网络问题通常分成三段。

第一段是代理，用 `HTTPS_PROXY` 或 `HTTP_PROXY` 指定总机，用 `NO_PROXY` 标记需要直连的地址；Claude Code 不支持 SOCKS。第二段是证书，公司根证书已经在系统信任库时通常不用额外配置，不行再用 `NODE_EXTRA_CA_CERTS` 指向自定义 CA。第三段是防火墙白名单，直连 Anthropic 时要放行 `api.anthropic.com`、`claude.ai` 等核心域名，第三方提供商则放行它们自己的地址。

## Scene 08｜终端只调三样：换行、通知、主题

终端配置主要解决“用着别扭”。

想让 `Shift+Enter` 换行，支持的终端可以直接用；VS Code、Cursor 这一类终端跑一次 `/terminal-setup`；不支持的终端记住通用后路，用 `Ctrl+J`，或者输入反斜杠再按 Enter。

长任务跑完没提醒，可以把通知渠道设成 `terminal_bell`。界面配色不搭，就用 `/theme` 选自动。它只改变 Claude Code 自己的界面，不会替你改终端应用的主题。

## Scene 09｜模型像排班：硬活派 Opus，日常用 Sonnet

模型配置解决的是“拿大炮打蚊子”。

复杂推理和架构设计可以用 `opus`，日常编程大多数时候 `sonnet` 就够，简单或对速度敏感的任务可以交给 `haiku`。如果想在规划时用更强的模型、执行时控制成本，可以选择 `opusplan`：计划阶段用 Opus，开始执行后切到 Sonnet。

临时切换可以用 `/model`，启动时可以传 `--model`，也可以用 `ANTHROPIC_MODEL`；想固定默认值，再写进 `settings.json`。别名会跟随提供商当前推荐的版本更新，团队需要可复现时再钉死完整模型名。

## Scene 10｜同一个模型，也能调“用多少脑子”

选完模型，还有一个 effort 旋钮，控制它思考得多深。从 `low` 到 `max`，越往后通常越愿意花更多 token 换取更深的推理。

只是这一轮遇到绕人的逻辑 bug，可以在提示里加 `ultrathink`；想固定级别，用 `/effort` 或 `settings.json` 里的 `effortLevel`。

如果你带团队，还可以用 `availableModels` 把成员能选的模型限制在 `sonnet` 和 `haiku`，把成本边界写进配置，而不是等月底看账单。

## Scene 11｜改配置之后，回头验它真的生效

光改配置不算完成，还要回头验结果。

先在会话里输入 `/sandbox`，选择自动允许。接着让 Claude 只在当前目录创建一个 `sandbox-test.txt`，如果不再弹权限提示，文件也确实出现，说明这条沙箱路径生效了。

然后输入 `/status`，记下当前模型；再用 `/model haiku` 临时切换，重新查看 `/status`。如果模型从原来的值变成 Haiku，切换就真的发生了。想让项目以后默认使用某个模型，再把它写进项目的 `settings.json`。

开发配置的通用方法就是：改配置，跑一个最小动作，再用状态或文件结果确认它真的生效。

## Scene 12｜把工作环境调顺，再进入下一种输入方式

回到开头，开发配置的价值其实很具体：老问权限时知道开沙箱，不熟的代码知道升级到容器或网页版，卡在公司网络后面知道查代理和证书，换行不顺知道用终端设置，额度烧得快知道按任务挑模型。

隔离、网络、终端、模型，再加上改完之后的验证，这五件事调顺了，Claude 才能更安全、更顺手，也少烧一些冤枉钱。
