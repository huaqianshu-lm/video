# Claude Code API 配置视频化 · 第五步：Visual Script

> 本文根据 `scene-script.md` 和 `narration-script.md` 编写，定义每个 Scene 如何展示信息、状态和动画关系。它不是 Remotion 配置，也不规定最终帧数；Visual Prototype 先验证结构，之后再根据真实口播音频和字幕时间轴确定时长。

## 全局视觉原则

### 1. 画面不能只是重复口播

口播负责解释原因、关系和行动判断，画面负责把凭证、优先级、命令执行和状态变化变成观众能直接看懂的过程。

不能只把口播中的句子换成标题和卡片；每个 Scene 至少要有一个只有视频才能有效表达的视觉事件。

### 2. 视觉承担“证明”和“演示”

本片最重要的不是展示配置名词，而是让观众看到：

- 两种凭证可以同时存在。
- 扫描指针如何命中更高优先级的凭证。
- `unset` 之后状态如何变化。
- `/status` 如何给出最终验收结果。

### 3. 一个 Scene 只表达一个视觉中心

每个 Scene 只保留一个主视觉任务。辅助分支、边界提醒和安全提示只能作为次级信息，不能与主流程争夺注意力。

### 4. 少做“页面”，多做“过程”

优先使用终端输入、浏览器授权、扫描、命中、覆盖、清除和复查等连续状态，不把视频做成静态配置说明页。

### 5. 动画必须有意义

所有动画都要对应实际信息变化：凭证出现、优先级扫描、命中状态切换、环境变量清除、模型覆盖或验收完成。装饰动画不能成为视觉中心。

## 视觉规格

- 画布：16:9 横屏，按 1920 × 1080 设计。
- 风格：深色、干净、克制、教程感；使用轻微蓝紫发光区分有效状态。
- 固定结构：顶部显示系列和当前 Scene，中央展示主信息，底部预留 1～2 行字幕安全区。
- 画面分工：声音解释原因和因果，画面展示凭证、覆盖关系、命令、状态变化和验证结果。
- 文字控制：主标题最多 1～2 行；单个卡片只保留一个主要结论；代码和环境变量使用等宽字体。
- 动画节奏：先出现问题，再出现关系或操作，最后停留在可读的结论状态；不使用快速闪切。
- 素材规则：不直接使用源文档中的 `assets/04-auth-priority-stack@2x.png`，优先用 CSS 卡片、终端、箭头、指针和状态标签重新表达。
- 占位规则：所有 key、邮箱、账单和版本号均使用示例或占位内容，不展示真实敏感信息。

## 通用画面和转场

### 通用画面层级

```text
背景层：深色渐变、细网格或低对比光晕
信息层：Scene 标题、主卡片、状态标签、流程箭头
动作层：扫描指针、终端输入、状态切换、覆盖关系
字幕层：底部固定安全区，显示当前口播的逐句字幕
```

### 通用转场

- 普通转场：上一 Scene 的主卡片向左收缩，下一 Scene 的主卡片从右侧进入。
- 关系转场：保留上一 Scene 的关键对象，通过箭头或镜头推进连接到下一 Scene。
- 机制转场：Scene 05 的两张凭证卡片向中央汇合，直接变成 Scene 06 的优先级栈。
- 结尾转场：Scene 12 的终端状态收束为验收卡片，再显示下一视频预告；预告不打断前面的验收结论。

# Scene 01｜登录了，为什么还会产生 API 费用？

## 视觉目标

在第一眼制造“订阅已连接”和“API 费用增加”的冲突。

## 构图

- 左侧约 45％：深色终端卡片，显示 `/login` 和 `Claude subscription: connected`。
- 右侧约 35％：账单卡片，显示 `API usage` 和递增金额占位符。
- 中央约 20％：冲突连接线和大字结论。

## 动作顺序

1. 终端输入 `/login`。
2. `Claude subscription: connected` 变为绿色有效状态。
3. 右侧 `API usage` 数值缓慢跳动。
4. 中央出现 `登录状态 ≠ 实际生效身份`。

## 屏幕文字

```text
登进去了，不等于用对了身份
```

## 声画关系

口播提出“为什么还在产生 API 费用”，画面同时给出两个相反状态，不提前展示优先级原因。

## 转场

中央冲突提示缩小为问题标签，进入两条路径对比。

# Scene 02｜先判断：订阅还是 API key？

## 视觉目标

把选择问题简化为个人日常与自动化按量两个分支。

## 构图

- 左右各一张等宽路径卡片。
- 左卡使用月卡／循环线条抽象图形，右卡使用一次性票据／代码块抽象图形。
- 中央顶部显示“先选使用方式”。

## 动作顺序

1. 标题出现：`你是哪种使用场景？`。
2. 左卡出现 `个人日常交互式开发 → 订阅`。
3. 右卡出现 `脚本 / CI / 团队按量 → API key`。
4. 两张卡片底部分别显示 `月度订阅`、`按 token 计费`。

## 屏幕文字

```text
个人日常 → 订阅
自动化按量 → API key
```

## 声画关系

口播解释适用场景和计费差异，画面只保留能帮助选择的维度，不展示完整对照表。

## 转场

两张卡片分别沿箭头进入 Scene 03 和 Scene 04，随后在 Scene 05 汇合。

# Scene 03｜订阅登录：`claude` 到浏览器授权

## 视觉目标

展示订阅用户从终端发起到浏览器授权、再返回终端的跨界面流程。

## 构图

- 左侧终端窗口：`$ claude`。
- 中央浏览器窗口：`Claude.ai / Sign in`。
- 右侧终端状态窗口：`Authenticated`。
- 用连续箭头连接三个状态。

## 动作顺序

1. 终端输入 `claude`。
2. 浏览器窗口滑入并显示登录授权。
3. 授权按钮高亮，浏览器窗口变为已完成。
4. 右侧终端显示 `Authenticated`。
5. 角落短暂显示辅助信息：`复制登录链接`、`远程环境：粘贴代码`、`/logout：换账号`。

## 屏幕文字

```text
claude → 浏览器登录 → 回到终端
```

## 声画关系

口播解释主路径，画面演示状态如何在终端和浏览器之间移动；辅助分支不抢主视觉。

## 转场

已授权终端卡片向右保留一条状态线，切入 API key 的另一条路径。

# Scene 04｜API key：Console、环境变量、批准

## 视觉目标

展示 API key 从创建到被 Claude Code 使用的三步链路，并明确安全边界。

## 构图

- 横向三步卡片：`01 Console`、`02 Environment`、`03 Claude Code`。
- 卡片之间用向右箭头连接。
- 下方固定安全提示条，不遮挡主流程。

## 动作顺序

1. `Create API key` 卡片亮起。
2. `ANTHROPIC_API_KEY=sk-ant-你的密钥` 写入环境变量卡片。
3. `Approve key` 在 Claude Code 卡片中完成。
4. 安全提示条出现：`不要写入代码 · 不要提交 Git`。

## 屏幕文字

```text
Console → 环境变量 → 批准
```

## 声画关系

口播解释三步和安全风险，画面只展示模糊化占位符，不展示真实 key。

## 转场

订阅卡片和 API key 卡片各自缩小，作为两个并存的凭证状态进入 Scene 05。

# Scene 05｜两条身份可以同时存在

## 视觉目标

让观众看到 OAuth 和 API key 同时存在，而不是把问题误判为登录失败。

## 构图

- 左侧凭证卡片：`OAuth subscription / PRESENT`。
- 右侧凭证卡片：`ANTHROPIC_API_KEY / PRESENT`。
- 中央问句：`谁先被读取？`。
- 顶部出现状态说明：`凭证可以同时存在`。

## 动作顺序

1. 两张卡片分别亮起。
2. 中央出现连接线，表示它们同时参与身份判断。
3. `谁先被读取？` 进入等待状态。
4. 两张卡片沿纵向排列，形成下一 Scene 的栈。

## 屏幕文字

```text
凭证可以同时存在
生效顺序由优先级决定
```

## 声画关系

口播说明主观选择不等于实际生效身份，画面把两个凭证同时存在的事实固定下来。

## 转场

中央连接线竖直展开，变成优先级栈的扫描轨道。

# Scene 06｜六层身份验证优先级栈

## 视觉目标

用原创 CSS 栈动画解释“从上往下找第一个有值的层”。

## 构图

- 中央占主要面积：六层垂直栈。
- 左侧：优先级编号和扫描指针。
- 右侧：当前层状态 `EMPTY` 或 `PRESENT`。
- 底部保留完整规则句。

## 栈内容

```text
1  云提供商
2  ANTHROPIC_AUTH_TOKEN
3  ANTHROPIC_API_KEY
4  apiKeyHelper
5  CLAUDE_CODE_OAUTH_TOKEN
6  /login 订阅
```

## 动作顺序

1. 六层从上到下依次进入。
2. 扫描指针从第 1 层向下移动。
3. 空层显示 `EMPTY` 并被跳过。
4. 指针停在第一个 `PRESENT` 层，显示 `USED`。
5. 底部出现：`从上往下找第一个有值的层`。

## 声画关系

口播负责念出六层和规则，画面负责展示顺序、空层、扫描和命中，不要求观众一次记住所有企业凭证细节。

## 转场

扫描指针停在第三层 `ANTHROPIC_API_KEY`，直接进入开场案例的具体命中状态。

# Scene 07｜为什么 API key 会盖过订阅？

## 视觉目标

把 Scene 06 的抽象规则应用到开场案例。

## 构图

- 继续使用 Scene 06 的栈，保持位置不变。
- 第三层高亮：`PRESENT / USED`。
- 第六层保留 `PRESENT`，但显示 `SKIPPED`。
- 右侧账单标签显示 `API usage`。

## 动作顺序

1. 指针回放到第三层。
2. `ANTHROPIC_API_KEY` 变为高亮命中。
3. `/login subscription` 保持存在但降低透明度，标记 `SKIPPED`。
4. 右侧账单卡片从“订阅已登录”切换为 `API usage`。

## 屏幕文字

```text
API key 有值 → 订阅被覆盖
```

## 声画关系

口播解释“订阅存在但没有命中”，画面让观众看到覆盖是实际状态，而不是抽象口号。

## 转场

保留栈和命中层，进入清理覆盖源的终端操作。

# Scene 08｜切回订阅：先清理，再复查

## 视觉目标

展示 `unset` 如何让扫描继续向下，并用 `/status` 完成复查。

## 构图

- 左侧终端：命令和 `/status` 结果。
- 右侧缩小版优先级栈：API key 从 `PRESENT` 变为 `EMPTY`。
- 最终状态卡：`Auth: Claude subscription (OAuth)`。

## 动作顺序

1. 终端输入 `unset ANTHROPIC_API_KEY`。
2. 右侧第三层状态从 `PRESENT` 变为 `EMPTY`。
3. 扫描指针继续向下，命中 `/login 订阅`。
4. 终端输入 `/status`，出现订阅身份结果。
5. 角落出现辅助入口：`/config → 关闭自定义 API 密钥`。

## 屏幕文字

```text
清除覆盖源 → /status 复查
```

## 声画关系

口播解释 `unset` 是移除覆盖源，不是重新登录；画面展示命令前后状态变化。

## 转场

最终 Auth 状态卡分裂成三个入口卡片，进入边界说明。

# Scene 09｜CLI、Desktop、Web：入口边界不同

## 视觉目标

用三列卡片明确不同入口的读取范围。

## 构图

```text
CLI       环境变量 + OAuth
Desktop   OAuth
Web       订阅凭证
```

三列等宽排列，顶部显示 `不同入口，不同凭证读取范围`。

## 动作顺序

1. CLI 卡片先出现并显示终端环境变量。
2. Desktop 卡片只亮起 OAuth。
3. Web 卡片只亮起订阅凭证。
4. 将 API key 标签拖向 Desktop 和 Web 时，在边界处弹出 `不是同一读取范围`，随后回到 CLI。

## 声画关系

口播说明入口差异，画面展示错误迁移会被边界拦截；不展开平台实现细节。

## 转场

三张入口卡片收束成一个“当前身份”标签，切到模型选择。

# Scene 10｜身份确认后，再选择模型

把“用谁的额度”和“用哪个模型”并列但分开。

## 构图

- 右侧：三个任务卡片，分别对应 `opus`、`sonnet`、`haiku`。

# Scene 11｜模型配置也有自己的优先级

## 视觉目标

展示模型配置入口的四层覆盖关系。

## 构图

- 中央横向或纵向四层链：`/model`、`claude --model`、`ANTHROPIC_MODEL`、`settings.json`。
- 右侧当前状态卡：`Model: default` → `Model: sonnet`。

## 动作顺序

1. 四层从低到高依次出现，箭头标注“上层覆盖下层”。
2. 终端输入 `/model sonnet`。
3. 最高层高亮，最终状态卡更新为 `Model: sonnet`。
4. 底部显示完整优先级：`/model > --model > 环境变量 > settings`。

## 声画关系

口播解释模型配置与身份配置是两条链路，画面只演示模型配置本身的覆盖关系。

## 转场

`Model: sonnet` 与 `Auth` 合并为最终状态卡，进入终端验收。

# Scene 12｜用 `/status` 验收：不要凭感觉判断

## 视觉目标

把整条视频转化为一套可重复执行的终端检查闭环，并承接结尾预告。

## 构图

- 左侧大终端：逐行执行检查命令。
- 右侧验收卡：`Auth`、`Model`、`Status`。
- 底部三条总结：订阅在底层、`/status` 看事实、模型按任务选。
- 预告放在验收卡确认之后，不与验收命令抢主视觉。

## 动作顺序

1. 终端执行 `claude`。
2. 输入 `/status`，显示账户、Auth 和 Model。
3. 输入 `/model`，显示模型选择入口。
4. 退出后执行 `echo $ANTHROPIC_API_KEY`。
5. 如需切换，执行 `unset ANTHROPIC_API_KEY`，再次进入 Claude Code。
6. 再次 `/status`，验收卡显示 `Auth: Claude subscription (OAuth)`、`Model: sonnet`、`Status: verified`。
7. 三条总结出现后，预告卡显示 `05 · 接入第三方 / 国产模型` 和 `ANTHROPIC_BASE_URL`。

## 屏幕文字

```text
不确定在用谁：/status
```

## 声画关系

口播给出执行顺序和验收标准，画面按顺序展示状态变化；预告只在核心验收完成后出现。

## 结束状态

最终画面必须同时让观众看见：当前 Auth、当前 Model、验证通过，以及下一条内容的一个入口线索。

优先复用现有六类场景组件：

# 动画层级建议

## 一级：信息动画

- 终端命令输入与结果出现。
- 凭证从 `EMPTY` 切换为 `PRESENT`。
- 扫描指针移动并停在命中层。
- `unset` 后 API key 清空，订阅身份被命中。
- `/status` 返回最终 Auth 和 Model。

## 二级：注意力动画

- 当前命中层高亮。
- 被覆盖凭证降低透明度。
- 流程箭头按操作顺序点亮。
- 入口边界在错误迁移时给出阻挡反馈。

## 三级：装饰动画

- 背景低对比光晕。
- 卡片轻微淡入和位移。
- 状态完成后的弱发光。

三级动画只能服务可读性，不能取代一级信息动画。

# Visual Script 最终标准

### 1

每个 Scene 必须有一个明确的视觉中心，并能指出该画面比纯口播多传递了什么信息。

### 2

口播解释因果，画面展示状态和过程；屏幕文字不重复整句口播。

### 3

Scene 06、07、08、12 必须形成连续的视觉闭环：优先级规则 → API key 命中 → 清除覆盖源 → `/status` 验收。

### 4

身份优先级、入口边界和模型优先级必须作为三种不同关系呈现，不能合并成一张配置总表。

### 5
