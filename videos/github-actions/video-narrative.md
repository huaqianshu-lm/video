# GitHub Actions 视频化 · 第二步：Video Narrative

> 目标：按观众从「为什么需要」到「如何触发、如何配置、如何安全验证」的认知路径组织视频。

## 1. 视频叙事目标

让观众完成一次工作边界的认知变化：

```text
半夜 PR 没人 review
↓
Claude Code 不必住在你的电脑里
↓
它可以住进 GitHub runner
↓
@claude 是评论里的派活入口，/claude 不是
↓
App、Secret、workflow 共同组成运行链路
↓
prompt 决定自动跑还是等人喊
↓
不同事件对应 review、改 issue、定时任务
↓
云端自动化必须用 Secrets、最小权限和人工审查兜底
```

## 2. 叙事结构

### 第一段：先让观众感受到「人不在场」的痛点

从深夜 PR 卡住的场景开场，不先给产品定义。画面先给出同事催上线、开发者已经睡下和自动 review 结果出现的时间差。

### 第二段：把本地 Claude Code 搬到云端

对比本地终端与 GitHub runner：触发者、运行地点、是否需要人在场和批准方式都发生变化。随后再下定义：它底层仍是 Claude Code，会读取 `CLAUDE.md`。

### 第三段：拆开 `@claude` 触发

展示评论位置和具体任务，再用 `@claude`／`/claude` 的对照消除最容易出现的误解。声音解释上下文读取，画面展示评论进入 workflow。

### 第四段：安装和 workflow 的骨架

先展示安装所需的 App、Secret、workflow 三件套和权限边界，再把 YAML 从 `name`、`on`、`jobs`、`steps` 四块拆开。不要让 YAML 变成大段静态代码，而要让每一块随着运行路径亮起。

### 第五段：用 `prompt` 统一解释三种模式

先给出「没有 `prompt` 就等 `@claude`，有 `prompt` 就自动跑」这条主线，再依次展示自动 review、按 issue 改、定时任务。让触发事件和结果一起出现。

### 第六段：自动化越强，安全边界越重要

先把真实 key 写进 YAML 的危险画面打叉，再将 key 放入 GitHub Secrets。之后补充最小权限、提示注入和合并前人工审查，形成「能跑」到「能安全地跑」的转折。

### 第七段：用五分钟验证闭环收束

用测试仓库完成安装、确认 workflow、确认 Secret、评论 `@claude`、看到 PR、审查再合并。结尾总结六个关键动作，并把 Agent SDK 作为下一集最后一个视觉事件。

## 3. 观众认知节奏

| 段落 | 观众问题 | 画面证明 |
| --- | --- | --- |
| 01 | 为什么需要它？ | 人睡下后 PR review 仍然出现 |
| 02 | 它和本地版有什么关系？ | 本地终端迁移到 GitHub runner |
| 03 | 我怎么喊它？ | `@claude` 评论进入执行链 |
| 04 | 怎么装？ | App、Secret、workflow 汇入仓库 |
| 05 | YAML 在做什么？ | `on` → `jobs` → `steps` 运行路径 |
| 06 | 为什么有时自动跑、有时等评论？ | `prompt` 有无切换模式 |
| 07 | 可以用在哪？ | review、issue、schedule 三条结果路径 |
| 08 | 会不会泄露 key 或乱改？ | Secrets、权限、人工 review 三道边界 |
| 09 | 怎么确认真的通了？ | workflow、评论、PR 和审查状态闭环 |

## 4. 结尾原则

最后一个正式视觉事件是「下一篇：Agent SDK」预告。预告只说明它是 GitHub Actions 之下的代码驱动层，不展开 SDK 用法；画面和口播都保持在 Source 已给出的下一集引导范围内。
