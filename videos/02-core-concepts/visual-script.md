# Codex 核心概念速览 · 第五步：Visual Script

> 目标：基于 Scene Script 和 Narration Script，为 8 个 Scene 设计与口播互补的视觉表达。声音负责解释意义和因果，画面负责展示动作、边界、状态变化与验证证据。

## 全局视觉原则

### 1．先展示过程，再给出结论

画面优先表现任务进入 Agent、动作经过边界、文件状态改变、请求进入审批和实验结果对照等过程。结论只在状态完成后短暂收束，不把整段口播压成一页说明。

### 2．画面负责证明，口播负责解释

- **声音**：解释 Agent、Sandbox、Approval、项目规则和补充上下文分别解决什么问题，说明它们之间的因果关系。
- **画面**：展示谁在行动、动作经过哪条路径、哪些资源被允许或阻止，以及相同请求在不同边界下产生的结果。

每个 Scene 都必须有至少一个能独立表达信息的视觉状态变化，避免用标题卡替代演示。

### 3．每个 Scene 只保留一个视觉中心

使用 16:9 横屏、1920 × 1080 的构图基准。顶部保留标题安全区，主体集中在中部，字幕稳定放在底部安全区。一个 Scene 中可以有多个节点或窗口，但它们必须共同服务于同一条动作路径。

### 4．统一视觉语言

- 背景使用深色蓝黑色，面板使用高不透明度深色，避免后方元素穿透。
- 主文字使用浅色，流程路径使用浅蓝，补充信息使用淡紫；成功、停止和警示色只表达明确状态。
- 代码名、模式名和文件名使用等宽字体或代码样式，例如 `workspace-write`、`AGENTS.md`、`hello.txt`。
- 连接线、箭头和状态标记要轻量、清晰，不使用复杂 3D、粒子或无意义旋转。

### 5．画面文字边界

屏幕文字只使用当前视频的 Source、Scene Script、Narration Script 和本 Visual Script 中已有的概念、状态与预告内容。每个 Scene 的“屏幕文字”清单是该 Scene 的可见文字白名单；不显示整段口播，不加入参考视频中的业务文案或制作提示。

### 6．动画必须传递信息

优先使用以下信息动画：节点出现、路径连接、文件状态改变、箭头通过或停止、请求分支、规则注入、信息汇入、实验轮次切换和关系图归位。动画完成后保留足够的阅读与理解时间，尤其是 Scene 08 的下一集预告卡应独立停留约 2～3 秒。

# Scene 01｜同一个任务，为什么只完成了一半

## 视觉目标

在开场立即建立一个真实且可验证的反常结果：同一条“统一重命名”任务同时触及项目目录和桌面目录，但最终只有项目文件发生变化。观众先看到分叉结果，再带着疑问进入后续概念解释。

## 画面结构

画面采用左右分区，中间放一张简短任务卡。左侧是“项目目录”，右侧是“桌面目录”；两侧各显示一个待重命名文件。两条路径从同一任务卡出发，不使用复杂 IDE 外壳，保证结果分叉是唯一视觉中心。

初始状态中，两侧文件都显示原名和等待状态。左侧文件随后变为已修改，右侧文件保持原名和未修改状态。完成后两侧同时定格，画面中央保留问题文字。

## 动画与状态变化

1. 任务卡从画面中央出现，连接线同时指向项目目录和桌面目录。
2. 两个目录收到同一个写入动作，连接线保持同源，明确请求没有改变。
3. 项目目录中的文件完成重命名，文件名替换为新状态并变为成功色。
4. 桌面目录的动作在文件旁停下，原名保持不变，状态显示为未修改。
5. 成功与未修改两种状态同时轻微高亮，最后显示问题文字并留出阅读时间。

## 视觉重点与口播互补

- **画面**展示“一条请求、两个位置、两种结果”的完整证据链。
- **口播**描述任务经过和疑问，不在屏幕上重复完整句子。
- 文件名可以用简短的前后变化表达重命名，但不显示额外路径、终端输出或未在当前资料中出现的文件内容。

## 屏幕文字

```text
统一重命名
项目目录：已修改
桌面目录：未修改
它漏做了吗？
```

以上文字对应 Scene Script 01 的 `keyOnScreenText`；文件状态只使用“已修改”和“未修改”表达口播中的结果。

## Visual Type

`OpeningScene / Split Result`

## 节奏约束

先让两条路径同时启动，再让结果错开出现。问题文字必须在两种结果都完成后出现，不能提前解释 Sandbox 或 Approval。

# Scene 02｜先确认谁在行动：Agent

## 视觉目标

把 Agent 表现为围绕目标持续推进的执行者，而不是只返回一段建议的聊天窗口。重点是“理解、读取、执行、查看、调整”的循环，以及失败后再次测试的闭环。

## 画面结构

主体是一个居中的 Agent 节点，左侧进入任务卡，右侧连接一条五步动作链。动作链不做成同时出现的卡片，而是沿同一条路径依次点亮：理解目标、读取、执行、查看结果、调整。下半部或后半段切换成一条测试闭环，使用同一个 Agent 节点承接失败后的下一步。

## 动画与状态变化

1. 任务卡进入 Agent 节点，节点亮起，表示任务被接收。
2. “理解目标”与“读取”依次点亮，文件或环境信息以短线条汇入 Agent。
3. “执行”节点亮起，动作箭头向右移动。
4. “查看结果”出现失败状态，路径不结束，而是回到“调整”。
5. 测试闭环依次显示运行测试、读取报错、修改代码、再次测试；再次测试恢复成功色并闭合回路。
6. 最后收束为四步短语，保持动作链而不是说明卡片。

## 视觉重点与口播互补

- **画面**用顺序、回路和失败后的状态恢复证明 Agent 会继续决策。
- **口播**解释这些动作为什么构成 Agent 与普通问答的区别。
- 不把口播中的每个解释句逐行显示，只让动作节点承担过程信息。

## 屏幕文字

```text
Agent
想 → 做 → 看 → 再决定
运行测试
读取报错
修改代码
再次测试
```

以上文字对应 Scene Script 02 的 `keyOnScreenText`；“理解目标”“读取”“执行”“查看结果”“调整”作为动作节点名称，来源于 Scene Script 02 的 `visualIntent`，不再添加解释性副标题。

## Visual Type

`StepListScene / Agent Loop`

## 节奏约束

动作节点必须按理解顺序依次出现，失败状态至少停留到观众看清回路重新开始；不要用一次性同时出现的五张卡片代替执行过程。

# Scene 03｜Sandbox 画出行动边界

## 视觉目标

解释 Scene 01 的分叉结果来自资源边界，而不是 Agent 的能力随机消失。让观众直接看到项目目录在可写范围内，桌面目录在范围外。

## 画面结构

主体是一块带发光边框的工作区，边框内放项目目录和待修改文件，边框外放桌面目录和未修改文件。右侧或中央放一个写入动作箭头，箭头尝试分别指向两侧资源。工作区边界是全幕唯一主要视觉中心，背景不加入多余软件窗口。

## 动画与状态变化

1. 先显示完整的工作区边界和两侧资源位置，边界内外形成空间对照。
2. `workspace-write` 标记出现在边界上方，工作区内的项目文件获得可写状态。
3. 写入箭头进入工作区并通过，项目文件变为已修改。
4. 同一箭头移动到边界外，在边界处停止；桌面文件保持未修改。
5. 边界线轻微高亮，最后保持两侧结果与边界的对应关系。

## 视觉重点与口播互补

- **画面**把“可写范围”变成空间关系，并回扣项目文件与桌面文件的不同位置。
- **口播**解释 Sandbox 还可以约束文件、命令和网络等资源，以及 `workspace-write` 的准确含义。
- 画面只演示文件写入边界，不把网络或其他资源另开成第二个视觉中心。

## 屏幕文字

```text
Sandbox
workspace-write
工作区内：可写
边界之外：当前不可直接写入
```

以上文字对应 Scene Script 03 的 `keyOnScreenText`；项目目录、桌面目录和文件状态作为结构性标识，沿用 Scene 01 的已修改／未修改结果。

## Visual Type

`ConceptScene / Boundary Map`

## 节奏约束

先建立边界，再展示箭头通过与停止。不要在边界出现前显示结论，避免观众把结果理解成随机失败。

# Scene 04｜越过边界之前，还要经过 Approval

## 视觉目标

将 Sandbox 的技术边界与 Approval 的授权过程拆成连续两步：先判断能否在边界内执行，再决定越界时是否请求许可。画面要同时表达边界内执行、获准继续和未获许可停止三种状态。

## 画面结构

画面以一条从左到右的决策流为主体。动作请求先进入“在 Sandbox 内吗”的判断节点；“是”路径直接到执行，“否”路径进入 Approval。Approval 后分成“获得许可”和“未获许可”两条终态，分别连接继续和停止。

决策节点保持少量文字，使用路径颜色区分通过、等待和停止。不要额外放两张定义卡，以免把两个概念拆成并列介绍。

## 动画与状态变化

1. 动作请求沿主线移动到“在 Sandbox 内吗”。
2. 先演示“是”的路径，动作直接进入执行，表示边界内按现有权限继续。
3. 回到判断节点，演示“否”的路径，动作转入 Approval 并暂停等待。
4. 第一轮分支显示“获得许可”，动作沿获准范围继续执行。
5. 第二轮分支显示“未获许可”，动作颜色变为停止色并停在终点。
6. 最后让 Sandbox 与 Approval 两个节点同时保持可见，突出先后关系。

## 视觉重点与口播互补

- **画面**展示一条动作如何依次经过边界判断和授权分支。
- **口播**解释 Sandbox 回答“现在能不能做”，Approval 回答“越过边界前要不要问”。
- 不把“能不能”和“问不问”的完整解释写成段落，只保留对应的短标签。

## 屏幕文字

```text
Sandbox：能不能
Approval：问不问
边界内 → 执行
边界外 → 请求许可
获准范围内继续
```

以上文字对应 Scene Script 04 的 `keyOnScreenText`；“未获许可 → 停止”是该 Scene Script `visualIntent` 中明确的终态，作为路径状态使用。

## Visual Type

`ComparisonScene / Decision Flow`

## 节奏约束

必须先完整走完 Sandbox 判断，再进入 Approval 分支；两个分支都出现后再收束。路径动画不能同时乱跳，否则会削弱“连续判断”的因果关系。

# Scene 05｜有权限，还要先读项目规则

## 视觉目标

说明权限只解决“能不能做”，项目规则进一步决定“应该怎样做”。画面要呈现 `AGENTS.md` 在行动前进入 Agent，并在纠正后沉淀为可复用规则。

## 画面结构

主体是 Agent 与一个打开的 `AGENTS.md` 文件之间的双向关系。任务目标从左侧进入 Agent，`AGENTS.md` 从上方进入；四条规则依次落入 Agent 周围的执行上下文。后半段让一次错误假设从 Agent 返回到规则文件，形成反馈回路。

规则使用轻量标签或短节点，不做成完整文档页面，也不展示无关的代码内容。

## 动画与状态变化

1. 任务目标和 `AGENTS.md` 同时靠近 Agent，但任务表示“要做什么”，规则文件表示“按什么约定做”。
2. 构建命令、测试要求、审查规则、仓库约定依次点亮并汇入 Agent。
3. Agent 开始执行时，规则节点保持亮起，表示规则参与当前动作。
4. 一次错误假设出现警示，用户纠正沿回路返回 `AGENTS.md`。
5. 规则文件更新为稳定规则，下一次任务再次从同一文件读取，形成可复用的反馈回路。

## 视觉重点与口播互补

- **画面**展示规则从文件进入上下文、被纠正后再回到文件的生命周期。
- **口播**解释项目约定、构建命令、测试要求和审查规则的意义。
- 画面不显示完整规则句子，只展示可追溯的规则类别和文件名。

## 屏幕文字

```text
AGENTS.md
构建命令
测试要求
审查规则
仓库约定
权限决定能做什么
规则决定应该怎样做
```

以上文字对应 Scene Script 05 的 `keyOnScreenText`；任务目标、错误假设和用户纠正只作为无额外文字的路径状态表现。

## Visual Type

`ConceptScene / Rule Injection`

## 节奏约束

四类规则要按顺序进入 Agent，反馈回路放在规则注入之后。结论文字在回路完成后出现，避免提前把“权限”和“规则”的关系说完。

# Scene 06｜规则负责确定，上下文负责补充

## 视觉目标

区分 `AGENTS.md`、Memory 和 Chronicle 的来源与职责。画面需要让观众看到三条信息路径都能汇入 Agent，但可靠性和用途并不相同。

## 画面结构

中心放 Agent，左上、左下和右上分别放 `AGENTS.md`、Memory、Chronicle。三条路径使用不同颜色和线型汇入同一个上下文区域：规则路径标记为确定，Memory 与 Chronicle 路径标记为补充。Chronicle 旁保留一组紧凑警示，提醒使用边界。

三条路径按顺序进入，不同时堆满画面；Agent 周围的“确定”和“补充”状态比额外解释卡更重要。

## 动画与状态变化

1. `AGENTS.md` 先出现，稳定规则沿主路径汇入 Agent，并锁定为确定性信息。
2. Memory 随后出现，从过去会话方向汇入，显示为补充信息。
3. Chronicle 最后出现，从近期屏幕活动方向汇入，显示为补充信息。
4. Chronicle 旁依次亮起隐私、提示注入、资源限制警示，然后降低亮度，避免警示抢过主关系图。
5. 三条路径同时保持可见，最后收束为“规则负责确定性，上下文负责补充性”的关系。

## 视觉重点与口播互补

- **画面**呈现信息来源、进入方向和职责标签的差异。
- **口播**解释 Memory 如何提炼过去会话、Chronicle 如何补充近期屏幕活动，以及为什么二者不能代替明确规则。
- 不把隐私、提示注入和资源限制展开成新的分支，只做与 Chronicle 相邻的风险提示。

## 屏幕文字

```text
AGENTS.md：稳定项目规则
Memory：过去会话的提炼信息
Chronicle：近期屏幕活动上下文
规则负责确定性
上下文负责补充性
```

以上文字对应 Scene Script 06 的 `keyOnScreenText`；“隐私”“提示注入”“资源限制”对应其 `visualIntent` 中明确的 Chronicle 警示，只显示为短警示词。

## Visual Type

`ComparisonScene / Context Map`

## 节奏约束

先建立确定性规则路径，再补充两条上下文路径；风险提示应在 Chronicle 出现后短暂出现，不打断三条路径的归位。

# Scene 07｜请求没变，边界变了，结果就变了

## 视觉目标

用一个受控的双轮实验，把前面关于 Sandbox 的抽象说明变成直接可观察的因果证据：请求相同，Agent 相同，只有 Sandbox 模式改变，文件树结果随之改变。

## 画面结构

画面上下分为两轮实验，共用顶部请求栏。请求栏只出现一次，内容是“在当前项目创建 `hello.txt`”。上轮显示 `read-only`，下轮显示 `workspace-write`。两轮各有一个简化文件树和写入动作，文件树是主要证据。

## 动画与状态变化

1. 顶部请求卡固定不变，左侧显示同一个 Agent 标记，强调实验控制变量。
2. 第一轮切换到 `read-only`，写入箭头到达边界后停止，文件树保持原状。
3. 第一轮结果定格为未写入，再启动第二轮；请求卡和 Agent 标记不移动。
4. 第二轮切换到 `workspace-write`，写入箭头通过边界，文件树新增 `hello.txt`。
5. 两轮结果上下对齐，依次高亮“请求没有变”“Agent 没有变”“边界变了”“结果就变了”。

## 视觉重点与口播互补

- **画面**完整展示同一请求、同一执行者、两种模式和两棵文件树的对照。
- **口播**指出唯一改变的是 Sandbox 模式，并解释受限环境中的失败不等于 Agent 时灵时不灵。
- 文件树只保留能证明结果的最小内容，不显示完整终端日志或实验环境说明。

## 屏幕文字

```text
在当前项目创建 hello.txt
read-only：未写入
workspace-write：hello.txt 已创建
请求没有变
Agent 没有变
边界变了
结果就变了
```

以上文字对应 Scene Script 07 的 `keyOnScreenText`；两棵文件树只显示“hello.txt”是否出现，作为上述状态的视觉证据。

## Visual Type

`TerminalScene / Controlled Experiment`

## 节奏约束

必须先完成 `read-only` 轮，再完成 `workspace-write` 轮；两轮结果要同时留在画面中，保证观众能比较而不是只看到第二轮成功。

# Scene 08｜把五个概念合成一套工作模型

## 视觉目标

将 Agent、Sandbox、Approval、项目规则和补充上下文组装为一张统一工作模型，回扣 Scene 01 的桌面文件结果，最后以独立的下一集预告结束全片。

## 画面结构

第一段是从左到右组装的主关系图：任务目标进入 Agent，Agent 连接 Sandbox，Sandbox 再连接 Approval。第二段从上方接入 `AGENTS.md`，从下方接入 Memory／Chronicle，形成规则与补充上下文的两层支撑。第三段让桌面文件回到边界外的结果位置，完成因果回扣。

关系图锁定后，整张模型淡化为背景，前景切换到独立的下一集预告卡。预告卡不与字幕区域重叠，保持足够留白，不再叠加关系图节点。

## 动画与状态变化

1. 任务目标卡出现并连接到 Agent，Agent 节点亮起。
2. Sandbox 接入并形成边界，Approval 沿越界方向接入，主链完成。
3. `AGENTS.md` 作为稳定规则从上方归位，Memory／Chronicle 作为补充上下文从下方归位。
4. 关系图锁定，开场的桌面文件结果回到边界之外，动作停在边界处，解释 Scene 01 的疑问。
5. 关系图降低亮度，主结论出现：“给清目标 · 画好边界 · 写下规则”。
6. 最后切换到独立预告卡，显示下一集主题和三个平台，静置约 2～3 秒后结束。

## 视觉重点与口播互补

- **画面**负责组装关系、回扣因果和留下系列导航。
- **口播**负责把五个概念压缩为一套工作模型，并解释桌面文件没有被改名的原因。
- 下一集预告必须是最后一个视觉事件，不能在关系图仍然高亮时与模型并列显示。

# 动画层级标准

## 一级：信息动画

必须保留，直接表达知识：

```text
任务进入 Agent
箭头通过或停在边界
文件从未修改变为已修改
请求进入 Approval
规则和上下文汇入 Agent
read-only 与 workspace-write 产生不同文件树
概念节点逐项归位
```

## 二级：注意力动画

少量使用，用于引导观众：

```text
当前节点高亮
路径完成后的短暂聚焦
失败状态的轻微放大
已完成路径降低亮度
```

## 三级：装饰动画

尽量不使用：

```text
无意义粒子
无意义旋转
过多弹跳
与动作无关的背景漂浮
```

如果删除一段动画后，观众仍能获得完全相同的信息，就不应把它作为必要动画。

# Visual Script 质量检查

### 1．静音检查

关闭声音后，至少能从每个 Scene 的路径、状态或对照关系看出这一幕发生了什么：结果分叉、Agent 循环、边界通过／停止、授权分支、规则注入、上下文汇入、双轮实验和统一关系图。

### 2．重复检查

画面不逐句显示 Narration Script。屏幕文字只保留任务名、概念名、状态、路径标签、实验结论和系列预告。

### 3．来源归属检查

逐项核对每个 Scene 的屏幕文字清单与 Scene Script 的 `keyOnScreenText`、`visualIntent` 和 Narration Script。不得加入参考视频业务语义、未在当前资料出现的状态文案或制作说明。

### 4．动画价值检查

每段主要动画都必须对应执行、连接、停止、修改、补充、比较或归位等信息变化；不以装饰动画填充时长。

### 5．布局与清洁检查

所有 Scene 使用 16:9 横屏安全区，主标题控制在 1～2 行，字幕放在底部稳定区域。Scene 08 的预告卡与字幕不重叠。预览控制、进度提示、调试标记和制作辅助说明不属于最终画面。
