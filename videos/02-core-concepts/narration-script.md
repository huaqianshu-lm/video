# Codex 核心概念速览 · 第四步：Narration Script

---

## Scene 01｜同一个任务，为什么只完成了一半

假设你让 Codex 同时重命名两个文件：一个在当前项目里，另一个在桌面上。

任务结束后，项目里的文件已经改名，桌面上的文件却没有变化。

它是漏做了，还是突然失灵了？

要解释这个反常结果，需要先认识五个核心概念：Agent、Sandbox、Approval、项目规则和上下文。

## Scene 02｜先确认谁在行动：Agent

先看 Agent。

你给它的不是每一步操作，而是一个想要完成的目标。

它会理解目标、读取环境、决定下一步、执行动作，再查看结果。如果结果不对，它还会继续调整。

比如测试失败以后，它可以读取报错、修改代码，然后再次运行测试。

把这套循环压缩成四个字，就是：想、做、看、再决定。

所以 Agent 不只是给出建议，而是会围绕目标持续推进任务。

## Scene 03｜Sandbox 画出行动边界

但 Agent 能行动，不代表它可以触碰电脑里的所有内容。

Sandbox，也就是沙箱，规定了它当前能够访问和修改哪些文件，能够运行哪些命令，以及能否使用网络等资源。

比如 `workspace-write` 表示工作区内可以写入，不代表整台电脑都可以写入。

这样再看开头的结果就清楚了：项目文件位于可写边界内，所以改名成功；桌面文件位于边界外，所以没有被直接修改。

这不是能力突然消失，而是行动遇到了明确边界。

## Scene 04｜越过边界之前，还要经过 Approval

边界外的动作是不是永远不能做？也不一定。

一个动作到来时，首先要判断它是否位于当前 Sandbox 之内。

边界内的动作，可以按照现有权限执行。边界外的动作，则可能进入 Approval，也就是授权流程。

只有你明确许可之后，Agent 才能在获准的范围内继续；没有获得许可，动作就会停止。

所以 Sandbox 回答的是“现在能不能做”，Approval 决定的是“越过边界前要不要问”。

两者连续工作，共同控制一次动作能否真正发生。

## Scene 05｜有权限，还要先读项目规则

不过，能够执行，只解决了“能不能做”，还没有回答“应该怎样做”。

Agent 进入一个项目后，需要先读取 `AGENTS.md`，了解这个项目的构建命令、测试要求、审查规则和仓库约定。

同样是修改代码，不同项目可能有完全不同的做法。规则写得越明确，Agent 越不容易靠猜测行动。

如果一次纠正以后仍然需要长期遵守，也应该把它写回规则文件，而不是期待系统以后自动记住。

权限决定能做什么，项目规则决定应该怎样做。

## Scene 06｜规则负责确定，上下文负责补充

除了项目规则，Agent 还可能获得另外两类信息：Memory 和 Chronicle。

Memory 会提炼过去会话里值得复用的信息，帮助后续任务延续已有背景。

Chronicle 则从近期的屏幕活动中补充工作上下文，让 Agent 更容易理解你刚刚在处理什么。使用这类信息时，也要注意隐私、提示注入和资源限制。

但它们都不能代替明确规则。

`AGENTS.md` 负责提供稳定、确定、需要持续遵守的约定；Memory 和 Chronicle 负责补充可能有帮助的上下文。

一个负责确定性，另外两个负责补充性。

## Scene 07｜请求没变，边界变了，结果就变了

现在用一个对照实验，把 Sandbox 的作用看得更清楚。

两轮实验都提出同一个请求：在当前项目创建 `hello.txt`。使用的 Agent 也没有变化，唯一改变的是 Sandbox 模式。

第一轮使用 `read-only`。Agent 可以读取内容，却不能写入，所以文件树保持不变。

第二轮改成 `workspace-write`。写入发生在工作区内，`hello.txt` 成功出现。

请求没有变，Agent 没有变，只是边界变了，结果就跟着改变。

这也解释了为什么受限环境里的某次失败，不等于 Agent 时灵时不灵。

## Scene 08｜把五个概念合成一套工作模型

最后，把这些概念合成一套完整的工作模型。

你先给出任务目标，Agent 围绕目标持续行动；Sandbox 划定当前边界，Approval 管理越界授权；`AGENTS.md` 提供稳定规则，Memory 和 Chronicle 补充上下文。

开头那个没有被改名的桌面文件，现在也有了答案：不是任务被忘记，而是动作停在了工作区边界之外。

想稳定地使用 Codex，可以先记住三件事：给清目标，画好边界，写下规则。
