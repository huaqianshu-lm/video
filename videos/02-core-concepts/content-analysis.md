# Codex 核心概念速览 · Content Analysis

> 目标：先确定“这条视频必须讲清楚什么”，提取知识骨架、关键关系和可视觉化内容；暂时不写口播，不拆 Scene，不设计具体镜头。

---

## 1. 核心命题

这篇内容表面上在解释五个 Codex 术语，但真正需要建立的认知不是：

> Codex 有哪些概念和配置。

而是：

> **Codex 是一个会自主执行任务的编程代理，但它的行动始终受到权限边界、审批规则和上下文来源的共同约束。**

五个概念并不是彼此独立的名词：

- Agent 说明“谁在行动”
- Sandbox 说明“能在哪里行动”
- Approval 说明“越过边界前是否需要询问”
- `AGENTS.md` 说明“行动时遵守什么项目规则”
- Memory／Chronicle 说明“过去的信息如何进入后续会话”

如果观众最后只记住一句话，应该是：

> **Codex 不是一个时灵时不灵的聊天框，而是一个会自己干活、同时被边界和规则约束的代理。**

---

## 2. 观众的起点与需要完成的认知变化

观众可能已经知道 Codex 能读代码、改文件和跑命令，却容易产生四个误解：

- 既然能跑命令，就应该能改机器上的任何文件
- 沙箱和审批是同一个开关
- 项目规则每次都要重新口头说明
- Memory 会默认、实时、可靠地记住所有内容

视频需要把这些零散误解统一成一个模型：

```text
任务目标
↓
Agent 在循环中想 → 做 → 看
↓
Sandbox 判断动作是否在边界内
↓
需要越界时由 Approval 决定是否询问
↓
AGENTS.md 提供当前项目的持久规则
↓
Memory／Chronicle 补充跨会话上下文
```

认知终点不是记住配置名，而是能解释：

> 为什么某个动作会直接执行、被阻止或停下来请求批准，以及应该把长期项目规则放在哪里。

## 3. 必须保留的核心信息

### A. Agent：从“回答”变成“完成任务”

必须讲清：

- Codex 是能读取代码、编辑文件和运行命令的编程代理
- Agent 会自己拆解目标、调用工具、检查结果，再决定下一步
- 它的基本工作方式可以压缩为“想 → 做 → 看”的循环
- 与普通问答的本质差异，不是回答更长，而是能把中间步骤真正执行出来

适合保留的任务链：

```text
运行测试
↓
读取报错
↓
定位问题
↓
修改代码
↓
再次验证
```

核心结论：

> **用户给目标，Agent 负责推进和验证过程。**

### B. Sandbox：划定技术上的行动边界

必须讲清：

- 沙箱限制 Codex 能读写哪些位置，以及命令能否访问网络等资源
- `workspace-write` 的关键含义是“工作区内可写”，不是“整台机器可写”
- Codex 派生出的终端命令也受同一边界约束
- 工作区外的文件没有被修改，不代表 Agent 偷懒或失灵，而是动作超出了边界

源材料列出的 `read-only`、`workspace-write`、`danger-full-access` 可用于说明边界由窄到宽，但具体默认值和平台行为属于易变信息，进入后续脚本前应以届时官方文档和本地界面为准。

### C. Approval：决定跨界动作如何获得许可

必须讲清：

- 沙箱与审批是两个独立维度
- 沙箱回答“这个动作是否在当前边界内”
- 审批回答“需要突破边界时，是否以及何时停下来询问用户”
- 审批不会自动扩大沙箱边界；不弹询问也不等于天然拥有全部权限

最重要的辨析：

```text
Sandbox：能不能
Approval：问不问
```

源材料中的 `untrusted`、`on-request`、`never` 以及 permission profiles 属于具体产品配置，名称和交互可能变化。视频主体应优先讲稳定关系，配置名只作为界面示例。

### D. Sandbox 与 Approval 的组合关系

这是整条视频最容易混淆、也最需要讲透的关系：

```text
Agent 准备执行动作
↓
动作是否在 Sandbox 边界内？
├─ 是：按当前权限直接执行
└─ 否：进入 Approval 判断
        ├─ 获得许可：在获准范围内继续
        └─ 未获许可：停止该动作
```

开头“只改了项目目录、没有改桌面文件”的故事必须保留，因为它能把抽象权限模型变成一个可观察的结果。

### E. `AGENTS.md`：项目级的持久规则

必须讲清：

- `AGENTS.md` 是 Agent 开工前读取的项目指导文件
- 适合写构建与测试命令、代码审查要求和仓库约定
- 全局与项目内文件可以形成层级，越接近当前工作目录的规则越具体
- 对代码库的纠正可以沉淀回项目规则，形成可复用的反馈回路
- 必须稳定生效的团队规则，应依赖项目指导文件，而不是概率性的记忆

核心结论：

> **权限决定 Agent 能做什么，`AGENTS.md` 决定它应该怎样做。**

### F. Memory 与 Chronicle：跨会话上下文的两种来源

必须先区分两者的信息来源：

- Memory 从过去会话中提炼可复用信息
- Chronicle 从屏幕活动中补充近期工作上下文

还必须保留这些边界：

- Memory 不是项目规则的替代品
- 它不是“刚说完就永久记住”的实时、确定性机制
- Chronicle 更接近实验性增强能力，并伴随隐私、提示注入和配额风险
- 涉及默认开关、地区、套餐、平台、存储方式和功能状态的具体描述都可能变化，不能当成长期不变的结论

这一部分的重点不应是教观众打开功能，而是建立信息来源的区别：

```text
AGENTS.md：明确写下、稳定生效的项目规则
Memory：从过去对话提炼的跨会话经验
Chronicle：从近期屏幕活动补充的上下文
```

### G. 五个概念需要合成一个统一模型

最终必须把五个概念放回同一张关系图，而不是讲成五段术语解释：

```text
                    AGENTS.md
                   项目规则输入
                        ↓
任务目标 → Agent → Sandbox 边界 → Approval → 外部资源
             ↑
      Memory／Chronicle
        跨会话上下文
```

这张图需要让观众看见：Agent 是中心，另外四个概念分别约束行动范围、越界方式和上下文来源。

### H. 最小实验：让权限边界变得可观察

源材料中的只读写文件实验具有明确教学价值，应保留它的因果对照：

```text
同一个“创建 hello.txt”请求

read-only
→ 写操作超出边界
→ 停止或请求许可

workspace-write
→ 工作区内写操作处于边界内
→ 可以直接执行
```

实验的价值不是教一条命令，而是让观众亲眼验证：

> **动作相同，边界不同，执行结果就不同。**

具体 `/permissions` 菜单文案可能随版本变化，后续叙事应保留 `--sandbox read-only` 作为更稳定的概念示例，并避免承诺唯一界面路径。

### I. 系列衔接必须保留

本篇承接“认识 Codex 与四种入口”，但不需要重新展开四种入口；它负责建立后续安装、配置和使用都依赖的概念地基。

结尾必须明确预告下一篇：

> **03 · 安装与登录：在 Mac、Windows 或 Linux 上安装 Codex、登录账号并跑通第一次使用。**

Linux 的沙箱前置条件可以作为悬念，但具体安装步骤留到下一篇。

## 4. 关键关系

### 因果关系

```text
Agent 能执行真实动作
↓
真实动作可能影响文件、命令和网络
↓
需要 Sandbox 限制行动范围
↓
越界需求仍然存在
↓
需要 Approval 管理授权过程
```

另一条因果链：

```text
Agent 每次进入项目都需要理解约定
↓
只靠临时口头说明容易遗漏
↓
把稳定规则写入 AGENTS.md
↓
后续任务可以持续复用
```

### 对比关系

必须保留四组对比：

| 对比 | 需要建立的认知 |
|---|---|
| 聊天机器人 vs Agent | 回答问题 vs 推进并验证任务 |
| Sandbox vs Approval | 技术边界 vs 授权策略 |
| read-only vs workspace-write | 相同写操作在不同边界下产生不同结果 |
| `AGENTS.md` vs Memory／Chronicle | 明确且稳定的项目规则 vs 补充性的跨会话上下文 |

### 流程关系

Agent 的执行循环：

```text
理解目标 → 读取上下文 → 执行动作 → 查看结果 → 验证或调整
```

权限判断流程：

```text
准备动作 → 判断沙箱边界 → 必要时请求审批 → 执行或停止
```

项目规则的反馈回路：

```text
Agent 对项目做出错误假设
↓
用户纠正
↓
稳定约定写入 AGENTS.md
↓
后续任务读取并遵守
```

### 层级关系

```text
中心执行者：Agent
├─ 行动边界：Sandbox
├─ 越界授权：Approval
├─ 当前项目规则：AGENTS.md
└─ 跨会话上下文
   ├─ Memory：过去会话
   └─ Chronicle：近期屏幕活动
```

## 5. 必须保留的案例

### 案例 1：批量重命名只改了项目内文件

这个案例同时承担三个作用：

- 以失败结果制造问题
- 解释工作区边界
- 纠正“Codex 挑食或失灵”的误判

它适合作为问题入口，但不应保留过多个人感叹和重复类比。

### 案例 2：修复失败测试的 Agent 循环

这个案例用连续动作证明 Agent 与聊天框的差异：

```text
跑测试 → 读报错 → 找 Bug → 修改 → 再跑测试
```

它比“代购”类比更接近真实产品使用，应该作为 Agent 概念的主要证据。

### 案例 3：只读与工作区可写的对照实验

这是整篇最强的可操作案例。它把 Sandbox 与 Approval 从定义转化为屏幕上可见的状态变化，应作为本篇 Video Value 的核心来源。

## 6. 可视觉化内容

### A. Agent 的任务循环

可以用一个任务卡在文件、终端、测试结果之间移动，形成：

```text
想 → 做 → 看 → 调整
```

画面重点是动作链和反馈闭环，不是把定义写成大段文字。

### B. Sandbox 的空间边界

可以把工作区表现为清晰围栏：

- 圈内项目文件可被修改
- 圈外桌面文件保持不变
- 网络连接位于另一条受控出口

文件状态的变化与不变化，可以直接证明边界存在。

### C. Sandbox 与 Approval 的两层决策

适合用决策流表达：

```text
动作
↓
边界内？
├─ 是 → 执行
└─ 否 → 审批 → 允许／拒绝
```

动画价值在于展示判断顺序，避免观众把两个概念合并成同一个开关。

### D. `AGENTS.md` 的规则注入与层级

可以展示一个 Agent 开工前依次读取全局规则和当前目录规则，再按规则选择构建命令。重点是“规则进入行动之前”，而不是展示完整 Markdown 文本。

### E. 三类上下文来源

适合把信息流汇入 Agent：

- `AGENTS.md`：项目规则
- Memory：历史会话
- Chronicle：屏幕活动

三条信息流需要使用不同标签，避免让观众误以为它们都具有同样的可靠性和作用。

### F. 权限实验的状态对照

同一个创建文件请求可以做成左右或前后状态切换：

- `read-only`：写入动作被拦截
- `workspace-write`：工作区内生成 `hello.txt`

文件树变化、权限状态和审批提示共同承担信息，不需要让画面重复整段旁白。

### G. 五概念总图

最终关系图应让 Agent 位于中心，Sandbox 形成外圈，Approval 位于出口，`AGENTS.md` 从上方注入规则，Memory／Chronicle 从下方补充上下文。它负责把前面的局部解释收束成一套完整心智模型。

## 7. 可以弱化或删除的信息

### 各平台沙箱底层实现细节

macOS Seatbelt、Windows 原生沙箱、Linux／WSL2 的具体前置条件可以简要点到，但不应展开为平台安装教程。详细操作属于下一篇“安装与登录”。

### 完整配置组合与配置文件写法

`sandbox_mode`、`approval_policy` 的完整组合、永久配置位置和所有菜单选项不应成为主体。当前视频只需让观众理解两个维度及一个日常组合示例。

### 过多生活类比

代购、儿童乐园、门禁卡、入职手册、老搭档都能辅助理解，但如果全部展开，会让信息密度下降。每个难点最多保留一个类比，优先让真实界面状态和任务过程承担解释。

### 重复的个人经历与情绪表达

“蠢事”“手心冒汗”等表达可以保留少量口语感，但不能遮住知识主线。开头案例保留一次即可。

### 安装与使用步骤

安装 Codex、登录账号、平台安装差异以及完整配置教程都应留给后续视频。本篇只保留完成权限实验所需的最小操作。

### 与 Claude Code 的逐项类比

“一模一样”“换了个壳”等判断不是解释 Codex 核心概念所必需，也容易模糊不同产品的实际差异。可以删除，不进入本篇知识骨架。

## 8. 事实边界与后续核查项

源材料已提示产品行为可能随版本变化。后续进入 Video Narrative 和口播前，应把信息分成两类：

### 稳定概念，可以作为主干

- Agent 会读取上下文、执行动作并验证结果
- Sandbox 与 Approval 是不同维度
- `AGENTS.md` 用于持久项目指导
- Memory／Chronicle 不是稳定项目规则的替代品
- 权限边界会影响同一个动作能否执行

### 易变事实，只能作为经核对的示例

- 沙箱模式和审批策略的具体名称
- 默认沙箱与默认审批行为
- `/permissions` 当前菜单文案和交互
- Memory 的默认开关、写入时机和控制入口
- Chronicle 的实验状态、套餐、平台与地区范围
- 各平台沙箱实现和安装前置条件

Content Analysis 只记录源材料中的信息边界，不在本阶段补写未经当前官方文档核对的新结论。

## 9. 认知升级路径

观众应该经历下面的认知变化：

```text
① Codex 不是能直接改任何东西吗？

↓

② 不，它是会行动的 Agent，但行动发生在边界内。

↓

③ Sandbox 负责划边界，Approval 负责管理越界许可。

↓

④ Agent 不只需要权限，还需要知道当前项目的规矩。

↓

⑤ AGENTS.md 提供稳定规则，Memory／Chronicle 只补充上下文。

↓

⑥ 同一个写文件实验，在不同边界下会出现不同结果。

↓

⑦ 所谓“时灵时不灵”，很多时候其实是权限、规则或上下文不同。
```

这条路径比按 Agent、Sandbox、Approval、`AGENTS.md`、Memory 的文章章节依次解释，更能形成因果连续性。

```text
   │
   ├─ 4. 行动时遵守什么：AGENTS.md
   │    └─ 稳定、明确的项目规则
   │
   ├─ 5. 过去的信息从哪里来

   │

   │    └─ read-only 与 workspace-write 下的同一写入请求
   │
   └─ 7. 最终结论

```
