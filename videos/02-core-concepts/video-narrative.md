# Codex 核心概念速览 · 第二步：Video Narrative

> 目标：不按术语列表机械讲解，而是围绕“为什么同一个任务有时能执行、有时会被拦住”，重新设计观众理解 Agent、Sandbox、Approval、`AGENTS.md`、Memory 与 Chronicle 的顺序。

---

## 1. 视频的叙事目标

这条视频不是为了让观众背下五个概念的定义。

真正的目标，是让观众完成一次认知变化：

```text
Codex 能改代码、跑命令
          ↓
那它应该什么都能直接做
          ↓
为什么项目里的文件改了，桌面文件却没改？
          ↓
因为 Agent 的行动发生在明确边界内
          ↓
Sandbox 决定“能不能”，Approval 决定“问不问”
          ↓
AGENTS.md 提供稳定规则，Memory／Chronicle 补充上下文
          ↓
Codex 的表现取决于目标、边界、规则和上下文如何组合
```

所以整条视频应该围绕：

> **一个会自主执行任务的 Agent，如何在权限边界、项目规则和上下文共同作用下完成工作。**

来展开。

视频结束时，观众不只要知道这些名词分别是什么，还应该能够解释：

- 为什么某个动作会直接执行
- 为什么某个动作会被阻止或请求许可
- 为什么稳定的项目约定应该写进 `AGENTS.md`
- 为什么 Memory 与 Chronicle 只能补充上下文，不能代替明确规则

---

## 2. 整体叙事结构

建议整条视频分成 8 个叙事段落：

```text
01 一个看似“失灵”的写文件任务
↓
02 先确认是谁在行动：Agent
↓
03 再揭示行动发生在哪里：Sandbox
↓
04 把“能不能”和“问不问”拆开：Approval
↓
05 Agent 开工时应该遵守什么：AGENTS.md
↓
06 过去的信息如何回来：Memory／Chronicle
↓
07 用同一个写入请求验证权限边界
↓
08 把五个概念合成一套工作模型
```

这条主线不是：

```text
概念一的定义
↓
概念二的定义
↓
概念三的定义
```

而是：

```text
先看到异常结果
↓
追问结果为什么不同
↓
逐层补齐执行者、边界、授权、规则和上下文
↓
再用实验验证
↓
最后形成统一模型
```

---

## 3. 第一段：不要先解释术语，先制造一个反常结果

### 叙事目的

先让观众产生一个具体疑问：

> Codex 明明会改文件，为什么这次只完成了一半？

不要一上来依次介绍 Agent、Sandbox 和 Approval。那会像术语词典，也无法解释这些概念为什么同时存在。

### 内容设计

给 Codex 一个看起来很直接的任务：

> 把项目目录和桌面上的一批文件统一重命名。

执行结束后，画面出现两个不同结果：

```text
项目目录
old-name.md → new-name.md
状态：已修改

桌面目录
old-name.md
状态：未修改
```

观众很容易先得出错误判断：

```text
它是不是漏做了？
它是不是只会改项目里的文件？
它是不是突然失灵了？
```

### 这一段真正表达的信息

这里先不急着给答案。

只建立一个贯穿全片的问题：

> **同一个 Agent、同一个任务，为什么不同位置会出现不同结果？**

这个问题会自然把观众带向行动者、行动边界和越界授权，而不是被动接受五个定义。

---

## 4. 第二段：先确认 Codex 不是在“给建议”，而是在执行任务

上一段已经看到真实文件状态发生变化。

现在先解释变化是谁造成的。

### 核心内容

Codex 不是只返回一段重命名建议。

它会围绕目标推进一串动作：

```text
理解目标
↓
读取目录和文件
↓
决定操作步骤
↓
执行命令或编辑文件
↓
查看结果
↓
验证或调整
```

这套过程可以压缩成：

> **想 → 做 → 看 → 再决定。**

### 用失败测试证明 Agent

为了避免 Agent 变成抽象定义，可以短暂切到一个更典型的开发任务：

```text
运行测试
↓
读取报错
↓
定位问题
↓
修改代码
↓
再次运行测试
```

普通问答只负责其中的建议环节；Agent 则能够把中间步骤真正执行出来，并根据结果继续推进。

### 这一段真正表达的信息

> **用户给出目标，Agent 负责推进和验证过程。**

也正因为它能执行真实动作，下一步才必须回答：它能在哪里行动？

---

## 5. 第三段：揭示 Sandbox，不是能力消失，而是边界出现

现在回到开头的文件重命名任务。

### 核心表达

把项目工作区表现成一块有明确边界的区域：

```text
┌──────── 工作区边界 ────────┐
│ 项目文件                    │
│ 状态：允许写入              │
└─────────────────────────────┘

边界之外：桌面文件
状态：不在当前可写范围内
```

这时再给出 Sandbox 的作用：

> **Sandbox 不是在判断任务有没有价值，而是在限制 Agent 能访问和修改哪些文件、命令、网络或其他资源。**

### 纠正第一个误解

`workspace-write` 的重点是：

> 工作区内可写。

它不是：

> 整台机器都可写。

Agent 派生出的终端命令也不会脱离这条边界。命令由 Agent 发出，不代表它自动获得了边界之外的权限。

### 这一段真正表达的信息

开头的结果不再是“做了一半”。

而是：

```text
项目文件在边界内
→ 可以被修改

桌面文件在边界外
→ 当前动作不能直接完成
```

观众到这里应该建立第二层认知：

> **Agent 决定如何推进任务，Sandbox 决定这些动作能否在当前边界内发生。**

---

## 6. 第四段：把 Sandbox 与 Approval 拆成两个连续判断

理解 Sandbox 以后，观众很容易继续追问：

> 边界外的动作，是永远不能做，还是可以先问我？

这正是 Approval 应该出现的位置。

### 不要把两者讲成两个并列开关

更适合视频的表达是一条决策流：

```text
Agent 准备执行动作
↓
动作是否在 Sandbox 边界内？
├─ 是 → 按当前权限执行
└─ 否 → 进入 Approval 判断
        ├─ 获得许可 → 在获准范围内继续
        └─ 未获许可 → 停止这个动作
```

### 核心辨析

用最短的两句话建立区分：

```text
Sandbox：能不能
Approval：问不问
```

Sandbox 描述技术边界。

Approval 描述遇到越界需求时，系统是否以及何时停下来请求用户许可。

### 纠正第二个误解

Approval 不会自动把边界变大。

同样，不出现询问也不等于 Agent 天然拥有全部权限。最终结果仍然取决于当前边界和授权策略如何组合。

### 这一段真正表达的信息

到这里，开头的“项目内成功、桌面失败”已经有了完整的权限解释：

> **动作先经过 Sandbox 判断；需要越界时，再由 Approval 管理授权过程。**

---

## 7. 第五段：有权限还不够，Agent 还要知道项目的规矩

前四段回答了：

> Agent 能不能执行某个动作。

现在需要补上另一个维度：

> 它执行时应该遵守什么规则。

### 内容设计

展示 Agent 进入项目以后，不是立刻修改代码，而是先读取项目指导文件：

```text
任务目标
↓
读取 AGENTS.md
↓
获得构建命令、测试要求、审查规则和仓库约定
↓
按项目规则执行任务
```

如果全局和项目目录中都存在规则，可以用从宽到具体的层级收束到当前工作目录。重点不是展示完整文件，而是让观众看到：

> **规则在行动之前进入 Agent 的上下文。**

### 形成反馈回路

这一段还要展示一次规则沉淀：

```text
Agent 对项目做出错误假设
↓
用户纠正
↓
把稳定约定写入 AGENTS.md
↓
后续任务继续复用
```

### 核心结论

> **权限决定 Agent 能做什么，`AGENTS.md` 决定它应该怎样做。**

这能纠正第三个误解：稳定的团队约定不应该每次临时重说，也不应该只期待系统“以后自己记住”。

---

## 8. 第六段：Memory 与 Chronicle 不是另一份项目规则

讲完 `AGENTS.md` 后，再引入跨会话上下文。

这时观众已经有了“稳定规则”的参照物，更容易理解 Memory 与 Chronicle 的边界。

### 先按信息来源区分

把三条信息流同时汇入 Agent：

```text
AGENTS.md
明确写下的项目规则
        ↓

Memory
从过去会话中提炼的信息
        ↓

Chronicle
从近期屏幕活动补充的上下文
        ↓

      Agent
```

### 这一段不做功能开启教程

重点不是介绍开关、套餐、地区、平台或存储方式。

重点是建立可靠性和用途的差异：

- `AGENTS.md` 用于明确、稳定、需要持续遵守的项目规则
- Memory 用于补充过去会话中提炼出的可复用信息
- Chronicle 用于补充近期屏幕活动形成的工作上下文

### 纠正第四个误解

Memory 不是“刚说完就会实时、永久、确定地记住一切”。

Chronicle 也不是没有代价的万能记录器；它涉及隐私、提示注入和资源限制等风险。

因此，必须稳定生效的团队约定仍然应该显式写入项目指导文件。

### 这一段真正表达的信息

> **规则负责确定性，上下文负责补充性。**

这句话把 `AGENTS.md`、Memory 与 Chronicle 放进同一张图里，但不会把它们混成同一种机制。

---

## 9. 第七段：用同一个请求，让权限边界亲眼可见

前面已经解释了概念。

现在用一个最小实验把抽象关系变成可观察结果。

### 实验设计

对 Codex 发出完全相同的请求：

> 在当前项目创建 `hello.txt`。

只改变 Sandbox 边界。

### 第一轮：只读边界

```text
请求：创建 hello.txt
模式：read-only
结果：写入动作超出当前边界
```

画面重点不是展示长错误信息，而是让文件树保持不变，并让写入动作在边界处被拦截或进入许可流程。

### 第二轮：工作区可写

```text
请求：创建 hello.txt
模式：workspace-write
结果：工作区内生成 hello.txt
```

文件树新增 `hello.txt`，形成与上一轮最直接的状态对照。

### 实验结论

```text
请求没有变
Agent 没有变
边界变了
结果就变了
```

因此观众可以亲眼验证：

> **很多看似“时灵时不灵”的表现，其实来自权限边界不同，而不是 Agent 突然变笨。**

具体菜单文案和交互路径可能变化，后续制作只把模式名称作为经核对的界面示例，不把某一条入口路径讲成唯一操作方式。

---

## 10. 第八段：最后不要复述五个定义，要把它们合成一台机器

视频最后不再逐项总结：

> Agent 是……Sandbox 是……Approval 是……

而是把前面的局部关系收束成一张统一工作模型。

### 最终关系图

```text
                    AGENTS.md
                  稳定项目规则
                        ↓
任务目标 → Agent → Sandbox 边界 → Approval → 边界外资源
             ↑
      Memory／Chronicle
        补充上下文
```

在这张图中：

- Agent 是中心执行者
- Sandbox 包住 Agent 的行动范围
- Approval 位于越界出口
- `AGENTS.md` 在行动前注入稳定规则
- Memory／Chronicle 从过去会话和近期活动补充上下文

### 最终结论

观众开头问的是：

> 为什么它没有改桌面文件？

现在应该能够回答：

> 因为 Codex 不是拥有无限权限的聊天框。它是会自主推进任务的 Agent，但每个动作都发生在权限边界内，并受到授权策略、项目规则和可用上下文的共同影响。

最后一句可以落在：

> **给清目标、画好边界、写下规则，才能稳定地让 Agent 干活。**

### 系列下一集预告

最后一个视觉事件必须进入：

> **03 · 安装与登录：在 Mac、Windows 或 Linux 上安装 Codex、登录账号并跑通第一次使用。**

可以用“不同系统如何建立第一条可用执行链”作为悬念，但不在本集展开平台安装步骤。预告卡需要独立停留约 2～3 秒，完成从概念地图到实际使用的自然过渡。

## 11. 整条视频的认知节奏

最终叙事节奏应该是：

```text
看见反常结果
↓
怀疑 Agent 漏做或失灵
↓
确认它确实在执行真实动作
↓
发现行动存在 Sandbox 边界
↓
用 Approval 解释越界授权
↓
用 AGENTS.md 补上稳定项目规则
↓
用 Memory／Chronicle 区分补充上下文
↓
通过同一请求的两轮实验验证边界
↓
把五个概念合成统一模型
↓
形成正确使用 Agent 的方法
```

这比：

```text
Agent 定义
↓
Sandbox 定义
↓
Approval 定义
↓
其他功能介绍
↓
总结
```

更适合视频。

因为每一个新概念都在回答上一个画面留下的问题，观众不是被动记词，而是在追踪因果关系。

## 12. Video Narrative 最终版

可以压缩成下面这一条主线：

```text
要求 Codex 同时修改项目文件和桌面文件
                ↓
项目文件改了，桌面文件没有变化
                ↓
它明明是会读、改、跑、验的 Agent
                ↓
为什么同一个任务只完成了边界内的部分？
                ↓
因为 Sandbox 划定了技术上的行动范围
                ↓
越界需求再由 Approval 管理是否询问和授权
                ↓

                ↓
AGENTS.md 提供明确、稳定的项目规则
                ↓
Memory／Chronicle 从过去会话和近期活动补充上下文
                ↓
同一个创建 hello.txt 的请求
在 read-only 与 workspace-write 下得到不同结果
                ↓
Agent、边界、授权、规则和上下文共同决定执行表现
                ↓
```

## 13. 下一步

完成 Video Narrative 之后，下一步应该进入：

> **Scene Script**

也就是第一次把这 8 个叙事段落拆成具体 Scene。

到了那一步，每个 Scene 都需要明确：

- `purpose`：这一幕为什么存在
- `narrativeRole`：它如何推进整条叙事
- `narrationIntent`：声音负责解释什么
- `visualIntent`：画面负责演示或证明什么
- `visualType`：采用哪种视觉表达
- `keyOnScreenText`：真正需要强调的屏幕文字
- `videoValue`：为什么这一幕必须用视频表达

Scene Script 需要优先保留四个关键视觉事件：

1. 项目文件与桌面文件的结果分叉
2. Sandbox 与 Approval 的连续决策流
3. `AGENTS.md`、Memory、Chronicle 汇入 Agent 的不同信息路径
4. `read-only` 与 `workspace-write` 下同一写入请求的状态对照

从 Scene Script 开始，才正式进入逐幕的视频制作设计。
