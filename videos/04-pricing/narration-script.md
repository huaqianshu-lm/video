# Codex 订阅与计费 · 第四步：Narration Script

## Scene 01｜同样一条消息，为什么消耗不同？

看起来同样是一条消息，实际消耗却可能完全不同。

让 AI 帮你改一个几行的小脚本，和让它处理一个大型代码库，表面上都只是发出一次请求。但后者可能还要读取更多文件，理解更大的项目，带上更长的历史会话，以及更多规则。

所以，消息条数只能说明你发了几次消息，不能单独代表实际用量。真正影响消耗的，是每次任务需要处理多少内容，以及要完成多少工作。

## Scene 02｜工具、模型与 token 不是一回事

要理解后面的计费，先把三个层次分开。

Codex 是使用模型能力的工具入口，模型负责处理你的任务，而输入 token、输出 token，以及每一轮携带的上下文，是观察处理量的基本计量单位。

输入 token 包括你给出的指令和需要读取的内容，输出 token 是模型生成的结果，上下文则可能包含文件、历史会话和其他相关信息。

Token 不是固定的字符数，也不等于固定的消息数。相同的一句话，放在不同的任务和上下文里，带来的实际处理量可能不同。

## Scene 03｜ChatGPT 订阅这条账

如果你登录 ChatGPT 账号，首先面对的是订阅这条账。

你支付固定的月费，按照当前订阅规则获得相应的使用额度和能力。这里的可用量通常不是每天固定清零，而是受到滚动限额和当前使用情况影响。

当订阅用量达到限额时，部分情况下可以购买积分，继续获得额外的使用通道。但积分解决的是订阅路径下的继续使用问题，它不会把 ChatGPT 订阅和 API 账单合并成一套账。

## Scene 04｜API key 这条账：两套账

另一条路径是 API key。

它主要面向脚本、CI/CD 和其他程序化任务。程序通过 API key 调用模型，按照实际的输入 token 和输出 token 用量计费，账单在 OpenAI Platform 中单独计算。

这就形成了两套账：一套是 ChatGPT 账号对应的订阅和积分，另一套是 API key 对应的 Platform 账单。

ChatGPT 的月费不是 API 余额，ChatGPT 积分也不是 API key 的预充值。判断费用之前，先确认自己走的是哪条使用路径。

## Scene 05｜套餐先按使用场景分层

确认付费路径之后，套餐不要先从金额或某个数字开始比较，而要先看自己的使用场景。

个人开发者通常先关注日常开发是否够用；如果是高频、重度的个人使用，就要进一步关注使用强度和额度空间。

团队协作时，重点会转向成员管理、共享工作方式和组织协作。到了组织级部署，还要关注管理、安全和合规需求。

因此，Plus、Pro、Business、Enterprise and Edu 可以先理解成从个人到重度个人、团队，再到组织级部署的不同层次。具体金额、消息区间、模型名称和支持范围可能变化，购买前要以当前页面为准；Free 或 Go 是否适用，也应单独核对当前支持范围。

## Scene 06｜滚动窗口与任务复杂度

限额更适合被理解成一个时间窗口里的动态资源，而不是每天固定清零的计数器。

以五小时滚动窗口为例，窗口会随着时间向前移动。一个小脚本可能只占用较小的处理量，而大型代码库、长会话、复杂任务，或者不同模型，都可能让同一条消息消耗得更快。

当窗口内的可用量触顶时，订阅路径下的积分可能提供额外使用通道。但它不会让上下文自动变小，也不会改变 ChatGPT 订阅和 API 账单之间的边界。

## Scene 07｜升级前先控制上下文

当你觉得额度不够时，先别急着升级套餐。很多时候，更有效的第一步是减少无效上下文。

第一，缩小输入范围，把模糊的“帮我看看”改成明确的文件、函数或问题。第二，压缩固定上下文，把一大套规则整理成真正需要的部分。第三，按需连接工具，不要让每个任务都加载全部能力。第四，让模型和任务匹配，简单工作不必一直使用最重的模型。

切换到无关工作时，还可以用 `/new` 清理旧会话，避免前一个任务继续影响当前上下文。

成本控制的核心不是把所有东西都关掉，而是让上下文变得短而准。

## Scene 08｜查看、调整、清理、复盘

可以把用量管理变成一个固定的四步习惯：查看、调整、清理、复盘。

开始任务前，用 `/status` 查看当前状态、审批策略和上下文容量；用 `/model` 确认当前模型是否适合这项工作。需要切换到另一件事时，用 `/new` 清理无关会话。

任务完成后再复盘用量：ChatGPT 用户查看订阅用量面板，API 用户查看 API Platform 账单。这样，你看到的是各自路径下的真实使用情况，而不是把两套账混成一个总数。

## Scene 09｜先识别付费路径，再进入模型接入

最后，可以用四个问题判断自己的下一步：我登录的是哪条路径？当前任务是手动使用还是程序化调用？任务需要多大的上下文？我应该在哪里观察用量？

先确认是订阅额度还是 API 按量计费，再结合任务类型和上下文规模，决定是否需要调整套餐或工作方式。很多额度问题，先通过减少无效上下文就能得到改善。
