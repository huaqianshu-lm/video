# Codex 订阅与计费 · Video Narrative

> 目标：不按套餐页面的栏目顺序罗列价格，而是让观众先建立「计费对象 → 付费路径 → 使用限额 → 成本控制」的判断框架。

---

## 1. 视频的叙事目标

这条视频不是为了替观众选择某一个套餐，也不是把价格表搬到画面上。

真正要完成的认知变化是：

```text
Codex 的成本就是消息数量
              ↓
先要分清：谁在登录、谁在付费、谁在处理任务
              ↓
ChatGPT 订阅和 API key 是两套彼此独立的账
              ↓
订阅用量还会受模型、任务复杂度和上下文规模影响
              ↓
套餐选择应先匹配使用场景，再比较强度、额度和预算
              ↓
真正稳定的成本控制，是减少无效上下文并持续观察用量
```

观众最后应该能够回答四个问题：

1. 我现在使用的是订阅额度，还是 API 按量计费？
2. 我的工作方式更像个人手动使用，还是程序化自动化？
3. 我遇到的额度问题，究竟来自套餐边界，还是任务和上下文过重？
4. 下一次开始任务前，我可以做什么来减少不必要的消耗？

核心结论：

> **人用 ChatGPT 订阅看用量限额，机器用 API key 按 token 计费；省额度的核心是减少不必要的上下文，而不是只盯着消息条数。**

---

## 2. 整体叙事结构

建议整条视频沿着一条「先纠正误解，再建立判断框架，最后给出操作闭环」的主线展开：

```text
01 先问：为什么同样是一条消息，消耗可能完全不同？
↓
02 拆开计费对象：工具、模型处理和 token 不是一回事
↓
03 画出两套账：ChatGPT 订阅登录 vs API key 登录
↓
04 再看订阅内部：套餐其实是在分层使用场景
↓
05 解释限额：滚动窗口和任务复杂度如何改变可用量
↓
06 处理触顶：积分能解决什么，不能解决什么
↓
07 找到真正的杠杆：减少上下文浪费，控制消耗速度
↓
08 建立用量闭环：查看状态、匹配模型、清理会话、复盘账单
↓
09 下一步：从付费路径延伸到模型接入方式
```

这条顺序有意把“套餐比较”放在付费逻辑之后。观众先知道自己比较的到底是什么，后面的 Plus、Pro、Business、Enterprise & Edu 才不会被误解成一张脱离使用方式的价格表。

## 3. 叙事原则

### 3.1 先解决计费误解，再展示方案

开场不直接报套餐名称或金额，而是从一个常见判断切入：

> 「我只发了几条消息，为什么额度掉得这么快？」

这个问题能够把观众从“数消息”带到“看任务实际处理了多少内容”。随后再解释输入、输出和上下文共同形成 token 消耗，让计费对象先于价格出现。

### 3.2 用两条路径建立清晰边界

ChatGPT 账号登录和 API key 登录必须作为两条平行路径处理：

```text
ChatGPT 账号
固定月费 → 订阅用量规则 → 达到限额 → 可购买积分

API key
程序或脚本 → 输入／输出 token → 按量扣费 → Platform 账单
```

中间放置明确的「两套账」边界，避免观众把订阅积分、订阅月费和 API 账单混在一起。两条路径的差别重点是“人手动使用”和“机器程序化使用”，不是简单地比较谁永远更便宜。

### 3.3 套餐用场景分层，不用易变数字当主角

Plus、Pro、Business、Enterprise & Edu 按使用者和工作方式排列：

```text
个人开发者 → 高频重度个人 → 团队协作 → 组织级部署
```

具体金额、消息区间、模型名称、积分费率和 Free／Go 支持范围属于会变化的官方信息。叙事只保留其判断维度，并把当前页面核对作为观看后的动作，不把某个快照数字写成永久承诺。

### 3.4 用反转说明“升级”不是唯一答案

在观众已经知道套餐分层后，制造一个反转：

> 额度消耗得快，不一定只是套餐太小，也可能是每轮请求都带着过大的项目、规则、工具描述和历史对话。

这个转折把问题从“要不要升级”转向“消耗速度是否可以降低”，并自然引出上下文管理和模型匹配。

### 3.5 声音解释规则，画面展示账本和过程

旁白负责解释 token、滚动窗口、两套账和套餐判断条件；画面负责展示：

- 一条任务如何拆成输入、输出与上下文。
- 两种登录路径如何进入不同的账本。
- 同一个时间窗口内，小脚本与大型项目为何占用速度不同。
- 模糊任务、巨型规则、全挂工具和全程强模型如何堆大上下文。
- `/status`、`/model`、`/new` 如何组成操作闭环。

不要让旁白和屏幕文字重复念同一张价格卡片。文字只承担关键标签、边界和状态变化。

## 4. 分段叙事设计

### 第一段：先从“消息条数”制造问题

#### 叙事目的

打破“发一条消息就消耗一格额度”的直觉，让观众意识到相同消息数量可能对应完全不同的实际消耗。

#### 内容推进

从两个表面相同的请求开始：一个只处理小脚本，另一个读取大型代码库、长会话和多份规则。两者都可以只显示为一条消息，但背后的处理量并不相同。

先不进入套餐名称，也不把个别用户的额度经历当作普遍结论。只提出核心问题：真正应该观察的，究竟是消息数量，还是每次任务携带和生成的内容规模？

#### 观众获得的结论

> 消息条数只能提供表面信息，不能单独代表实际用量。

#### 视觉叙事方向

用同样大小的消息入口，连接到大小不同的上下文块，制造“看起来一样，消耗速度不同”的第一处反差。

---

### 第二段：拆开工具、模型和 token

#### 叙事目的

建立后续所有计费解释都需要的三层模型，避免把 Codex 工具入口直接等同于收费单位。

#### 内容推进

先把 Codex 放在入口层：它是使用模型能力的工具。再把模型处理放在中间层：任务真正消耗的是模型处理时使用的算力。最后落到 token：输入 token、输出 token，以及每轮对话携带的上下文共同影响实际消耗。

需要特别说明，token 不是简单的字符数，也不能拿固定的 token 数去换算固定消息条数。输出通常更昂贵，而长文件、长会话和冗长项目规则会让输入侧的上下文迅速膨胀。

#### 观众获得的结论

> Codex 是入口，模型处理才产生实际消耗，token 是观察这类消耗的基本计量单位。

#### 视觉叙事方向

用三层拆解图把“工具入口 → 模型处理 → 输入／输出 token”逐层展开，画面重点从产品名称转移到处理量。

---

### 第三段：画出 ChatGPT 订阅这条账

#### 叙事目的

让观众先理解订阅登录的付费对象和使用边界，再进入套餐差异。

#### 内容推进

ChatGPT 账号登录对应固定月费换取一定订阅权益。可用量受本地消息、云端任务、模型、任务规模和滚动窗口等规则共同影响。达到相关限额后，积分可以让使用继续，但积分解决的是“继续使用”，不是把订阅和 API 账单合并成同一套账。

这条路径更适合个人日常手动使用，画面要把“月费”“包含的用量”“滚动限额”“积分”排成因果链，而不是堆一组孤立数字。

#### 观众获得的结论

> 订阅登录首先要看包含的用量和使用规则，不能只看月费金额。

#### 视觉叙事方向

用一条从月费到用量限额、再到积分的单向路径，明确积分是限额后的额外用量机制。

---

### 第四段：画出 API key 这条账，并标记“两套账”

#### 叙事目的

解释为什么脚本、CI/CD 和程序化任务要单独看 API 账单，切断“订阅够不够用等于 API 价格”的错误类比。

#### 内容推进

API key 登录不依赖 ChatGPT 订阅额度，而是按实际 token 用量实时扣费，账单在 OpenAI Platform 单独计算。这种路径更适合自动化、CI/CD 和其他程序化任务。

这一段必须明确三个不能混算的对象：ChatGPT 订阅月费、ChatGPT 积分和 API key 账单。它们服务的使用路径不同，功能边界也不同。

#### 观众获得的结论

> 人手动使用和机器程序化使用对应两套独立的付费逻辑，先确认登录路径，再谈成本。

#### 视觉叙事方向

与上一段形成左右对照：左侧是订阅额度与积分，右侧是 API key、token 用量与 Platform 账单；中央固定显示「两套账」。

---

### 第五段：把套餐还原成使用场景的分层

#### 叙事目的

让观众用工作方式和组织规模理解套餐，而不是在不清楚需求时直接追逐更大的数字。

#### 内容推进

先判断是个人还是团队，再判断是手动还是自动化，最后才看使用强度、用量上限、管理需求和预算：

```text
Plus
个人开发者的基础订阅，先看日常工作是否够用。

Pro
高频、重度个人使用，重点看更高的用量上限和额外能力。

Business
团队使用，重点从个人额度转向席位、管理和安全控制。

Enterprise & Edu
组织级部署，重点看弹性用量、优先处理、身份和审计能力。
```

Free 与 Go 的 Codex 支持范围如果当前页面没有明确承诺，就保留为待核对边界，不能把“可能进入某个入口”表达成“获得完整编程能力”。

#### 观众获得的结论

> 套餐选择顺序是场景、强度、管理需求和预算，而不是先找一个看起来最大的额度。

#### 视觉叙事方向

把四档套餐做成从个人到组织的场景卡片，弱化金额，突出使用者、工作方式和管理范围；Free／Go 作为信息未确认的边界提示，不作为主路径。

---

### 第六段：解释滚动窗口、任务复杂度和触顶

#### 叙事目的

把“套餐包含多少”转化为动态的用量模型，解释为什么限额不是每天固定清零，也不是每条消息均匀消耗。

#### 内容推进

用 5 小时滚动窗口作为理解例子：它不是自然日清零的静态计数器。同一窗口里，小脚本、大型代码库和长会话会以不同速度消耗可用量；模型、任务规模、复杂度和执行位置也会改变单位消息的消耗。

当额度触顶时，积分提供的是额外使用通道，但它不会改变当前任务的上下文体积，也不会把 API key 账单纳入订阅账本。具体可用量和价格应以当前官方页面为准，画面不固定承诺某个数字。

#### 观众获得的结论

> 额度是时间窗口中的动态资源，任务越重、上下文越大，消耗速度越快。

#### 视觉叙事方向

用横向滚动时间窗承载三种大小不同的消耗块，让观众看到“窗口相同，速度不同”；触顶后只增加积分分支，不改写两套账的边界。

---

### 第七段：制造反转——升级前先控制上下文

#### 叙事目的

把观众从“额度不够就升级”带到“先减少无效输入”，给出成本控制的核心原则。

#### 内容推进

把消耗速度拆成四个可以主动调整的杠杆：

1. 缩小输入范围：明确任务、文件和目标函数，减少盲目搜索。
2. 压缩固定上下文：精简根目录规则文件，只在需要的目录加载具体说明。
3. 按需连接工具：不使用的 MCP server 不要长期挂载，减少重复注入的工具描述。
4. 匹配模型与任务：常规任务使用更小的模型，复杂任务再使用更强模型。

再补充会话管理：切换到无关工作时用 `/new` 重置上下文，避免历史内容在后续每轮继续占用输入空间。

这里不承诺固定节省比例，只展示上下文从“大而杂”变成“短而准”后，消耗速度可以被管理。

#### 观众获得的结论

> 成本控制的第一杠杆是上下文管理，升级套餐只是众多选择之一。

#### 视觉叙事方向

用四组“浪费状态 → 精确状态”替换卡片：模糊请求对比精确文件／函数，巨型规则对比分层规则，全挂工具对比按需开启，全程强模型对比任务匹配模型。视觉重点是上下文体积变化，不显示虚构的节省百分比。

---

### 第八段：用 CLI 建立用量感知闭环

#### 叙事目的

让成本管理从事后查看账单，变成任务过程中的连续动作。

#### 内容推进

把三个 CLI 动作串成一个闭环：

```text
/status
先看模型、审批策略、上下文容量和会话状态
        ↓
/model
根据任务复杂度切换匹配的模型
        ↓
/new
切换到无关工作时清理旧上下文
        ↓
复盘
订阅用户查看 Codex 用量面板；API key 用户查看 Platform 账单和用量
```

这不是一套自动省钱按钮，而是一种在开始、执行、切换和复盘时保持用量可见的工作习惯。结尾将“查看 → 调整 → 清理 → 复盘”闭合，回扣开场的额度焦虑。

#### 观众获得的结论

> 先观察当前状态，再匹配模型和上下文，最后到对应账户复盘，成本才真正可控。

#### 视觉叙事方向

用终端状态逐步变化串联 `/status`、`/model`、`/new`，末端分流到订阅用量面板和 API Platform 账单，形成两个出口而不是一个总账。

---

### 第九段：以模型接入方式承接下一篇

#### 叙事目的

收束当前视频的判断框架，并为系列下一篇留下明确但不展开的认知缺口。

#### 内容推进

总结不是再次重复四个套餐，而是回到两条付费路径：订阅登录适合围绕个人使用量做管理，API key 适合围绕程序化 token 用量做管理。无论走哪条路径，都要先知道自己的登录方式、任务类型、上下文规模和用量观察位置。

最后承接下一篇：当观众已经理解“付费路径”和“计量方式”之后，下一步自然会问：如果要接入 DeepSeek 等国产模型，应该走什么模型接入方式？这一问只作为预告，不在本条视频中提前展开具体配置。

#### 观众获得的结论

> 先识别自己的付费路径和消耗来源，再决定要不要换套餐；模型接入是下一层问题。

#### 视觉叙事方向

让两条账本在结尾收束成一个选择框架，旁边出现下一集预告卡「接入 DeepSeek 等国产模型」，预告作为最后一个视觉事件保留约 2～3 秒的阅读停留，不与字幕区域重叠。

## 5. 整条视频的认知节奏

这条视频的节奏不是“套餐介绍 → 价格对比 → 总结”，而是持续完成四次认知推进：

| 认知阶段 | 观众的问题 | 视频给出的回答 | 叙事作用 |
| --- | --- | --- | --- |
| 产生疑问 | 为什么消息少，额度却掉得快？ | 消耗与任务处理量有关 | 打破消息计数直觉 |
| 建立边界 | 到底是谁在收费？ | 工具、模型、token 分属不同层 | 给后续判断提供坐标 |
| 做出判断 | 我该看订阅还是 API？ | 先看登录方式和工作场景 | 切断两套账混算 |
| 调整行为 | 额度不够只能升级吗？ | 先缩小上下文并匹配任务 | 把问题变成可执行动作 |
| 形成闭环 | 如何持续知道自己在消耗什么？ | 查看、调整、清理、复盘 | 让结论可以落地 |

整体情绪应从“额度焦虑”逐步转向“账本清晰”，再转向“我可以主动控制消耗”。不要制造促销感，也不要用固定价格或个别使用经历制造普遍承诺。

## 6. 画面文字与事实边界

Video Narrative 阶段只确定叙事关系，后续所有屏幕文字仍需回溯到当前视频的生产资料。当前已确定的文字边界如下：

- 可以稳定使用的概念标签：`ChatGPT 订阅`、`API key`、`两套账`、`输入 token`、`输出 token`、`上下文`、`5 小时滚动窗口`、`/status`、`/model`、`/new`。
- 套餐名称可以作为定位标签，但金额、消息区间、模型名称、积分费率和支持范围必须按当前官方页面核对，不能在叙事中固化为永久事实。
- 不使用“某套餐一定适合所有个人用户”“升级后一定不会触顶”“固定 token 等于固定消息数”等绝对承诺。
- 不把个人“几天触顶”的经历写成普遍用量结论，只把它抽象成任务复杂度影响消耗速度的案例关系。
- 不把 API key 价格和订阅月费、积分放进同一张总价卡，不暗示积分可以抵扣 API 账单。

## 7. Video Narrative 最终版

可以压缩成下面这一条主线：

```text
观众发现消息数量解释不了额度变化
          ↓
先拆开工具、模型处理和 token 计量
          ↓
再分清 ChatGPT 订阅与 API key 两套账
          ↓
用个人、重度个人、团队、组织场景理解套餐分层
          ↓
用滚动窗口和任务复杂度解释动态限额
          ↓
触顶时，积分只能解决继续使用，不能改变账本边界
          ↓
升级前先缩小输入、压缩规则、按需工具、匹配模型
          ↓
通过 /status → /model → /new → 复盘建立用量闭环
          ↓
带着清晰的付费路径进入下一篇模型接入主题
```

最终认知落点是：

> **先识别自己是在用订阅额度还是 API 按量计费，再判断任务和上下文如何消耗用量；选择方案只是成本管理的一步，持续控制上下文才是长期方法。**

## 8. 下一步

完成 Video Narrative 后，下一步进入：

> **Scene Script**

下一阶段需要把上述九个叙事段落进一步拆成具有明确认知任务的 Scene，并为每个 Scene 定义：

- Scene 的目的和叙事作用。
- 口播需要解释的关系。
- 画面需要演示或证明的状态变化。
- Visual Type 和关键屏幕文字。
- 这一幕为什么必须用视频表达。
- 与前后 Scene 的转折和节奏关系。

本阶段不预先写口播正文、字幕、TTS 输入、视觉原型或 Remotion 配置。
