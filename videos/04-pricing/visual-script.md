# Codex 订阅与计费 · 第六步：Visual Script

> 目标：把 9 个 Scene 设计为可验证的横屏视觉事件。声音负责解释计费关系与判断顺序，画面负责展示处理量变化、两套账的分流、滚动窗口和可执行的用量管理动作。

## 全局视觉原则

### 1. 用“路径、处理量、账本”组织信息

- 全片使用近黑背景、细网格和低强度青绿色环境光，延续 Codex 系列的系统感。
- 青绿色代表当前正在观察的主路径，蓝色用于 Platform 账单和外部出口，琥珀色只用于达到限额、需要核对或边界提醒。
- 用入口节点、上下文块、账本和状态卡表达关系，不把套餐做成静态价格墙。
- 不固化易变化的金额、消息区间、模型名称或支持范围；需要提示时使用已有的“支持范围待核对”。

### 2. 画面演示过程，不复述整段口播

- 口播解释工具、模型、token、订阅和 API 的区别，画面用拆层、汇入、分流和状态变化证明这些关系。
- 每个 Scene 只保留一组主视觉事件，屏幕文字只放当前关系的关键词、命令、路径和结论。
- 卡片正文保持短句，避免把完整解释搬到画面；字幕区始终与主体视觉区分离。

### 3. 横屏结构与字幕安全区

- 画布按 1920 × 1080、16:9 构图，系列标题和每个 Scene 标题统一从左上安全边距开始。
- 主体视觉位于中上部，底部保留约 150px 字幕安全区；所有流程、时间窗口和账本卡片不得压入字幕区。
- 标题最多两行，卡片数量控制在四张以内，长文本拆成多次状态变化而不是缩小字号。
- Scene 09 的下一集预告卡在判断框架完成后单独出现，放在字幕区上方并保留约 2～3 秒停留。

### 4. 统一界面语言

- 文件、会话、规则和工具都使用低对比度深色面板、细边框、圆角和克制阴影。
- 连接线、箭头和窗口沿用同一套线宽；token、账单和限额状态使用小型等宽标签，避免模拟完整的真实产品界面。
- 不出现预览导航、调试标记、制作说明或与当前视频无关的业务文案。

### 5. 动画服务于计量关系

- 展开动画表达上下文体积和处理层级，大小差异必须清晰可见。
- 分流动画表达订阅路径与 API key 路径不能混算；窗口移动表达限额随时间变化。
- 收缩、替换和清理动画表达降低无效上下文的主动动作；不使用与内容无关的旋转、粒子爆炸或高强度发光。

# Scene 01｜同样一条消息，为什么消耗不同？

## 视觉目标

用两个相同的消息入口制造表面相同的起点，再以不同大小的上下文块和不同速度的消耗条形成反差，让“消息条数 ≠ 实际用量”成为可见结论。

## 画面结构

- 标题固定在左上，中央并列两个同尺寸消息入口。
- 左侧连接到“小脚本”卡，卡内只出现少量文件和短会话线条。
- 右侧连接到“大型项目＋长会话＋规则”上下文堆栈，堆栈高度和连接线数量明显更多。
- 两条路径底部各有一条用量条，右侧消耗速度更快；字幕区保持空置。

## 动画

1. 两个相同的消息入口同时亮起，确认起点相同。
2. 左侧展开小脚本，右侧连续展开大型项目、长会话和规则上下文块。
3. 两组上下文块沿连线汇入各自用量条，右侧用量条更快推进。
4. 两个入口保持同样数量，中央结论最后出现，锁定消息数量与实际用量的差异。

## 屏幕文字

```text
消息条数 ≠ 实际用量
小脚本
大型项目＋长会话＋规则
```

## Visual Type

`ComparisonScene + OpeningScene`

# Scene 02｜工具、模型与 token 不是一回事

## 视觉目标

把 Codex 入口逐层拆到模型处理和 token／上下文计量，画面帮助观众建立三层坐标，而不是把入口直接等同于收费单位。

## 画面结构

- 左侧放一个 Codex 入口节点，中央为模型处理层，右侧为输入 token、输出 token 和上下文三个计量节点。
- 长文件、历史会话和规则以小型输入块从下方汇入上下文节点。
- 三层节点使用逐级变亮的连接线，token 节点保持同一层级，不做字符数换算。

## 动画

1. Codex 入口先单独出现，随后沿水平轴展开到模型处理。
2. 模型处理层分出输入 token、输出 token 和上下文三个节点。
3. 长文件、历史会话和规则块汇入上下文，连接线逐条点亮。
4. 三层关系稳定后，计量节点保留为观察坐标，不出现固定字符数或消息数的替代表达。

## 屏幕文字

```text
工具入口
模型处理
输入 token
输出 token
上下文
```

## Visual Type

`ConceptScene + Layered Diagram`

# Scene 03｜ChatGPT 订阅这条账

## 视觉目标

沿单向路径展示 ChatGPT 账号、月费、订阅规则、滚动限额和积分的先后关系，明确积分是限额后的订阅路径分支。

## 画面结构

- 主体是一条从左上向右下推进的订阅路径，节点之间用青绿色连线相连。
- 路径依次包含 ChatGPT 订阅、固定月费、订阅用量规则和滚动限额。
- 滚动限额节点后向下分出积分卡，积分卡不与固定月费并列，也不接入 API 账本。

## 动画

1. ChatGPT 订阅节点亮起，固定月费卡沿路径进入。
2. 订阅用量规则和滚动限额依次变为已观察状态。
3. 限额节点触发后，积分从下方分支出现，主路径保留“达到限额”的状态。
4. 积分支路停在订阅账本内，画面不连向 API key 或 Platform 账单。

## 屏幕文字

```text
ChatGPT 订阅
固定月费
订阅用量规则
滚动限额
积分
```

## Visual Type

`StepListScene + Process Path`

# Scene 04｜API key 这条账：两套账

## 视觉目标

与上一幕形成平行对照，展示程序化调用从程序或脚本到 API key、token 和 Platform 账单的独立路径。

## 画面结构

- 画面中央固定放置“两套账”分界标识。
- 左侧保留缩小后的 ChatGPT 订阅路径，归入订阅账本；右侧展开程序或脚本、API key、输入／输出 token 和 Platform 账单。
- ChatGPT 订阅、ChatGPT 积分和 API key 分别回到所属账本，账本之间不画汇总箭头。

## 动画

1. 左侧订阅路径从 Scene 03 的结构收缩为第一本账。
2. 右侧程序或脚本卡出现，经过 API key 后分出输入／输出 token。
3. token 流沿蓝色连线进入 Platform 账单，中央“两套账”同时亮起。
4. 三种对象分别回到对应账本，交叉连线被边界线阻断。

## 屏幕文字

```text
两套账
ChatGPT 订阅
ChatGPT 积分
API key
Platform 账单
```

## Visual Type

`ComparisonScene + Connection Diagram`

# Scene 05｜套餐先按使用场景分层

## 视觉目标

让套餐选择从金额比较转成使用场景分层，画面只展示使用者、工作方式和管理重点，不锁定易变的产品细节。

## 画面结构

- 四张场景卡按从个人到组织的顺序由左向右展开，卡片高度保持一致。
- 第一张对应 Plus 和个人开发者，第二张对应 Pro 和高频重度个人，第三张对应 Business 和团队协作，第四张对应 Enterprise & Edu 和组织级部署。
- 卡片底部只放使用强度、协作、管理和安全等判断维度；画面边缘另放“支持范围待核对”边界提示，不进入主排序。

## 动画

1. 个人开发者卡先出现，Plus 标签与卡片连接。
2. 高频重度个人卡向右展开，Pro 标签亮起，强调使用强度。
3. 团队协作卡与组织级部署卡依次进入，分别接上 Business 和 Enterprise & Edu。
4. 四张卡稳定排列，右下角出现支持范围待核对提示，避免把边界提示误读为第五个套餐层级。

## 屏幕文字

```text
Plus
Pro
Business
Enterprise & Edu
个人 → 重度个人 → 团队 → 组织
支持范围待核对
```

## Visual Type

`ComparisonScene + StepListScene`

# Scene 06｜滚动窗口与任务复杂度

## 视觉目标

用移动的时间窗口和不同大小的消耗块说明限额是动态资源，并把触顶后的积分支路与 API 账本保持隔离。

## 画面结构

- 中央是一条持续向右移动的 5 小时滚动窗口，窗口内有连续刻度但不做每日清零标记。
- 窗口内依次放入小脚本、大型项目和长会话三组不同大小的消耗块。
- 窗口右端到达“达到限额”状态后，从订阅账本向下分出积分支路；右侧另保留独立的 API 账本轮廓。

## 动画

1. 5 小时滚动窗口向前移动，小脚本消耗块先进入并占用少量空间。
2. 大型项目和长会话块依次进入，较大的块让窗口内可用空间更快减少。
3. 窗口推进到达到限额，边界转为琥珀色并暂停。
4. 积分从订阅账本分出，API 账本保持原位，最后显示两者不能混算的边界。

## 屏幕文字

```text
5 小时滚动窗口
小脚本
大型项目
长会话
达到限额
积分 ≠ API 账单
```

## Visual Type

`Process + ComparisonScene`

# Scene 07｜升级前先控制上下文

## 视觉目标

把“先减少无效输入”的建议变成四组可见的收缩与替换动作，并用 `/new` 完成无关会话清理。

## 画面结构

- 画面中央为一条从“大而杂”到“短而准”的上下文带，四个动作依次作用于这条带。
- 左侧依次显示模糊请求、巨型规则、全挂工具和全程强模型的浪费状态；右侧显示对应的精确文件／函数、分层规则、按需工具和任务匹配模型。
- 最后旧会话从工作区移出，`/new` 命令固定在清理动作旁，不与四个调整方向混为一个模型选择卡。

## 动画

1. 模糊请求收缩为明确文件或函数，第一组上下文块减少。
2. 巨型规则折叠为分层规则，固定上下文继续变短。
3. 全挂工具切换为按需连接，随后全程强模型切换为任务匹配模型。
4. 旧会话滑出当前工作区，`/new` 亮起，所有动作收束到“短而准”。

## 屏幕文字

```text
缩小输入范围
压缩固定上下文
按需连接工具
匹配模型与任务
/new
短而准
```

`Process + StepListScene`

# Scene 08｜查看、调整、清理、复盘

## 视觉目标

用一个终端状态闭环演示四步用量管理习惯，并在结尾将订阅和 API 用户分流到各自的观察位置。

## 画面结构

- 主体为大尺寸终端窗口，顶部状态栏显示当前任务状态和上下文容量。
- 终端下方依次保留 `/status`、`/model`、`/new` 三次操作痕迹，右侧用四个短状态标签串起查看、调整、清理、复盘。
- 复盘状态后，终端下方分成两个出口：订阅用量面板和 API Platform 账单；两条出口不汇总。

## 动画

1. `/status` 输入并回车，当前状态、审批策略和上下文容量出现。
2. `/model` 执行后，当前模型状态切换为与任务匹配的状态。
3. `/new` 执行后，无关会话从终端工作区移除，清理状态完成。
4. 复盘节点亮起，终端向订阅用量面板和 API Platform 账单分流，形成双出口闭环。

## 屏幕文字

```text
/status
/model
/new
查看
调整
清理
复盘
订阅用量面板
API Platform 账单
```

# Scene 09｜先识别付费路径，再进入模型接入

## 视觉目标

把两本账收束成四问判断框架，完成当前视频的认知闭环，并将“接入 DeepSeek 等国产模型”作为最后一个独立视觉事件。

## 画面结构

- 上半部保留订阅账本和 API 账本的两个入口，随后收束为四张判断卡：登录路径、任务类型、上下文规模、用量观察位置。
- 四张卡按顺序进入中央判断框架，周围不再出现套餐金额或新的模型配置细节。
- 判断框架稳定后，下一集预告卡从右侧进入，放在字幕区上方并与字幕保持间距；预告卡单独占据最后的停留时间。

## 动画

1. 订阅账本和 API 账本从两侧向中央靠拢，但保留两条独立边界。
2. 登录路径、任务类型、上下文规模和用量观察位置四张卡依次落位。
3. 四张卡完成后，中央判断框架锁定，账本路径保持可追溯。
4. 最后才让下一集预告卡出现，卡片保持约 2～3 秒可读停留，随后不再添加新的视觉事件。

## 屏幕文字

```text
订阅额度 or API 按量计费
任务类型
上下文规模
用量观察位置
接入 DeepSeek 等国产模型
```

`SummaryScene + Decision Framework`

## 全片视觉类型／组件／动画标准

- `OpeningScene`：用于 Scene 01 的同消息反差，优先使用入口卡、上下文块和消耗条。
- `ConceptScene`：用于 Scene 02 的三层计量关系，优先使用节点、连线和汇入动画。
- `StepListScene`：用于 Scene 03、05、07 的路径或分层动作，单次只突出一个步骤。
- `ComparisonScene`：用于 Scene 01、04、05、06 的并列关系，左右或前后路径必须保持同一视觉尺度。
- `TerminalScene`：用于 Scene 08，终端命令和状态变化使用等宽字体，命令只展示当前 Scene 已声明的命令。
- `SummaryScene`：用于 Scene 09，先完成判断框架，再显示下一集预告。
- 所有 Scene 复用 Codex 的近黑网格、圆角面板、细边框、左上标题锚点和底部字幕安全区；不在 Scene 内另起一套外壳或标题定位。
- 动画统一采用淡入、位移、展开、收缩、连线和状态变色；视觉事件按顺序完成后再切换，不使用与主题无关的复杂转场。
- 屏幕文字只使用各 Scene 已列出的关键词、命令、路径和结论；字幕负责承载完整口播，画面不重复整段解释。
