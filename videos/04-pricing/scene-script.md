# Codex 订阅与计费 · Scene Script

> 本文件把 Video Narrative 拆成 9 个具有独立认知任务的 Scene。本阶段只定义叙事、口播方向和视觉表达，不预先写口播正文、字幕、TTS 输入、视觉原型或 Remotion 配置。

## Scene 01｜同样一条消息，为什么消耗不同？

### 目的

打破“发一条消息就消耗一格额度”的直觉，让观众先意识到消息条数不能单独代表实际用量。

### narrativeRole

以额度焦虑开场，提出整条视频要解决的问题，并为后续引入任务处理量建立悬念。

### narrationIntent

解释两个表面相同的请求，可能因为读取的文件、项目规模、历史会话和规则数量不同，而产生完全不同的处理量；暂不进入套餐和价格。

### visualIntent

先出现两个相同大小的消息入口，随后分别展开为“小脚本”和“大型代码库＋长会话＋多份规则”上下文块。让第二条路径的上下文块明显更大，并以消耗速度变化制造第一处反差。

### visualType

Comparison／OpeningScene

### keyOnScreenText

`消息条数 ≠ 实际用量`；`小脚本`；`大型项目＋长会话＋规则`

### videoValue

通过同一时间内的展开、连接和消耗速度变化，把“消息数量相同但处理量不同”的关系变成可见过程；静态价格表无法表达这处反差。

## Scene 02｜工具、模型与 token 不是一回事

### 目的

建立后续所有计费解释都需要的三层计量模型，切断“Codex 入口就是收费单位”的误解。

### narrativeRole

承接开场的“处理量”，从现象下沉到计费对象，给两套账和套餐判断提供共同坐标。

### narrationIntent

依次说明 Codex 是使用模型能力的入口，模型处理是实际工作的中间层，输入 token、输出 token 和每轮携带的上下文是观察消耗的基本计量单位；强调 token 不等于固定字符数，也不等于固定消息数。

### visualIntent

将一个 Codex 入口节点逐层拆开为“工具入口 → 模型处理 → 输入 token／输出 token／上下文”，用连接线和展开动画明确层级关系，并让长文件、长会话等输入块汇入上下文层。

### visualType

Concept Diagram／ConceptScene

### keyOnScreenText

`工具入口`；`模型处理`；`输入 token`；`输出 token`；`上下文`

### videoValue

逐层拆解能展示抽象计量关系从入口到处理量的变化，帮助观众建立可复用的判断坐标，而不是记住一组孤立定义。

## Scene 03｜ChatGPT 订阅这条账

### 目的

让观众理解 ChatGPT 账号登录对应的付费对象、订阅权益和限额边界，再进入套餐分层。

### narrativeRole

先建立第一本账，说明个人手动使用时应该观察什么，为下一幕 API key 的平行路径准备对照面。

### narrationIntent

解释固定月费、订阅用量规则、滚动限额和达到限额后可购买积分之间的因果关系；明确积分解决的是继续使用，不会把订阅和 API 账单合成同一套账。

### visualIntent

沿一条单向路径依次展示“ChatGPT 账号 → 固定月费 → 订阅用量规则 → 达到限额 → 积分”，让积分作为限额后的分支出现，而不是与月费并列的总价项目。

### visualType

Process／StepListScene

### keyOnScreenText

`ChatGPT 订阅`；`固定月费`；`订阅用量规则`；`滚动限额`；`积分`

### videoValue

路径的逐步推进能把月费、包含用量、限额和额外使用的先后关系显性化，避免观众只看价格或把积分理解为 API 余额。

## Scene 04｜API key 这条账：两套账

### 目的

明确 API key 面向程序化使用，按实际 token 用量计费，并与 ChatGPT 订阅形成不可混算的边界。

### narrativeRole

与上一幕构成平行对照，回答“脚本和 CI/CD 应该看哪本账”，完成付费路径的关键分流。

### narrationIntent

解释 API key 适合脚本、CI/CD 和其他自动化任务，按输入／输出 token 用量扣费，账单在 OpenAI Platform 单独计算；明确 ChatGPT 订阅月费、ChatGPT 积分和 API key 账单服务的路径不同。

### visualIntent

把 Scene 03 的订阅路径移到左侧，同时在右侧展开“程序或脚本 → API key → 输入／输出 token → Platform 账单”。中央固定出现“两套账”，三种不能混算的对象分别回到对应账本。

### visualType

Comparison／Connection Diagram

### keyOnScreenText

`两套账`；`ChatGPT 订阅`；`ChatGPT 积分`；`API key`；`Platform 账单`

### videoValue

两条路径同时出现并分流到不同账本，能直接展示“人手动使用”和“机器程序化使用”的边界；线性文字难以形成同样清晰的对照。

## Scene 05｜套餐先按使用场景分层

### 目的

把套餐选择从追逐金额和额度，转成按使用者、工作方式、管理需求和预算匹配场景。

### narrativeRole

在付费路径清晰后，进入观众最容易误判的套餐问题，先给选择顺序，再展示四种典型使用场景。

### narrationIntent

依次解释个人开发者、高频重度个人、团队协作和组织级部署的差异，说明 Plus、Pro、Business、Enterprise & Edu 各自应优先观察的使用强度、管理和安全需求；不固化易变的金额、消息区间、模型名称或支持范围。

### visualIntent

让四张场景卡按“个人开发者 → 高频重度个人 → 团队协作 → 组织级部署”由左到右或由近到远展开，卡片只保留使用者、工作方式和管理重点。Free／Go 作为“支持范围待核对”的边界提示，不放进主排序。

### visualType

Comparison／StepListScene

### keyOnScreenText

`Plus`；`Pro`；`Business`；`Enterprise & Edu`；`个人 → 重度个人 → 团队 → 组织`；`支持范围待核对`

### videoValue

场景卡的连续展开能展示套餐从个人到组织的分层关系，并让观众看到判断顺序；不需要依赖易变化的价格数字。

## Scene 06｜滚动窗口与任务复杂度

### 目的

解释限额是时间窗口中的动态资源，不是每天固定清零、每条消息均匀消耗的静态计数器。

### narrativeRole

把“套餐包含多少”转成“使用速度如何变化”，并处理触顶后积分能做什么、不能做什么。

### narrationIntent

用 5 小时滚动窗口作为理解例子，说明小脚本、大型代码库、长会话、模型和任务复杂度会改变单位消息的消耗速度；触顶后积分提供额外使用通道，但不改变上下文体积，也不改变两套账的边界。

### visualIntent

展示一条持续向前移动的 5 小时窗口，在同一窗口内依次放入小脚本、大型项目和长会话的不同大小消耗块。窗口推进到触顶状态后，仅从订阅账本分出“积分”支路，API 账本保持独立。

### visualType

Process／Comparison

### keyOnScreenText

`5 小时滚动窗口`；`小脚本`；`大型项目`；`长会话`；`达到限额`；`积分 ≠ API 账单`

### videoValue

窗口的移动、消耗块的堆积和触顶分支能同时表现时间、任务复杂度与可用量的动态关系，避免把限额误读成固定日额度。

## Scene 07｜升级前先控制上下文

### 目的

把观众从“额度不够就升级”转向“先减少无效输入”，明确成本控制的四个主动杠杆。

### narrativeRole

制造反转并给出可执行的方法，承接动态限额，推动情绪从额度焦虑转向可管理的行为调整。

### narrationIntent

依次说明缩小输入范围、压缩固定上下文、按需连接工具、匹配模型与任务四个调整方向，并补充切换无关工作时用 `/new` 清理旧会话；不承诺固定节省比例。

### visualIntent

以四组“浪费状态 → 精确状态”的替换动作展示上下文变小变准：模糊请求变为明确文件／函数，巨型规则变为分层规则，全挂工具变为按需开启，全程强模型变为任务匹配模型。最后把旧会话移出当前工作区并标记 `/new`。

### visualType

Process／StepListScene

### keyOnScreenText

`缩小输入范围`；`压缩固定上下文`；`按需连接工具`；`匹配模型与任务`；`/new`；`短而准`

### videoValue

通过替换和收缩的连续动作展示“上下文从大而杂到短而准”的因果变化，比静态建议清单更能证明成本控制来自输入结构而非口号。

## Scene 08｜查看、调整、清理、复盘

### 目的

把成本管理变成任务开始、执行、切换和结束时都可重复的用量感知闭环。

### narrativeRole

将前面的抽象判断落到 CLI 工作习惯，收束订阅与 API 用户各自应该查看的位置，并回扣开场的额度问题。

### narrationIntent

按照 `/status → /model → /new → 复盘` 解释先观察模型、审批策略、上下文容量和会话状态，再匹配模型、清理无关上下文，最后在订阅用量面板或 API Platform 账单中复盘。

### visualIntent

用终端状态逐步变更串起 `/status`、`/model` 和 `/new`：先显示当前状态，再切换匹配模型，再清空无关会话；终端最后分流到“订阅用量面板”和“API Platform 账单”两个出口，不生成一个总账。

### visualType

Demo／TerminalScene

### keyOnScreenText

`/status`；`/model`；`/new`；`查看`；`调整`；`清理`；`复盘`；`订阅用量面板`；`API Platform 账单`

### videoValue

终端命令、状态变化和双出口分流能把四步闭环演示成可执行过程，并让观众看到每一步如何减少混算和无效上下文。

## Scene 09｜先识别付费路径，再进入模型接入

### 目的

收束“付费路径、计量方式、任务和上下文”的判断框架，并留下下一篇关于国产模型接入方式的明确认知缺口。

### narrativeRole

总结全片，不重复罗列套餐；把两套账重新收束成一个选择框架，再把模型接入作为下一层问题交给下一集。

### narrationIntent

回到最终判断：先确认自己使用的是订阅额度还是 API 按量计费，再判断任务类型和上下文规模，最后决定是否需要调整套餐或工作方式。结尾只预告“接入 DeepSeek 等国产模型”，不展开具体配置。

### visualIntent

先让订阅账本与 API 账本收束成一个四问判断框架：登录路径、任务类型、上下文规模、用量观察位置。完成收束后，最后一个视觉事件才出现下一集预告卡“接入 DeepSeek 等国产模型”，单独保留约 2～3 秒阅读停留，并避开字幕区域。

### visualType

Summary／SummaryScene

### keyOnScreenText

`订阅额度 or API 按量计费`；`任务类型`；`上下文规模`；`用量观察位置`；`接入 DeepSeek 等国产模型`

### videoValue

账本收束、判断项依次确认和最后预告卡的出现顺序，能让观众看到从混淆到判断再到下一步的问题闭环；预告也作为可停留的最终视觉事件，而不是口播备注。
