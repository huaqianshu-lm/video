# Codex 订阅与计费 · Content Analysis

> 目标：从源文档中提取这条视频必须讲清楚的计费概念、判断关系和可视觉化信息，不提前编写口播或拆分 Scene。

---

## 1. 核心命题

这篇内容表面上是在比较 ChatGPT 订阅档位，真正需要建立的认知是：

> **Codex 的花费不是简单按消息数量计算，而是由登录方式、模型处理量和上下文规模共同决定；先分清两套付费逻辑，再根据自己的使用方式选择方案，才能控制成本。**

观众最后应该记住：

> **人用 ChatGPT 订阅看用量限额，机器用 API key 按 token 计费；省额度的核心是减少不必要的上下文，而不是只盯着消息条数。**

本条视频的核心不是鼓励购买某一个套餐，而是帮助观众建立一套「计费对象 → 付费路径 → 使用限额 → 成本控制」的判断框架。

## 2. 观众需要解决的问题

- Codex 工具本身、背后的模型算力和实际付费对象分别是什么。
- ChatGPT 账号登录与 API key 登录为什么是两套账，以及它们适合的工作方式。
- Plus、Pro、Business、Enterprise & Edu 的定位差异，个人和团队应从什么维度判断。
- Free 与 Go 的 Codex 支持为何不能直接预设，需要以当前官方页面为准。
- 5 小时滚动窗口、模型、任务复杂度和 token 之间如何共同影响用量。
- 额度触顶后积分的作用是什么，为什么不应把「升级套餐」当成唯一解决方案。
- 哪些上下文和使用习惯会加速消耗额度，如何在 CLI 中检查状态和用量。

## 3. 知识骨架

### 3.1 先区分工具、模型和计费单位

1. Codex 是使用模型能力的工具入口，安装和使用入口本身不是主要计费对象。
2. 真正消耗成本的是模型处理任务时使用的算力。
3. token 是内容被模型处理时的基本计量单位，输入 token、输出 token 和每轮对话携带的上下文都会影响消耗。
4. 输出 token 通常比输入 token 更贵；长文件、长会话和冗长项目规则会显著扩大上下文。

### 3.2 两套彼此独立的付费逻辑

#### ChatGPT 订阅登录

- 以固定月费换取包含一定用量的订阅权益。
- 使用量受本地消息、云端任务、模型和滚动窗口等规则影响。
- 达到限额后，可通过购买积分继续使用。
- 面向个人日常使用，通常包含更多面向订阅用户的云端入口和功能。

#### API key 登录

- 不依赖 ChatGPT 订阅额度。
- 按实际 token 用量实时扣费，账单与 ChatGPT 订阅单独计算。
- 更适合 CI/CD、脚本和其他程序化任务。
- 不能把 API key 的按量价格与订阅方案的月费或积分直接混算。

两者的关键差异不是单纯的「谁更便宜」，而是「人手动使用」与「机器程序化使用」对应不同的付费和功能边界。

### 3.3 订阅档位是使用场景的分层

- Plus：个人开发者的基础订阅，关键问题是包含的用量是否够日常工作。
- Pro：面向高频、重度使用者，主要价值是更高的用量上限和额外模型能力。
- Business：面向团队，重点从个人额度转向席位、管理和安全控制。
- Enterprise & Edu：面向组织级部署，重点是弹性用量、优先处理、身份与审计能力。
- Free 与 Go：源文档未确认其 Codex 额度，不能把「可能可进入某个入口」等同于「获得完整编程能力」。

选择顺序应是：先判断个人还是团队、手动还是自动化，再判断使用强度，最后才比较套餐和积分。

### 3.4 限额、积分与任务复杂度

1. 订阅限额按滚动时间窗口计算，源文档以 5 小时窗口举例，而不是简单按自然日清零。
2. 本地消息和云端任务共享相关用量规则，具体可用量会因模型、任务规模、复杂度和执行位置变化。
3. 同样一条消息，读取大型代码库、执行长任务或携带大量上下文时，消耗会明显高于小脚本任务。
4. 官方页面给出的金额、消息区间和积分费率属于会变化的定价快照，不应当被表达成永久承诺。
5. 积分是达到订阅限额后的额外用量机制，解决的是「继续使用」问题，不改变 ChatGPT 订阅与 API key 的账务边界。

### 3.5 成本控制的本质是控制上下文

源文档给出的省额度方法可以归纳为四类：

- **缩小输入范围**：把任务、文件和目标函数说具体，减少模型在项目中盲目搜索。
- **压缩固定上下文**：精简根目录规则文件，并按目录拆分只在需要处生效的说明。
- **按需连接工具**：不使用的 MCP server 不要长期挂载，减少重复注入的工具描述。
- **匹配模型与任务**：常规任务使用更小的模型，复杂任务再使用更强模型。

额外的会话管理习惯是：切换到不相关的工作时用 `/new` 重置上下文，避免无关历史在后续每轮继续占用输入空间。

### 3.6 用 CLI 建立用量感知

- `/status`：查看当前模型、审批策略、可写目录、上下文容量和会话状态；也可用于观察当前限额信息。
- `/model`：根据任务复杂度切换模型。
- `/new`：开始不相关任务时清理当前对话上下文。
- ChatGPT 订阅用户可进一步查看 Codex 用量面板；API key 用户应在 OpenAI Platform 查看账单和用量。

信息顺序应形成闭环：先看当前状态，再选择匹配任务的模型，切换工作时清理上下文，最后到对应账户后台看整体用量。

## 4. 关键关系

| 起点 | 关系 | 结果或判断 |
| --- | --- | --- |
| Codex 工具 | 调用模型处理任务 | 工具入口免费不等于模型处理没有成本 |
| 输入、输出与上下文 | 共同构成 token 消耗 | 消息数量不能单独代表实际用量 |
| ChatGPT 账号登录 | 订阅月费、用量限额、积分 | 适合个人日常手动使用 |
| API key 登录 | 按 token 实时扣费 | 适合自动化、CI/CD 和程序化任务 |
| 模型与任务复杂度 | 决定单位消息可消耗的额度 | 大型项目和长任务更容易触顶 |
| 套餐档位 | 对应个人、重度、团队或组织场景 | 先按使用场景分层，再看价格和额度 |
| 精确提示、短上下文、按需工具、小模型 | 减少 token 浪费 | 同样的工作量可以更耐用 |
| `/status`、`/model`、`/new` | 形成会话内管理动作 | 让用量从事后账单变成过程中的可观察状态 |

## 5. 可视觉化内容

### 5.1 计费对象的三层拆解

用三层关系表达「工具入口 → 模型处理 → token 计量」，将“免费工具”和“有成本的模型处理”分开。可用一个任务从输入上下文进入模型、再拆成输入 token 与输出 token 的流程图。

### 5.2 两条付费路径

把 ChatGPT 订阅登录与 API key 登录呈左右两路：

- 左路：固定月费 → 用量限额 → 达到上限 → 购买积分。
- 右路：API key → 输入／输出 token → 按量扣费 → Platform 账单。

两路之间需要有明显的「两套账」边界，避免观众误以为积分可以抵扣 API key 账单。

### 5.3 套餐定位卡片

以个人、重度个人、团队、组织四组卡片呈现 Plus、Pro、Business、Enterprise & Edu 的使用场景，不把易变的金额做成视觉主体。Free 与 Go 可作为「官方当前页面未明确承诺」的边界提示。

### 5.4 5 小时滚动窗口与消耗速度

用横向滚动时间窗表现限额不是每天清零；同一窗口内放入小脚本、大型代码库、长会话三种不同大小的消耗块，直观看出任务复杂度会改变可用消息数量。

### 5.5 省额度前后对比

用四组可替换的输入状态卡片展示：模糊请求对比精确文件／函数、巨型规则文件对比分层规则、全挂 MCP 对比按需开启、全程强模型对比任务匹配模型。视觉重点是上下文体积减少，而不是承诺固定节省比例。

### 5.6 CLI 用量检查流程

用终端界面串起 `/status`、`/model`、`/new` 三个动作，并在末端分流到订阅用量面板或 API Platform 账单，形成「查看 → 调整 → 清理 → 复盘」的操作闭环。

### 5.7 下一篇的承接关系

结尾可把当前视频的「订阅／API key 两条路径」连接到下一篇的「接入 DeepSeek 等国产模型」，明确这是模型接入方式的延伸，而不是当前视频已经展开的新主题。

## 6. 事实边界与制作注意

- 价格、消息区间、模型名称、积分单价、Free／Go 支持范围和 CLI 行为都可能随官方政策或版本变化；视频中的具体数字必须标明是参考快照，并引导观众以当前官方页面为准。
- 不把个人经历中的「两天触顶」当作普遍用量结论，它只能作为复杂任务消耗更快的案例背景。
- 不把「Plus 适合个人」表达为对所有用户的强制购买建议；应保留使用强度、任务类型和预算的判断条件。
- 不混淆 ChatGPT 订阅额度、ChatGPT 积分和 API key 账单。
- 不把 token 简化为字符数，也不承诺某个固定 token 与消息条数的换算关系。
- 本阶段只完成内容分析；套餐比较的叙事顺序、Scene 划分、口播文本、视觉脚本和原型属于后续阶段。
