# Claude Code 安装与使用 · 第二步：Video Narrative

> 目标：不按原文章节机械朗读，而是重新设计“观众怎样从不知道该怎么装，走到真正完成第一次 Claude Code 任务”的认知顺序。

本文基于 `content-analysis.md` 编写，只确定整条视频的叙事主线、段落关系和信息取舍，暂不拆分 Scene、编写逐句口播或设计最终画面。

---

## 1. 视频的叙事目标

这条视频不是为了让观众记住一组安装命令，而是让第一次使用 Claude Code 的人完成一次可验证的上手闭环：

```text
不知道从哪里装
        ↓
根据系统和终端选对入口
        ↓
确认命令真的可用
        ↓
完成账号授权
        ↓
让 Claude Code 完成一次可控任务
        ↓
知道出了问题应该从哪一层排查
```

观众最后应该形成的认知是：

> **安装成功不是安装命令执行完，而是验证、登录和第一次受控任务都跑通。**

这条视频的成功标准不是“看过所有平台命令”，而是观众能在自己的环境中做出正确选择，并知道怎样判断自己已经真正准备好使用 Claude Code。

---

## 2. 整体叙事结构

建议整条视频分成八个叙事段落。前六段推动第一次使用闭环，后两段负责建立维护能力和系列收束。

| 段落 | 观众此时的问题 | 叙事作用 | 核心表达 |
| --- | --- | --- | --- |
| 01 开场钩子 | 安装命令跑完，为什么还不能确定能用？ | 制造不确定性并给出观看承诺 | 安装完成不等于使用链路打通 |
| 02 安装前检查 | 我现在到底能不能装？ | 先挡住系统、账号和入口不匹配 | 先确认三个前提 |
| 03 选择安装入口 | 我应该执行哪一条命令？ | 把平台和终端分支变成选择题 | 官方原生优先，终端决定命令 |
| 04 验证安装结果 | 怎么证明它真的装好了？ | 把“命令执行完”转换成可观察证据 | 版本检查加诊断检查 |
| 05 完成登录 | 为什么命令能用，却还不能工作？ | 补齐账号授权和远程环境分支 | 启动、授权、回到终端 |
| 06 跑通第一次任务 | 我怎样确认这不是假安装？ | 让观众看到完整使用闭环 | 创建文件、查看 diff、确认写入 |
| 07 遇到问题怎么办 | 出错时是否只能重装？ | 建立分层排错和维护边界 | 先判断错误层级，再处理 |
| 08 收束与预告 | 什么状态才算真正准备好了？ | 用 checklist 收束，并衔接下一节 | 可安装、可验证、可授权、可完成任务 |

这八段对应 Content Analysis 中的五层知识骨架：

```text
第一层：先确认能不能装       → 02
第二层：选择正确安装入口     → 03
第三层：确认装好并完成登录   → 04、05
第四层：完成第一次可控任务   → 06
第五层：建立维护和排错能力   → 07
结尾：收束本节并衔接下一节  → 08
```

---

## 3. 叙事主线：让“状态变化”代替“命令列表”

原文按安装、验证、登录、升级、卸载、报错和第一次任务展开。视频不直接复制这个章节顺序，而是围绕用户状态变化组织内容：

```text
环境未知
  ↓
安装路径已选择
  ↓
命令已被系统找到
  ↓
账号已授权
  ↓
任务已提交
  ↓
修改已被用户确认并写入
  ↓
问题可以按层诊断
```

每个阶段都要回答两个问题：

1. 观众现在处于什么状态？
2. 通过什么可观察结果，证明自己进入了下一状态？

这样可以避免视频变成“输入一条命令、切到下一条命令”的流水账。命令只在它推动状态变化时出现，完整命令表和平台细节留给文章或后续资料查阅。

---

## 4. 第一段：开场先提出“装完不等于能用”

### 叙事目的

先建立一个新手最容易忽略的矛盾：安装器执行结束，只能说明某一步完成了，并不能证明终端能找到命令、账号已经授权，或者 Claude Code 能完成真实任务。

### 内容设计

开场可以从一个熟悉的错误判断切入：

> 命令执行完了，终端也没有报错，是不是就算安装成功？

紧接着给出本视频的承诺：

> 这次不只讲怎么安装，而是从选择安装入口开始，一直跑通登录和第一次文件修改；最后再告诉你，遇到报错应该先查哪一层。

这一段不介绍 Claude Code 的历史、功能或代理原理，也不在开场展示完整命令。它只负责提出问题，让观众知道后面会得到一个明确的“成功证据”。

### 这一段的 Video Value

把抽象的“安装教程”转换成一个有终点的任务：

```text
安装命令结束
        ≠
第一次任务完成
```

---

## 5. 第二段：安装前先做三个检查

### 叙事目的

让观众在执行任何命令前先做环境判断，减少“命令没问题但环境不满足”的无效排查。

### 三个检查

只保留判断所必需的信息：

1. **系统和运行环境**：操作系统、架构、可用资源和网络是否满足要求。
2. **账号资格**：当前账号是否具备使用 Claude Code 的条件。
3. **使用入口**：这次是否准备使用 CLI；桌面 App、编辑器集成等入口不混进本条主线。

三项检查不需要逐项朗读原文表格，也不需要在这里讲完整的订阅和产品矩阵。它们的作用是让观众先完成一次入口筛选：

```text
能不能装？
能不能登录？
是不是要走 CLI？
```

### 叙事转折

完成检查后，问题从“我能不能用”变成：

> 既然条件满足，我当前这个系统和终端应该走哪条安装路径？

这自然引出下一段的平台分流。

---

## 6. 第三段：把安装方式讲成“入口决策”

### 叙事目的

观众真正需要的不是一张命令清单，而是一条选择规则：先识别系统和终端，再选择官方推荐的安装入口。

### 内容顺序

建议按以下优先级讲：

```text
确认当前系统
      ↓
确认当前终端
      ↓
优先选择官方原生安装
      ↓
只有在特殊需求下再考虑 npm 等备选方式
```

必须明确的分支关系：

- macOS、Linux 和 WSL 按各自的 Unix 环境处理。
- Windows 原生环境要区分 PowerShell 和 CMD。
- WSL 要在 WSL 终端内部执行 Linux 命令，不能把 PowerShell、CMD 和 WSL 混成一个环境。
- npm 作为备选入口时，要说明它带来额外的版本、权限和升级维护责任。
- `sudo npm` 不是通用的权限修复方案，不能因为命令失败就直接加上 `sudo`。

### 这段不做什么

- 不把所有安装命令逐条平铺成教程字幕。
- 不在主线里展开桌面 App、VS Code、JetBrains 和第三方模型接入。
- 不在这里讲升级、卸载和全部错误信息。

### 这一段的 Video Value

让观众看到“终端类型决定入口”的关系，而不是看到三个互相竞争的命令：

```text
Windows
├─ PowerShell → PowerShell 入口
├─ CMD        → CMD 入口
└─ WSL        → Linux 入口
```

具体命令、URL 和当前版本信息在后续脚本阶段再做时效性核验，不在 Narrative 阶段固化易变细节。

---

## 7. 第四段：用验证证据确认“安装真的完成”

### 叙事目的

把安装结果从“安装器说完成了”转换成“系统和 Claude Code 都给出了证据”。

### 验证链

核心顺序保持简单：

```text
打开一个新的终端
        ↓
运行 `claude --version`
        ↓
确认系统能找到命令并返回版本
        ↓
需要排查时运行 `claude doctor`
```

这里要解释新终端的意义：安装程序可能修改了 PATH，旧终端未必已经加载新的环境变量。`claude --version` 是第一层可用性证明，`claude doctor` 是出现异常时的诊断入口，不需要每次都把所有检查结果念完。

### 关键误区

如果出现 `command not found: claude` 或 Windows 对应错误，不要立即得出“安装失败”的结论。先判断：

- 当前终端是否重新打开。
- PATH 是否包含安装目录。
- 是否存在多个安装来源。
- 是否把命令粘贴到了错误的 shell。

这会为后面的排错段落埋下方法，而不是把每个错误提前打断主线。

### 状态转折

当版本检查通过时，观众获得第一个明确结果：

> 终端已经能找到 Claude Code。

但“命令可用”还不等于“账号可用”，下一段继续处理登录。

---

## 8. 第五段：登录是第二个必须打通的环节

### 叙事目的

让观众理解安装和授权是两件事：前者让命令存在，后者让 Claude Code 能代表当前账号工作。

### 主路径

登录主线只保留一条清晰流程：

```text
进入一个项目目录
        ↓
运行 `claude`
        ↓
浏览器完成授权
        ↓
回到终端继续操作
```

### 远程环境分支

远程服务器、SSH 或 WSL 中浏览器不在当前设备时，只展示一个异常分支：

```text
浏览器没有自动打开
        ↓
复制 OAuth URL
        ↓
在可访问浏览器的设备上完成授权
        ↓
把授权结果带回终端
```

必要时再提示 `claude auth login` 是更明确的登录入口，但不把所有登录变体做成第二条主线。

### 隐蔽问题的处理位置

如果登录后出现组织禁用、权限异常等现象，只点出一个高价值排查方向：检查残留的 `ANTHROPIC_API_KEY`。这属于异常提示，不应盖过首次登录的主流程，也不在 Narrative 阶段断言具体账号政策。

### 这一段的 Video Value

登录最适合表现为一个跨设备授权回路，而不是连续几行终端文字。观众要看到授权从浏览器出发，最后回到终端，形成状态闭环。

---

## 9. 第六段：用第一次真实任务证明“真的能用”

这是整条视频的核心段落和情绪落点。前面的检查、安装和登录都在为这一刻服务。

### 叙事目的

让观众完成一个风险低、结果明确、可以马上验证的测试任务，并亲眼看到 Claude Code 的工作方式。

### 任务主线

```text
创建一个空的测试目录
        ↓
启动 Claude Code
        ↓
输入 `/help`，确认交互正常
        ↓
用自然语言要求创建 `test.py`
        ↓
Claude Code 提出文件修改
        ↓
观众查看 diff
        ↓
确认后写入文件
        ↓
退出并检查文件结果
```

### 这一段真正要讲什么

重点不是 `test.py` 里面的代码有多复杂，而是让观众理解这个受控闭环：

```text
提出目标
  ↓
查看修改方案
  ↓
人确认
  ↓
文件落盘
```

这里需要明确人的作用：Claude Code 可以帮助完成任务，但文件真正发生修改前，用户仍然有机会检查 diff 并做决定。这样既证明工具能执行任务，也避免把视频讲成“启动后完全交给 AI”。

### 叙事高潮

`diff` 出现并被确认，是本条视频最重要的视觉和认知事件。它把前面所有抽象的“安装成功”转化成了一个可观察结果：

> Claude Code 已经在当前环境中完成了一次真实、可检查、可回退的文件修改。

### 这一段不提前展开的内容

- 不解释代理循环为什么会读取文件、调用工具和反复执行。
- 不介绍复杂项目任务、MCP 或多文件重构。
- 不把测试任务做成过长的编码演示。

这些内容属于后续系列或更深入的视频；本节只完成第一次使用闭环。

---

## 10. 第七段：把排错和维护放在成功之后

### 叙事目的

观众已经看到正确路径后，再补充“如果不顺利怎么办”。这样排错是对主线的保护，而不是开场就把新手淹没在错误表格里。

### 先建立错误分层

不平均讲九类报错，而是按错误发生的位置建立一个诊断地图：

```text
命令层     → 当前 shell 和命令是否匹配
网络层     → 下载内容和响应是否正常
PATH 层    → 系统是否能找到已安装程序
资源层     → 内存和系统运行库是否满足
账号层     → 订阅、权限和环境变量是否正常
安装来源层 → 是否存在多个版本互相覆盖
```

每一类只配一个代表性现象和一个判断方向，例如：

- `command not found`：先查 PATH 和终端环境。
- `irm is not recognized` 或 shell 语法错误：先查终端是否匹配。
- `which -a claude` 出现多个路径：先查重复安装来源。
- 登录组织异常：先查账号状态和残留 API Key。

### 升级与卸载的最小原则

这部分不抢走主线，只传达两条规则：

1. 升级和卸载要匹配最初的安装来源，不能混用原生安装和 npm 的维护命令。
2. 彻底删除配置、缓存或项目本地设置前，必须明确这是不可逆操作；视频不把完整破坏性清理命令作为主画面重点。

### 这一段的结论

遇到问题时，正确顺序是：

```text
先确认错误发生在哪一层
        ↓
再选择换命令、修 PATH、检查资源、处理账号或清理重复安装
        ↓
最后才决定是否重新安装
```

## 11. 第八段：用“成功标准”收束，而不是重复命令

### 结尾总结

结尾不再复述所有平台命令，而是用四个结果判断本节是否完成：

```text
我知道自己的环境是否满足
我选对了系统和终端对应的安装入口
我能验证命令、完成授权
我跑通了一次查看 diff 后再写入文件的任务
```

最后的核心总结可以落在：

> **Claude Code 的安装不是执行一条命令，而是把“环境、命令、账号和第一次任务”这条链路完整打通。**

### 下节预告

只在视频最后用一句话或一个很短的收束卡带过，不提前铺垫，也不展开新知识：

> **下一节，我们会拆开 Claude Code 背后的“代理循环”，看看一句自然语言指令是怎样变成一次真实文件修改的。**

预告的作用只是连接系列内容；本节的最后一个实质信息仍然是“安装并跑通第一次受控任务”。

## 12. 整条视频的认知节奏

整条视频应当沿着下面的节奏推进：

```text
怀疑安装是否真的成功
        ↓
先做环境判断
        ↓
选择正确入口
        ↓
用证据验证安装
        ↓
完成账号授权
        ↓
提交第一次任务
        ↓
看到 diff 并确认写入
        ↓
知道如何分层排错和维护
        ↓
用成功标准收束
        ↓
一句话预告下一节
```

这比原文的章节顺序更适合视频，因为观众始终知道自己正在解决哪个问题，并且每一段都推动状态向“可用”前进。

## 13. 内容优先级与边界

### 必须进入主线

- 安装前的三个前提。
- 官方原生安装优先级。
- Windows 原生、PowerShell、CMD 和 WSL 的入口分支。
- `claude --version` 和 `claude doctor` 的验证意义。
- 浏览器授权和远程环境的 OAuth 处理。
- 第一次任务中的 diff 确认闭环。
- 按错误层级排查，而不是条件反射地重装。

### 可以压缩为提示

- 系统要求的完整数值表。
- npm 的完整参数和全部升级命令。
- 九类报错的完整表格。
- 各平台的完整卸载路径。
- 自动更新配置和高级设置。

### 本节暂不展开

- Claude Code 的代理循环原理。
- MCP、第三方模型和复杂项目配置。
- 编辑器、桌面 App 和 Web 入口的完整教程。
- 复杂代码任务和多文件重构。
- 破坏性清理命令的完整复制粘贴演示。

### 信息密度原则

视频不设置固定总时长。后续根据口播内容、必要停顿和视觉事件入场时间确定节奏；第一次任务和 diff 确认应获得足够时间，平台分支和错误清单则通过压缩信息、分层展示来控制密度。

## 14. 视觉叙事方向（仅到 Narrative 层）

这里暂不定义 Scene ID 或具体动画，只确定画面应该服务于哪些认知变化：

1. **状态卡**：用状态变化表现“未知 → 可安装 → 可用 → 已授权 → 任务完成”。
2. **入口分流**：用简洁路线图表现系统、终端和安装方式之间的关系。
3. **终端证据**：展示版本检查、诊断结果和授权回到终端的闭环。
4. **文件与 diff**：把第一次任务的修改提案、用户确认和文件落盘作为全片核心视觉事件。
5. **错误地图**：用错误层级到处理方向的映射，替代九类报错的长表格。
6. **结尾收束**：用四项成功标准和一条短预告结束，不用大段字幕堆叠。

画面应优先展示“发生了什么变化”，而不是把文章段落全部放到屏幕上。具体终端文本、代码内容、字幕句子和 Scene 时长留到后续资料阶段决定。

## 15. 时效性与制作注意事项

进入 Scene Script 和 Narration Script 前，需要再次核验原文中的易变信息：

- 官方安装 URL 和各平台当前命令。
- 支持的系统版本、架构、资源要求和账号条件。
- 安装包名称、版本示例、安装路径和 PATH 行为。
- 升级、卸载和登录命令是否仍然适用。
- API Key 优先级、组织权限和支持地区等政策信息。

因此，本 Narrative 使用“官方原生安装入口”“PowerShell／CMD／WSL 分支”等稳定叙事概念，不把未复核的版本号和命令细节写死。

涉及 `rm -rf ~/.claude`、删除 `~/.claude.json`、项目 `.claude` 或 `.mcp.json` 等彻底清理动作时，后续脚本必须明确风险，并避免把它们包装成普通排错步骤。
