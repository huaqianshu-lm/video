# Claude Code 安装与使用 · 第六步：Visual Script

> 目标：基于 Scene Script 和 Narration Script，明确每个 Scene 的画面结构、视觉动作、状态变化、屏幕文字和声音／画面分工。
>
> 本文档是进入 Visual Prototype 前的视觉设计稿，不是 HTML、CSS 或 Remotion 实现。整条视频按 1920 × 1080、16:9 横屏设计，不预设固定总时长；后续以实际口播、必要停顿和主要视觉事件的完成时间确定节奏。

## 视觉脚本使用边界

这条视频的主线不是“把安装命令展示一遍”，而是让观众看到一条完整的可验证链路：

~~~text
环境判断
  ↓
选择入口
  ↓
安装验证
  ↓
账号授权
  ↓
第一次受控任务
  ↓
查看 diff 并确认写入
~~~

声音负责解释判断原则、因果和操作顺序；画面负责展示终端、浏览器、文件树、状态变化和人工确认。屏幕文字只保留命令、关键状态和判断结论，不把口播全文铺到画面上。

本稿不锁定易变的官方 URL、版本号、完整安装命令、登录界面原文、升级／卸载命令或破坏性清理命令。进入 Visual Prototype 和 Remotion 前，仍需依据当前官方文档做事实核验。

## 全局视觉语言

### 1. 画面基调

- 深色背景，以接近黑蓝的工作区承载终端和软件界面。
- 主色使用冷蓝或青色，表示当前路径和进行中的动作。
- 绿色只用于“已通过、已找到、已授权、已写入”等确定结果。
- 琥珀色用于“待确认、备选、需要检查”的状态。
- 红色只用于错误层级或不可逆风险，不把整屏做成警报页面。
- 面板、终端和浏览器使用轻微边框与柔和阴影，避免厚重卡片堆叠。

### 2. 固定画面区域

~~~text
┌──────────────────────────────────────────────────────────────┐
│ Scene 标题／当前阶段                                         │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│ 主视觉区：终端、文件树、浏览器、流程或对比关系               │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ 字幕区：逐句口播字幕，控制在一到两行                         │
└──────────────────────────────────────────────────────────────┘
~~~

- Scene 标题只在需要建立新阶段时短暂出现，不能每幕都变成完整标题页。
- 主视觉区优先使用过程和状态变化，避免同一时间出现完整命令表、完整错误表和完整口播。
- 字幕区保持在安全边距内，不能与终端底部状态栏或操作按钮重叠。
- 主文案控制在一到两行；详细解释交给声音。

### 3. 动画层级

#### 一级：信息动画

必须保留，用来表达知识本身：

- 检查项从未确认变成通过。
- 命令从一个终端流入另一个终端或浏览器。
- 终端输出从等待变成已找到、已授权。
- 文件树从空目录变成出现 test.py。
- diff 从提案状态变成确认写入。
- 错误指针落到对应诊断层级。

#### 二级：注意力动画

少量使用：

- 高亮当前分支。
- 将非当前路径降为低对比度。
- 对 diff、确认按钮和最终状态做短暂聚焦。
- 在状态发生变化时轻微放大或描边。

#### 三级：装饰动画

尽量不使用。背景网格、光晕和微弱噪点只作为统一风格，不承担叙事任务；删除后不影响理解的动画不进入原型。

### 4. 统一 UI 语法

全片复用以下视觉原子，避免每个 Scene 发明一种新界面：

~~~text
Terminal Window
Browser Window
File Tree
Status Chip
Command Line
Process Arrow
Diff Panel
Decision Marker
Warning Banner
Checklist Row
~~~

这些是视觉设计层的表达单元，正式 Remotion 阶段优先映射到已有的 OpeningScene、ConceptScene、ComparisonScene、StepListScene、TerminalScene 和 SummaryScene。

## Scene 01｜安装命令结束，真的能用了吗？

### 视觉目标

把“安装器执行结束”与“真正可用”拆开，开场只制造一个明确问题：还有哪些状态没有被证明？

### 画面结构

~~~text
┌──────────────────────────────────────────────────────────────┐
│ INSTALLATION                                                 │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ $ install command                                     │  │
│  │ Installation finished                                │  │
│  │ ▌                                                     │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  命令可用？       未确认                                      │
│  账号已登录？     未确认                                      │
│  任务能完成？     未确认                                      │
│                                                              │
│                  安装完成 ≠ 真正能用                         │
└──────────────────────────────────────────────────────────────┘
~~~

终端占据主视觉区，右侧或下方出现三枚纵向状态芯片。不要出现完整安装命令和长输出，终端只需要让观众知道“安装步骤已经结束”。

### 状态与动画顺序

1. 终端光标停止闪烁，安装完成状态出现。
2. 第一枚“命令可用？”状态变成琥珀色“未确认”。
3. 第二枚“账号已登录？”和第三枚“任务能完成？”依次出现。
4. 三枚状态之间连出一条尚未完成的链路：

   ~~~text
   安装 → 验证 → 登录 → 第一次任务
   ~~~

5. 结论文字最后出现，短暂聚焦后将画面交给 Scene 02。

### 关键屏幕文字

主文字：

安装完成 ≠ 真正能用

辅助状态：

~~~text
命令可用？   未确认
账号已登录？ 未确认
任务能完成？ 未确认
~~~

不要在画面上重复 Scene 01 的完整口播。

### 声音与画面分工

- 声音提出“命令跑完是不是就成功”的问题，并说明本片会跑通完整链路。
- 画面把“能用”拆成命令、账号和任务三个可观察状态。
- 字幕只强调“安装完成 ≠ 真正能用”。

### 转场

三项未确认状态缩成三个检查入口，进入 Scene 02 的安装前检查门。转场由“问题”推动，不使用与内容无关的炫技转场。

### 实现约束

- 不把“Installation finished”当作官方固定输出，只作为示意文本。
- 不显示版本号、URL 或平台命令。
- 原型中要保证结论文字和三项状态在 1920 × 1080 下清晰可读。

## Scene 02｜安装之前，先确认三个前提

### 视觉目标

把原文里的系统要求、账号条件和入口差异压缩成一扇安装前的“检查门”，让观众看到不满足条件时应该停下来判断。

### 画面结构

~~~text
┌──────────────────────────────────────────────────────────────┐
│ 安装前检查                                                   │
│                                                              │
│  01 运行环境       02 账号资格        03 使用入口            │
│  系统／架构        订阅或 Console     CLI／其他入口          │
│  资源／网络        条件待核验         选择 CLI 主线          │
│                                                              │
│  [当前检查项展开区]                         [待执行安装]      │
└──────────────────────────────────────────────────────────────┘
~~~

三项不同时作为静态卡片堆满屏幕。默认先显示第一项，其余两项以低对比度标题存在；当前项确认后，检查线向右移动。

### 状态与动画顺序

1. “运行环境”成为当前检查项，显示四个短关键词：系统、架构、资源、网络。
2. 通过后出现绿色勾选，第一项缩小到顶部进度条。
3. “账号资格”进入当前位，只保留“条件待核验”的提示，不展示完整政策表。
4. “使用入口”最后进入当前位，CLI 被高亮，桌面 App 和编辑器集成退到旁支。
5. 三项完成后，底部“待执行安装”由琥珀色变成蓝色可进入状态。

### 关键屏幕文字

主文字：

先确认：环境、账号、入口

检查关键词：

~~~text
运行环境
账号资格
使用入口：CLI
~~~

### 声音与画面分工

- 声音说明每个前提为什么会影响后续安装。
- 画面只展示检查顺序和通过状态，不展示完整系统规格。
- 字幕保留三个关键词，不重复资源、账号和网络的完整解释。

### 转场

三项通过后，进度线从“能不能装”指向“应该在哪个终端里装”，进入 Scene 03。

### 实现约束

- 不把当前系统要求和账号政策写死为永久画面文案。
- 卡片数量固定为三项，避免原型变成信息表。
- 若要表现未满足条件，只让当前项停住，不增加一套错误页面。

## Scene 03｜不是 Windows 一条命令：终端决定入口

### 视觉目标

把平台差异表现成“先识别环境、再选择入口”的决策过程，而不是平铺三套命令。

### 画面结构

~~~text
                         当前环境
                            │
             ┌──────────────┴──────────────┐
             │                             │
        macOS / Linux                     Windows
        Unix 终端                    ┌─────┼─────┐
                                      │     │     │
                                  PowerShell CMD  WSL
~~~

左侧显示 macOS／Linux 的 Unix 终端入口，右侧展开 Windows 的三个终端分支。主视觉中心始终是“当前终端”节点，不显示完整安装命令。

### 状态与动画顺序

1. “当前环境”节点落下，平台分支向两侧展开。
2. Windows 分支再展开 PowerShell、CMD、WSL。
3. 光标依次掠过三个提示符，表现“窗口看起来相似，但环境不同”。
4. 选中其中一个终端后，该分支变成高亮，其余分支降低对比度。
5. WSL 分支旁出现短提示：

   WSL 命令要在 WSL 内执行

### 关键屏幕文字

主文字：

先识别终端，再选命令

辅助文字：

~~~text
PowerShell
CMD
WSL
~~~

### 声音与画面分工

- 声音解释 Windows 终端之间的运行环境边界。
- 画面演示从平台到终端的分流和当前分支选择。
- 字幕只保留“终端决定入口”或“先识别终端，再选命令”。

### 转场

被选中的终端节点变成安装入口，其他分支折叠成背景，进入 Scene 04 的安装方式比较。

### 实现约束

- 不展示可能随版本变化的安装 URL 或完整命令。
- 提示符只作为环境示意，不能让观众误以为一套提示符覆盖所有系统配置。
- 画面重点是环境识别，不是记忆命令。

## Scene 04｜官方原生安装优先，npm 是备选

### 视觉目标

用路径优先级表达安装方式的选择，避免把多个安装入口做成等权菜单。

### 画面结构

~~~text
┌─────────────────────────────┬─────────────────────────────┐
│ 官方原生安装                 │ npm 安装                    │
│ DEFAULT                      │ FALLBACK                    │
│ 路径直接                     │ 需要关注包管理与权限         │
│ 官方更新机制                 │ 版本冲突与维护成本           │
└─────────────────────────────┴─────────────────────────────┘

             官方原生优先

                 sudo npm
             ≠ 通用权限修复
~~~

左侧面板比右侧更亮，顶部用“默认入口／备选入口”标签建立层级。右侧不放完整安装命令，只显示可能需要关注的维护问题。

### 状态与动画顺序

1. 从 Scene 03 选中的终端流入两条安装路径。
2. 左侧官方原生路径先亮起，出现“默认入口”。
3. 右侧 npm 路径保持低对比度，随后出现“明确需求时再考虑”的条件标记。
4. 底部警示短暂出现，sudo npm 被描边后淡回，不做红色大弹窗。
5. 两条路径最后汇合到同一个“验证安装结果”节点。

### 关键屏幕文字

主文字：

官方原生安装优先

辅助文字：

~~~text
默认入口
备选入口
不要用 sudo npm 掩盖问题
~~~

### 声音与画面分工

- 声音讲清原生安装、npm、权限和维护之间的取舍。
- 画面只证明两条路径有优先级，并表现错误权限处理不是通用修复。
- 字幕保留“官方原生优先”和“不要用 sudo npm 掩盖问题”。

### 转场

安装入口标签收束成一个“已执行安装”的终端状态，进入 Scene 05。不要让左右对比面板停留成一张静态说明页。

### 实现约束

- 官方安装 URL、npm 命令和升级命令留待事实核验。
- 不展示 sudo 的完整执行过程，避免视觉上把它变成可复制建议。
- 两列比例要明显表达“默认／备选”，不能做成对称推荐。

## Scene 05｜安装之后，用证据确认命令可用

### 视觉目标

把“安装完成”转换为系统层面可以观察到的证据，并区分版本检查和诊断检查的作用。

### 画面结构

~~~text
┌──────────────────────────────────────────────────────────────┐
│ Terminal · new session                                       │
│                                                              │
│ $ claude --version                                           │
│ Claude Code <version>                                        │
│                                                              │
│ 命令已被系统找到                                              │
│                                                              │
│ $ claude doctor                                              │
│ [ installation ] [ configuration ] [ update ]               │
└──────────────────────────────────────────────────────────────┘
~~~

画面先只显示新终端和版本检查；诊断命令作为通过后的较小分支出现，不把完整诊断日志铺满主视觉区。

### 状态与动画顺序

1. 旧终端标签收起，新的终端窗口从右侧进入，提示 new session。
2. claude --version 逐字出现，光标停顿。
3. 版本输出用 <version> 示意，随后绿色状态条出现：

   命令已被系统找到

4. 如果需要诊断，claude doctor 从状态条下方展开，三个诊断类别依次通过。
5. 版本检查成为主证据，诊断命令退到辅助位置。

### 关键屏幕文字

主文字：

安装成功，要有验证证据

命令与状态：

~~~text
claude --version
claude doctor
~~~

命令已被系统找到

### 声音与画面分工

- 声音解释打开新终端的原因，以及两个命令分别证明什么。
- 画面展示“新终端 → 版本输出 → 必要时诊断”的证据链。
- 字幕不复述诊断细节，只跟随当前命令和状态。

### 转场

绿色“命令已被系统找到”状态沿着右侧连接线变成“需要授权”，进入 Scene 06。

### 实现约束

- 不锁定具体版本号和诊断输出。
- 当前系统若使用 where 等平台对应命令，后续事实核验时再决定是否加入；本幕主线只保留文章已确定的两个命令。
- 版本输出出现后必须留出可读时间，不能只做一帧闪现。

## Scene 06｜命令可用，还要完成登录

### 视觉目标

表现“命令可用”到“账号已授权”的跨界状态转换，让登录成为主链路的一部分。

### 画面结构

~~~text
┌────────────────────┐     ┌────────────────────┐     ┌────────────────────┐
│ Terminal            │     │ Browser            │     │ Terminal            │
│ ~/project           │ ──→ │ Sign in / Authorize│ ──→ │ Authenticated       │
│ $ claude            │     │ [Authorize]        │     │ Ready for task      │
└────────────────────┘     └────────────────────┘     └────────────────────┘
~~~

三个面板不同时展示完整内容。当前面板高亮，前后面板保留低对比度轮廓，形成一个清晰的授权回路。

### 状态与动画顺序

1. 终端显示项目目录和 claude 启动动作。
2. 一条蓝色连接线从终端流向浏览器，浏览器授权面板亮起。
3. 授权动作完成后，连接线返回终端。
4. 终端状态从“等待授权”变成绿色“已授权／可继续”。
5. 中央结论最后出现：

   命令可用 ≠ 账号已授权

### 关键屏幕文字

主文字：

命令可用 ≠ 账号已授权

示意状态：

~~~text
$ claude
等待授权
已授权，可继续
~~~

### 声音与画面分工

- 声音解释程序安装和账号授权是两个不同状态。
- 画面演示浏览器授权如何回到终端，而不是显示一张登录截图。
- 字幕只强调两种状态的差异。

### 转场

终端的“已授权”状态保持不变，浏览器面板向左收起，右侧展开远程环境分支进入 Scene 07。

### 实现约束

### 视觉目标

检查内容
检查修改范围
确认后写入
~~~

### 声音与画面分工

- 声音解释 diff 的意义和人的确认责任。
- 画面展示修改如何从“提案”转成“文件存在”，不重复朗读代码。
- 字幕只强调“先检查 diff，再确认写入”。

## 节奏与停留原则

不预设总时长。后续根据实际口播和画面完成时间确定 Scene 时长，遵循以下优先级：

- Scene 01 快速建立问题，但三项未确认状态必须看清。
- Scene 02～04 以判断和分流为主，卡片和分支不能同时堆满屏幕。
- Scene 05～07 要给版本输出、浏览器授权和跨设备 URL 回路留出完整状态变化时间。
- Scene 08 是任务准备，Scene 09 是核心高潮；不能为了赶节奏跳过“尚未落盘”和“确认后落盘”的差异。
- Scene 10～11 压缩错误和维护细节，保留层级判断与风险边界。
- Scene 12 的四项 checklist 完整出现后，要留出读字和思考时间；下节预告再短暂出现并直接结束。

## Visual Prototype 实现范围

下一阶段的 visual-prototype.html 只需要验证：

## 制作前事实核验清单

进入 Visual Prototype 或 Remotion 前，逐项确认：

- 当前官方安装入口、平台命令和安装 URL。
- 支持的操作系统、架构、资源和账号条件。
- PowerShell、CMD、WSL、macOS／Linux 终端之间的命令边界。
- 官方原生安装、Homebrew、WinGet、npm 的适用范围和维护方式。
- claude --version、claude doctor、claude auth login 的当前行为和输出。
- OAuth 在本地、SSH、远程服务器和 WSL 中的实际交互流程。
- ANTHROPIC_API_KEY 或其他环境变量对登录和组织识别的当前影响。
- 路径检查命令在不同平台的对应形式。
- 升级、卸载、配置清理和缓存清理的实际风险。
- diff 审查、确认写入和退出动作的当前 UI 表现。

在核验完成前，Prototype 中的输出、按钮、URL 和错误文本都按“语义示意”处理，不宣称为当前产品原文。

## Visual Script 自检标准

### Silent Test

关闭声音后，观众是否能看懂：

- 安装结束后仍有三个状态待确认。
- 终端和平台决定入口。
- 命令可用与登录完成是两个状态。
- 远程授权需要跨设备传递 URL 和结果。
- 文件是在确认 diff 后才出现。
- 错误需要先定位层级。
- 四项结果完成后才进入下节预告。

### Duplication Test

- 口播解释“为什么”，画面展示“怎么发生”。
- 不把系统规格、错误表、口播结论完整复制到屏幕。
- Scene 09 不朗读 diff，而是展示检查和写入状态。

### Motion Value Test

删除每个状态变化后，画面是否会失去含义？如果不会，就删掉该装饰动画。

### Video Value Test

每一幕必须能回答“为什么需要用视频表达”：

~~~text
状态变化
流程分流
跨设备授权
终端执行
diff 审查
文件落盘
错误定位
~~~

如果某个 Scene 在静态截图中已经能完整理解，优先补充过程或状态变化，而不是继续增加文字。
