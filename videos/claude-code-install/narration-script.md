## Scene 01｜安装命令结束，真的能用了吗？

安装命令跑完，终端也没有明显报错，是不是就算成功了？

其实还不能确定。

真正能用，至少要确认三件事：系统能找到 `claude` 命令，账号已经完成授权，而且它能在一个真实目录里完成一次受控任务。

所以这条视频不会只停在“怎么安装”，而是从安装前的选择开始，一直跑到第一次文件修改，再补上遇到问题时应该先查哪一层。

---

## Scene 02｜安装之前，先确认三个前提

在执行任何安装命令之前，先确认三个前提。

第一，系统和运行环境是否满足当前官方要求，包括操作系统、处理器、可用内存和网络。

第二，当前账号是否具备使用 Claude Code 的条件。能登录 Claude 网页版，不一定就代表可以直接使用 Claude Code，所以账号类型要先确认清楚。

第三，这次准备使用哪一种入口。本文走的是 CLI，也就是命令行；桌面 App 和编辑器集成是另外的使用路径，不要和终端安装混在一起。

这三项先确认，再开始安装，后面会少很多无效排查。

---

## Scene 03｜不是 Windows 一条命令：终端决定入口

安装命令不是简单的“Mac 一条，Windows 一条”。

尤其在 Windows 上，PowerShell、CMD 和 WSL 虽然都能看到终端窗口，但它们并不是同一个运行环境，命令也不能随便混用。

先看自己当前在哪个终端里，再选择对应的安装入口。

如果使用 WSL，就要在 WSL 终端内部执行 Linux 方式的命令；不要在 PowerShell 里复制一条 WSL 命令，然后把它当成自己已经进入了 WSL。

记住一句话：先识别终端，再执行命令。

---

## Scene 04｜官方原生安装优先，npm 是备选

大多数情况下，官方原生安装应该是默认入口。

它更适合作为第一次安装的路径，后续更新也更直接。

npm 可以作为备选，但它会把包管理、权限、版本冲突和后续维护一起带进来。只有在你明确需要 npm，或者当前环境确实适合 npm 时，再考虑这条路。

还有一个常见坑：遇到 npm 权限错误，不要条件反射地给命令加上 `sudo`。

先换回官方安装方式，或者先处理真正的权限和环境问题。用更高权限把错误压过去，往往只是把问题留到更新和维护时再爆出来。

所以安装方式的简单优先级是：官方原生安装优先，包管理器按需选择，npm 最后考虑。

---

## Scene 05｜安装之后，用证据确认命令可用

安装命令结束以后，不要马上进入下一步。

先打开一个新的终端，让新的 PATH 配置真正生效。

然后运行 `claude --version`。

如果能返回版本信息，说明系统已经找到了 Claude Code 命令。

如果提示找不到命令，先检查 PATH 和当前终端，不要立刻重复安装。

遇到更复杂的情况，再运行 `claude doctor`，让它把安装、配置和更新状态列出来。

这两个命令的作用不一样：`claude --version` 证明命令能不能被找到，`claude doctor` 帮你定位安装之后到底是哪一环出了问题。

---

## Scene 06｜命令可用，还要完成登录

现在终端已经能找到 Claude Code，但它还不知道你要使用哪个账号。

进入一个项目目录，运行 `claude`，按照提示在浏览器里完成授权，再回到终端继续操作。

这里要分清两件事：安装成功，只代表程序已经在电脑上；登录完成，才代表它具备使用当前账号工作的条件。

也就是说，命令可用，不等于账号已经授权。

第一次启动时，把这次登录完整走通，后面才能验证真正的使用链路。

---

## Scene 07｜远程环境没有浏览器，也能完成授权

如果你是在远程服务器、SSH，或者某些 WSL 环境中运行，浏览器可能不会在当前设备自动打开。

这时候不用重装，也不用一直等弹窗出现。

按照终端提示，把 OAuth 地址复制出来，在另一台能打开浏览器的设备上完成授权，再把授权结果带回终端。

整个过程可以理解成三步：复制 URL，完成授权，再把结果交回当前终端。

如果交互式登录不方便，也可以使用更明确的 `claude auth login` 入口，按照提示完成登录。

远程环境的关键不是换一套软件，而是把浏览器授权和终端之间的这条回路接通。

---

## Scene 08｜先用一个空目录跑通第一次任务

登录完成以后，不要马上把 Claude Code 交给一个复杂项目。

先创建一个空的测试目录，在里面启动 Claude Code。

这样做的好处是，第一次验证只需要观察工具本身，不会把真实项目里的配置、依赖和历史问题一起带进来。

进入之后，可以先输入 `/help`，确认交互和命令列表都能正常打开。

接着提出一个很小、结果明确的任务，比如：在 `test.py` 文件里写一个打印 hello world 的函数。

第一次任务越小，越容易看清楚它到底做了什么，也越容易在出现问题时定位原因。

---

## Scene 09｜先看 diff，再让文件真正落盘

这一步是第一次使用里最重要的环节。

Claude Code 收到任务以后，不是悄悄把文件改完，而是会先把准备进行的修改展示出来。

先看 diff。

确认文件名、具体内容和修改范围都符合预期，再允许它写入文件。

如果不符合预期，就先拒绝或提出调整，让它重新生成修改方案。

确认之后，文件才真正落盘，测试目录里也才会出现 `test.py`。

这个过程可以压缩成四步：提出目标，生成修改，人工检查 diff，确认后写入。

所以 Claude Code 的核心节奏不是“说一句话，文件就被偷偷改掉”，而是先给出方案，再由你确认是否执行。

走完这一步，安装才真正被验证成了“可以使用”。

---

## Scene 10｜遇到报错，先判断错误发生在哪一层

如果中间出现报错，不要第一反应就是重新安装。

先问一个问题：错误发生在哪一层？

是当前终端和命令不匹配，还是网络返回了异常？

是 PATH 没有找到命令，还是系统资源、运行库、账号权限出了问题？

也有一种情况，是同一台电脑上装了多个来源的 Claude Code，导致版本和路径互相冲突。

判断清楚层级以后，再选择对应处理方式。

比如找不到命令，先查 PATH；行为异常，检查是不是有多个安装；登录失败，先看账号和环境变量；安装器下载异常，再回头检查网络和平台。

排错的原则只有一句：先对症，再下药，不要把所有问题都当成“没装好”。

---

## Scene 11｜升级和卸载，要匹配最初的安装来源

维护 Claude Code 时，也要记住一个原则：安装来源决定维护方式。

官方原生安装、Homebrew、WinGet 和 npm，各自对应不同的升级与卸载命令，不能混着维护。

如果最初使用官方方式安装，优先使用它对应的更新入口；如果使用包管理器，就交给原来的包管理器处理。

另外，卸载程序本体，不等于删除所有配置、授权和会话历史。

如果只是排查普通问题，不要一上来就做彻底清理。

删除用户配置、缓存或项目本地设置之前，先确认这些内容是否还需要，因为彻底清理通常是不可逆的。

先确认来源，再执行维护；先确认后果，再做清理。

---

## Scene 12｜四项结果，才算真正准备好

现在回到开头的问题：什么状态才算真的装好了？

你应该能确认四件事。

第一，当前环境满足要求。

第二，安装入口和当前终端是匹配的。

第三，`claude --version` 和登录流程都已经验证通过。

第四，你在测试目录里完成过一次小任务，并且先看过 diff，再确认文件写入。

所以，Claude Code 的安装不是执行一条命令，而是把环境、命令、账号和第一次任务这条链路完整打通。
