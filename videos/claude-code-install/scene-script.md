# Claude Code 安装与使用 · 第三步：Scene Script

> 目标：把 Video Narrative 拆成可制作的视频场景。每个 Scene 同时定义：认知任务、口播方向、画面事件、屏幕重点、Scene Type、Video Value 和信息分工。

本条视频暂拆为 12 个视觉事件。Scene 数量服务于认知变化，不按原文章节数量固定；不设置固定总时长，也不在本阶段编写最终逐句口播、字幕时间轴或 Remotion 配置。

---

## Scene 01｜安装命令结束，真的能用了吗？

### 目的

先制造新手最容易忽略的不确定性：安装器执行结束，只能说明安装步骤结束，不能证明命令可用、账号已授权或第一次任务能完成。

### 认知任务

让观众接受本条视频的成功标准不是“命令跑完”，而是“整条使用链路打通”。

### 口播方向

命令执行完了，终端也没有明显报错，是不是就算安装成功？

其实还不能确定。你还需要确认系统能找到命令、账号已经完成授权，并且 Claude Code 能在一个真实目录里完成一次可控任务。

这条视频就从安装前的选择开始，一直跑到第一次文件修改，再补充遇到问题时应该先查哪一层。

### 画面

深色终端中显示安装命令执行结束，终端状态暂时停在：

```text
Installation finished
```

随后画面旁边出现三个尚未确认的状态：

```text
命令可用？   未确认
账号已登录？ 未确认
任务能完成？ 未确认
```

最后将三项状态收束成一条待完成链路：

```text
安装 → 验证 → 登录 → 第一次任务
```

### 屏幕重点

```text
安装完成 ≠ 真正能用
```

### Scene Type

`OpeningScene`

### Video Value

把“安装教程”转换成一个有明确终点的任务，建立全片的观看动力。

### 信息分工

- **声音**：提出问题，给出本条视频的承诺。
- **画面**：把安装成功拆成几个需要继续验证的状态。
- **字幕**：只保留“安装完成 ≠ 真正能用”。

### 转场

从未确认状态切到三个检查入口，进入安装前判断。

## Scene 02｜安装之前，先确认三个前提

### 目的

避免观众直接复制命令，直到安装过程中才发现系统、账号或使用入口不匹配。

### 认知任务

让观众在执行命令前完成一次环境筛选：能不能装、能不能登录、是不是要走 CLI。

### 口播方向

在执行任何安装命令前，先确认三件事。

第一，系统和运行环境是否满足要求，包括操作系统、架构、可用资源和网络。

第二，当前账号是否具备使用 Claude Code 的条件。

第三，你这次是不是准备使用 CLI。桌面 App 和编辑器集成是其他入口，不要和这条终端主线混在一起。

### 画面

三个依次亮起的检查卡片：

```text
01 运行环境
系统、架构、资源、网络

02 账号资格
订阅或 Console 条件

03 使用入口
CLI 还是其他入口？
```

每张卡片确认后显示绿色勾选；没有满足条件时，不进入安装命令，而是停在当前卡片。

### 屏幕重点

```text
先确认：环境、账号、入口
```

### Scene Type

`StepListScene`

### Video Value

把原文的系统要求和账号说明压缩成一个安装前决策门槛，降低无效尝试。

### 信息分工

- **声音**：解释三项检查为什么重要。
- **画面**：展示三个前置条件的顺序关系。
- **字幕**：只呈现三个关键词，不展示完整规格表。

### 转场

三个检查卡片全部通过后，画面从“能不能装”切换到“应该走哪条入口”。

## Scene 03｜不是 Windows 一条命令：终端决定入口

### 目的

把平台和终端差异表现成选择关系，避免观众把 PowerShell、CMD 和 WSL 当成同一个环境。

### 认知任务

让观众先识别当前终端，再决定后续安装命令，而不是从网上随便复制一条“Windows 命令”。

### 口播方向

安装命令不是简单的“Mac 一条、Windows 一条”。尤其在 Windows 上，PowerShell、CMD 和 WSL 使用的环境不同，命令也不应该混用。

WSL 要在 WSL 终端内部执行 Linux 方式的命令，而不是在 PowerShell 里假装自己已经进入了 WSL。

### 画面

先出现系统入口，再展开终端分支：

```text
当前环境
├─ macOS / Linux
│  └─ Unix 终端
└─ Windows
   ├─ PowerShell
   ├─ CMD
   └─ WSL
```

鼠标或高亮框分别停在三种 Windows 提示符上，错误的命令放入错误终端时出现“环境不匹配”的提示，但不展示长错误日志。

### 屏幕重点

```text
先识别终端，再选命令
```

### Scene Type

`ConceptScene`

### Video Value

把跨平台安装从平铺命令表转成一个可复用的环境识别方法。

### 信息分工

- **声音**：解释平台与终端的边界。
- **画面**：展示系统、终端和命令入口的树状关系。
- **字幕**：突出“终端决定入口”。

### 转场

终端节点被选中后，进入安装方式优先级比较。

---

## Scene 04｜官方原生安装优先，npm 是备选

### 目的

让观众理解安装方式存在优先级，而不是看到多个选项后随意选择最熟悉的 npm。

### 认知任务

建立一个简单规则：满足条件时优先官方原生安装；只有存在明确需求时再考虑 npm 等备选方式。

### 口播方向

在大多数平台上，官方原生安装应该是默认入口。它更适合作为新手的第一条路径，后续更新也更直接。

npm 可以作为备选，但它会带来包管理、权限、版本冲突和后续维护的问题。遇到权限错误时，也不要条件反射地给 `npm` 加上 `sudo`。

### 画面

左右两列对比：

```text
官方原生安装                 npm 安装
默认入口                     备选入口
安装路径更直接               需要自己关注版本和升级
官方更新机制                 可能遇到权限或全局包冲突
```

底部单独出现警示：

```text
sudo npm ≠ 通用权限修复
```

画面只展示安装方式的判断关系，不展示三套完整命令。

### 屏幕重点

```text
先选正确入口，再执行安装
```

### Scene Type

`ComparisonScene`

### Video Value

传达安装方式的决策逻辑，减少复制旧教程和混用安装来源造成的后续问题。

### 信息分工

- **声音**：解释原生安装与 npm 的取舍。
- **画面**：表现默认入口、备选入口和权限风险。
- **字幕**：保留“官方原生优先”和“不要用 sudo npm 掩盖问题”。

### 转场

选择入口后，所有分支汇合到同一个“验证安装结果”的终端。

## Scene 05｜安装之后，用证据确认命令可用

### 目的

把“安装器显示完成”转换成系统层面的可观察证据。

### 认知任务

让观众掌握最小验证链：打开新终端，用版本检查确认命令可被找到；出现异常时，再用诊断命令定位问题。

### 口播方向

安装命令结束后，不要马上进入下一步。先打开一个新的终端，让新的 PATH 配置生效。

运行 `claude --version`，确认系统能找到 Claude Code 并返回版本信息。遇到异常时，再用 `claude doctor` 检查安装、配置和更新状态。

### 画面

终端从旧窗口切换到新窗口，依次显示：

```bash
claude --version
```

输出版本信息后，状态条从“安装完成”变成：

```text
命令已被系统找到
```

随后以较小的分支提示展示：

```bash
claude doctor
```

诊断项逐个通过，不把完整诊断日志铺满画面。

### 屏幕重点

```text
安装成功，要有验证证据
```

### Scene Type

`TerminalScene`

### Video Value

让观众形成“安装 → 新终端 → 版本检查 → 必要时诊断”的可复用验证习惯。

### 信息分工

- **声音**：说明两个命令分别证明什么。
- **画面**：展示新终端、命令输出和状态变化。
- **字幕**：只保留命令名和“命令已被系统找到”。

### 转场

版本检查通过后，终端中的状态从“命令可用”继续进入“账号授权”。

## Scene 06｜命令可用，还要完成登录

### 目的

明确区分“安装完成”和“账号授权完成”，补齐从启动到登录的主路径。

### 认知任务

让观众理解登录不是另一个复杂功能，而是第一次使用必须完成的状态转换。

### 口播方向

现在终端已经能找到 Claude Code，但它还需要知道你使用的是哪个账号。

进入一个项目目录，运行 `claude`，然后按提示在浏览器完成授权，再回到终端继续操作。

### 画面

三段式授权回路：

```text
Terminal                 Browser                 Terminal
运行 claude  ─────────→  登录并授权  ─────────→  返回已登录状态
```

终端先显示等待授权，浏览器卡片出现授权确认，回到终端后显示：

```text
Authentication complete
```

实际文案和当前登录提示在后续脚本阶段核验，不在本阶段锁定易变的界面细节。

### 屏幕重点

```text
命令可用 ≠ 账号已授权
```

### Scene Type

`TerminalScene`

### Video Value

用一个跨终端和浏览器的状态回路，解释为什么安装后还必须登录。

### 信息分工

- **声音**：讲清“安装”和“授权”的区别。
- **画面**：展示浏览器授权如何回到终端。
- **字幕**：突出“命令可用 ≠ 账号已授权”。

### 转场

主路径完成后，短暂展开远程环境分支，再回到同一个已登录终端。

---

## Scene 07｜远程环境没有浏览器，也能完成授权

### 目的

处理 SSH、远程服务器或 WSL 中浏览器不在当前设备的高频问题，不让异常路径打断主登录流程。

### 认知任务

让观众知道浏览器没有自动打开时不必重装，授权 URL 和终端之间仍然可以手动完成闭环。

### 口播方向

如果你是在远程服务器、SSH 或某些 WSL 环境里运行，浏览器可能不会在当前设备自动打开。

这时可以按提示复制 OAuth URL，在另一台能访问浏览器的设备上完成授权，再把授权结果带回终端。必要时，也可以使用更明确的 `claude auth login` 登录入口。

### 画面

左右两个设备：

```text
远程终端                         本地浏览器
等待授权  ──复制 URL──────────→  打开并登录
等待 code  ←─带回授权结果──────  完成授权
```

底部只出现一次异常提示：

```text
登录组织异常？检查残留的 ANTHROPIC_API_KEY
```

该提示作为诊断分支短暂出现，不展开账号政策和环境变量优先级细节。

### 屏幕重点

```text
浏览器不在当前设备，不等于登录失败
```

### Scene Type

`ComparisonScene`

### Video Value

把远程授权从“卡住的异常”变成一个可理解的跨设备流程。

### 信息分工

- **声音**：解释远程环境的处理方式。
- **画面**：展示 URL 和授权结果在两个设备之间流动。
- **字幕**：保留“复制 URL → 授权 → 带回终端”。

### 转场

两个设备的箭头汇合为“已登录”，画面进入测试目录。

---

## Scene 08｜先用一个空目录跑通第一次任务

### 目的

把“已安装、已登录”推进到“开始执行真实任务”，并控制任务范围，避免第一次演示带来额外风险。

### 认知任务

让观众知道第一次验证不需要拿真实项目冒险，一个空的测试目录就足以确认基本链路。

### 口播方向

现在不要马上把它交给一个复杂项目。先创建一个空的测试目录，在里面启动 Claude Code。

进入后可以先输入 `/help`，确认交互正常，再用自然语言提出一个很小、结果明确的任务：创建一个 `test.py` 文件。

### 画面

文件树从空目录开始：

```text
claude-code-test/
└── （空）
```

终端依次出现：

```bash
claude
/help
请创建一个简单的 test.py 文件。
```

Claude Code 读取当前目录并给出准备修改的提示，但文件暂时还没有落盘。

### 屏幕重点

```text
先在测试目录里验证
```

### Scene Type

`TerminalScene`

### Video Value

把安装验证变成低风险、可复现的真实任务，为下一幕的 diff 确认建立必要上下文。

### 信息分工

- **声音**：说明为什么使用空目录和小任务。
- **画面**：展示空目录、启动命令、`/help` 和自然语言任务。
- **字幕**：只保留测试目录和任务目标。

### 转场

任务提交后，画面停在 Claude Code 的修改提案，进入全片的核心事件。

## Scene 09｜先看 diff，再让文件真正落盘

### 目的

用第一次文件修改证明 Claude Code 已经真正可用，同时保留人的确认权。

### 认知任务

让观众看到“提出目标 → 生成修改 → 人检查 diff → 确认写入”的完整受控闭环。

### 口播方向

Claude Code 不是收到一句话后就悄悄改完文件。它会先把准备进行的修改展示出来。

先看 diff，确认文件名、内容和修改范围都符合预期，再允许它写入。

这一步完成后，安装才真正被验证成了“可以使用”。

### 画面

终端右侧或下方出现文件修改提案：

```diff
++ test.py
def hello():
+    print("hello world")
```

修改区域高亮，旁边出现明确的确认动作：

```text
Review changes
[ Yes ]   [ No ]
```

用户确认后，文件树从空目录变成：

```text
claude-code-test/
└── test.py
```

最后出现短暂的退出动作：

```text
exit
```

### 屏幕重点

```text
先检查 diff，再确认写入
```

### Scene Type

`TerminalScene`

### Video Value

这是全片最重要的 Video Value：把“安装成功”转化成一个真实、可检查、由用户确认后落盘的文件修改结果。

### 信息分工

- **声音**：解释 diff 和人的确认责任。
- **画面**：负责展示提案、确认、文件出现和退出的连续状态变化。
- **字幕**：只强调“先检查 diff，再确认写入”。

### 转场

文件出现后不要马上切走，留出足够时间让观众读完 diff 和最终结果，再进入“遇到问题怎么办”。

## Scene 10｜遇到报错，先判断错误发生在哪一层

### 目的

在观众已经看到正确路径之后，补充一套可迁移的排错方法，避免把所有问题都归结为“重装”。

### 认知任务

让观众先识别错误层级，再决定换命令、修 PATH、检查资源、处理账号还是检查安装来源。

### 口播方向

如果中间出现报错，不要第一反应就是重新安装。

先问一个问题：错误发生在哪一层？是当前终端和命令不匹配，还是网络返回异常？是 PATH 找不到命令，还是资源、系统库、账号或多个安装来源冲突？

### 画面

用一张从下到上的诊断地图替代完整错误表：

```text
账号与权限       403、组织或 API Key 异常
安装来源         多个 claude 路径互相覆盖
系统资源与运行库  Killed、shared library 错误
PATH             command not found: claude
网络             下载内容或响应异常
终端             命令与当前 shell 不匹配
```

其中只短暂放入代表性判断：

```bash
which -a claude
```

用于说明重复安装需要先确认路径，而不是直接覆盖安装。

### 屏幕重点

```text
先找错误层级，再决定修复方式
```

### Scene Type

`ConceptScene`

### Video Value

把九类报错压缩成一个可复用的诊断框架，避免视频退化成错误信息朗读。

### 信息分工

- **声音**：讲清“先诊断、后处理”的顺序。
- **画面**：呈现错误层级和代表性现象的对应关系。
- **字幕**：只保留层级名称和一句原则。

### 转场

诊断地图从多个分支收束为一个维护原则，进入升级和卸载边界。

---

## Scene 11｜升级和卸载，要匹配最初的安装来源

### 目的

补齐文章承诺的维护内容，并提醒彻底清理操作具有不可逆风险。

### 认知任务

让观众记住两个边界：安装来源决定维护方式；彻底删除配置和缓存前要确认后果。

### 口播方向

升级和卸载时，要先回忆自己最初是通过哪种方式安装的。官方原生安装和 npm 安装不能随意混用维护命令。

如果要删除用户配置、缓存或项目本地设置，也要先确认这些内容是否还需要。彻底清理是不可逆操作，不应该作为普通排错的第一步。

### 画面

左右两条维护路径：

```text
官方原生安装 → 使用对应的升级／卸载方式
npm 安装      → 使用对应的包管理方式
```

随后出现一个明显但克制的危险提示：

```text
彻底清理
不可逆，先确认再执行
```

不在主画面展示完整的破坏性删除命令，只展示“操作边界”。

### 屏幕重点

```text
按安装来源维护
危险清理不要盲目执行
```

### Scene Type

`StepListScene`

### Video Value

让观众获得安装后的最低维护能力，同时避免把高风险命令包装成快捷修复方案。

### 信息分工

- **声音**：说明安装来源与维护方式的对应关系。
- **画面**：展示两条维护路径和不可逆警示。
- **字幕**：强调“按来源维护”和“先确认再清理”。

### 转场

两条维护路径收束为同一张成功检查清单，进入结尾。

## Scene 12｜四项结果，才算真正准备好

### 目的

用可验证结果收束全片，并在最后用一句话承接下一节，不展开新的知识。

### 认知任务

让观众用四项结果判断自己是否完成了本节，而不是回忆所有命令。

### 口播方向

回到最开始的问题：什么状态才算真的装好了？

你应该能确认四件事：环境满足要求，安装入口选对了，命令和账号都已经验证，最后还在测试目录里完成过一次查看 diff 后再写入文件的任务。

所以，Claude Code 的安装不是执行一条命令，而是把环境、命令、账号和第一次任务这条链路完整打通。

最后只保留一句下节预告：

下一节，我们会拆开 Claude Code 背后的“代理循环”，看看一句自然语言指令是怎样变成一次真实文件修改的。

### 画面

四项结果依次出现并被勾选：

```text
✓ 环境满足要求
✓ 入口选择正确
✓ 命令可用并完成登录
✓ 第一次任务已查看 diff 并确认写入
```

四项勾选后汇合成最终状态：

```text
Claude Code Ready
```

画面停留片刻，随后只出现一张很短的系列承接卡：

```text
下一节：Claude Code 如何工作？
代理循环，如何把一句话变成一次文件修改？
```

承接卡之后结束，不再增加新的安装信息。

### 屏幕重点

```text
可安装、可验证、可授权、可完成任务
```

### Scene Type

`SummaryScene`

### Video Value

用四个结果证明本节完成，并用极短的系列预告建立下一节的观看动机。

### 信息分工

- **声音**：总结成功标准，最后说出一句预告。
- **画面**：展示四项勾选和最终承接卡。
- **字幕**：控制在一到两行，不重复整篇命令。

### 结束原则

## 信息分工总原则

- **声音**负责解释为什么要做这一步、它证明了什么，以及用户应该如何判断。
- **画面**负责展示环境分流、状态变化、终端操作、授权回路和 diff 事件。
- **屏幕文字**只保留命令、关键状态和判断原则，不复制文章段落。
- **Scene 转场**优先由状态完成推动：检查通过、命令可用、授权完成、文件落盘。

全片最重要的画面不是安装命令本身，而是 Scene 09 的 diff 确认。安装入口和排错信息应服务于这条主线，不能让完整命令表或错误表抢走视觉中心。

---

## 节奏与时长原则

不预设固定总时长。后续根据实际口播、必要停顿和视觉元素完成入场来确定 Scene 时长：

- Scene 01 和 Scene 12 要短而明确，负责开场承诺和结尾收束。
- Scene 02～05 以判断和验证为主，避免系统规格和命令列表停留过久。
- Scene 06～07 的授权回路要给观众看清状态变化。
- Scene 08～09 是核心使用闭环，尤其要为 diff 阅读和确认动作留足时间。
- Scene 10～11 以分层提示和边界说明为主，不做完整错误手册。

任何 Scene 都不能在主要状态变化尚未完成前切走，尤其不能让 diff、文件写入或结尾 checklist 只出现一瞬间。

---

## 时效性与实现前核验

进入 Narration Script 前，需要重新核验并决定最终口播中是否保留：

- 官方安装 URL、平台命令和当前版本示例。
- 系统要求、账号条件、安装路径和 PATH 行为。
- 登录命令、OAuth 提示和 `ANTHROPIC_API_KEY` 相关说明。
- 升级、卸载和重复安装检查命令。
- 代表性错误文本是否仍然准确。

当前 Scene Script 只使用这些信息的叙事作用，没有把易变的版本号、完整 URL 或破坏性清理命令写成最终交付文案。
