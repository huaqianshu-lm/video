## 1. 内容定位

### 1.1 原文解决的问题

这篇文章面向第一次安装 Claude Code 的用户，解决的不是「Claude Code 是什么」，而是：

> **如何选对安装路径，在自己的电脑上安全装好 Claude Code，确认它确实能工作，并完成第一次真实任务。**

原文同时试图降低新手在以下环节中的不确定性：

- 不知道自己的系统、账号和使用方式是否满足要求。
- 不知道 macOS、Linux、WSL、PowerShell、CMD 应该使用哪条命令。
- 只知道 npm 安装，误把 `sudo` 当作权限问题的通用解法。
- 安装后没有验证，直到真正运行时才发现 PATH、网络或账号问题。
- 登录时浏览器没有自动打开，不知道远程环境如何完成授权。
- 看到报错就重装，没有先判断报错属于命令、网络、PATH、账号还是资源问题。
- 安装成功了，却没有完成「启动、登录、给任务、确认 diff、写入文件」的第一条闭环。

### 1.2 内容类型

这不是 Claude Code 的概念介绍，也不是完整命令参考，而是一篇：

- 面向新手的安装与首次使用教程。
- 带平台分支的操作指南。
- 带故障诊断的上手流程。
- 以「从零跑通一次」作为最终成功标准的实践文章。

### 1.3 目标读者

主要读者是：

- 没有使用过 Claude Code 的开发者。
- 知道基本终端操作，但不熟悉跨平台安装差异的人。
- 已经知道 Claude Code 是什么，准备在本机真正使用的人。
- 曾经用 npm 或旧教程安装失败，需要重新理顺安装方式的人。

次要读者是：

- 在远程服务器、SSH 或 WSL 中安装 Claude Code 的用户。
- 已安装但遇到 `command not found`、登录失败或多个版本冲突的用户。

不适合作为本篇主体的读者问题：

- Claude Code 的代理循环原理。
- MCP 的深入配置。
- 第三方模型接入。
- VS Code、JetBrains、桌面 App 的完整使用教程。

这些内容在原文中只作为边界或后续系列的引导，不应抢走「安装并跑通第一次任务」这条主线。

## 2. 核心命题

这篇文章表面上是在列安装命令，真正要建立的认知是：

> **安装 Claude Code 不只是把一个命令放进电脑，而是要根据环境选对入口，再通过验证、登录和一次真实任务确认整条使用链路已经打通。**

如果观众最后只记住一句话，应该是：

> **先确认环境，再选正确安装方式；装好后用版本检查、登录和一次可控的文件修改，把“安装成功”验证成“真的能用”。**

原文还包含一个重要的避坑命题：

> **安装遇到问题时，先判断错误发生在哪一层，不要条件反射地重装，更不要用 `sudo npm` 掩盖权限问题。**

因此，这条视频不应做成「命令清单朗读」，而应围绕一条可验证的上手闭环展开：

```text
检查前提
↓
根据平台和终端选安装入口
↓
安装
↓
打开新终端验证版本
↓
登录
↓
创建测试目录并完成第一次任务
↓
查看 diff 并确认写入
↓
遇到问题时按层诊断
```

## 3. 必须保留的核心信息

### A. 安装前的三个前提

这一部分必须保留，但不需要把文章中的表格逐项念完。观众至少要知道安装前先确认三件事：

1. **系统和运行环境够用**：操作系统版本、CPU 架构、可用内存和网络满足要求。
2. **账号具备使用资格**：不是所有 Claude.ai 账号都能直接使用 Claude Code，需要符合文章所列的订阅或 Console 条件。
3. **先确定使用入口**：本篇以 CLI 为主；桌面 App 和编辑器集成属于其他入口，不应混入主操作线。

这三件事的认知作用是避免用户在安装过程中才发现「机器不支持」「账号不能用」或「其实不想用终端」。

### B. 官方原生安装是默认入口

必须保留文章的主判断：

- macOS、Linux、WSL 优先使用官方原生安装脚本。
- Windows 原生环境根据终端选择 PowerShell 或 CMD 命令。
- 官方脚本的主要优势是安装简单并支持后台自动更新。
- npm 可以作为备选，但不应作为新手默认路径。
- 不要用 `sudo npm install -g ...` 解决权限问题；这可能造成后续权限和自动更新问题。

这里真正需要传达的是「安装方式有优先级」，而不是把三种方式做成平铺的功能列表。

### C. Windows 的终端分支

这是原文最明确的平台分支，必须保留：

- PowerShell 与 CMD 不是同一个终端。
- PowerShell 使用 `irm` 方式。
- CMD 使用对应的 `.cmd` 安装方式。
- WSL 要在 WSL 终端内部执行 Linux 命令，不是在 PowerShell 里假装执行。
- 根据提示符识别当前终端，可以避免把命令粘贴到错误环境。

视频不必完整解释所有 shell 语法，但必须让观众理解：

> **命令不是“Windows 一条、Mac 一条”这么简单，终端类型会决定正确的安装入口。**

### D. 安装后的验证链

安装命令执行完不能直接宣布成功，至少要展示两级验证：

- `claude --version`：确认命令已经可以被系统找到，并输出版本号。
- `claude doctor`：在新机器或出现异常时，检查安装、配置和更新状态。

其中，`command not found: claude` 或 Windows 对应错误不一定代表安装失败，优先考虑 PATH 没有包含安装目录。

### E. 登录与异常授权路径

必须保留最小登录闭环：

```text
进入项目目录
↓
运行 `claude`
↓
浏览器授权
↓
回到终端完成登录
```

还需要保留远程环境的关键分支：

- 浏览器没有自动打开时，按 `c` 复制 OAuth URL。
- 在另一台可访问浏览器的设备上打开 URL。
- 将授权结果中的 code 贴回终端。
- 必要时使用 `claude auth login` 作为更稳的登录方式。

登录后出现组织被禁用等异常时，文章给出的重要排查方向是残留的 `ANTHROPIC_API_KEY`。这不是普通安装步骤，但属于新手很难自行想到的高价值诊断点。

### F. 第一次真实任务

这是整篇最需要视频化的部分，不能只保留为文字步骤。

最小成功流程是：

```text
创建空目录
↓
运行 `claude`
↓
完成登录
↓
输入 `/help`
↓
用自然语言要求创建 `test.py`
↓
Claude Code 展示 diff
↓
用户确认后写入文件
↓
输入 `exit` 退出
```

需要强调的核心行为不是「它能写一个 hello world」，而是：

> **Claude Code 先提出文件修改方案并展示 diff，等用户确认后才真正写入。**

这一步把「安装完成」转化为「使用闭环跑通」，也是本篇最有 Video Value 的结果。

### G. 常见错误要按原因分类

文章的报错表可以保留为诊断框架，但不必在视频中平均展开全部错误。至少要让观众建立以下分类：

| 错误层 | 典型问题 | 核心判断 |
| --- | --- | --- |
| 终端不匹配 | `irm is not recognized`、`&& is not valid`、`bash is not recognized` | 当前 shell 与命令不对应 |
| 网络或响应内容异常 | `unexpected token '<'` | 下载到 HTML 或网络返回异常 |
| PATH | `command not found: claude` | 程序存在，但系统找不到它 |
| 系统资源 | Linux 安装时 `Killed` | 可能是内存不足或 OOM |
| 系统运行库 | `Error loading shared library` | libc 类型或安装变体不匹配 |
| 账号与权限 | `403 Forbidden`、登录组织异常 | 订阅、账号角色或环境变量问题 |
| 重复安装 | `which -a claude` 出现多个路径 | 多个安装来源互相覆盖 |

文章反复强调的诊断原则必须保留：

> **先对症，再下药；先找到错误层级，再决定是换命令、修 PATH、换安装方式还是检查账号。**

### H. 升级与卸载的基本边界

升级和卸载不是本篇的第一主线，但文章明确承诺了这两部分，因此不能完全删除。

建议保留以下最小信息：

- 官方脚本安装通常会后台更新，也可以用 `claude update` 主动更新。
- Homebrew、WinGet、npm 等方式的升级需要使用各自的包管理命令。
- 卸载必须按照原来的安装方式对应处理。
- 删除程序本体不等于删除配置、授权和会话历史。
- 彻底清理 `~/.claude`、`~/.claude.json` 或项目配置前必须明确这是不可逆操作。

这一部分的重点是「安装来源决定维护方式」和「程序、配置、历史是不同层」，不需要在主线中展示所有清理命令。

## 4. 知识骨架与关系

### 4.1 安装入口决策关系

安装命令不是独立记忆点，而是由两个条件共同决定：

```text
操作系统
├─ macOS / Linux
│  └─ 终端：官方原生脚本
├─ WSL
│  └─ WSL 终端：按 Linux 方式安装
└─ Windows 原生
   ├─ PowerShell：PowerShell 安装命令
   └─ CMD：CMD 安装命令
```

因此，视频应该先让观众判断「我在哪里运行」，再出现命令，而不是先连续展示多段代码。

### 4.2 安装方式的取舍关系

三种方式的关系不是简单的并列：

```text
官方原生安装
├─ 默认推荐
├─ 操作简单
└─ 支持后台自动更新

Homebrew / WinGet
├─ 适合已经使用对应包管理器的人
└─ 通常需要手动升级

npm
├─ 作为最后备选
├─ 需要 Node.js 18+
└─ 不要用 sudo 解决权限问题
```

观众需要记住的是选择逻辑：

> **新手走官方原生安装；已有包管理习惯的人可以沿用包管理器；npm 不是默认答案。**

### 4.3 成功状态关系

「安装命令没有报错」并不等于「Claude Code 可以工作」。完整状态应逐步推进：

```text
命令执行完成
↓
系统能找到 `claude`
↓
`claude --version` 有输出
↓
账号完成授权
↓
Claude Code 能打开项目会话
↓
能理解自然语言任务
↓
能展示 diff 并在确认后写文件
```

这条状态链是文章最适合被转换成视频的结构之一。

### 4.4 错误诊断关系

错误处理应该从「报错文字」回到「发生层级」：

```text
命令跑不起来
├─ 终端类型不对 → 换对应 shell 命令
├─ 下载内容不对 → 检查网络或换安装方式
├─ 安装后找不到 → 修 PATH
├─ 运行时被杀 → 检查内存和系统运行库
├─ 登录被拒绝 → 检查账号、订阅和 API key
└─ 行为互相冲突 → 检查是否有多个安装
```

### 4.5 维护关系

安装方式会影响之后的升级和卸载：

```text
安装来源
├─ 官方脚本 → 后台更新 / `claude update`
├─ Homebrew → `brew upgrade`
├─ WinGet → `winget upgrade`
└─ npm → `npm install -g ...@latest`
```

卸载时还要区分：

```text
程序本体
≠
配置 / 授权 / 会话历史
```

## 5. 文章中的关键误区

这些误区比单条命令更值得保留，因为它们决定观众能否迁移到自己的环境：

1. **把 npm 当成唯一安装方式**：应该先了解官方原生安装。
2. **把 `sudo` 当成权限问题的万能解法**：权限异常时应改用正确的安装路径。
3. **把平台当成唯一判断条件**：Windows 还要进一步区分 PowerShell、CMD 和 WSL。
4. **把安装命令成功当成安装完成**：还要打开新终端检查版本。
5. **把 `command not found` 当成程序不存在**：通常需要先检查 PATH。
6. **在远程环境等待浏览器自动打开**：应复制 OAuth URL 到可用浏览器授权。
7. **忽略环境变量对登录方式的影响**：残留的 `ANTHROPIC_API_KEY` 可能覆盖订阅登录。
8. **遇到报错就重装**：先使用错误类型判断工具和修复方向。
9. **只验证能启动，不验证能完成任务**：第一次文件修改和 diff 确认才是完整闭环。
10. **只删除程序，不区分配置和历史**：彻底清理是另一种不可逆操作。

## 6. 最有视频价值的内容

### A. 平台与终端分流

适合表现为动态决策过程：

- 先显示用户当前系统和终端。
- 根据分支只保留对应命令。
- 错误命令进入错误状态，再切换到正确入口。

它比同时摆出多段代码更能让观众理解「为什么这条命令适用于我」。

### B. 安装后的状态变化

适合表现为终端状态推进：

```text
未安装
→ 安装完成
→ 命令可发现
→ 版本已确认
→ 已登录
→ 已完成首次任务
```

每一步都应该有可观察的输出或状态，不要只用一张「安装成功」的静态卡片带过。

### C. 登录授权回路

适合表现为终端与浏览器之间的连接：

- 终端等待授权。
- 浏览器完成授权。
- 授权结果回到终端。
- 远程环境没有自动打开浏览器时，切换为复制 URL 的路径。

### D. 错误与原因的映射

适合表现为「报错 → 错误层 → 修复动作」：

```text
`command not found`
→ PATH
→ 加入 `~/.local/bin`
→ 重新打开终端
```

不要把整个错误表变成密集文字墙，应优先演示 PATH、终端不匹配、重复安装这几个认知差异最大的例子。

### E. 第一次任务中的 diff 确认

这是全篇最强的过程化表达：

```text
用户：在 `test.py` 里写一个 hello world 函数
↓
Claude Code：展示修改前后 diff
↓
用户：确认 yes
↓
文件：实际写入
```

画面不应重复显示「Claude Code 会修改文件」这句口播，而应展示文件从不存在、出现 diff、确认后落盘的状态变化。

## 9. 最终知识骨架

这篇文章最终可以压缩为五个知识层：

### 第一层：先确认能不能装

系统、账号、网络和使用入口满足条件。

### 第二层：选择正确安装入口

按系统和终端选择官方原生脚本；Windows 进一步区分 PowerShell、CMD 和 WSL；npm 作为最后备选。

### 第三层：确认装好并完成登录

使用 `claude --version` 和 `claude doctor` 验证，再通过浏览器或远程 OAuth 流程登录。

### 第四层：完成第一次可控任务
