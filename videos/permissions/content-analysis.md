## 2. 核心命题

Claude Code 的权限不是“让模型自觉一点”的口头提醒，而是由权限系统控制工具操作能否直接执行、是否需要批准或是否被直接拒绝。真正合适的权限没有脱离环境的固定答案：隔离容器、玩具项目可以承担更高自主度，本机真实代码和生产环境则应保留更强的确认与隔离边界。

如果观众最后只记住一句话，应该是：

> 权限松紧要跟使用环境匹配；想精确控制，就用权限模式、`settings.json` 规则和沙箱叠出边界。

## 3. 知识骨架

### 3.1 权限系统究竟在管什么

文章先把操作分成三类：

1. 只读：读文件、`Grep` 搜索，默认直接放行。
2. Bash 命令：执行 shell 命令，默认需要批准。
3. 文件修改：`Edit` / `Write` 改文件，默认需要批准。

关键认知是：`CLAUDE.md` 只能影响模型想做什么，真正能拦截操作的是 Claude Code 的权限规则。

### 3.2 六种权限模式

文章用“从步步问到全放开”的光谱解释六种模式：

- `default`：仅只读免问，改文件和跑命令都问。
- `acceptEdits`：文件编辑和常见文件系统命令免问，其他 Bash 仍可能询问。
- `plan`：只读研究和出方案，不碰源码。
- `auto`：基本不问，由后台分类器检查越界操作，属于研究预览版。
- `dontAsk`：只有预先批准的工具可用，未批准的直接拒绝。
- `bypassPermissions`：跳过所有检查，只适合隔离容器或 VM 等隔离环境。

### 3.3 模式如何进入和切换

默认 `Shift+Tab` 循环是 `default → acceptEdits → plan → default`。`auto`、`bypassPermissions` 和 `dontAsk` 的进入方式不同。也可以用 `--permission-mode` 在启动时指定模式，或在 `settings.json` 中通过 `permissions.defaultMode` 固定默认模式；原文特别提醒，`auto` 的默认设置不应由项目或本地设置偷偷开启。

### 3.4 精细规则：allow / ask / deny

三种规则分别代表自动放行、弹提示交由用户决定、直接拦截。匹配优先级是 `deny → ask → allow`。规则可以只写工具名，也可以写工具和说明符，例如精确匹配 Bash 命令、文件路径或 WebFetch 域名；通配符后的空格会影响匹配范围。

### 3.5 单层 deny 的边界

`Read` / `Edit` 的 `deny` 只约束内置文件工具，拦不住 Bash 子进程里的 Python 或 Node 脚本绕道读写。若需要阻止所有进程访问敏感路径，文章给出的方向是叠加沙箱，形成更深的防御。

### 3.6 按环境选择松紧

文章给出两套模板：

- 玩具或个人小项目：`acceptEdits` 提速，再 deny `rm -rf` 和 `git push` 等危险操作。
- 生产或公司项目：默认 `default`，放行低风险查看命令，deny 危险命令和敏感文件，并认识到仍需沙箱。

`--dangerously-skip-permissions` 等价于 `bypassPermissions`，只能在隔离容器、VM 或一次性 CI 环境中考虑；本机和生产代码机器不应开启。

### 3.7 五分钟验证链路

文章用一个玩具项目验证规则是否生效：

`mkdir perm-demo → mkdir .claude → 写入 settings.json → 启动 claude → /permissions 查看 → 让 git push 被 deny → 让 git status 被 allow`

重点不是命令本身，而是观察“规则被加载、deny 不执行不提示、allow 不弹批准”的完整反馈。

### 3.8 本篇结尾和系列边界

本篇收束为：模式控制询问频率，`Shift+Tab` 快速切换，`defaultMode` 固定默认，`allow` / `ask` / `deny` 精确控权，敏感文件需要规则和沙箱的组合。下一篇标题和风险主题只作为预告，不展开其正文。

## 4. 认知关系

### 因果关系

使用环境不同 → 可承受的自主度不同 → 选择不同权限模式和规则 → 操作的确认、放行或拒绝边界不同。

### 对比关系

- 只读 vs Bash / 文件修改：查看通常免问，动手通常需要批准。
- `default` vs `acceptEdits` vs `plan`：分别对应步步问、改码免问、只研究不改动。
- `auto` vs `bypassPermissions`：都减少询问，但前者有分类器检查，后者跳过检查。
- `allow`、`ask`、`deny`：放行、询问、拦截。
- 玩具项目 vs 生产项目：可恢复性和真实影响不同，权限松紧不同。
- 内置工具 deny vs 沙箱：工具层限制与 OS 级隔离的防护范围不同。

### 流程关系

`
识别使用环境
    ↓
选择权限模式
    ↓
用 Shift+Tab 或启动参数进入模式
    ↓
用 settings.json 写 allow / ask / deny
    ↓
用 /permissions 验证规则
    ↓
根据 deny、allow 的实际反馈修正边界
`
